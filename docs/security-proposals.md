# Security proposals: random numbers, constant time, execute-only code, IOMMU

[← pdp64 index](../README.md)

For the author's annotation. Each section gives the question, the state of the repository, what other systems do (OpenBSD first), the pain points already collected in [`kernel-pain-points.md`](kernel-pain-points.md) and [`hardware-vulnerabilities.md`](hardware-vulnerabilities.md), and several recommendations scored against the definitive priority list (errata 83): **1** security and safety (an error that can never arise; else easy to detect; else cheap to recover from; restart and recovery together; no strange side effects), **2** opcode choice, **3** opcode encoding, **4** speed and power (low gate count), **5** compiler target, **6** pleasant in assembler; beside them, out-of-order readiness, the soft-rule test, hot-loop weight and Occam. The bus is PCI Express with virtio as the standard device interface (errata 75 to 81); a mitigation that lives on the processor side is invisible to cards.

**Sourcing.** Facts about pdp64 come from the repository, with paths. Facts about OpenBSD marked *fetched* were read from the OpenBSD source on GitHub (files and commit messages); *local* were read from the sparse trees under `../kernel-src`. Anything else outside the repository is marked *(from memory, not confirmed)*. Developer opinions are taken only from commit messages and source comments.

## Summary of the leans

| Section | Question | Lean |
|---|---|---|
| 1. P9 | Random numbers | A software generator that works from the first call (OpenBSD's structure), a boot seed from firmware, and virtio-rng in front of a hardware source; no RNG instruction and no system register for it. |
| 2. P17 | Constant time and cryptography | A hybrid: crypto devices on PCI Express hold the keys and do the bulk work, serial and constant-time, so the main cores can run tickless; the cores keep a small core set (carry-less multiply, rotate, a branch-free select) and a visible constant-time bit defined always on. |
| 3. P18 | Literal pool and execute-only code | Constants in a separate read-only section, so code pages can be execute-only, accepting 2 more bytes per wide-constant load; a segment flag for legacy objects. |
| 4. F25 | IOMMU hardening | Ten always-on processor-side layers; byte-granular bounds in each IOMMU leaf for data buffers; per-queue windows for rings if cheap; port-based trust tiers as policy. |

## 1. A source of random numbers (decision P9)


**Question.** Does pdp64 need a hardware source of random bits, in what form (instruction, privileged register, bus device, boot-loader seed, or none), and which of OpenBSD's choices does it adopt?

**Current state.**
- `docs/decisions-pending.md:359-381` (P9) lists five options and recommends option 1, "an entropy device on the bus (one more eight-register device: a status and a data register)", with option 5, a seed passed in by the boot loader, as the supplement; "if nothing is done: option 4" (software jitter only).
- That wording predates errata 75 and 80 (`docs/errata.md:225,230`): Q64 is now PCI Express, and the eight-register device rule is retired. Option 1 therefore has to be restated as a PCI Express device, which errata 79 (`docs/errata.md:229`) already names for the other classes: virtio.
- `docs/openbsd-mitigations.md:117-118,147` records "the entropy device (not an instruction: P9 declined a `rdrand`-style instruction)".
- `docs/pdp64-isa.md` defines no random-number instruction or register (grep for `RNG`, `random`, `rdrand` finds nothing in the instruction tables). `RDTIME` (P3) is proposed, with a privileged disable control in `docs/architecture-recommendations.md:118` (R-4).

### What OpenBSD does and prefers

**Design of the kernel generator** (`sys/dev/rnd.c`, fetched). The file's own header, `rnd.c:44-68`, is the shortest correct description: the boot loader pre-fills `.openbsd.randomdata` "with seed material (on-disk from previous boot, hopefully mixed with a hardware rng)"; "the first arc4random(9) call initializes this seed material as a chacha state. Calls can be done early in kernel bootstrap code -- early use is encouraged"; entropy events go into a ring `rnd_event_space[]`, a selection of the ring is mixed with a CRC-style twisted shift register into `entropy_pool[]` (2048 32-bit words, `rnd.c:107`); "from time to time, entropy_pool[] is SHA512-whitened ... XOR'd with the inner and outer states of the existing chacha state, to create a new chacha state". Restated: three layers (a cheap event ring that tolerates damage, a bit pool that spreads input, a stream cipher that serves output), joined by a hash so that no layer's state can be read off from the next.
- Output is ChaCha20 keystream (`_rs_rekey`; `RSBUFSZ` = 16 blocks of 64 bytes, line 126). After each refill the generator rekeys itself from its own output "immediately ... for backtracking resistance" (`rnd.c:484`): a stolen state cannot be run backwards to recover earlier output. Bytes handed out are zeroed in the buffer at once (`rnd.c` `_rs_random_buf`).
- Reseed: after 1,600,000 bytes (`rnd.c:381`) and by a timeout every 10 minutes ("per dm@'s suggestion", `rnd.c:632`).
- Locking: one mutex `rndlock` at `IPL_HIGH` guards the generator; the pool extraction is "INTENTIONALLY not protected by any lock" (`rnd.c:294`), because a race there only changes the input data.
- Event timestamps use `cpu_rnd_messybits()`, "something with bits that change", not a correct clock (commit 01802d2c, dlg, 2020-05-31: "cpus with cycle counters that vary in their speed and arent kept consistent between cores may even be desirable in this context"). Local: `sys/arch/amd64/include/cpu.h:347-354` (`rdtsc`, high xor low), `sys/arch/arm64/include/cpu.h:248-254` (`CNTVCT_EL0`, bit-reversed).

**How a hardware generator is used: mixed in, never alone.** Every hardware source in the tree ends in `enqueue_randomness()`, the single input function.
- amd64 (`sys/arch/amd64/amd64/cpu.c:1379-1417`, local): a 10 ms timeout runs `rdseed`, falls back to `rdrand`, XORs the result with `rdtsc` and the `valid` flag, adds a second `rdtsc` ("potential vmexit latency"), and enqueues two words. Commit c6faab6d (deraadt, 2020-02-27): "This works on the fundamental concept that the input-side of entropy collection can accept bad or weak data. entropypool ^= weakdata is not saturative or attackable, the entropy pool either remains as good or becomes better."
- arm64 (`sys/arch/arm64/arm64/cpu.c:362-379`, local): once a second, `rndrrs` (the reseeded variant) and then `rndr`, two words enqueued.
- A bus device: AMD `ccp` reads one 32-bit register every 100 ms and skips zero (`sys/dev/ic/ccp.c:28-58`, fetched); StarFive `stfrng` reads eight data registers once a second, reseeds on the "LFSR_LOCKUP" status (`sys/arch/riscv64/dev/stfrng.c`, local); `viornd` (virtio-rng) asks the host for 16 bytes at boot and every 15 seconds times a power of two, because "the host may not have an unlimited supply of entropy" (`sys/dev/pv/viornd.c:27-31`, fetched); Hyper-V's 64 bytes through an ACPI table (commit e5b36f11, 2017: "less interesting for machines with rdrand").
- The one case that is not "mixed": VIA `xstorerng`. The driver comment: "If the RNG wedges, then the chances of you having a defective CPU are very high. Let it wedge" (`sys/arch/amd64/amd64/via.c:477-480`, local). Even there the output goes to `enqueue_randomness()`.
- OpenBSD's polling intervals (10 ms, 100 ms, 1 s, 15 s) mean no OpenBSD path executes a hardware-random instruction in a hot loop. User programs never touch it: they call `arc4random(3)`.
- Statements about trust: commit 1cdc2ead (deraadt, 2014-06-02, removing `lib/libcrypto/engine/eng_rdrand.c`): "A few months back there was a big community fuss regarding direct-use of the intel RDRAND instruction. Consensus was RDRAND should probably only be used as an additional source of entropy in a mixer." Commit f63c0148 (jsg, 2015-12-27): "rdrand output comes from a prng that is periodically reseeded. rdseed should give us more bits of entropy." Commit dd423e20 (naddy, 2020-06-15): retry up to ten times "as recommended by Intel".

**Boot-time seeding.**
- The boot loader reads `/etc/random.seed` (`BOOTRANDOM_MAX` 256 bytes, "no point being greater than RC4STATE"), sets the sticky bit on the file, and passes the bytes to the kernel; if the sticky bit was already set it prints "NOTE: random seed is being reused" and the seed does not count as good (`sys/arch/amd64/stand/rdboot/rdboot.c:45-47,119-160`, local). The flag `RB_GOODRANDOM` (`sys/sys/reboot.h:60`) goes to `random_start()`, which prints "random: good seed from bootblocks" or "boothowto does not indicate good seed" with the note `/* XXX kernel should work harder here */` (`rnd.c:667-670`).
- `rc` writes the next seed at shutdown and at boot: `store_random()` reads 512 bytes from `/dev/random` into `/etc/random.seed` and 65,536 bytes into `/var/db/host.random`, then clears the sticky bit "to indicate the file has fresh contents" (`etc/rc:77-89`, fetched). If the boot blocks gave nothing, `rc` pushes `dmesg` and `sysctl hw.{uuid,serialno,sensors}` into `/dev/random` (`etc/rc:428-429`).
- The x86 boot loader's own gatherer `mdrandom()` XORs `rdtsc`, then `rdrand`, then `rdseed` into the buffer, each as a separate pass (`sys/arch/amd64/stand/libsa/mdrandom.c:25-80`, local); commit 55f8664c (deraadt, 2020): "now always run both sequences, and also support rdseed as a third procedure".
- When the loader supplies nothing, the kernel falls back to what it has: the previous boot's message buffer, and 8 KB of its own text just below `etext` (`rnd.c:654-660`). Commit 86f75043 (deraadt, 2018-02-09): "a new source of entropy arrived a few months ago -- KARL generates highly disturbed images for some kernels". On pdp64 the relinked kernel (`docs/openbsd-mitigations.md` 2.8) would supply the same.
- Suspend and resume: commit e3892ee8 (deraadt, 2014-12-18): "At suspend time, process all queued entropy and create a brand new pool to prevent backtracking upon resume. At resume time, process the entropy queue ... and force all higher to reseed."

**User space.**
- `arc4random(3)` is a ChaCha20 generator per process, rekeyed from `getentropy(2)` after a random 1-2 MiB of output (`lib/libc/crypt/arc4random.c:52,106-109`, fetched). Its state lives in a page marked `MAP_INHERIT_ZERO`, so a forked child sees zeros and restarts (`arc4random.c:54`, `arc4random.h:44-50`); if `getentropy` fails the process is killed with `SIGKILL` (`arc4random.h:34`). Restated: failure to get randomness is a crash, not a silent weak value (priority 1: an error that cannot go unnoticed).
- `getentropy(2)` returns at most 256 bytes and "is not intended for regular code" (`getentropy.2`, fetched). `/dev/urandom` "produces high quality pseudo-random output data without ever blocking", and "for portability reasons, never use /dev/random ... on many systems [it] misbehaves by blocking because their random number generators lack a robust boot-time initialization sequence" (`share/man/man4/random.4`, fetched). The man page states "these functions are always successful, and no return value is reserved to indicate an error" (`arc4random.3`).
- Fork safety history: commit 4caf194b (an OpenBSD developer, 2014-06-17) replaced a `getpid()` check on every call by `MAP_INHERIT_ZERO`; commit 6e3588f2 (2014-06-19) first moved the state so a child would still mix in parent randomness, then the current layout keeps `rs` zeroed and `rsx` inheritable (`arc4random.c:54-62`). This needs a kernel facility (inherit-as-zero, ISA-neutral) and nothing from the ISA.

**History of OpenBSD's generator problems and the lessons** (from commit messages; the complaints themselves are not quoted there unless shown).
- RC4 was replaced by ChaCha20 in the kernel and libc (commit ea03ca46, markus, 2013-11-02; `arc4random.3` HISTORY: "In OpenBSD 5.5 it was replaced with the ChaCha20 cipher"); MD5 then SHA-256 then SHA-512 for the hash ("md5 smells bad", 2013-12-11; 2014-10-20).
- A repeated seed pattern: commit f65494e6 (deraadt, 2019-10-29): the 512-byte seed block was found repeated through the `.openbsd.randomdata` section as retguard keys ("Mortimer discovered the repeated 512-byte sequence"). Lesson: a seed must be expanded by a generator, never tiled.
- Cloned disks share `random.seed`: commit 1c7698b3 (sthen, 2019-10-02), feeding `sysctl hw` "for systems where /etc/random.seed may be known (e.g. cloned disk images)".
- Weak seeding is expected and designed for: commit 618bc41b (deraadt, 2020-05-26): the rewrite is to "compensate rapidly for weak seeding in unidentifiable conditions, and ensure quality to arc4random() calls early in boot", with rekeying on every event until `cold` is cleared.
- Locks on the interrupt path: commit eea06480 (mikeb, 2017-11-19) removed producer/consumer interlocks: "a lot of randomness event producers are executed in the interrupt context ... in practice randomness event producers require interlocking between each other, but not with consumers".
- Hardware not trusted alone: commit 1cdc2ead above; the AMD failure is in the BearSSL source (`<work>/corpora/bearssl/src/rand/sysrng.c:60-74`, local): "AMD bug: there are reports that some AMD processors have a bug that makes them fail silently after a suspend/resume cycle, in which case RDRAND will report a success but always return 0xFFFFFFFF", citing `bugzilla.kernel.org/show_bug.cgi?id=85911`. OpenBSD's mixer makes that failure harmless; a program that used `rdrand` directly would not be.
- Not confirmed in the sources read: any OpenBSD statement about the 2019 AMD `rdrand` bug specifically; OpenBSD's reasoning for dropping `/dev/srandom` and the sysctl `kern.arandom`; Theo de Raadt's talks on the generator.

### What other systems do

- **x86** (from memory): `rdrand` (Ivy Bridge, 2012; OpenBSD added it in commit 31816377, 2012-09-19) returns output of an on-die generator that is conditioned and reseeded; `rdseed` (Broadwell, 2014) returns conditioned entropy; both signal failure in the carry flag. Intel's SRBDS fix (2020) made `rdrand`/`rdseed` delay other cores' memory misses (`docs/kernel-pain-points.md:806`: "Executions of RDRAND at the same time on multiple logical processors will be serialized"; `docs/hardware-vulnerabilities.md:67,94`). The AMD silent-failure bug is quoted above from BearSSL's source (the year, 2019, and a later Zen 5 `rdseed` bug in 2025 are from memory).
- **AArch64**: `RNDR` and `RNDRRS` (FEAT_RNG, Armv8.5; OpenBSD `cpu.c:363-376`, local). **RISC-V** Zkr: a `seed` CSR whose reads return status (BIST, WAIT, ES16, DEAD) and 16 bits of raw entropy for the OS to condition, so the entropy source is explicitly not a generator (from memory). **s390** `PRNO` (deterministic and true-random functions in the CPACF facility), **POWER9** `darn` (from memory; `docs/decisions-pending.md:367` counts the instruction uses in the corpus: `rdrand` 12, `rdseed` 9).
- **Virtual machines**: virtio-rng (device ID 4, one queue the guest fills with buffers; from memory, and the OpenBSD driver above confirms the shape).
- **Linux** (from memory): mixes hardware, interrupts and a seed file in a ChaCha20-based generator with a BLAKE2s pool since 5.17-5.18; a boot option decides whether to credit `rdrand` as entropy. Not read in this draft.

### Pain points

- `docs/kernel-pain-points.md:806`: an RNG instruction became a cross-core serialization point (SRBDS). A pdp64 entropy register "must not be reachable through a buffer shared with other threads".
- `docs/hardware-vulnerabilities.md:67,94,156` (C5): special-register buffers that outlive a domain change; the rule C5 holds for any random source whose last output sits in a shared buffer.
- `docs/openbsd-mitigations.md:53,93`: ASLR and KARL spend entropy; with 38 usable user address bits the quality of the generator matters more, not less.
- `docs/architecture-recommendations.md:118` (R-4, rule 9): a precise user timer is the instrument of every cache-timing attack; OpenBSD's event timestamps want exactly that counter (privileged read is enough).
- Tickless main cores (the author's direction in section 2) deliver fewer timer interrupts, which are one of rnd.c's inputs (`kern_tc.c:479,510,560,594` call `enqueue_randomness`, local). With few interrupts, a hardware or virtio source and the boot seed carry more of the load.

### Recommendations

Options compose; they are not mutually exclusive. Scores use the author's list: P1 security and safety, P2 opcode choice, P3 encoding, P4 speed and gates, P5 compiler, P6 assembler; OoO = readiness for out-of-order execution.

1. **No hardware source: OpenBSD's entropy gathering only** (P9 option 4). *What:* port `rnd.c` as it is; inputs are interrupt, disk, network and clock timing through `enqueue_randomness`, plus the seed. *Gains:* nothing to trust or to fail, no device. *Costs:* first boot with no good seed is weak, and tickless cores produce few events. *Score:* P1 poor on first boot (the very case `RB_GOODRANDOM` exists to flag), P2-P6 neutral (needs only a fast counter for `cpu_rnd_messybits`), OoO neutral.
2. **A bus device that exposes raw hardware entropy, polled and mixed in** (the ccp/stfrng shape). *What:* a PCI Express function with a status register and a data register; the kernel polls it from a timeout and calls `enqueue_randomness`. *Gains:* no opcode; the physical source (ring oscillators, a conditioner) is the platform's choice; the failure status ("LFSR lockup", empty) is visible to the driver. *Costs:* one more driver, and a platform-specific one unless it is virtio. *Score:* P1 good (mixed, never alone; failure is detected by the status bit), P2 zero opcodes, P3 none, P4 gates only in the device, P5/P6 nothing, OoO good (an uncached register read is a serialized access already).
3. **virtio-rng as the standard interface** (option 2 in virtio form). *What:* the standard entropy device of the virtio family; `viornd.c` is about 200 lines; the same device runs in QEMU, `sim64` and the FPGA (errata 79 already chose virtio for network, graphics and audio, so the transport driver exists). On real silicon a virtio-rng function fronts the TRNG. *Gains:* one interface for virtual and real machines; the host bounds the draw rate; nothing new in the ISA. *Costs:* a virtqueue round trip (DMA through the IOMMU) for 16 bytes at a time, irrelevant at one request per 15 seconds; trust in the host in virtual machines (which is why it is only mixed). *Score:* P1 good, P2-P3 none, P4 good, OoO good.
4. **A boot seed passed by firmware, renewed at shutdown** (P9 option 5, OpenBSD's mechanism). *What:* the boot loader reads a 256-byte seed file, XORs in whatever the platform has (counter, device bytes), passes it with a "good seed" flag, and the kernel clears the flag when the sticky bit shows reuse. *Gains:* arc4random works from the first call ("early use is encouraged"); the flag turns an invisible weakness into a printed one (priority 1: easy to detect). *Costs:* persistent storage and a writable boot filesystem; a cloned disk repeats the seed (hence the `sysctl hw` push). *Score:* P1 good, P2-P6 none, OoO none.
5. **A random-number instruction or an `mfsr` register** (P9 options 2 and 3, `rdrand`, `rndr`, a Zkr-style CSR). *Gains:* fast, universal. *Costs:* an opcode; a promise about quality that the ISA must keep for decades; the SRBDS lesson (the shared buffer); a trapping or privilege story for each of them; and the hot-loop test fails, because OpenBSD polls it at 10 ms to 1 s intervals and user programs call `arc4random`. *Score:* P1 poor-to-neutral, P2 costs an opcode with execution count near zero, P3 uses an encoding, P4 gates for a conditioner, OoO needs a serializing rule.

**Lean:** options 1 + 4 + 3 together, with option 2's physical source behind the virtio function, and option 5 declined. That is OpenBSD's structure with the transport made standard: a software generator that works from the first call (seed), absorbs whatever arrives (events and a device), and treats every source as weak. It adds no opcode (priorities 2-3), moves gates into an optional device (4), and makes weak seeding visible (1). **What the author must decide:** (a) confirm "no instruction, no register", restating P9 option 1 as virtio-rng; (b) where the seed file lives and who writes it (NVMe boot partition, firmware flash); (c) whether the kernel may read a high-resolution counter when R-4 gives user programs a coarse one (a privileged read is enough for `cpu_rnd_messybits`); (d) whether the first iteration's `sim64` and QEMU devices expose virtio-rng backed by the host's entropy; (e) whether to keep OpenBSD's single `IPL_HIGH` mutex or give each core its own ChaCha instance keyed from the main one (see below).

### Optimizing OpenBSD's algorithms

The ChaCha20 core is `lib/libc/crypt/chacha_private.h:45-49` (fetched): per quarter-round 4 additions, 4 XORs, 4 rotations by 16, 12, 8, 7; 80 quarter-rounds per 64-byte block, so about 960 ALU operations plus 16 loads and stores, roughly 15 operations per output byte (my count, not measured).
- **Rotate.** All four rotation counts are compile-time constants; `RORI32` (`docs/pdp64-isa.md:543`) is one four-byte instruction that reads only `rs[31:0]` and returns `sign-extend(ror32(...))`. Because it reads only the low 32 bits, a 64-bit `ADD` and `XOR` may leave garbage in bits 63:32 and no fix-up is needed before the next `RORI32`. So ChaCha20 on pdp64 is 12 instructions per quarter-round with existing instructions. The ISA already records the reason (`pdp64-isa.md:392`): "crypto rotates by compile-time constants".
- **`ROR`/`DSHR`/`CLMUL`.** None helps ChaCha. `CLMULL/CLMULH` (`pdp64-isa.md:596`) serves CRC, GHASH and polynomial arithmetic. The one rotate in `rnd.c` that is not constant is `add_entropy_words` (`rnd.c:221-222`), a variable 32-bit rotate by `entropy_input_rotate`; with the 64-bit `ROR` it is "copy the word into both halves, rotate, take the low half", three instructions, once per event word on the interrupt path, which is not hot. SHA-512 (used by `extract_entropy`) is 64-bit rotates, a native fit for `RORI`.
- **Register pressure is the real cost.** ChaCha keeps 16 words live; pdp64 has 16 registers with `SP` among them (`pdp64-isa.md:80`), so about 12 are usable and a block loop spills. A fused instruction would not remove that; a longer state-in-memory ALU form (already present: ALU-to-memory forms at four bytes) does.
- **A fused xor-rotate** (`d = ror32(d ^ a, n)`, writing only `d`) would cut a quarter-round from 12 to 8 instructions and would serve BLAKE2 and the SHA-2 sigma functions. A fused add-xor-rotate would write two registers (`a` and `d`), which is a side effect and an out-of-order renaming cost; I do not propose it. *Hot-loop weight:* the kernel generator draws bytes at interrupt and syscall rates; at 1 MB/s that is about 15 million operations per second, under 1% of one core (my estimate). Bulk ChaCha20-Poly1305 would weigh more, but section 2 puts bulk crypto on a device. *Verdict:* no new instruction justified; `RORI32` suffices. Re-test only if bulk ChaCha stays on the cores, with `sim64` instruction counts.
- **Algorithm structure that could be improved** (my proposals, none measured): (1) a per-core ChaCha instance keyed from the main one, using the `arc4random_ctx_new()` mechanism that `rnd.c:548-581` already has for large reads, so that `rndlock` is not contended on a many-core machine and so that tickless cores do not wait on one lock; (2) fill `rs_buf` for four blocks at a time only if the loop is unrolled with state in memory; (3) keep the pool and SHA-512 whitening unchanged: they run at event and 10-minute rates, and the design purpose is cheap input-side work in interrupt context.

## 2. Constant-time execution and cryptography (decision P17)


**Question.** How should pdp64 stop timing differences from leaking secrets: a promise and a mode bit on the cores (P17 as written), or move the secret-handling algorithms to dedicated crypto devices on the PCI Express bus, so that the main cores need no constant-time mode and can run tickless?

**Current state.**
- `docs/decisions-pending.md:579-609` (P17, "PROPOSED, not decided"): five options; the current recommendation is option 3, a core set of instructions promised data-independent in time always, plus a `DIT` bit in the `PSW` that extends the promise to `DIV`, `mscn` and the block operations. Corpus counts: `div`/`divu` 0.040% of instructions, `mscn` none, multiply 0.595% (static, not run time).
- `docs/architecture-recommendations.md:24,61-62,119`: R-8 adds the `DIT` bit; rule 10 requires an out-of-order core to honour it.
- `docs/hardware-vulnerabilities.md:105-125` (section 4) lists which instructions leak; `:158` rule C7 (a published constant-time set); `:258` N6 (a mode bit in `PSW`); `:305` records that the bit "covers less than the name suggests" because Hertzbleed leaks through frequency even when only constant-latency instructions run.
- `docs/pdp64-isa.md:1899`: `MASKEQZ`/`MASKNEZ` "on hold"; `SET cc, Rd` exists (`:858`). **`docs/hardware-vulnerabilities.md:111,115` name `MASKEQZ` as if it exists; it does not.** `AES`, `SHA` and `ChaCha` instructions: none (grep of `pdp64-isa.md`). `CLMULL/CLMULH` (`:596`) and `RORI32` (`:543`) exist.
- Errata 75-82 (`docs/errata.md:225-232`): the bus is PCI Express with an IOMMU; standard devices are virtio; extra security circuitry is welcome. Errata 76 already dedicates cores to the network and graphics.

### What OpenBSD and its libraries do and prefer

- **Kernel and libc comparison primitives** are written with no secret-dependent branch: `timingsafe_bcmp` ORs the XOR of every byte pair and returns `ret != 0` (`sys/lib/libkern/timingsafe_bcmp.c`, local). pdp64's `MCMP` stops at the first difference "by definition" (`hardware-vulnerabilities.md:116`) and must not be used for secrets.
- **OpenBSD uses the CPU's AES instructions where they exist**: `aesni(4)` (`sys/arch/amd64/amd64/aesni.c`, fetched) and the VIA PadLock `xcrypt` driver (`sys/arch/amd64/amd64/via.c`, local); libcrypto routes `AES_set_encrypt_key`, CBC, CTR and XTS to AES-NI when present (OpenBSD libcrypto commits of May-July 2025, found by commit search: "Remove AES-NI specific EVP_CIPHER methods ... These now end up in aesni_encrypt() via AES_encrypt(), when appropriate"). Restated: crypto is done by instructions on the core, because a table-based AES leaks through the cache.
- **OpenBSD removed its PCI crypto accelerators.** Commit 0a828ff4 (2021-10-21, deleting `hifn(4)`, `safe(4)`, `ubsec(4)`): "They require the asynchronous crypto API which makes progress in MP difficult. The hardware is rarely available. They support only obsolete crypto algorithms. Scheduling crypto tasks via PCI is probably slower than the CPU, especially as modern CPUs have their own accelerators." This is the most direct evidence in the sources read against the author's idea, and it must be answered by the design (below).
- **OpenBSD has no virtio-crypto driver.** The fetched listing of `sys/dev/pv` shows `viornd`, `vioblk`, `vioscsi`, `viogpu`, `viomb`, `viocon`, `if_vio`, `vmmci` and no crypto device. A search of commit messages for "virtio-crypto" returned none.
- **BearSSL** (`<work>/corpora/bearssl`) is written so that no secret decides a branch or an address. Its primitives are in `src/inner.h`: `MUX(ctl, x, y)` is `y ^ (-ctl & (x ^ y))` (`inner.h:770-773`), `EQ`/`NEQ`/`CMP` use `(q | -q) >> 31` (`inner.h:779-838`), `CCOPY` is a masked conditional copy. ChaCha20 (`src/symcipher/chacha20_ct.c`) uses only add, xor and rotate and is "naturally constant-time" in the library author's words (`hardware-vulnerabilities.md:141`). Its AES comes in table-based ("big"), constant-time bitsliced ("ct", "ct64") and CPU-instruction (AES-NI, POWER8) versions; the measured cost of constant time in software is 0.32 and 0.54 times the table speed for CTR on amd64, and AES-NI is 14 times faster than tables (`hardware-vulnerabilities.md:141`, the library author's measurements). On multipliers: constant-time on almost all recent CPUs, variable on the 80486 and ARM9 (`:142`). The idiom depends on the target giving it a branch-free select: `MUX` costs about 3 instructions on pdp64 without a select instruction (`SET` then `NEG` then mask-xor-xor).
- **CPU facilities**: Arm `DIT` (a bit in `PSTATE`), Intel `DOITM` (a model-specific control, off by default and not recommended globally), RISC-V Zkt (a published list, no mode) are catalogued in `hardware-vulnerabilities.md:133-137`. Hertzbleed and GoFetch show their limits (`:305`, `:140`). Conditional select is in Arm's DIT set (`:137`).
- Not confirmed in the sources read: how much of libressl's own libcrypto is constant-time (bignum/RSA/EC blinding), and bcrypt in libc (it uses secret-indexed Blowfish S-boxes, from memory, which is a cache-timing exposure on any core).

### What other systems do

- **Instructions on the core** (from memory except where cited above): x86 AES-NI, PCLMULQDQ, SHA extensions; Arm AES/SHA/PMULL; RISC-V Zk (Zkne/Zknd, Zknh, Zkt); s390 CPACF (instructions that call a co-processor in the core); IBM POWER `vcipher`. Fast for small messages, no DMA, no key handed to anything outside the core's memory.
- **Dedicated engines on a bus** (from memory): Intel QuickAssist (QAT, PCIe, symmetric and public-key offload; Linux `qat` drivers); Arm CryptoCell and Cortex-M CryptoCell-310 (an on-SoC block with a register interface and its own secure RAM); AMD PSP/CCP (seen above for its TRNG); smart cards, TPM 2.0 (keys created inside, only handles leave) and network-attached HSMs (PKCS#11). Linux's crypto API has an asynchronous interface (`crypto_wait_req`, completion callbacks) for these; the OpenBSD commit above and a long-standing Linux observation (from memory) agree that offload only pays for large requests or for algorithms the CPU lacks.
- **virtio-crypto** (from memory): a standard virtio device (device ID 20, virtio specification 1.1 or later) with a control queue for session creation and data queues for symmetric, hash/MAC, AEAD, and (later) asymmetric requests; the Linux guest driver is `virtio_crypto`; QEMU provides backends. Status in OpenBSD: none (above). Status in the repository: not mentioned.

### Pain points

- `docs/kernel-pain-points.md:144` (row 3): "constant-time code undermined by hardware" is **OPEN**; Hertzbleed shows a `DIT` bit would not cover frequency scaling.
- `docs/hardware-vulnerabilities.md:84,86`: port contention and data-dependent prefetchers (GoFetch, SLAP, FLOP) bypass constant-time code; `:81` cache timing; `:243,298` Hertzbleed. All of these concern secrets sitting in the memory and caches of a core that also runs untrusted code.
- `docs/hardware-vulnerabilities.md:141`: software constant-time AES is 3 to 6 times slower than tables; AES-NI is 14 times faster.
- `docs/kernel-pain-points.md:142`: speculation leaks need years of mitigation code; keys that never enter a core's cache and registers are outside that class.
- Hot-loop evidence for the cores: `div`/`divu` are 149 instructions of 370,115 in the corpus (`docs/decisions-pending.md` P17, "what it would cost"), so a worst-case divide costs about 1% by the document's own estimate.

### The author's idea, developed

*Idea.* Common crypto algorithms live on one or more PCI Express devices; "they can pay the price of constant time computing and serial execution, etc, while the main cores are tickless."

**What goes on the device.** A fixed-latency, one-request-at-a-time pipeline implementing: AES (CTR, GCM, XTS, CBC as needed by the OS), SHA-256/512 and SHA-3 with HMAC and HKDF, ChaCha20-Poly1305, X25519 and Ed25519 (fixed-window constant-time scalar multiplication), the key derivation and password hashes the OS uses (bcrypt, or its replacement), and a TRNG that feeds section 1. RSA private operations are a judgment call: RSA is a legacy of the 1990s, its constant-time modular exponentiation needs a wide multiplier, and modern protocols prefer X25519/Ed25519 (from memory); include it only if the author wants TLS server certificates with RSA keys. Post-quantum algorithms (ML-KEM, ML-DSA) can be added later with no ISA change. That is the main architectural gain: the algorithm list lives in a device and a driver, not in opcodes; the ISA made the same argument for `CLMUL` against a `CRC` instruction (`pdp64-isa.md:598`).

**How a core talks to it.** As a virtio device: sessions are created through a control queue; the key is imported once, wrapped, and the device returns a handle; data requests carry the handle, the nonce and DMA buffer addresses; the device writes the result and a status word. If virtio-crypto is chosen the specification exists and Linux and QEMU support it (from memory), but **OpenBSD has no driver, so one must be written** (the size of `viornd` suggests a driver for symmetric operations is a few hundred lines; my estimate). Alternatives: a pdp64-specific PCI Express function with a submission and completion ring (as NVMe does, errata 75), which can carry whatever the author wants (one "extended capability" per errata 81), but which no other system supports.

**What it buys.**
1. *Key custody.* A key imported into the device never appears in core memory, caches, registers or speculative state. Spectre, Meltdown, GoFetch and cache-timing attacks (`hardware-vulnerabilities.md:81-86`) cannot read it. This is the strongest security gain of any option and is the "as if we were the NSA" argument: the keys sit in a smaller, simpler, separately reviewed machine, as in a TPM or an HSM. A compromised kernel can still ask the device to sign (a confused deputy), but cannot copy the key.
2. *No constant-time mode on the cores.* The `DIT` bit, its fast-path disable logic and rule 10 for out-of-order cores (`architecture-recommendations.md:119`) are not needed for crypto, which was the reason for them. The divide, `mscn` and block-copy sequencers keep their fast paths (priority 4).
3. *Tickless cores.* Crypto no longer runs on the cores for long stretches, so there is no need to bound the time a core spends in one constant-time loop between interrupts. (The coupling to tickless operation is the author's; I read it as: no core has to be pinned in a long serial computation. Not confirmed beyond that.)
4. *One serial pipeline.* A single in-order pipeline with fixed cycle counts per block has no cache, no predictor, no frequency scaling in its datapath, which removes the Hertzbleed class from the secret computation (power analysis excepted, which is not a timing channel).

**What is lost.**
1. *Latency and small messages.* Every call crosses PCI Express, an IOMMU translation and an interrupt or poll; OpenBSD's 2021 commit above states the objection. A 64-byte request pays more than software ChaCha20 would on the core (a few hundred nanoseconds to a microsecond of round trip, from memory, against about 1000 operations of ChaCha: under a microsecond). Bulk (TLS records, disk blocks, IPsec packets) amortises it. The device therefore needs a batch-friendly ring and the kernel needs a size threshold.
2. *Contention.* One serial pipeline queues requests from all cores; per-session fairness and a completion interrupt (or polling, which tickless cores do cheaply) are needed.
3. *Early boot and the RNG.* `arc4random` must work before any device is enumerated (`rnd.c:44-48`: "early use is encouraged"); the generator uses ChaCha20 and SHA-512 in software on the core. Both are add-xor-rotate and constant-time by construction, so they need no device, but the cores keep a software implementation, and boot-time signature checking (if the loader verifies anything) needs one too.
4. *DMA exposure.* The device reads and writes memory: the IOMMU domain for the crypto function must map only the request buffers (`architecture-recommendations.md:176`, R-12 range-based protection); a buffer holding plaintext is as exposed as before. Keys avoid this by the handle design.
5. *Everything that is not a crypto algorithm remains on the cores:* comparing MACs (`timingsafe_bcmp`), parsing, user programs with their own secrets (password managers, GnuPG, any language runtime), table-indexed code anyone writes. The device does not remove the need for a promise on the cores; it shrinks which instructions must carry it.
6. *A new trusted component.* Firmware, microarchitecture and supply chain of the device are now the security boundary; a bug in its constant-time pipeline affects every key.
7. *Failure and recovery (priority 1).* A device that wedges or fails self-test must be detected by the driver (status, timeout) and replaced or restarted, with a software fallback for non-secret uses; this is the "restart and recovery go together" case, and virtio gives a standard device reset.

**ISA pieces that remain on the cores.** (1) The always-promised core set of P17 option 2: add, logic, shifts and rotates, `RORI32`, multiply, `CLMUL`, `POPCNT`, byte swap, `SET`, `MIN`/`MAX` have fixed latency (free: a fixed-latency multiplier needs fewer gates than an early-out one, `decisions-pending.md` P17). (2) A branch-free select (`MASKEQZ`/`MASKNEZ` or a conditional select): 3 instructions for `MUX` without it, 1 with it; BearSSL, `timingsafe_bcmp` and every constant-time library use it; this is a priority-2 case (fewer instructions in a hot loop). (3) `CLMUL` stays (GHASH on cores for small messages, CRC). (4) The `DIT` bit: with crypto off the core, its main customer disappears; reserve `PSW` bit 13 and define the bit as "always on" in the first implementation so adding it later costs nothing. (5) A rule (not an instruction) that `MCMP` and `MSCN` are not for secrets.

### Recommendations

Scores as in section 1.

1. **Cores only: P17 option 3 as written** (core set always promised + `DIT` bit; crypto in software). *Gains:* nothing outside the cores; works at boot and for any user program. *Costs:* `DIT` and its fast-path disable (a bit and logic on the divider, `mscn`, `mcmp`, FPU), rule 10 for out-of-order, software AES either slow (bitsliced, 0.32-0.54 of table speed) or leaking (tables); keys live in core memory, exposed to the whole speculation and cache family; Hertzbleed is not covered. *Score:* P1 medium, P2 neutral, P3 one `PSW` bit, P4 costs gates for the bit and slow software AES, P5-P6 neutral, OoO needs the honour rule.
2. **The author's idea in full: all common crypto on PCI Express devices; no constant-time promise on the cores at all.** *Gains:* key custody, smaller cores, no `DIT`, algorithm agility, tickless cores. *Costs:* every crypto-dependent path crosses the bus; no safe instructions for user code with its own secrets; the boot and RNG path still needs software ChaCha20 and SHA-512; OpenBSD removed this class of driver for speed and MP reasons in 2021. *Score:* P1 high for keys on the device, low for anything off it, P2-P3 saves opcodes and bits, P4 good for the core and poor for small-message latency, OoO good (an MMIO doorbell and a completion are ordinary uncached accesses).
3. **Hybrid: crypto devices for bulk and for key custody, plus the always-promised core set and a branch-free select on the cores; no `DIT` bit at first.** *What:* option 2's device list, with the core set of P17 option 2 (zero gates), a select instruction, `RORI32` and `CLMUL` kept, and software ChaCha20/SHA-512 on the cores for boot and the RNG. The `PSW` bit is reserved and defined always-on; if later a core adds an early-out unit or a program needs divide in a secret computation, the bit is added without changing code. *Gains:* most of option 2's gains, none of its holes (user code with secrets still has safe instructions and a select; small messages stay in software ChaCha20 at no loss), no mode state. *Costs:* two places to implement crypto; a select instruction (an opcode, which P17 and `pdp64-isa.md:1899` already hold "on hold"). *Score:* P1 high, P2 one new opcode with high hot-loop weight in every constant-time library, P3 a rare-tier encoding, P4 best, P5 the compiler can emit select for `?:` as well, P6 plain, OoO good.
4. **Crypto instructions on the cores** (AES round, SHA, as x86/Arm/RISC-V Zk). *Gains:* fast for small messages; no DMA; no new component. *Costs:* the ISA commits to AES and SHA for the life of the architecture (the argument made against `CRC`, `pdp64-isa.md:598`); opcodes and gates in every core; keys sit in core registers and state; the constant-time promise must cover them (RISC-V Zkt, Intel's list). *Score:* P1 medium, P2 many opcodes, P3 more encodings, P4 gates, OoO needs the promise honoured. Only worth it for small-message latency, which the author's dedicated cores (errata 76) may not need.
5. **Software only, no architectural promise** (P17 option 5). *Cheapest to specify, worst for P1:* the situation that produced surprises on other architectures. Listed for completeness.

**Lean:** option 3. It keeps the author's idea at its centre (devices own the keys and the bulk work, serial and constant-time, so the main cores can drop a global constant-time mode and run tickless) while closing the gaps that option 2 leaves open (user code with its own secrets, boot, small messages). It adds one instruction (select) whose hot-loop weight is the constant-time idiom itself. **What the author must decide:** (a) whether the crypto device is standard virtio-crypto (writing the OpenBSD driver) or a pdp64 function; (b) the device's algorithm list, in particular whether RSA and bcrypt-class password hashing are in; (c) whether the `DIT` bit stays reserved-and-always-on or is dropped from P17 and R-8; (d) whether the select instruction is admitted (`MASKEQZ`/`MASKNEZ` or a conditional select) and the doc inconsistency at `hardware-vulnerabilities.md:111,115` is corrected; (e) the key-wrapping model (keys imported by handle, or also exported wrapped), because it decides how a restart recovers; (f) whether tickless operation is in scope for iteration one, since section 1's entropy gathering and the 10 ms to 1 s polling assume some timer activity.

## 3. The literal pool and execute-only code (decision P18)

**Question.** Should the 8-byte constants loaded by `movq =K, rd` stay in `.text` (errata 33), or move to a read-only section outside the code, so that code pages hold only instructions and can be mapped **execute-only** (the page can be run but not read as data, so a memory-disclosure bug cannot be used to read the program's code and find gadgets, the short instruction sequences an attacker chains together)?

**Current state.**
* The pool lives in `.text`, "flushed at the end of the section or at `.pool`", and is read by one PC-relative load (`docs/errata.md:139-143`; `docs/pdp64-isa.md:295`, "`MOVQ d(PC), Rn`, two parcels, ±2 KB reach").
* The page-table entry already has separate `R`, `W`, `X` bits: bit 1 `R`, bit 2 `W`, bit 3 `X` (`docs/pdp64-system-architecture.md:371`). Execute-only (`R` = 0, `X` = 1) is an ordinary entry; a data read of it takes protection abort 10, a fetch abort 9, so fetch and data faults are already told apart (`docs/openbsd-mitigations.md:60`). With `UA` = 0 a kernel `MCPY` from such a page faults too (same line).
* A PC-relative operand is 4 bytes at ±2 KB (`len = 01`, 12-bit displacement) and 6 bytes at 28-bit displacement, ±128 MB (`len = 10`; `docs/pdp64-isa.md:205-223`). `docs/openbsd-mitigations.md:62` and the `LEA` text at `pdp64-isa.md:293` say ±2 GB for the 32-bit payload; that disagrees with the 28-bit field of the `len = 10` form and needs reconciling before the reach of a separate pool is fixed.
* Jump tables read by `JTAG`/`JMPI` from text have the same problem as the pool (`docs/openbsd-mitigations.md:62`).
* The direct page register `DP` (kernel, supervisor and user copies) reaches global data with a 12-bit displacement in a 4-byte instruction and uses no general register (`docs/pdp64-isa.md:108`).
* `docs/decisions-pending.md:611-640` (P18) proposes moving the pool to a read-only section beside the text, and says the cost is "a few code-size bytes if a long form is needed". That understates it: see the next point.

**The consequence the P18 text does not state.** Permissions are per 4 KB page. A pool outside the code pages is therefore always on a different page from its loads, and the 4-byte form (±2 KB) can reach it only from the last 2 KB of a code page that happens to border a pool page. In practice every pooled constant load becomes the 6-byte form: **+2 bytes and one more parcel fetched per wide-constant load**, plus a data-side fetch from a second page (one more data TLB entry, one more cache line). The 8 data bytes cost the same wherever the pool sits.

**What other systems do.**
* OpenBSD enforces execute-only by hardware wherever the MMU can. amd64: a protection key marks the page (`PG_XO` "key1 used for execute-only", `sys/arch/amd64/include/pte.h:126`). powerpc64: the same idea with the AMR register (`sys/arch/powerpc64/powerpc64/cpu.c:255-262`). arm64 lists `PROT_EXEC` alone as its own attribute combination (`sys/arch/arm64/arm64/pmap.c:194,205`). The kernel insists that `libc.so` text is execute-only (`sys/uvm/uvm_mmap.c:664`) and the signal trampoline is mapped execute-only, so a core dump reads it through the kernel mapping (`sys/kern/exec_elf.c:1221-1223`).
* Where the MMU cannot, OpenBSD falls back to blocking system calls from reading the text (`docs/openbsd-mitigations.md:57`, quoting its innovations page and Bluhm's slides). The slides mark "X-only .text?" and "X-only kernel?" with question marks (`docs/openbsd-mitigations.md:275`): the kernel's own text is not settled.
* Toolchains (from memory, not confirmed in the sources read): clang `-mexecute-only` and lld/GNU ld `--execute-only` exist for AArch64 and ARM; in that mode the compiler builds wide constants from `movz`/`movk` (AArch64) or `movw`/`movt` (Thumb-2) rather than loading from a pool, and ADRP+ADD addressing reaches `.rodata` for data. ARM32 normally puts the pool in text next to the code. RISC-V compilers load 64-bit constants from a `.rodata` pool with `auipc`+`ld` or build them from `lui`/`addi`/`slli` sequences.
* The PDP-11 with split instruction and data space (I&D) had immediates in the instruction stream, which was the nearest ancestor: the program could not read its instruction space as data except through the move-from-instruction-space instructions (`docs/decisions-pending.md:638`, itself marked unconfirmed).

**Pain points.**
* `docs/openbsd-mitigations.md:62`: "In an execute-only binary every such load faults."
* `docs/kernel-pain-points.md:528`: data in the code segment defeats the mitigations (OpenSSL tables containing the byte `0xC3` in text).
* `docs/hardware-vulnerabilities.md:34`: a permission check that comes after the data (Meltdown, Foreshadow, the buffer-sampling family) is the way execute-only has been broken in speculative cores; stale data forwarded "to a load that is going to fault".
* `docs/openbsd-mitigations.md:99`: a pool in text can hold bytes equal to `RET`; the pool rule removes that too.

**Recommendations.**

1. **A separate read-only pool section, `.rodata.pool`, 6-byte PC-relative load (P18 option 1, with its cost stated).** The assembler and linker place each object's pool in a read-only section; the linker orders it within ±128 MB of its text. *Gains:* code pages are pure instructions; no hardware; the pool is also gone from the gadget search space (`RET` bytes). *Costs:* +2 bytes and +1 parcel fetched per wide-constant load (not measured; the compiler can hoist loop-invariant constants, so weigh by hot-loop weight, not by count); a second data-side page. *Priorities:* (1) high, execute-only becomes complete and the disclosure bug no longer yields code; (2) slightly worse, one more parcel per wide constant; (3) slightly worse, 6 bytes instead of 4; (4) none; (5) good, it is an ordinary section; (6) unchanged, `=K` is still the syntax. *Out-of-order:* nothing speculative to fix; the pool load is an ordinary load from a readable page. Requirement for every option that uses execute-only: a load that hits an `X`-only page must not forward data to dependent instructions before the abort (the Meltdown row above), and that rule is written as architecture, not left to the implementation.

2. **Constants in the direct-page window (4-byte load, no new rule for the code).** The linker places the main program's wide constants in a read-only area just below the `DP` base (addressed `d(DP)`, mode 0011), so the load is 4 bytes, one parcel fewer than option 1, and uses no register. *Gains:* the loss of option 1 disappears for the constants of the main image. *Costs:* the ±2 KB window is shared with the hottest globals (256 eight-byte constants fill the negative half); `DP` is one register per mode, so shared libraries cannot use it and fall back to option 1; the window must straddle a read-only page and a writable page, which constrains the data layout. *Priorities:* (1) as option 1; (2) best; (3) best; (4) none; (5) the register allocator is unaffected but the linker has a packing problem; (6) unchanged. *Out-of-order:* as option 1. Best used on top of option 1 as an optimisation, not instead of it.

3. **Keep the pool in text; mark the segment.** Binaries built with pools in `.text` keep `R` = 1 on their code pages; binaries built without are mapped `X` only; the linker records which in the segment flags (an ELF program header with no `PF_R`). *Gains:* nothing to build now; old and third-party code keeps working. *Costs:* the mitigation is per binary, so it is only as good as the weakest library in the process (a readable libc defeats it for gadgets inside libc); OpenBSD's own experience is that "many sloppy practices in userland code had to be repaired" (`docs/openbsd-mitigations.md:57`). *Priorities:* (1) middle, partial; (2) (3) best; (4) none; (5) (6) unchanged. *Out-of-order:* none. Combine with option 1 as the rule for legacy objects.

4. **Hardware: let PC-relative loads read their own execute-only page.** A flag in the entry (or a rule) lets a `MOVQ d(PC)` load read an `X` page. *Gains:* 4-byte loads, no separate section. *Costs:* the page is not execute-only: an attacker who can run any gadget that issues a PC-relative load with a chosen displacement reads code; the fetch-versus-data distinction of abort 9 and 10 becomes "which opcode"; extra decode logic and one more case for the speculation rule above. *Priorities:* (1) worst, a new read path into code, and an exception to a clean rule (priority 1 asks for no strange side effects); (2) (3) best; (4) worse, gates; (5) fine; (6) fine. *Out-of-order:* worst, because the load unit must know the page is execute-only and still forward the data. Not recommended; recorded as the way to get 4-byte loads in hardware.

5. **No pool: build wide constants from pieces.** Two 6-byte or three 4-byte instructions (`movq #hi32`, shift, or) per constant. *Gains:* no data in or beside code at all; no second page. *Costs:* 3 instructions and 8 to 16 bytes fetched per constant against 1 instruction and 6 bytes plus 8 data bytes (not measured); the ISA deliberately has no partial-write instruction such as `MOVK` (`docs/pdp64-isa.md:1608`). *Priorities:* (1) as option 1; (2) worse, more instructions executed; (3) worse; (4) none; (5) harder for the compiler; (6) worse. *Out-of-order:* a dependency chain of three, no hazard. Not recommended; it is the toolchain choice on AArch64 where the encoding forces it.

**Lean:** option 1 as the rule for every object built execute-only, with option 3's segment flag for legacy objects, and option 2 as a later linker optimisation for the main program's hot constants once the cost of option 1 is measured. Reason: option 1 is the only one that makes code pages truly pure at no hardware cost, and the 2-byte penalty falls on a rarely executed instruction (a wide constant) except in a hot loop, where the compiler hoists it. **The author must decide:** (a) whether the 6-byte penalty is acceptable, or whether option 2 is wanted at once; (b) whether the kernel's own text is execute-only (OpenBSD itself has it as a question); (c) the real reach of a PC-relative `len = 10` operand (±128 MB or ±2 GB), which fixes how far the pool section may sit; (d) that the Meltdown-class rule (no data forwarded from a faulting load) is stated in the architecture.

## 4. IOMMU hardening for PCI Express devices (question F25)

**Question.** The IOMMU (the input-output memory-management unit, which translates and checks every address a device puts on the bus, the way the processor's MMU does for programs) is in the design (errata 75). Thunderclap showed that an IOMMU alone does not stop a hostile or compromised device. What does the Q64 root complex enforce on its own, what does the kernel enforce, and what, if anything, needs a device that cooperates?

**Current state.**
* R6 recommended "none for now; devices address all of physical memory" (`docs/decisions-pending.md:1072,1210-1233`); errata 75 reversed it: "an IOMMU is part of the design, and later maps a C64/C128 window". F4 leans to reusing the CPU's page-table format; F25 holds the one-line lean quoted in the question (`docs/decisions-pending.md:1595`).
* Errata 81 (`docs/errata.md:231`): a mitigation that lives wholly on the processor side "is invisible to cards and needs no discovery"; only an extension that needs a card's cooperation is announced.
* Physical addresses are 40 bits; bit 39 set is device space, clear is memory (errata 60). The CPU's entry must agree: a leaf whose physical page has bit 39 set must be device-typed, otherwise a protection fault (errata 65, `docs/errata.md:215`). The page-table entry is 64 bits with bits 10-11 and 40-63 reserved (`docs/pdp64-system-architecture.md:371`).
* DMA buffers are mapped uncached with an explicit `FENCE` before the doorbell (`docs/manual/02-bus.md:49-51`; F5). A read of nonexistent memory is a precise `BUSFAULT`; a timed-out posted write is a machine check (`manual/02-bus.md:35`; `docs/pdp64-isa.md:1196`).
* `docs/architecture-recommendations.md:74,176` (R-12): a descriptor never holds a kernel pointer, only an offset into a region the kernel registered; DMA into device space is refused; the unit should be range-based and on by default, with per-device windows. `docs/hardware-vulnerabilities.md:281` (N8): every bus master is bounded by a window or a translation unit "on by default".
* The standard devices are virtio-net, virtio-gpu and virtio-snd (errata 79), NVMe and xHCI (errata 75); any other device may be attached (errata 78).

**What other systems do.**
* Linux marks a PCI device `untrusted` and, for such a device, forces every mapping through the bounce-buffer layer (`dev_use_swiotlb`, `drivers/iommu/dma-iommu.c:591-602`), forces the scatter-gather path to bounce (line 1772), zeroes the padding around the bounced copy so "untrusted devices should not see padding areas with random leftover kernel data" (lines 1186-1198), and refuses to probe a driver that tries to put an untrusted device in any domain other than the translated default (`drivers/iommu/iommu.c:1927-1934`). That devices behind external-facing ports (Thunderbolt, USB4) get the flag is from memory, not confirmed in the sources read (the setting code is under `drivers/pci`, which is not in the local tree).
* Linux invalidation is strict or lazy: `iommu.strict=0` "Request that DMA unmap operations use deferred invalidation of hardware TLBs, for increased throughput at the cost of reduced device isolation" (`Documentation/admin-guide/kernel-parameters.txt:2651-2658`); the choice is a build-time default (`iommu.c:47`, `244-245`). The cost of the strict choice in Thunderclap: "Synchronous IOTLB invalidation ... can reduce throughput by as much as 80% for high-performance I/O workloads" (`docs/hardware-vulnerabilities.md:300`, from the paper).
* Linux groups devices that cannot be told apart by the IOMMU (no PCIe access-control services between them) into one group that is one domain; `Documentation/driver-api/vfio.rst:60` mentions the non-ACS case. What the four ACS (access control services) controls are (source validation, peer-to-peer request redirect, completion redirect, upstream forwarding), and that ATS (address translation services, which let a device cache translations and then send "pre-translated" requests that skip the IOMMU check) is a documented bypass risk, are from memory, not confirmed in the sources read.
* Linux interrupt remapping exists as a separate layer (`drivers/iommu/irq_remapping.c`); x86 MSI writes are plain memory writes to an address window, which is why a device can forge them without it (from memory).
* OpenBSD: the local tree has two IOMMU drivers, sparc64 (`sys/arch/sparc64/dev/iommu.c`, with a streaming-buffer flush on unload, `iommu_strbuf_flush_done`) and the arm64 SMMU (`sys/arch/arm64/dev/smmu.c`, per-domain page tables; `smmu_dmamap_unload` removes the mapping then calls the parent unload, lines 1517-1524). The x86 DMAR driver (`dev/acpi/acpidmar.c`) is not in the sparse tree and was not read. The amd64 `bus_dma.c` uses bounce buffers only for SEV guests, `use_bounce_buffer = cpu_sev_guestmode || FORCE_BOUNCE_BUFFER` (`sys/arch/amd64/amd64/bus_dma.c:184-189`).
* Thunderclap (NDSS 2019, as recorded in `docs/hardware-vulnerabilities.md:300`): "MacOS was the only OS to enable the IOMMU by default"; per-device mappings versus "a single IOMMU page table that is used by all devices"; the spatial leak of 4 KB granularity; kernel pointers in descriptors; "Byte-granularity or non-paged IOMMUs could prevent spatial vulnerabilities but would need a new hardware paradigm."
* Apple's DART and Windows' Kernel DMA Protection are the same default-deny for external ports (from memory, not confirmed).
* Ancestors: the Unibus map of the larger PDP-11s and the VAX Unibus adapter's map registers were a simple IOMMU for the 18-bit bus (`docs/decisions-pending.md:1230`).

**Pain points.**
* `docs/kernel-pain-points.md:111`: "Devices as DMA masters: protection ... an IOMMU alone is not enough"; its re-marked cell lists the lean of F25.
* `docs/kernel-pain-points.md:110`: devices that cannot reach all of memory (bounce buffers); closed by the IOMMU.
* `docs/kernel-pain-points.md:618-621`: changing IOMMU mappings can cost more than copying ("memcpy can be significantly faster"; unmap time fell "97%, 94%, 90%, and 87%" when bounce buffers replaced mappings); locks in the IOMMU layers limit multithreaded DMA; the IOVA cache falls over for long mappings.
* `docs/kernel-pain-points.md:949-950`: Thunderbolt devices are DMA masters; "the common practice of leaking kernel pointers to peripheral devices is no longer acceptable"; "Spatial vulnerabilities occur when the 4KiB page ... granularity of translations allows undesired access beyond the intended physical memory range".
* `docs/hardware-vulnerabilities.md:273-274, 281`: Thunderclap, the Thunderbolt text, rule N8.
* `docs/kernel-pain-points.md:114,117` (re-marked 2026-11-03): device errors and a bus reset that must not look like a removal (F27).

**Layers common to every option below.** These are processor side (root complex and IOMMU) and need no announcement (errata 81), except where marked.

* **L1. Default deny.** At reset every requester identity (bus, device, function) has an empty domain; no DMA works until the kernel installs a domain. The unit is enabled before the first bus-master bit can be set.
* **L2. One domain per requester, never shared**, with the exception of devices the hardware cannot tell apart (behind a bridge or switch without ACS), which are one group and one domain, and are always treated as untrusted. The root complex always routes device-to-device (peer) requests upstream to the IOMMU (the ACS redirect behaviour) on its own ports; a switch outside the root complex must offer ACS or its downstream devices form one group.
* **L3. The space bit.** The IOMMU's input is a 39-bit I/O virtual address in the CPU's page-table format (F4); a device address that is not canonical (bits 63 to 39 not all equal) is a fault, the same rule as `NONCANON` for the CPU. Its output page must have bit 39 clear (memory) unless the domain carries an explicit peer/C64 window flag; so no ordinary domain can reach device space (the rule of R-12(b) and the mirror of errata 65). A device that can only emit 32-bit addresses fits in a domain with its I/O virtual addresses below 4 GB, so it needs no bounce buffer (closes the pain at `kernel-pain-points.md:110`).
* **L4. Direction in the leaf.** The leaf's `R` and `W` bits constrain the device: a buffer the device only reads is never writable by it, a receive buffer never readable by it. No `X`.
* **L5. ATS and page requests off.** The root complex drops any request carrying a "translated" address type and any page-request message, unless the domain is flagged; no standard device of iteration one needs them. Invisible to cards, since a card that does not use ATS never notices.
* **L6. Interrupt remapping.** A write to the interrupt window is looked up in a per-requester table: the device supplies an index, the table supplies target core and vector, and a device that writes outside its own entries is faulted. A device cannot raise another device's vector or one the kernel did not give it. The entry can be retargeted atomically and masked while it changes (F24). This is the one place a device can otherwise inject a vector; no card cooperation.
* **L7. Strict invalidation, never lazy.** Unmapping completes only when the IOMMU has dropped the translation; the cost is cut by removing unmaps from the hot path (permanent ring mappings, pooled buffers), not by deferring them. Lazy invalidation leaves a window in which a stale translation lets a device write into a page the kernel has reused.
* **L8. Faults are events, not exceptions, and quarantine the device.** An IOMMU fault is asynchronous to every instruction the processor has run, so it cannot be a precise `BUSFAULT`. It becomes: a record (requester, I/O virtual address, access type, cause) appended to a fault ring in memory with an overflow flag; a read by the device completes with an error (unsupported request) so the device sees it; a posted write is dropped; the requester's domain goes empty in hardware until the kernel resets the device (function-level reset) and reinstalls it; one interrupt reports it, rate-limited. Recovery is cheap and restartable: detach the driver, reset, remap. Where the kernel then reads the device's registers and the link is gone or the device returns an error completion, F27 makes that read a precise `BUSFAULT`, so the driver learns by the normal path.
* **L9. Table coherence and order.** The IOMMU's walker reads tables the processor has written; tables sit in uncached memory (F5) or are written back, and a map or unmap is a table write, `FENCE`, then a write to an invalidate register that the kernel waits on. Written so that no speculative or out-of-order processor access is involved: the IOMMU does not speculate and a stale entry cannot be created by a processor-side speculative read.
* **L10. Software rules (kernel and drivers, no hardware).** (i) `bus_dma` hands a driver an I/O virtual address, a distinct type from a kernel pointer; a descriptor holds that address or an offset, never a kernel pointer, and never a function pointer. (ii) The kernel copies what a device-writable ring says exactly once into private memory before using it, so a device cannot change a length between the check and the use (a double fetch). (iii) I/O virtual address space for a domain is allocated from a randomised, guard-paged range.

**Recommendations.** The options differ in how the 4 KB granularity problem is solved and in the trust policy; L1 to L10 apply to all of them.

1. **Paged IOMMU with copying for small buffers (the F25 lean as written).** Translation per 4 KB page; rings permanently mapped in pages used for nothing else; any buffer smaller than a threshold, or not page-aligned at both ends, is copied into a pre-mapped bounce page owned by that device's domain. *Gains:* no new hardware beyond a standard paged unit; Linux's `untrusted` path is the same shape (`dma-iommu.c:591-616`), so the code is well trodden. *Costs:* every small I/O pays a copy (the pain table says a copy can beat a remap, `kernel-pain-points.md:618`); the bounce pool's own pages are shared among that device's buffers, so one buffer's tail is visible to the device alongside the next; zeroing padding costs more cycles; the copy is memory traffic, which is the slow resource. *Priorities:* (1) good for the leak, nothing for the cost; (2) worse, copies are extra instructions and fetches; (3) none; (4) smallest gate count; (5) (6) no effect. *Out-of-order:* nothing speculative in the IOMMU; the copy is ordinary code.

2. **Paged IOMMU with a byte range in each leaf (recommended hardware addition).** The IOMMU leaf (same format as the CPU's, F4) uses reserved bits 40-63 for a first-valid-byte and a last-valid-byte within the page (12 + 12 bits). A mapping of a buffer sets the first page's start offset and the last page's end offset; a device access outside the range is a fault. PCI Express memory requests never cross a 4 KB boundary (from memory, not confirmed), so one range check on the leaf already fetched suffices for each request: two 12-bit comparators per translation, no second lookup. *Gains:* the buffer's neighbours in the same page are unreachable: the spatial leak Thunderclap reports closes without copying, at byte granularity ("Byte-granularity ... IOMMUs could prevent spatial vulnerabilities" and, without "a new hardware paradigm", because the table is still paged, only the leaf is richer); no bounce for sub-page buffers; invalidation is the same single-page invalidate; the IOTLB entry carries the range. *Costs:* a few hundred gates in the root complex; slightly larger leaves in the IOMMU's tables; the driver sets two offsets per end page (a few instructions per map). Not standard PCI Express IOMMU behaviour, so software that expects a plain paged unit still works (the range is full by default) and does not know. *Priorities:* (1) best: leak closed in hardware, a fault is the error and it is easy to detect; (2) best: no copy; (3) none; (4) small; (5) one more field in the map call; (6) none. *Out-of-order:* the range check is in the unit, which does not speculate; nothing for the core.

3. **Per-queue base-and-length windows instead of paging (R-12, range-based unit).** Each requester has a small set of window registers (base, length, direction); the device uses offsets into windows. *Gains:* byte granular by construction; revocation is a register write, so the 80% invalidation cost disappears; trivial verification. *Costs:* scatter-gather fits poorly (an NVMe request with a list of 4 KB pages, a virtio buffer chain, an indirect table each need a window per segment or a window large enough to cover the whole region, which leaks the in-between); stock devices put absolute bus addresses in descriptors, so the window base must be subtracted by the unit, which is a translation in all but name; a window count that is too small is a new limit, too large is a table. *Priorities:* (1) good for rings, awkward for data; (2) good; (3) none; (4) middle; (5) harder; (6) harder. *Out-of-order:* none. Best as the mechanism for rings only, beside option 2 for data.

4. **Trust tiers by port, with bounce-only for untrusted devices.** The root complex knows which of its ports are internal (fixed on the board) and which are external or hot-pluggable. A device behind an internal port in the kernel's trusted list (the standard virtio set, the NVMe drive, the xHCI controller) gets option 2 mappings. Any other device, and anything that appears on an external or hot-plug port or behind a non-ACS bridge, is untrusted: it is attached with bus-mastering off, no peer traffic, no ATS, strict invalidation, only a fixed bounce region (a single permanently mapped pool, with zeroed padding as in `dma-iommu.c:1186-1198`), and no mapping of user pages; promotion to trusted needs an operator action. *Gains:* this is the Thunderclap posture ("the common practice of leaking kernel pointers to peripheral devices is no longer acceptable") for the case that matters, a stranger plugged into a port; nothing changes for the internal devices. *Costs:* untrusted devices are slow (copies); the kernel needs a trust list and the root complex needs a bit per port; the trust list itself is policy to maintain. *Priorities:* (1) best for hot-plug; (2) none for trusted devices, bad for untrusted; (3) none; (4) one bit per port; (5) (6) none. *Out-of-order:* none. A policy layer on top of option 1, 2 or 3; not an alternative to them.

5. **Cooperating devices: region handles and offsets (an announced extension).** A pdp64-aware device is given a region (base and length) once through a configuration register, and every descriptor then carries a handle and an offset, so the device never sees a raw bus address and the IOMMU checks offset against length. Announced by a PCI Express extended capability (errata 81). *Gains:* descriptors carry no addresses to leak, and a buggy (not hostile) device that miscounts is stopped by its own hardware. *Costs:* it protects nothing against a hostile device, which simply ignores the handle; the enforcement therefore has to be the IOMMU anyway (option 2 or 3), so the extension adds device logic and a driver path for no new guarantee; the standard virtio devices would need a new feature bit and a spec change. *Priorities:* (1) low; (2) none; (3) none; (4) more gates, in the card; (5) (6) worse. *Out-of-order:* none. Not recommended; recorded because R-12(a) of the architecture recommendations asks for "an offset into a region the kernel registered". Done on the kernel side instead, it is rule L10(i).

**DMA to user buffers, by option.** None of the options maps a user page into an untrusted device. For a trusted device the kernel wires the page, maps it with the direction bits and (option 2) the byte range, and unmaps strictly before unwiring. A user-space driver gets its own domain per device and is as trusted as that device (`kernel-pain-points.md:111`, "a user-space driver is as trusted as its device").

**Permanent mappings versus per-I/O mapping.** Rings, completion queues and a pool of data buffers owned by a device (receive buffers of the network card, say) are mapped once at attach. Data that cannot come from the pool (a disk block to a user buffer) is either copied through the pool (small) or mapped per I/O with a strict, batched invalidate (one invalidate per completion batch, waited on before the pages are reused). Pool pages are type-stable (they only ever hold payload for that device), so a late invalidation of a pool mapping could not expose kernel secrets; that is the only case where a deferred invalidate is harmless, and the design does not use it, to keep one rule.

**Lean:** layers L1 to L10 always; option 2 as the mechanism for data buffers, option 3 for rings only if the window registers prove cheap, option 1's copy kept only for buffers the driver cannot align and for untrusted devices; option 4 as the policy on top; not option 5. Reason: Thunderclap's two serious findings, kernel pointers and page granularity, are answered at the root complex without any card's help (priority 1: the error cannot arise because the access faults; detection is automatic, recovery is a reset and remap), and option 2 does it without copying (priority 2: memory traffic is the cost to minimise). Strict invalidation with permanent mappings keeps the cost of strictness to the rare per-I/O unmap. **The author must decide:** (a) whether the IOMMU leaf may carry the byte range in reserved bits 40-63 of the CPU's entry format, or the I/O format is separate; (b) the trust policy: which ports are internal, who may promote a device, whether an untrusted device is allowed at all on a machine without a console operator; (c) whether an IOMMU fault quarantines the device in hardware (L8) or only reports; (d) whether a peer-to-peer window for the C64/C128 card (errata 77) is a domain flag in iteration one or later; (e) the fault-ring size and what the kernel does when it overflows; (f) whether Thunderbolt/USB4 tunnelled PCI Express is supported in iteration one at all (the safest answer is no).
