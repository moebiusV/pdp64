# Hardware vulnerabilities that needed mitigations, and the rules that keep pdp64 from repeating them

[← pdp64 index](../README.md)

**Companion of [`kernel-pain-points.md`](kernel-pain-points.md) (chapters 4 and 13) and of the kernel assembly survey ([`kernel-asm-survey.md`](kernel-asm-survey.md)).** The author's requirement: no Rowhammer, no Spectre, no timing-channel attacks. This document lists the processor, memory and system flaws of the last decade that forced operating systems to add mitigation code; says in plain words how each one works; and turns each into a rule (C1 to C16, section 5) that any pdp64 implementation, in-order today and perhaps out-of-order tomorrow (errata 38), must obey.

**Status.** Written from: the Linux hardware-vulnerability documents in `Documentation/admin-guide/hw-vuln/` (commit `7be4bc52`, local), the x86 and arm64 mitigation code (local), mailing-list posts and commit messages read in Phase 2 of the pain-points study, the OpenBSD sources and pages, and Wikipedia pages used only as pointers. **Evidence labels:** **[G]** guarantee (a manual, standard or kernel documentation says it); **[P]** practice (the current code shows it); **[D]** developer statement (a list post or commit message, URL in `kernel-pain-points.md` section 14A and Appendix C); **[S]** secondary (Wikipedia or an article); **[U]** unverified, from memory, to be fetched. Disclosure years that are not in a local source are **[U]**. No exploit code and no exploit recipes are given: each entry says what the flaw is and what prevents it.

## 1. The pdp64 position today

pdp64 as documented is an **in-order, non-speculative, single-core machine** with a sequentially consistent memory model (ISA section 17.1; errata 38). It has **no SMT, no hardware transactional memory, no speculation, no performance counters, no virtualization, no enclave** (ISA section 17.5; system architecture section 15). On that machine most of the entries below **cannot occur**, because they all need the processor to run instructions it may later undo (transient execution), to share predictor or buffer state between mutually distrusting programs, or to give timing that depends on secrets. This is a design property of the *design point*, not a proof: it holds as long as the implementation does not add the features of section 2. The architecture is, by the author's decision (errata 38), kept ready for a large out-of-order core; the rules of section 5 are what keep that door from reintroducing the whole list.

What is still exposed on today's machine, honestly: data-dependent **timing** of a few instructions (section 4); **cache timing** if a cache is shared between mutually untrusting programs (ISA says only that caches are "a cache question"); **DRAM disturbance (Rowhammer)** is a property of the memory chips and controller, which the bus and memory documents do not yet mention; **DMA** and cold-boot access to memory (R6, R7); **unprivileged timers** are proposed (P3), which is a decision with a side-channel cost.

## 2. How these attacks work, in plain words

* **Speculative execution** (the processor guesses the outcome of a branch or a load and runs ahead, undoing the *architectural* results if it guessed wrong) leaves traces in the **microarchitecture** (the hidden state of caches, buffers and predictors). A program that can read those traces by timing learns what the undone instructions touched. This is a **transient execution attack**.
* **Branch predictors** (tables that remember where branches went) are *trained* by one program and *used* by another when they are shared and not tagged by who owns them: this is **branch target injection** (Spectre v2 family). **Return predictors** (a small hardware stack of return addresses, the return stack buffer) can be under- or over-flowed.
* **Permission checks that come after the data** (the load returns data to dependent instructions before the privilege check retires) give **Meltdown**, **Foreshadow (L1 terminal fault)** and the **line-fill-buffer, store-buffer and load-port sampling** family (MDS and relatives): *stale data inside the core is forwarded to a load that is going to fault.*
* **Side channels by time** (measuring how long something takes) work on caches (**Prime+Probe**, **Flush+Reload**, **Evict+Time**: fill, flush or evict cache lines and time the victim or the attacker's own re-access), translation caches (**TLBleed**), shared execution ports (**port contention**, visible between SMT siblings), and on **frequency or power** (**Hertzbleed**, **Platypus**).
* **Prefetchers and value predictors** that act on data values (**GoFetch**, **SLAP**, **FLOP**) turn data into addresses without any architectural access.
* **Fault injection** (changing voltage, frequency or memory contents to make the hardware compute a wrong result: **Plundervolt**, **CLKscrew**, **Rowhammer** and descendants) attacks correctness instead of confidentiality.
* **DRAM** stores bits as charge in capacitors; activating a row many times disturbs its neighbours: **Rowhammer**. **Cold boot** and **DMA** attacks read memory the CPU has not been asked about.

### 3.2 Permission checks after the data: Meltdown and the buffer-sampling family

| Name | Mechanism (plain) | Feature that enabled it | Disclosed | Affected | Mitigation and cost | Rule | pdp64 today |
|---|---|---|---|---|---|---|---|
| **Meltdown**, rogue data cache load (CVE-2017-5754) | a user program reads kernel memory; the load faults, but dependent instructions already ran with the data and left a cache trace | privilege check performed late, data forwarded early; kernel mapped in every user address space | Jan 2018 (found independently by three teams, per the authors' site **[S]**) | Intel (all x86 of the time), some Arm and Power cores, IBM z | **page-table isolation (KPTI/KAISER)**: unmap the kernel while user code runs. Cost, Dave Hansen (KAISER cover letter, 31 Oct 2017) **[D]**: "a few hundred cycles" per syscall or interrupt, "5% ... typical", "roughly 30%" worst case; Linux `pti.rst`: a `cr3` write "on the order of a hundred cycles" at each entry and exit [G]; PCIDs keep the TLB. OpenBSD, NetBSD and FreeBSD each added it within 11 weeks (commits `bd50262f705c`, `03db57fb7f3c`, `b767b017801a`) | **C1**, C9 | cannot occur; **but pdp64 maps the kernel in every address space** (D6), so on a speculating core this is the first rule to obey |
| **Foreshadow / L1TF** (L1 terminal fault) | a page-table entry marked not-present still lets the L1 data cache supply its (stale) data speculatively when the physical address bits point at cached data; breaks virtual machines and SGX | speculation past a not-present translation using the physical address in the entry | Aug 2018 **[U]** | Intel | **PTE inversion** (the kernel writes unmapped entries with address bits pointing to non-existent memory), L1D flush on VM entry, SMT control; `l1tf.rst` 615 lines [P] | C1, C5 | cannot occur; the walker never forwards data from an invalid entry. **Rule for the entry format:** a not-present entry's other bits must not be used by any speculative path; pdp64 already faults on any set reserved bit (system architecture 15) |
| **MDS: RIDL, Fallout, ZombieLoad** (microarchitectural data sampling) | a faulting or assisted load is given stale bytes from the line-fill buffer, store buffer or load ports belonging to another thread or privilege level | shared internal buffers forwarded to a load that will fault | May 2019 **[U]** | Intel (not AMD) | `VERW` repurposed to clear the buffers on every return to user mode and every VM entry; disable SMT where affected. `mds.rst` 303 lines [P]; "SMT disabling can have a significant performance impact" [G] | **C5**, C6 | cannot occur; no such buffers shared |
| **TAA** (TSX asynchronous abort), **SRBDS/CrossTalk**, **MMIO stale data**, **RFDS** | the same sampling idea through transactional aborts, a shared special-register buffer, device-register accesses and the register file of Atom cores | internal buffers and register files not cleared at domain change | 2019 to 2024 **[U]** | Intel | the same `VERW`; microcode; TSX disabled; 270, 150, 269 and 96 lines of documentation [P] | C5 | no TSX, no shared buffers |
| **LVI** (load value injection) | the reverse of the above: the attacker injects values into the victim's loads | the same buffers | Mar 2020 **[S]** | Intel | compiler inserts `lfence` before every load that could be affected; extreme cost **[U]** | C5, C4 | cannot occur |
| **SWAPGS** (CVE-2019-1125) | speculation past the kernel's `swapgs` using the wrong base register | speculation across a privileged-state change | 2019 **[U]** | Intel, AMD | barrier after `swapgs` on paths, comment in OpenBSD `cpu.c`: protection depends on SMAP faulting [P] | C1 | no `swapgs`; banked `DP` (E36) |
| **Lazy FP state restore** | the previous process's floating-point registers are readable until the lazily-delayed restore traps | lazy FPU context switching | Jun 2018 **[U]** | Intel | eager FPU save and restore; the Linux commit calls the lazy design "rather messy" and says setting the task-switched bit is "far slower" than saving the state **[D]** (commit `58122bf1d856`) | C5 | no FPU state; floating point lives in the general registers |
| **Zenbleed** | a mis-speculated vector instruction (`vzeroupper`) leaves registers holding other processes' data | speculation with an incorrectly rolled back register file | Jul 2023 **[S]** | AMD Zen 2 | a "chicken bit" disabling an optimisation (FreeBSD `ebaea1bcd2eb`, Sep 2023 **[D]**), microcode | C5 | no vectors yet (S-decisions) |
| **Downfall / GDS** (gather data sampling) | a vector `gather` instruction leaks data from a shared vector register buffer | shared gather buffer | Aug 2023 **[U]** | Intel Skylake to Tiger Lake | microcode; `gather_data_sampling.rst` 109 lines [P]; costs reported up to 50% on gather-heavy code **[U]** | C5 | no gather |
| **TSA** (transient scheduler attacks) | the scheduler forwards wrong data on false completion of speculative loads | scheduler timing leak | Jul 2025 **[S]** | AMD Zen 3/4 | microcode, `VERW`-style clear | C5 | cannot occur |
| **Meltdown-like on others** | Arm Cortex-A75 and others (Variant 3a), Power (cache-flush hooks), IBM z (kernel unmapping), AMD (a 2021 variant, Wikipedia says no new mitigation) | same as Meltdown | 2018 on **[S]** | Arm, Power, s390, AMD | per-architecture kernel work: Linux `arch/powerpc` 5 and `arch/s390` 4 matching lines (counted) [P]; arm64 `proton-pack.c` 1,213 lines | C1 | cannot occur |

|---|---|---|---|---|---|---|---|
| **SMT attacks and OpenBSD's SMT policy** | two hardware threads share one core's caches, ports, predictors and buffers; one can measure or sample the other. ## 4. Constant time: which pdp64 instructions leak through their timing

The author wants a **constant-time facility** (a flag or similar so that instructions take equal time whatever their inputs; decision P17 is being written). This section lists which pdp64 instructions are, in any plausible implementation, **data-dependent in time**, and which are naturally constant-time. **Caveat that governs all of it:** constant-time *instructions* do not make constant-time *code*. A load or store whose address depends on a secret leaks through the cache (C9); a branch that depends on a secret leaks through the predictor and through time; a loop whose count depends on a secret leaks the count. The facility removes one class of leak (instruction latency) and leaves the program's addresses and branches to the programmer and the compiler.

| Instruction family | Data-dependent in a plausible implementation? | Why | What a constant-time mode would have to do |
|---|---|---|---|
| `ADD SUB AND OR XOR NOT NEG`, `MOV`, `LEA`, shifts and rotates by immediate, `SET`, `MASKEQZ`/`MASKNEZ`, byte swap, bit reverse, `POPCNT`, count leading/trailing zeros (as a combinational circuit), `CLMUL` | **naturally constant-time** | single-cycle or fixed-depth logic; no early out in a sane design | nothing; `MASKEQZ`/`MASKNEZ` already give branch-free select (the ISA's note on constant-time crypto) |
| shifts and rotates by **register count** | constant in a barrel shifter; may be iterative in a small core | an iterative shifter is count-dependent | require a barrel shifter, or fixed latency |
| `MUL`, `MULH`, `MULHU` | **plausibly data-dependent** on a small in-order core (early termination when high bits are zero is a classic area saving); constant on a pipelined multiplier | early-out multipliers leak the operand magnitude | no early out; document the latency as fixed |
| `DIV`, `DIVU`, remainder | **data-dependent**: a non-restoring or radix-4 sequencer takes a time that depends on the quotient size or leading zeros | the divide is a multi-cycle sequencer (the ISA's opcode table calls them "multi-cycle") | fixed worst-case cycles in constant-time mode, or forbid for secrets |
| compare, `CBCC`, `bCC`, `JMPI`, `CALLI` | the *outcome* of a branch is visible through timing and predictors | branch resolution, prediction state | the program must not branch on secrets; use `SET`/`MASKEQZ` |
| `MCMP` (compare `Rn` bytes, "flags from the first difference") | **data-dependent by definition**: stops at the first difference | classic `memcmp` timing leak | a constant-time compare variant that scans all `Rn` bytes, or a flag that makes `MCMP` do so |
| `MSCN`, `MCPY`, `MSET` | length-dependent (inevitable) and, for `MSCN`, early exit on a match | the duration reveals the length or the position of the byte | length must not be secret; constant-time `MSCN` scans the whole range |
| loads and stores | **data- and address-dependent through the cache** and the TLB | hit or miss times differ by many cycles | only partitioning and flushing (C9) or secret-independent addresses help |
| atomics (`CAS`, `LL/SC`, fetch-and-op) | depend on contention and coherence state | other cores' behaviour | not a data-dependence on operands; relevant only for SMP |
| floating point add, multiply, FMA | **subnormal** operands or results can take a slow path on some designs (assists, microcode) | handling of denormal numbers | flush-to-zero or fixed-latency handling in constant-time mode; ISA must say which |
| `FDIV`, `FSQRT`, conversions | **data-dependent** iterative sequencers | multi-cycle sequencers | fixed worst case or forbid for secrets |
| `FCLASS`, `FMIN/FMAX`, sign operations | constant | combinational | none |
| privileged: `TLBI`, `ICINV`, `MFSR` | constant on one core; broadcast cost depends on other cores | | none now |

**Reading this table:** the cheapest and strongest rule is to make the *architecture* state that a named set of instructions has operand-independent latency, with the iterative ones (divide, square root, early-out multiply, `MCMP`/`MSCN` early exits, floating-point subnormals) either specified as fixed-latency or excluded from the set. A processor-wide "constant-time mode" bit costs gates only in the sequencers (a counter that always runs to its maximum) and is a mode bit in the sense of errata 42; its benefit is named (secret-independent latency) and its cost is the worst-case latency of every divide while it is on. This follows the principle order: (a) no code size; (b) one failure class removed from all crypto code; (c) cost only while enabled. Details are P17's.

## 5. A checklist for any pdp64 implementation

Each rule says what must hold, in the form of a design or review item. "Today" is the status of the in-order, single-core design.

| # | Rule | Prevents | Today |
|---|---|---|---|
| **C1** | **No speculation across protection domains, and no early forwarding of data that fails a permission check.** The privilege, permission and valid-bit checks complete before any value derived from the access is visible to a dependent instruction. A not-present or reserved-bit entry produces no data. | Meltdown, Foreshadow/L1TF, MDS-style forwarding to faulting loads, Spectre v1 (partly: C4) | holds (no speculation) |
| **C2** | **No predictor state is shared between privilege levels or address spaces without being flushed or tagged by ASID and mode.** This covers direction predictors, target predictors, return predictors, branch history and loop predictors; a hardware return stack must be per domain or cleared at the mode change; the architecture provides a single instruction that clears predictors (an `IBPB`-equivalent) and a way to prevent the kernel's indirect branches from using user-trained entries. | Spectre v2, RSB, Retbleed, SRSO/Inception, BHI, ITS, Phantom, VMScape | holds (no predictors) |
| **C3** | **No value, address or store-to-load prediction that lets a load return a wrong value to later instructions without a verified recovery before any observable effect, unless it can be disabled per domain by an architectural bit.** | Spectre v4, SLAP, FLOP, LVI | holds |
| **C4** | **A defined speculation barrier exists and is architecturally guaranteed** (`HINT #2` is defined by E39); an architectural per-domain switch can disable all speculation for a domain. RISC-V's lack of a dedicated barrier was a finding in Aug 2026 **[S]**; pdp64 has one. | Spectre v1 and the barrier-based software mitigations | defined; unimplemented because no speculation |
| **C5** | **No microarchitectural buffer holds data from one domain where a load of another domain can receive it**: fill buffers, store buffers, load ports, vector and register files, scheduler queues are partitioned per thread or domain, or an architectural clear instruction empties them at domain change. | MDS family, TAA, SRBDS, RFDS, Zenbleed, Downfall, TSA, lazy FPU | holds |
| **C6** | **No SMT between mutually untrusting domains**: either the implementation has none (today), or the resources it shares are partitioned and a core-scheduling control exists. | SMT attacks, TLBleed, port-contention channels | holds (no SMT) |
| **C7** | **A published constant-time set**: the architecture names the instructions whose latency is independent of operand values, specifies a constant-time mode for the sequencer-based ones (divide, square root, early-out multiply), a full-length compare and a full-length scan, and floating-point subnormal handling. | timing attacks on crypto and compare routines | **not met**: section 4 |
| **C8** | **No data-dependent prefetcher**; any prefetcher acts on addresses only and is disabled by a single architectural bit during secret work; prefetch instructions do not fault and do not reveal translation state. | GoFetch, AnC, prefetch-based ASLR breaks | holds (no prefetcher; P15 pending) |
| **C9** | **Caches and TLBs are flushed or partitioned at a privilege change when they are shared with another domain**; cache lines carry no secret-dependent state across the change; page-table walker accesses do not leave a user-observable trace of mapped addresses. The ISA states the required cache indexing and a flush-by-address (P6). | cache and TLB timing, AnC, Meltdown-class cache traces | **not met**: undefined |
| **C10** | **Voltage, frequency and energy interfaces are privileged and cannot be set from the rest of the system; frequency does not depend on data while secret work runs; energy counters are not readable by unprivileged code.** | Plundervolt, CLKscrew, Platypus, Hertzbleed | holds (none defined) |
| **C11** | **The memory controller and the bus specification say what protects DRAM**: a row-activation limit or target-row refresh, refresh management, ECC with scrubbing that detects at least double-bit errors, a reporting path for corrected errors (R7), and a statement that address scrambling is not a defence. | Rowhammer, TRRespass, Half-Double, ECCploit, RAMBleed | **not met**: no text |
| **C12** | **Default-deny for bus masters** (an I/O translation unit, R6) and memory scrubbing or encryption at reset. | DMA attacks, cold boot | **not met**: R6 open |
| **C13** | **Every microarchitectural state that survives a privilege change is documented, and the chip reports which flaws it does not have** (feature registers with "not vulnerable" bits, P4, instead of a per-model blacklist); errata are published in a stable table. | the 58-row x86 blacklist and `old_microcode` problems | feature registers proposed (P4) |
| **C14** | **Timers**: an unprivileged counter (P3) has a documented granularity and can be disabled per process; no instruction reads a more precise clock than the program has a right to. | Flush+Reload and every timing channel | decision P3 pending |
| **C15** | **No enclave claims without partitioned hardware**: if a trusted-execution feature is ever added it must come with C1 to C9 for its domain. | SGX/TEE attacks | none planned |
| **C16** | **Pointer authentication and memory tagging, if ever added, must be unbypassable by speculation and must not give a timing oracle to a failed check.** | PACMAN, MTE speculative probing | not present |

## 8. What this does not show

* Years and mitigation costs not marked [D], [P] or [S] are from memory and are listed as unverified; the next pass should fetch the original papers (Spectre, Meltdown, Foreshadow, RIDL, ZombieLoad, Retbleed, Downfall, Hertzbleed, GoFetch, Rowhammer) and the vendor advisories.
* The cost percentages are workload-dependent and come from different measurements (a developer's benchmark, a news site, a paper); they are not comparable with each other.
* "Cannot occur" means: cannot occur in the documented in-order, non-speculative design. Any real implementation may add structures (a return stack, a prefetcher, a store buffer with forwarding) that bring back the same questions; section 5 is the review list for that day.
* Rules C7 and C9 are not satisfied by the current specification; C11 and C12 are not addressed by it. They are open items, not facts about the machine.
* The coverage of vendors is Intel, AMD and Arm because that is where the disclosures were; RISC-V and Power findings are fewer, and a 2026 report says commercial RISC-V cores already show the same classes of weakness **[S]**.
