# Questions the owner asked, and the answers

*A record, kept because the owner asked that the answers to his queries be saved (answers01.txt, 2026-11-25; errata 204). Plain words; each answer says where the facts come from. This is a dated record, not a statement of the architecture: the manual and the errata say what is decided.*

## Round of 2026-11-25 (on answers01.txt)

**The rule that applies to the main loop only (the vector block).** A block that keeps sums in registers (an accumulator block) may not both read and write the same stream of memory in its *main loop*, the instructions that repeat for every strip. The reason: if a restart repeats a strip that updated memory in place (`a[i] += 1`), the update happens twice and the answer is silently wrong (measured: 4 of 8 lanes came out 2 instead of 1). The *epilogue*, the part after `vfin` that runs once, may read and write the same register or location (the matrix micro-kernel does, by design), so the rule must not cover it. With resume the strip is not repeated, but a restart across a context switch still repeats it, so the rule stays for the main loop.

**A block with `vfin` or `vfmab` but no `vclr`.** Today it is wrongly treated as a block with hidden state. It is an ordinary block that can resume by its pointers. To be fixed (the owner: "fix hidden issue").

**A sequential token for each guest.** The resume design marks a suspended block with a one-use token, a counter run through a scrambler with a secret key. If one counter served all guests, a guest could learn how many times other guests were suspended. The owner's idea is right and cheap: the key is per guest, loaded at the entry into the guest, so tokens of different guests are unrelated and the count is invisible. The counter itself stays one per core.

**Interrupts inside a block.** Today the simulators run a whole vector block before looking at interrupts, so a long block delays an interrupt by its whole length (a 1 MiB int8 dot product: 1,048,580 model cycles). A real core must take an interrupt at a strip boundary, which is every few cycles, and the resume design depends on that. So yes, there should be: the simulators get a poll between strips and an option to inject an interrupt after N strips, so that tests can interrupt a block.

**Arena against a directory of walked table pages (hole 1).** Both close the hole completely for the guest's stage-2 tables. The *directory* is hardware that remembers which pages were used as page tables and discards the affected translations when anything stores to one of them: it needs no rule for the hypervisor, covers the kernel's own tables too (it could replace most `TLBI`), and restricts nothing, but it costs 6,000 to 28,800 gates per core. The *arena* makes the hypervisor keep its stage-2 tables in one contiguous pool and the hardware refuse a walk that leaves the pool; a store into the pool, or a "tables changed" flag, discards the guest's translations at the next entry: about 1,300 gates, but it covers only stage 2 and limits the hypervisor's allocator, and stores from other cores were not counted. Measured gates are in `docs/encoding-work/closing-holes-by-construction.md`; the owner asked for both to be benchmarked, and the figures will be saved with the others.

**Hole 6: where is the hole if the kernel restores the user's registers?** If the kernel really restores every register to the user's value (or to the result), there is no hole. The hole is the registers the kernel used for its own work and did not overwrite on the way out: they still hold kernel pointers or fragments of secrets, and the user can read them after the return, which defeats address randomization and can leak keys. Careless or compiled kernel code leaves such values. `RTI #mask` keeps the registers named in the mask and clears the rest in hardware, so forgetting costs the kernel a visible, immediate failure (a cleared register) and not a quiet leak.

**The floating-point flags.** Floating-point operations set five sticky flags (IEEE 754): invalid operation, divide by zero, overflow, underflow, inexact. Sticky means they stay set until cleared. They help a program notice numerical trouble in a long calculation by checking once at the end instead of after every operation, which is faster. If they carried from one process to the next, one process would see the other's flags: a small information leak, and wrong error reports. They are cleared whenever the address-space number, the guest register or the page-table base is written (about 7 gates, no cycles), and the kernel restores the incoming process's flags afterwards, as it already does.

**Why are 46 instructions missing, and which?** The grammar defines them and the manual has entries, but the reference executor (shared by `sim64` and QEMU) does not implement them yet (`spec/facts/core.toml`, `exec = "H_UNIMPL"`). I found no recorded decision to leave them out: it is a to-do. *Three* are not missing at all: `syspg3`, `syspg4` and `syspg5` are reserved system words, unassigned on purpose. *The other 43:* 20 atomic read-modify-write words (`xadd`, `swap`, `xand`, `xor_`, `xxor`, `xmax`, `xmin`, `xmaxu`, `xminu`, `cas`, each with a `_db` form for the second set) and the two `ll`/`sc` (their operand layout is still an open item, J.7.3 and J.9.3, so the executor waited for it); 15 scalar cryptographic words (`aeses`, `aesesm`, `aesds`, `aesdsm`, `aesim`, `aesks1`, `aesks2`, `sha256sig0`, `sha256sig1`, `sha256sum0`, `sha256sum1`, `sha512sig0`, `sha512sig1`, `sha512sum0`, `sha512sum1`) and 3 block cryptographic words (`msha256`, `msha512`, `maesctr`); and 3 text and string words (`utf8dec`, `utf8enc`, `mval`). The executor was built in phases, starting with the encoding and the core integer, floating-point and system instructions, and these were left for later.

## Earlier rounds (2026-11-18 to 2026-11-19), in brief

**Which instructions leak the machine's state to a guest?** `MFCPUID` (no privilege check; now privileged), `MFPS` (shows the real mode and priority), `MTPS` and `SPL` in user mode (silently ignored); `SEV`, `ICINV` and `ICINVA` are harmless to data. See `docs/encoding-work/sensitive-instructions-audit.md`.

**Who needs virtualization, and what does it mean not to have it?** Cloud servers, laptops running another system, phones' protected VMs, embedded systems on one chip and test farms; without hardware support a hypervisor runs the guest kernel in user mode, traps every privileged instruction and keeps shadow page tables (manual 6.14, sources checked there).

**How much nested virtualization is needed, and what does it cost?** For developers' VMs inside cloud VMs, laptops that are themselves guests, and hypervisor developers. Software nesting needs no new gates and about 45 to 105 person-days; a hardware register page costs about 0.2 to 1.0% of the core; a hardware walk through two second stages about 5 to 10% (`docs/encoding-work/nested-virtualization-estimate.md`; the figures are estimates, the gate counts partly measured).

**What did the manual say of five-parcel instructions?** Only `MOVQL` (a 64-bit literal) is five parcels; the other leaves are one to three. The owner accepted it (errata 185). The first-parcel space: 98.6% assigned.

**Why `NAMEfam.py`, and the single table?** `NAMEfam.py` was a placeholder name, no such file; the facts files (`spec/facts/`) are the single table of what a grammar cannot hold.

**seL4 round:** the core number and count (`MFCPUID`, a register as in Arm's `MPIDR_EL1` and RISC-V's `mhartid`, or a per-core register page as x86's local APIC; page zero of the virtual space stays unmapped so a null pointer faults); invalidate by address-space number (a process's entries can be dropped without flushing everything; seL4 frees and reuses address spaces); why the hypervisor level needs its own translation (seL4's hypervisor configuration runs its kernel there); why a separate kernel root register (no kernel entries copied into every process table); CompCert (a formally verified C compiler in Coq, for ARM, PowerPC, RISC-V and x86, not free software: a non-commercial release for evaluation and research; a pdp64 backend would need a Coq model of the instruction set and proofs per pass); the checks (a proof makes them dead code in the verified kernel).

**Vector hidden state:** resume in place keeps a block within about 2% of an uninterrupted run where restart costs 2 to 25 times with faults and never finishes under fast ticks; it adds about 7,500 gates (2.7% of the vector unit); `docs/encoding-work/vector-resume-design.md`.

**Did any of our seL4 support items make the seL4 proof smaller than for the other processors? (2026-11-25, in theory only: seL4 is not built for the pdp64.)** No item has been shown to make the proof *smaller*, and nothing is measured. What they do is shrink what the proof has to *assume or trust* about the hardware (the seL4 pages say the proofs leave the TLB, caches and DMA outside the model and assume about 340 lines of assembly correct; the virtual-memory argument is "the weakest assumption", made informally; sources in `docs/encoding-work/sel4-fit.md` 2.2). In theory the real savings would be: a TLB that cannot go stale by construction (a hardware directory of walked table pages, or the arena) turns the informal virtual-memory assumption into a hardware property that can be tested; `RTI #mask` makes "the kernel returns to the user with only the user's registers" true by construction instead of a duty of the assumed assembly; an IOMMU blocked at reset with no bypass makes "DMA is off" true in hardware (seL4 has no verified IOMMU on any architecture, so a small fixed design might make a future proof of it smaller than for VT-d or SMMU: a guess); every illegal encoding being defined removes a case from the binary-correctness proof; sequentially consistent memory would remove all weak-memory reasoning from a future multicore proof (seL4's multicore proof is not finished, and RISC-V and Arm are weakly ordered: this is the largest possible gain and is in the future). The page-table shape equals RISC-V's verified three-level one, which helps by reuse, not by size. The cost of writing a formal model of the pdp64's instruction set for the binary proof is an extra cost, not a saving. No source gives the share of seL4's proof that depends on the architecture (the TOCS paper: about 20 person-years in all, 11 specific to seL4; 17% of the proof for one API change), so how much an ISA design can save is unknown.
