# Translation, protection, exception entry and virtualization: best of breed, then amended

*For the owner to read. Nothing here changes the manual, the grammar, the tools, the executor, the QEMU model, a test or a record. Every proposal is a proposal; the ones that go against a recorded decision are put as questions (section 4.4 and the decisions of section 5). Files of the repository are named from its top; files of the QEMU v11.1.2 source are named from the top of that tree (`target/riscv/...`, `target/arm/...`, `target/i386/...`). A statement about another architecture is either **verified** (a short quotation with its source, read on 2026-11-19) or marked **unverified** and kept out of every conclusion. A statement about the pdp64 cites a manual statement number, an errata number or code as file:line. Effort and risk are labelled estimates; there is no measurement in this document.*

## 0. The principles applied, with their sources

The owner's method (errata 198, R521; ledger section 01, "Best of breed first, amended so that the hole closes by construction"): start from what the other architectures do, or something close to it; change it only where it contradicts our principles; make the smallest change of meaning or of instruction set so that the hole or problem is closed **by construction** (impossible to write, not detected afterwards), "just like the openbsd principles"; take a bold change when it is a big win overall. Decisions made before errata 198 are not reopened by it (errata 198, "Not done"), so every place where a proposal below disagrees with an earlier decision is a question.

The pdp64's own principles, which decide what "contradicts our principles" means:

* **P1, safety and security first, then opcode choice, encoding, speed and power, compiler target, pleasantness in assembler** (manual 1.6.1, errata 83, R323). Under safety: "errors that can never arise, then errors that are easy to detect, then errors that are cheap to recover from"; and "restart and recovery go together" (R323).
* **P2, all rules are soft** (1.6.2, R242): a rule yields when breaking it is worth more than it costs, with the cost written down.
* **P3, no strange side effects; do not multiply entities** (1.6.3): an instruction does what its name says and nothing else.
* **P4, efficient for in-order and out-of-order cores; nothing that is safe only because the core does not speculate** (1.6.4, R297).
* **P5, no new hardware unless it buys safety** (R491, errata 178: "safety and security first, no new hardware"). Virtualization is the owner's exception: in errata 181 the owner chose the hardware forms (a mode, a second root, a tag, virtual lines, a timer offset) against the assistant's recommendation of the staged or software forms, and "the owner's choice governs".
* **P6, precise exceptions and restartable instructions** (6.4, R455, errata 172, 186 decision 13): an abort changes nothing; hidden state is cleared at entry and at a world switch.
* **P7, determinism and no side channel from an unprivileged read**: no unprivileged instruction reads a clock, a counter or the core identity (6.14.2, errata 186 decision 14); the walker never writes a page table (6.8.1); the user half of the address space is never walked in user mode (6.9.1, errata 71).
* **P8, discoverable at run time** (errata 96: "as long as this info is discoverable easily at runtime"), so one kernel image adapts.
* **P9, the reader knows nothing after the 1970s** (1.2.1, errata 103): every term is defined where it is first used. This document follows it.
* **P10, minimal silicon and a small verified surface** (1.5; sel4-fit.md section 1: "fewer things to model"); the walker has a fixed meaning and a verifier can model it.
* **P11, no new encoding that moves a pattern, where avoidable** (errata 185, 196: `GENTER` took a reserved word "no leaf added, no pattern moved").

Where the owner has already decided a point (errata 60, 65, 71, 96, 97, 103, 178, 181, 186, 187, 190, 192, 195, 196), this document takes the decision as the input and says so.

### Words used (defined once, here)

* **Translation buffer (TLB)**: the processor's small cache of translations (6.8). **Stale translation**: a cached translation that no longer matches the page table.
* **ASID** (address-space number, 16 bits, 6.8): a tag in each buffer entry that names the process, so entries of several processes coexist.
* **Stage 1, stage 2, guest tag**: the guest's own page tables, the hypervisor's tables below them, and the number (16 bits, `GTAG`) in each buffer entry that names the guest (errata 195 decision 11; hypervisor-design.md 1.7).
* **Exit**: the guest stops and the hypervisor runs.
* **VMID, VPID**: the other architectures' names for the guest tag.

## 1. The baseline: how the other architectures solve each problem

*Sources.* **RISC-V**: the privileged specification, current published version v20260120, supervisor chapter and hypervisor chapter (https://docs.riscv.org/reference/isa/v20260120/priv/supervisor.html and `.../hypervisor.html`), read 2026-11-19; the machine chapter was read only in part. **Arm**: "Learn the architecture, AArch64 virtualization", document 102142_0100_03_en, issue 03 (Arm's own guide; the copy read was a mirror at https://www.scs.stanford.edu/~zyedidia/docs/arm/virtualization.pdf, read 2026-11-19), and the QEMU source. The Arm Architecture Reference Manual pages (developer.arm.com, support.arm.com) were fetched and returned no text (they are built by script), so every Arm instruction-level statement below rests on the guide or on QEMU and is labelled so. **x86**: Intel SDM volume 3A, system programming guide part 1, https://cdrdv2.intel.com/v1/dl/getContent/671190, read 2026-11-19 (it holds paging, PCID, SMEP/SMAP, protection keys; it does not hold the EPT and VMX chapters, only their table of contents), and QEMU `target/i386`. QEMU's TCG does not implement Intel VMX, so EPT behaviour is not verifiable locally (section 6).

### 1.1 Page tables, levels, entry bits

* **RISC-V.** Three to five levels. Quote: "When SXLEN=64, three paged virtual-memory schemes are defined: Sv39, Sv48, and Sv57" (supervisor, 11.1.1.11). The entry has V R W X U G A D in the low eight bits (verified: `target/riscv/cpu_bits.h`, `PTE_V` 0x001 to `PTE_D` 0x080, then two software bits `PTE_SOFT` 0x300), a page-based memory type in bits 62 to 61 (Svpbmt), and a NAPOT bit 63 (Svnapot). Quote: "Bits 62-61 are reserved for use by the Svpbmt extension" (11.1.4); Svnapot: "the PTE represents a translation that is part of a range of contiguous virtual-to-physical translations" (11.1.7). One `satp` register, 16-bit ASID (verified: `target/riscv/cpu_bits.h` `SATP64_ASID` 0x0FFFF00000000000), no second root.
* **Arm.** Two translation base registers selected by the top bits of the address (`TTBR0`, `TTBR1`): **unverified** from a primary source here; QEMU's `target/arm/ptw.c` implements both ranges (not read end to end). Arm's EL2 regime has "ASID support" only with VHE: quote (guide, section on VHE): "The EL0/1 virtual address space also supports Address Space Identifiers (ASID), but EL2 does not."
* **x86.** Four- and five-level paging; quote: "CR4.PCIDE enables process-context identifiers (PCIDs) for 4-level paging and 5-level paging." (SDM 3A, chapter 2). Five-level: the PML5 table (SDM 3A, 5-level paging text).

### 1.2 Accessed and dirty bits

* **RISC-V** offers both and lets the platform choose. Quote: "The Svadu extension adds support and CSR controls for hardware updating of PTE A/D bits." (11.1.10). The alternative, Svade, raises a page fault on a clear A or on a write with D clear (11.1.3.1: "when a virtual page is accessed and the A bit is clear, or is written and the D bit is clear"). QEMU has both, with an enable bit `MENVCFG_ADUE` (`target/riscv/cpu_bits.h`).
* **Arm** has hardware management as an option (FEAT_HAFDBS). Verified in QEMU: `target/arm/ptw.c` lines 2238 to 2262 fault with `ARMFault_AccessFlag` when AF is clear and `param.ha` is not set, and otherwise set AF in the descriptor.
* **x86** always sets them. Quote: "Whenever the processor uses a paging-structure entry as part of linear-address translation, it sets the accessed flag in that entry (if it is not already set)." (SDM 3A, 5.8).

### 1.3 Memory type

* **RISC-V**: Svpbmt gives page-based types that "override the PMA(s) for the associated memory pages" (11.1.8); the PMA, the physical memory attribute, is the platform's per-address attribute. A page table can therefore *loosen* what the physical address says. (That PMAs are fixed per physical region is **unverified** here: the machine chapter page read did not show the defining sentence.)
* **Arm**: the memory type is in the descriptor or via an attribute index. Across two stages: quote (guide, 4.3): "The MMU does this by selecting the stage that is more restrictive." The hypervisor may override: "HCR_EL2.FWB. This allows stage 2 to override the stage 1 attribute, instead of regular attribute combining."
* **x86**: the SDM contents list a section "31.3.7 EPT and Memory Typing" (title only; the text is in volume 3C, not read): the combining rule is **unverified**.

### 1.4 Supervisor access to user pages

* **x86**: quote: "If CR4.SMEP = 1, software operating in supervisor mode cannot fetch instructions from linear addresses that are accessible in user mode." and "cannot access data at linear addresses that are accessible in user mode. Software can override this protection by setting EFLAGS.AC." (SDM 3A, chapter 2: SMEP, SMAP). Protection keys: "CR4.PKE and CR4.PKS enable specification of access rights based on protection keys."
* **RISC-V**: quote (11.1.1.1.2): "When SUM=0, S-mode memory accesses to pages that are accessible by U-mode (U=1 in Figure 19) will fault." and "When MXR=1, loads from pages marked either readable or executable (R=1 or X=1) will succeed." That supervisor mode may never execute user pages: **unverified** from the page read (the passage was not in the part fetched).
* **Arm**: PAN, PXN and UAO exist (names only): **unverified** from a primary source. QEMU has the PAN translation regimes (`ARMMMUIdx_E10_1_PAN` and others in `target/arm/ptw.c`, lines 172 to 318, verified).

### 1.5 Invalidating the translation buffer

* **RISC-V**: `SFENCE.VMA` with a second register: quote "rs2 can specify the address space" (11.1.2.1). `HFENCE.VVMA` and `HFENCE.GVMA` exist for the guest: quotes "HFENCE.GVMA is valid only in HS-mode when mstatus.TVM=0, or in M-mode" and "HFENCE.VVMA is valid only in M-mode or HS-mode" (hypervisor, 14.1.3.2). Both take two register operands, address and tag (verified: `target/riscv/insn32.decode` lines 96, 97, 365, 366). Whether the invalidate reaches other harts: **unverified** here (I believe software must send an inter-processor interrupt; not read).
* **Arm**: a family by address, by ASID, by VMID and by IPA (the guest-physical address), with range forms and inner-shareable (broadcast) forms. Verified as names in QEMU `target/arm/tcg/tlb-insns.c`: `TLBI_VAE1IS`, `TLBI_ASIDE1IS`, `TLBI_VMALLS12E1IS`, `TLBI_IPAS2E1IS`, `TLBI_RVAE1IS`, `TLBI_RIPAS2E1IS`, and the non-broadcast forms. The operand format (ASID in the upper bits of the register): **unverified**. A change of the guest tag flushes in the model (`target/arm/helper.c:2847`, `vttbr_write`: "A change in VMID to the stage2 page table (Stage2) invalidates the combined stage 1&2 TLBs").
* **x86**: `INVLPG` by address, and by tag: quote "The INVPCID (Invalidate Process-Context Identifier) instruction invalidates (flushes) the TLB entries for the specified PCID." (SDM 3A, 2.8.6). `INVEPT` and `INVVPID` exist (verified as titles in the SDM contents, "INVEPT: Invalidate Translations Derived from EPT", "INVVPID: Invalidate Translations Based on VPID"; their semantics unread).

### 1.6 The hypervisor level

* **Arm**: a separate exception level with its own registers (`ELR_EL2`, `ESR_EL2`, `HPFAR_EL2`: verified in `target/arm/helper.c`). The guide on the guest-physical address of a fault: "For stage 2 faults, there is an additional register, HPFAR_EL2, which reports the IPA of the address that aborted." The tag: "The VMID is used to tag translation lookaside buffer (TLB) entries, to identify which VM each entry belongs to."; "Each VM has its own ASID namespace."; 8 or 16 bits (guide: "can either be 8 or 16 bits"). The hypervisor's own regime is not tagged: "Translations for the EL2 and EL3 translation regimes are not tagged with a VMID". With the E2H bit a host kernel runs at EL2: "E2H: Controls whether VHE is enabled." (VHE: the virtualization host extensions: the host operating system itself runs in the hypervisor level, with a second address range and ASIDs.) The core identity is virtualised: "VMPIDR_EL2. This is the value to return for EL1 reads of MPIDR_EL1." Trap bits for `WFI`/`WFE` in `HCR_EL2` (verified: `target/arm/tcg/op_helper.c` `check_wfx_trap`, per hypervisor-design.md section 8). The virtual timer: "The virtual count is the physical count minus an offset." (guide, 7); verified in `target/arm/helper.c:1441`, `cntvoff_el2`. Virtual interrupts: the hypervisor sets `HCR_EL2.VI`, or the interrupt controller forwards a physical interrupt as a virtual one (guide, 6: "The GIC will then assert the vIRQ or vFIQ signal").
* **RISC-V**: hypervisor-extended supervisor mode (HS) is the ordinary kernel with translation; a guest runs in VS mode (**virtualization on**, the V bit); the guest's registers are duplicated (`vsstatus`, `vsepc`, and others: `target/riscv/cpu.h`). Quotes: "The maximal value of VMIDLEN, termed VMIDMAX, is 7 for Sv32x4 or 14 for Sv39x4, Sv48x4, and Sv57x4." (14.1.2.10); "htval is written with either zero or the guest physical address that faulted, shifted right by 2 bits." (14.1.2.8); "CSR mtinst or htinst may also be written with information about the faulting instruction" (14.1.5.2); "hvip is an HSXLEN-bit read/write register that a hypervisor can write to indicate virtual interrupts" (14.1.2.3); "The hedeleg and hideleg CSRs allow these traps to be further delegated to a VS-mode guest" (14.1.2.2); `htimedelta` is a 64-bit delta added to `time` for a guest (14.1.2.7; verified: `target/riscv/tcg/csr.c:1681`, `delta = env->virt_enabled ? env->htimedelta : 0`); "A virtual supervisor timer interrupt becomes pending, as reflected in the VSTIP bit in the hip register" (`vstimecmp`, 14.1.2.19). The G-stage root is "x4", a root four times larger (Sv39x4), the same idea as our two-page root.
* **x86**: a separate "root" state; AMD's SVM is readable in QEMU: `helper_vmrun` reads the guest's `asid` from the control block in memory (`target/i386/tcg/system/svm_helper.c:156,267`), and `helper_vmmcall` is the hypercall instruction (line 472). Intel's VMX and EPT: titles only (above). EPT violation: a mirror of an older SDM (secondary source, https://xem.github.io/minix86/manual/intel-x86-and-64-manual-vol3/o_fe12b1e2a880e0ce-1125.html, read through a search result, not the current SDM) says the exit qualification "contains information about the access causing the EPT violation". Treat as **unverified**.

## 3. The holes found after the fact, and how the baseline closes each by construction

For each: what it is, the **cause in the design**, and how the baseline avoids it from the start. "Closed by 192" and the like mean already repaired after the fact: those are the ones the owner's principle exists to prevent, and they are listed so the cause is on record.

**H1. The stale-translation class (CVE-2026-99312, errata 178).**
*What:* a cached translation outlives the state that made it; the repository's own account is of the Linux x86 hypervisor not resetting the MMU context when emulating an INIT with paging disabled (errata 178; I did not look at any outside source for the CVE).
*Cause:* the architecture left open (J.6.8) what a write to the translation registers does to the cache, and a guest reset was not an architectural event.
*State now:* closed for a core (6.8.4, 6.8.5, tested in `tests/qemu/mmu-flush.S`) and for the tag by G-a to G-d. **Two residuals found by reading, not by running.** (a) The hardware guard of a guest reset is only "write `MMUCTL` as 0": that discards only if bit 0 *changes* (6.8.4(a)), and G-c discards only if the stage-2 root or the enable *changes* (hypervisor-design.md 1.7). A guest reset **in place** (same root, translation already off, stage-2 contents rewritten) changes neither, so correctness depends on the hypervisor remembering `TLBIA` (step 3 of 2.6). The tested case is the reverse (`hv-stage2`: forgetting is caught by the model). (b) `KTBR` is not in 6.8.4 at all (it does not exist yet: H10).
*Baseline:* none closes it by construction; Arm's model flushes on a VMID change and leaves a reuse to software (verified, `vttbr_write`). So this hole is one the baseline has too.

**H2. Sensitive instructions that were not trapped or masked: `MFCPUID`, `SPL`, and the guest reset.** (sensitive-instructions-audit.md sections 3, 4.)
*Causes:* `MFCPUID` returned the real core number to any program (the audit ran it in user mode); `SPL` and `MTPS` set the real interrupt mask, so a guest could raise its priority to 7 and stop the hypervisor's timer tick (audit decision 1); there is **no `RESET` instruction** in the executor or grammar (searched), so "reset" is the vector-0 event (audit row 26), which a guest cannot cause. *Closed* by errata 186 (decisions 1, 2) and 192 (`MFCPUID` privileged), and by the virtual core number `VCPUID` (`pdp64exec.c:671`).
*Baseline:* Arm virtualises the identity register by construction: "VMPIDR_EL2. This is the value to return for EL1 reads of MPIDR_EL1." (verified), and routes physical interrupts to EL2 by one bit (`HCR_EL2.IMO`, guide 6). So the two are closed from the start there; ours were closed after an audit.

**H3. `ICINV` needs `ISYNC` but `ISYNC` was privileged (audit decision 7).**
*Cause:* one instruction (`ISYNC`) was given two jobs, publishing privileged system-register writes and ordering instruction fetch after `ICINV`; its privilege was set for the first. *Closed* by errata 190, 192 (unprivileged; a user-mode `ISYNC` flushes nothing). *Baseline:* Arm `ISB` and RISC-V `FENCE.I` are unprivileged barriers (names only, unverified): the two jobs were never joined.

**H4. No invalidate by ASID, and the remote-core rule for `TLBI` is not stated (J.6.8; sel4-fit.md headline 2(d), R5).**
*Cause:* the operand of `TLBI` is only an address, and 6.8.3 says "for the current address space". With the broadcast of 6.8.3 the manual does not say *whose* current address space the other cores use: the issuing core's, or each core's own. I found no statement; the QEMU model has one core, so it cannot show it. If a receiving core used its own current `ASID`, a retained entry of the issuer's `ASID` in that core's buffer would survive (6.8.4(c) allows retention): a stale translation by construction of the wording. A kernel that wraps its 16-bit `ASID` counter can only issue `TLBIA`.
*Baseline:* all three name the tag in the operand or instruction: RISC-V `rs2` "can specify the address space" (verified), Arm `TLBI ASIDE1IS` (name verified in QEMU), x86 `INVPCID` (verified). So the operand carries the tag from the first design.

**H5. The hypervisor has no translation regime of its own (hypervisor-design.md 1.2 rule 1; sel4-fit.md 1(e), R8).**
*Cause:* the hypervisor runs on physical addresses to avoid a third table set (decision 2, errata 195). Consequences: no protection of the hypervisor from its own stray pointers, no way to run an ordinary kernel as the host (a "type 2" hypervisor, an operating system that also runs guests, as RISC-V HS-mode and Arm VHE allow), and no translated seL4 at hypervisor level (the configuration seL4 has verified on Arm only, sel4-fit.md 3).
*Baseline:* all three give the hypervisor level a regime: Arm EL2 stage 1 untagged by VMID (verified), VHE adds a second address range and ASIDs for a host kernel (verified, guide), RISC-V HS is the kernel (verified).

**H6. The memory type across the two stages, and errata 65 against errata 97.**
*Cause 1:* the design left the combining "to the hypervisor" (hypervisor-design.md 1.7; decision 12 open sub-point). The guest controls its stage-1 type; so a guest can request a *cached* access to a page that stage 2 maps onto a device, or the reverse. The model today checks the stage-2 leaf against the space bit, a rule the design never asked for (errata 196). *Cause 2:* errata 65 requires the leaf's type to agree with bit 39 of the physical address; errata 97 says "no physical-address bit selects device space" and "the physical address is free to be wider than 40 bits". The check, the two-page-root argument ("bit 39 is the space bit", hypervisor-design.md 1.7), `mmu.c:299`, `common/pdp64exec.h:92` and the test `tests/qemu/mmu-space.S` still use the bit. I found no record that errata 97 withdrew errata 65; it reads as a gap, not a decision.
*Baseline:* Arm combines "by selecting the stage that is more restrictive" and lets the hypervisor override with `FWB` (verified). RISC-V's PBMT overrides the PMA (verified), i.e. the page table can loosen the platform: the other design point, not the safer one.

**H7. The virtual timer is a device on a bus, not a register offset.**
*Cause:* no instruction reads a clock (6.14.2, errata 186(14)), so the counter is a device read by a load. An offset in hardware needs the device to know which core and which guest is asking; the chosen design (T2) is a core-local page, which in the executor and QEMU became a system-bus device at a provisional address, one core, and "not built, not testable with one core" for several (errata 196). With four or more cores (1.1.4) a read from a bus device has no core identity unless the bus carries one (not stated); moving a guest between cores moves `VTOFF` but the page address is the same on every core.
*Baseline:* the offset is applied inside the core on a register read (`CNTVOFF_EL2`, `htimedelta`; verified), so the question of which core never arises; Arm and RISC-V both have a register for the compare value too (`vstimecmp`, verified).

**H8. Guest-tag width (sel4-fit.md headline 2(e); 2.11.8).** *Was open; closed* by errata 195 decision 11 (16 bits, the width of the ASID and of the IOMMU tag). Baseline: Arm 8 or 16 bits (verified), RISC-V up to 14 bits (verified). No residual.

**H9. `TLBI` at `H` = 1 is by guest-virtual address; the hypervisor knows guest-physical addresses.**
*Cause:* rule G-d reuses the one-register `TLBI` for the guest tag, with the same meaning (a virtual page of the guest's ASID). The hypervisor changing one stage-2 entry (dirty logging, a page moved) knows the guest-physical page only, so it must use `TLBIA` and lose every entry of the guest on each edit. The design noted this ("a finer invalidate by guest-physical page is an optimisation for a later version", hypervisor-design.md 1.7). It is a cost, not a stale-translation risk.
*Baseline:* Arm `TLBI IPAS2E1IS` and RISC-V `HFENCE.GVMA` take a guest-physical address (names verified in QEMU).

**H10. The split address space has holes where it is not built.** `KTBR` has no register number (J.6.4), is not in the rules of 6.8.4, has no trap-control bit in `HTRAP` (hypervisor-design.md 1.5 lists `PTBR`, `MMUCTL`, `VBR`, not `KTBR`), and the QEMU walker walks the upper half from `PTBR` (`mmu.c:236` to `:362`: one root, canonical check on bits 63 to 39). So the property 6.9.1 states ("in user mode the upper half is never walked") is not implemented, and the model cannot test it. *Cause:* the decision (errata 71) predates the registers. *Baseline:* Arm's two roots are in the first architecture (unverified from a primary source).

**H11. Level count is not discoverable and not selectable.** Errata 96 requires discoverability; 6.6.1 says it is "readable" and J.6.1 is open; code has `MMU_LEVELS 3`. *Cause:* decided before the register. *Baseline:* Arm and x86 report widths in identification registers (unverified here); RISC-V by writing the mode field and reading it back (unverified here).

**H12. The direct-mapping windows bypass translation, so they bypass stage 2.** *Cause:* a window "takes effect over real physical memory" (hypervisor-design.md 1.5), so in a guest it must always exit (6.14.14); the format is not even decided (6.9.2). *Baseline:* none of the three has them.

**H13. `sim64` has no MMU (errata 178, 196).** Stage 1, stage 2, the tag and every invalidate are tested only in QEMU, and QEMU and `sim64` share one executor, so they are not independent witnesses (sel4-fit.md section 5).

**H14. Not holes, but listed because the baseline has them and we do not.** (i) No acknowledge or end-of-interrupt register for a virtual line (Arm's virtual interface has one: unverified in detail); a second device on the same level shares a line and a queue in software (hypervisor-design.md 1.8, "Against"). (ii) A virtual interrupt for a guest vCPU on another core needs an inter-processor interrupt and an exit (the per-core `VIRQ`); the same cost as the baseline's, not a flaw.

**What the owner has asked in reviews that lands here** (each is addressed above): the exposure to the stale-translation CVE (errata 178, H1); "why does it say that 3 level tlb isn't supported?" and "discoverable easily at runtime" (errata 96, H11); "if we are going to mmap petabytes, we need those bits" (errata 97, H6); the owner's choice of hardware forms for virtualization against the recommendation (errata 181); the requests for a hypervisor translation regime and guest-tag width come from the seL4 review (R8, H5, H8), not from the owner directly.

## 4. The proposals

Each amendment is the smallest change that closes its hole by construction. "Exists now" lists what would change. Effort and risk are my estimates.

### 4.1 Amendments

**A1. Put the tag in the invalidate operand: `TLBIAS` (by ASID), and state whose tag a broadcast carries (H4).**
*Change of meaning:* (i) 6.8.3 states that a broadcast `TLBI` or `TLBIA` carries the issuing core's guest tag and its current `ASID` and every core invalidates *that* (tag, `ASID`, page) plus the global entries; (ii) a new instruction `TLBIAS rN` invalidates every entry of the `ASID` in the low 16 bits of `rN`, in the issuer's guest tag, on every core, waited for by `TLBSYNC`.
*By construction:* a wrap of the `ASID` counter or a reuse of one number is one instruction, and a remote core cannot apply the invalidate to the wrong number.
*Cost:* **one instruction.** Silicon: each core's buffer needs a search by tag on a broadcast (the cost the owner's J.6.8 option 4 named: "each core must search the tag"), and the bus carries 16 more bits. Encoding: a one-register system leaf; the one-register system leaves are full (hypervisor-design.md 3.3), so it needs a new leaf in the free block of 926 patterns, a generator run and an optimiser run (an estimate: medium). Statement (i) alone costs no instruction and no silicon.
*Exists now that would change:* `common/pdp64exec.c:731` (`TLBI`) and a new case; `common/pdp64exec.h:85` (new `PDP64_TLB_ASID`); `qemu/target-pdp64/mmu.c:194` `pdp64_acache_flush`; the grammar (`spec/grammars.d/40-mn-system.hbnf`, `20-enc-forms.hbnf`) and all generated tables, `as64`, the LLVM tables; manual 6.8.3, 9 (the entry), J.6.8; tests: a new `tests/qemu` case in the style of `mmu-flush.S`, a `tests/sim` case that only checks decoding. Reverses no owner decision: J.6.8 left it open ("What stays open ... an invalidate by `ASID`"), and it overturns the *assistant's leaning* only (sel4-fit.md R5).

**A2. Give the hypervisor level a translation regime of its own (H5).**
*Change:* a system register `HPTBR` (one root, like `PTBR`) and an enable bit; at `H` = 1 with the enable clear the machine is exactly as today (untranslated); with it set the hypervisor's addresses are translated by one stage only (no stage 2) with tag 0 (the host), the page-table entry of 6.7, one extra buffer attribute "hypervisor regime" so a guest entry never answers a hypervisor access. A write to `HPTBR` follows 6.8.4(b) for tag 0. `HPTBR`'s number and enable are in the free block 148 and up.
*By construction:* the hypervisor can be protected from its own wild pointers by the same walker the kernel has; a kernel can later run at `H` = 1 (A2 leaves the path to the bold alternative B2 open).
*Cost:* no instruction. Silicon: one root register, one enable, one more translation-mode index in the walker and the buffer (a few gates and one attribute bit on each entry); no new walker. Estimated effort: medium (the executor's `H` = 1 path says "untranslated" in several places).
*Exists now:* `common/pdp64exec.c` (the `H` checks), `qemu/target-pdp64/mmu.c` and `cpu.c` (`pdp64_mmu_idx_mode`, new index), the register list in `spec/grammars.d/41-sysreg.hbnf` and `52-hypervisor-v1`, `common/pdp64exec.h` constants; tests `hv-regs`, `hv-stage2`, `hv-first` (a hypervisor with translation on), the reset table (hypervisor-design.md section 4); manual 6.14.3 and 6.14.8. It changes a rule of an accepted decision: errata 195 decision 2 ("untranslated in version 1") with a recorded "way out later" (hypervisor-design.md 1.2): put as question D2.

**A3. Combine the memory type across the two stages by "the more restrictive" (H6, cause 1).**
*Change:* the effective type of an access is the more restrictive of the stage-1 type and the stage-2 type, in the order device-strong, device-weak, uncached, cached (most to least restrictive). It is a total order on four values: one small combinational function, not an order of the two-bit code (cached 0, uncached 1, device-strong 2, device-weak 3, errata 65), so it is a four-by-four table, not a `max`.
*By construction:* a guest cannot make a device page cached, nor a hypervisor-protected page weaker than the hypervisor mapped it.
*Cost:* no instruction; a few gates; the model gains one function. The override control of Arm (`FWB`) is **not** proposed (it is a second mode; P3).
*Exists now:* `qemu/target-pdp64/mmu.c` (the result of `mmu_walk` and `s2_walk` carry no type today: "the memory type MT makes no difference to QEMU", `mmu.c` near line 335), `common/pdp64exec.h`; tests `hv-stage2` (a generated test) plus a new case; manual 6.14.4 and hypervisor-design.md 1.7. Reverses nothing: it fills the open sub-point of decision 12 (errata 195).

**A4. Reconcile errata 65 with errata 97 (H6, cause 2).** *Question, not an amendment:* what is the rule that kept a cached access off a device? Options: (a) keep errata 65 with a platform-defined *physical attribute map* (which physical ranges are device), the effective type being the most restrictive of stage 1, stage 2 and that map (the RISC-V PMA idea, verified only as a name; the map is the platform's existing address decode and needs no new storage in a model, but silicon needs a range check at the bus bridge: an estimate, small); (b) drop the check and accept that the page table alone decides (the RISC-V Svpbmt way, verified, which lets a page table loosen the platform: contradicts P1). Recommendation: (a).
*Exists now:* the check in `mmu.c:106,299`, `common/pdp64exec.h:92`, the system map `MAP_*` constants and `tests/qemu/mmu-space.S`; the manual 6.7 and the bus chapter 2.1.6, which errata 97 says is to be rewritten.

**A5. Write the guest reset as one write: a flush flag in `GTBR` (H1 residual a).**
*Change:* one more bit in `GTBR` (bit 1, `S2FL`): a write with it set discards every entry of the tag written, whether or not the root changed, and it reads as zero. A world switch writes `GTBR` without it and keeps its tagged entries; a guest reset writes root, tag and flag in one register write, the one-write idea the design already uses for root and tag (hypervisor-design.md 1.7).
*By construction:* the reset is atomic with respect to the cache; the hypervisor no longer needs a separate `TLBIA` that can be forgotten *for this operation* (it can still forget to set the flag: the by-construction part is that the correct sequence is one instruction).
*Cost:* no instruction, one bit decoded, no state; manual 6.14.4, 6.14.8, hypervisor-design.md 2.6 step 3. *Exists now:* `common/pdp64exec.c` (the `GTBR` write and `PDP64_TLB_GTBR`, `pdp64exec.h:88`), `mmu.c:194`; tests `hv-stage2` (the G-c cases), `hv-regs` (reserved bits mask today: `GTBR` "masks reserved bits silently", errata 196 differences).

**A6. `TLBI` at `H` = 1 invalidates by guest-physical page (H9).**
*Change:* at `H` = 1, `TLBI rN` removes every entry of the tag in `GTBR` whose translation used the guest-physical page in `rN`, in either stage; an implementation that keeps no guest-physical field may discard the whole tag (permitted, 6.8.4(d)). The guest-virtual form at `H` = 1 is dropped: the hypervisor that must remove one guest-virtual page uses `TLBIA`; a guest's own `TLBI` at `H` = 0 is unchanged.
*By construction:* the instruction the hypervisor uses after editing stage 2 names what it edited.
*Cost:* no new instruction. Silicon: none required (the whole-tag fallback is legal), an entry field if an implementation wants the fine form. A **mode-dependent meaning** of one mnemonic: a mild strangeness against P3; the alternative is a new mnemonic (a one-register leaf: as A1). Exists now: `pdp64exec.c:731`, `mmu.c:206`, `hv-stage2`, manual 6.14.4 and hypervisor-design.md 1.7 G-d. Reverses part of an accepted decision: errata 195 decision 13 (G-d): question D6.

**A7. Virtual time in system registers, as Arm and RISC-V do (H7).**
*Change:* privileged system registers `TIMECNT` (read: real counter minus `VTOFF` at `H` = 0, real at `H` = 1), `TIMECMP` (a compare value), and `TIMECTL` (enable), raising virtual line 6 at expiry. The timer *device* at level 6, vector 32 stays for the hypervisor's own use. No unprivileged clock is added (P7, 6.14.2): a user program still gets the time from its kernel. There is then no page to place and no "which core" question: the registers are the core's.
*By construction:* the offset is applied inside the core; there is nothing on the bus that must know who is asking.
*Cost:* no new instruction (system register numbers 13 and up are free; `MFSR`/`MTSR` exist); the same subtractor and comparator T2 already needed (hypervisor-design.md 1.9, "an estimate of the order of 200 bits of state"); the kernel reads time by `MFSR` instead of a load. Effort: small to medium. Exists now: `qemu/hw-pdp64/vtimer.c` (replaced or kept as the device), `qemu/hw-pdp64/virt.c:144`, `common/pdp64exec.c` (`VTOFF` hook), `spec/pdp64-system.hbnf` (`MAP_VTIMER`), tests `hv-vtimer`, `hv-timer`, `hv-first`; manual 6.14.5 and J.6.3. **Reverses** the T2 half of an accepted decision (errata 195 decision 17): question D7.

**A8. Report and select the level count; put `KTBR` in the rules (H10, H11).** One read-only system register `MMUINFO` (levels supported, virtual and physical address widths, `ASID` width, guest-tag width: the Arm/x86 idea of identification registers, unverified here), a level-select field in `MMUCTL`, a number for `KTBR` (sel4-fit.md decision 10 leans to 13; J.6.1 and J.6.4 interact because both want number 13: assign `MMUINFO` and `KTBR` together), `KTBR` added to 6.8.4(b) (a changed `KTBR` discards the global entries) and a `KTBR` bit in `HTRAP`. *By construction:* one kernel image adapts; the split is built, so "the upper half is never walked in user mode" is a fact the walker enforces. *Cost:* no instruction, two registers, one walker input; QEMU walker, `mmu.c`, constants, executor and tests (`mmu-flush.S` extension, a user-mode walk test); the manual 6.6.1, 6.8.4, 6.9.1. Reverses nothing; it carries out errata 71, 96. Effort: medium (four- and five-level walks are new code).

**A9. Define the direct-mapping window as a guest-physical range when the format is decided (H12).** When 6.9.2's format is decided, say a window maps **guest-physical** addresses and, with `S2EN` set, goes through stage 2; the always-exit of 6.14.14 then goes away and a guest may use its windows. *By construction:* a window cannot reach what stage 2 did not map. *Cost:* the format decision (open), then one stage-2 lookup on a window access; until then keep the exit. Exists now: `pdp64exec.c:678,734`, 6.14.14 and errata 186(8). It would reverse the exit half of errata 186(8): question D9. The bold alternative of dropping windows (RISC-V way) reverses errata 96's "good thing we already had dmw".

**A10. Keep, unchanged, because they are already best of breed** (so the proposals are not read as a wholesale rewrite): the entry layout (RISC-V's low bits, 2), software A and D with a never-writing walker (4: this is also what makes stage 2 simple: no guest-table write has to be translated and permitted at stage 2), the split roots (8), entry-clears-the-guard `UA` and `.U` (10), `HGPA`/`HINSN`/`HEXITR` (16), the single `GTBR` register (19), the 16-bit tag (19), `GENTER` and the hypercall as `TRAP` (24, 25).

### 4.2 Bold alternatives

**B1. Adopt the RISC-V hypervisor extension wholesale, with its register names and meanings.** HS mode is the kernel with translation and an `hgatp` root; guests run in VS mode with the V bit; duplicated guest registers (`vsstatus`, `vsepc`, and so on); `hedeleg`/`hideleg` for delegation, `hvip` for virtual interrupts, `htval`/`htinst`, `HFENCE.GVMA`/`HFENCE.VVMA`, `htimedelta` and `vstimecmp` for the timer (all verified in section 1.6).
*Win:* the host operating system and the hypervisor are one program (Option B of hypervisor-design.md 1.1), a translated hypervisor (H5), the invalidate by guest-physical address and tag (H9, H4), the timer in registers (H7), exit registers that match `htval`/`htinst` already, the guest's saved registers swapped by the bit so no `GEVA`/`GECAUSE`/`GKSP` aliases, mature software (the model in QEMU is verified to exist; its use by software is **unverified** here).
*Cost:* it reverses errata 181 (2), 195 decisions 1 to 6, 14 and 21; the executor, the QEMU target and 194 exits of `hv-exits` are rebuilt around a V bit; the thirteen system registers are duplicated in hardware; `GENTER` becomes `sret` with a bit; the audit of 186 is redone against a different state. Effort: large; risk: medium (a verified shape, a rewrite of tested code). Not recommended now.

**B2. Arm's split with VHE: the hypervisor level is where a host kernel runs.** The hypervisor level gets its own copies of the kernel's translation registers (`PTBR`, `KTBR`, `ASID`, `MMUCTL`, `VBR`) and the mapping of register names at `H` = 1 (the Arm `E2H` idea: guide: "E2H: Controls whether VHE is enabled"), so an unmodified pdp64 kernel runs at `H` = 1 and its guests at `H` = 0. A2 is the first step of this.
*Win:* a type-2 hypervisor (an OpenBSD-style in-kernel one: unverified here that `vmm(4)` is kernel-resident), the hypervisor regime (H5) with ASIDs, no world switch for the host's own work.
*Cost:* about six more registers duplicated and a name-redirect bit; changes the meaning of the 13 system registers at `H` = 1 (today `MFSR` at `H` = 1 reaches the **guest's** `EPC` and `EPSW`: hypervisor-design.md 1.2 rule 3), so a bigger reversal of an accepted design than A2. Effort: large; risk: medium. Recommended only as a later step, after A2, if an in-kernel hypervisor is wanted.

**B3. Adopt Arm's whole tagged-invalidate set.** By address, by ASID, by guest tag, by guest-physical address, with range forms and shareability: and an operand register that carries the tag (the Arm format is **unverified**). *Win:* every invalidate the three baselines have; one instruction for a large unmap (the range forms); a clean map from seL4's machine interface (invalidate by address and by ASID: sel4-fit.md section 2.2). *Cost:* several mnemonics and a two-register or descriptor operand, a larger buffer search, the free-block leaf and generator and optimiser runs; against P5 and P10 (minimal silicon, small surface); the owner's own J.6.8 leaning was to need only `TLBIA`. Not recommended: A1 and A6 take the two that closed holes; ranges are an optimisation to add if a measurement asks.

### 4.3 Recommendation

**Amend, not adopt wholesale, not bold.** Most of the design already *is* the best of breed (A10). Take A1 (statement part now, `TLBIAS` with the first kernel), A3, A5, A8 and the question A4 as the low-risk closers; take A2 and A6 and A7 as the three amendments that touch a recorded decision and are worth asking about; keep B2 as the planned later step; do not take B1 or B3.

## 5. Decisions for the owner, each with a recommendation

*Each can be answered **accept / change / not decided**. Nothing is recorded as decided until you answer.*

1. **Is the baseline-first method applied as stated in section 4.3: amend (A1 to A9), keep what is already best of breed (A10), and take neither B1 nor B3?** *Recommendation:* accept.
2. **Give the hypervisor level its own translation regime by one root register `HPTBR` and an enable bit (A2), replacing the "untranslated in version 1" rule of errata 195 decision 2; and keep the Arm VHE-style host kernel (B2) as a later step?** *Recommendation:* accept A2 now (off by default, so no existing test changes); B2 not decided.
3. **State in 6.8.3 that a broadcast `TLBI`/`TLBIA` carries the issuer's guest tag and `ASID` (A1(i)), a statement with no instruction or silicon cost?** *Recommendation:* accept.
4. **Add `TLBIAS rN`, invalidate by `ASID` (A1(ii)), at the first kernel's need, in a new leaf of the free block; this overturns the assistant's leaning in J.6.8 and answers sel4-fit.md R5?** *Recommendation:* accept (decide the encoding with the first kernel; the statement can be written now).
5. **Combine the memory type of the two stages as the more restrictive, by a four-by-four table (A3), and reject an override like Arm's `FWB`?** *Recommendation:* accept.
6. **Which rule replaces errata 65 now that errata 97 removed the space bit (A4): the most restrictive of stage 1, stage 2 and a platform physical-attribute map (a), or the page table alone (b)?** *Recommendation:* (a). Not decided is also fair until the bus chapter's address map is rewritten.
7. **Add the flush flag `S2FL` to `GTBR` so that a guest reset is one write (A5)?** *Recommendation:* accept.
8. **Change `TLBI` at `H` = 1 to invalidate by guest-physical page, with the whole-tag fallback, and drop its guest-virtual form at `H` = 1 (A6), altering rule G-d of errata 195 decision 13?** *Recommendation:* accept. The alternative, a separate mnemonic, costs a leaf, a generator run and an optimiser run.
9. **Put the virtual timer in system registers (A7), reversing the T2 half of errata 195 decision 17 and leaving the timer device for the hypervisor's own use?** *Recommendation:* accept: it removes the hole by taking away the bus device, at the same arithmetic cost, and keeps P7 (no unprivileged clock). If you refuse, say how the bus carries the core's identity to the timer page.
10. **Add the read-only register `MMUINFO` and a level-select field in `MMUCTL`; assign `KTBR` a number together with `MMUINFO`; add `KTBR` to 6.8.4(b) and a `KTBR` bit to `HTRAP` (A8)?** *Recommendation:* accept (numbers: decide J.6.1 and J.6.4 together, since both want the first free number).
11. **When the window format is decided, make a direct-mapping window a guest-physical range under stage 2 and drop the always-exit of 6.14.14 (A9)? Or drop windows altogether (the RISC-V way)?** *Recommendation:* the first; keep the exit until then.
12. **Should the model's missing pieces be done in this order for the principle's "by construction" claim to be testable: the `KTBR` walk (H10) first, then A2 and A3, and a second core for the `TLBI` remote-core rule (H4), since a one-core model cannot show it; and should `sim64` get a translation walk so that stage 1 has a second witness (H13, sel4-fit.md R3)?** *Recommendation:* accept the order; the `sim64` walk: not decided.
13. **Record the two checks I could not finish as open before any text goes into the manual: that the data register and size of every load and store lie in the first 32 bits kept in `HINSN`, and the remote-core behaviour of `TLBI` in a multi-core model?** *Recommendation:* accept.
