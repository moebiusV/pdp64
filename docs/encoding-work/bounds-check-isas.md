# Bounds-check and compare-and-trap instructions: what architectures have, why compilers do not emit them, what they could save, and what pdp64 could add

The author asked (2026-11-17): how do we find out which bounds-check instructions would be a net win; and for a detailed document of what LoongArch and the other architectures have in this department, why they are not emitted, how much they could theoretically save, and what could usefully be added to the pdp64. This extends `loongarch.md` (the census of checks in C and the price of each form) and J.9.13.

Scripts: `tools/arch-compare/adacheck.py` (new), `boundscan.py`, `bounds-price.py`; data: `docs/encoding-work/arch-data/ada/` and `arch-data/loongarch/`. Sources read: the QEMU, LLVM, GCC 14.2, binutils 2.43 and Linux trees on the author's machine (named below by their own relative paths), and the output of clang 21, rustc 1.93 and GNAT 14.3.

## 0. Summary

* **How to find out** (section 1): price every candidate form per check, weight it by a census of the checks in code that really has them, subtract the cost in opcode space, and ask whether a compiler will ever emit it. The census must come from languages that check every access; C with a sanitizer under-counts them tenfold.
* **What exists** (section 2): compare-and-trap on MIPS, SPARC, PowerPC and s390x; bounds checks on the 68000 (`CHK`, `CHK2`), 80186 (`BOUND`), VAX (`INDEX`) and Intel MPX (dead); fused check-and-access only on Loongson (MIPS) and LoongArch. RISC-V, ARM, AArch64, Alpha, OpenRISC and Xtensa have none.
* **Why they are not emitted** (section 3): LLVM and GCC can emit a compare-and-trap only through if-conversion of a branch to a bare trap (GCC `ctrap`, eight targets; LLVM, on s390x only, where it works: `clrthe %r2,%r3` straight into the load); the checked languages never reach it, because their failure path carries data (the index, the length, the file and line) that a bare trap does not.
* **How much they could save** (section 4): not much in executed instructions, a lot in code size. On Ada's own run-time library the checks add **21.3%** to the instructions (102,607 on 481,454); the failure paths alone are **55,736 instructions, 9.5% of the code, 3.0 for each of 18,556 check sites**, and more than half of the overhead. A compare-and-branch is already one instruction; a fused compare-and-trap saves the compare's branch on machines with only compare-and-branch and, with a table that finds the failing site, the whole cold block. In Rust (hbnf's generated parsers) the stubs are 3.1% of the code on x86-64 (1.1 instructions a check). On the C corpus the figures are an order of magnitude smaller (834 checks in 840 files).
* **What to add to the pdp64** (section 5; the author decided on 2026-11-17 a compare-and-trap with a table of check sites, a trap-if-zero, a two-bound check and the pcc path first; the table is explained in section 5.0 and the kernel's use of it in section 6): a one-sided unsigned compare-and-trap with a register or immediate bound and a **table of check sites** in the object file (so the trap needs no arguments), a **trap-if-zero** for null checks (the largest class in Ada: 45% of all checks), and a **two-bound** check for indexes with a lower bound other than zero; a compiler path (pcc) before any of them. Not recommended: fused check-and-access (LoongArch's), bounds in registers (MPX), a bounds check with the bounds in memory (`BOUND`, `CHK2`'s memory pair).

## 1. How to find out what is a net win

A form is a net win when what it saves, weighted by how often checks occur, exceeds what it costs, and when something will emit it. The procedure used here, and to be repeated when the corpus or the candidate list changes:

1. **List the forms** with their exact semantics (section 2): one-sided or two-sided; register or immediate bound; with or without a fused memory access; what the trap reports.
2. **Price each form per check**, in instructions, bytes and opcode patterns, from the grammar of the encoding (`spec/pdp64/tables.md`; `bounds-price.py`), for the check shapes that occur.
3. **Count the check shapes in code that has them** (the census): C compiled with the bounds sanitizer (`boundscan.py`: 834 sites, but only arrays of known size); **Ada**, which checks every index, range, null access, length and overflow (`adacheck.py`: the GNAT run-time library, 654 bodies, 18,556 check sites); **Rust** (`panic_bounds_check` on every slice index, overflow checks on in a checked build; `rustcheck.py`: six parsers generated by hbnf, 45,556 lines, on x86-64 and, from rustc's LLVM IR, on AArch64, RISC-V and LoongArch). Ada and Rust are now corpora of the project: `tools/arch-compare/corpus-ada.txt`, `corpus-rust.txt`, `mkrustcorpus.sh`.
4. **Weigh static and dynamic separately.** The failure path (cold) costs code size and no time; the compare and branch (hot) costs time and little size. A form that removes only cold code is a code-size win; one that removes a hot instruction is a speed win.
5. **Ask whether it will be emitted.** A form no compiler selects is worth nothing: LoongArch's bounds-check instructions are the example. The route must exist: an LLVM or GCC pattern, or an explicit built-in of pcc, with the failure data carried by a table.
6. **Subtract the cost**: opcode patterns of the 65,536 first parcels (the encoding optimiser is to be re-run, J.9.13), a new vector, the table, verification.
7. **Test the sensitivity**: the verdict must survive halving the check density and doubling it, because the corpus is not the future workload.
8. **What remains unmeasured** and would settle the close calls: dynamic counts of checked code on the simulator (needs a pcc or LLVM that compiles Ada or Rust for the pdp64); a Rust corpus; the Spectre-v1 interaction (a check is also an index-masking point, `array_index_nospec`).

## 3. Why they are not emitted

Verified in the source and in the output of the compilers named.

1. **The path from a bounds check to a compare-and-trap is narrow.** Clang's check emitter (`clang/lib/CodeGen/CGExpr.cpp`, `EmitTrapCheck`) writes a conditional branch to a shared cold block that calls `llvm.ubsantrap(handler id)` and `unreachable`. GCC's only creator of a conditional trap is the RTL if-conversion pass (`ifcvt.cc`, `find_cond_trap`: a branch over or to a block that holds only a trap), using the optab `ctrap`, which only eight targets define: **mips, nios2, ia64, m68k, nvptx, rs6000, s390, sparc**; not x86, ARM, AArch64, RISC-V or LoongArch.
2. **LLVM selects none of these from ordinary IR** except on **s390x**: there the unconditional `Trap` is turned into `CondTrap` by the early if-converter and fused with the compare by `SystemZElimCompare` into `CRT/CLRT/CIT/CLFIT`: for `br (icmp uge i, n), trap` the output is a single `clrthe %r2,%r3` followed by the load (tested with clang 21). PowerPC's `tw/td/twi/tdi`, SPARC's `Tcc`, MIPS's `T*`, LoongArch's `ASRT*` are defined with no pattern (intrinsics or assembler only); MIPS's `teq` appears only in the divide-by-zero check.
3. **The failure path carries data that a bare trap does not.** Rust calls `core::panicking::panic_bounds_check(index, len, &Location)`; Ada calls `__gnat_rcheck_CE_Index_Check(file, line)`; the output of rustc and gnat confirms both. A trap can report only that a check failed, unless the handler finds the site in a table. Clang's trap mode carries a handler id (x86 `ud1l` displacement, AArch64 `brk #imm`) and loses it on RISC-V, LoongArch, MIPS and PowerPC.
4. **Compare-and-branch is already one instruction and the cold block is shared.** On RISC-V and LoongArch the check is `bgeu` to a shared block; on AArch64 `cmp; b.hs`; on x86 `cmp; jae`. A compare-and-trap saves the branch and, if the trap can be shared, nothing else.
5. **Sanitizers want a recoverable diagnostic**, not a trap (`ubsan_minimal` and the recover modes); a trap cannot continue after the check.
6. **A trap needs a handler and, to say anything, a table of check sites**; JIT compilers own the signal handler and build such a table (HotSpot's trap-based range checks on PowerPC and implicit null checks, WebAssembly engines' guard pages: unverified, general knowledge). Ahead-of-time compilers of Rust and Ada have no such table.
7. **Missing immediates**: LoongArch has no compare-and-trap with an immediate and no `bgeu` against an immediate, so a constant bound (60% of the C checks) costs a load; s390x's `CIT/CLFIT` and PowerPC's `twi` have immediates, which is why they fuse.
8. **Speculation**: a trap-based check still speculates past the check until it retires; Spectre-v1 mitigation needs index masking whatever the check instruction is (`docs/hardware-vulnerabilities.md`, the bounds-check-bypass row; Linux's `include/linux/nospec.h` defines `array_index_nospec`, which clamps the index after the check, and `arch/x86/include/asm/barrier.h` does it branchlessly with `cmp; sbb`).
9. **History**: Intel MPX, the one attempt to give x86 bounds in registers, was removed because it was slow, bulky and unpopular (GCC 9 `WarnRemoved`); `BOUND` died with 64-bit mode.

## 4. How much they could save

**Executed instructions.** In every language measured the hot part of a check is the compare and the branch: two instructions on x86, **one on a machine with compare-and-branch** (RISC-V, LoongArch, and the pdp64: `CBHIS rs, rb|#imm, stub`, 4 bytes, or `CBEQ rs, #0, stub`, 2 bytes). A fused compare-and-trap executes one instruction as well. So a fused form saves **0 hot instructions on the pdp64** and one on x86-like machines; the exceptions are the forms that remove another instruction: a constant bound that must first be loaded (LoongArch: 483 `ori` for 508 checks), the `lea` before a biased compare (the lower bound is not zero), and the compare after a load of a pointer (`LAT`).

**Code size.** The cold blocks are where the bytes are.

* **Ada** (the GNAT run-time library, 654 bodies, x86-64, `-O2`; `adacheck.py`): the default checks add **102,607 instructions to 481,454 (21.3%)**; **18,556 check sites**, 3.18 for each 100 instructions. The cold blocks that call a check routine (not counting the blocks of explicit `raise` statements, which stay when the checks are suppressed) hold **55,736 instructions (9.5% of the code; 3.0 for each site)**, **54% of the whole overhead**; the remaining 46,871 are the compares, branches and biases. By kind: access (null) 44.6%, range 27.0%, index 16.6%, length 5.0%, invalid data 2.2%, elaboration 2.1%, finalization 0.8%, overflow 0.7%, discriminant 0.5%, divide by zero 0.2%. Of the 8,087 index and range checks, about 10% are biased (a lower bound other than zero, found by the `lea` or `sub` before the compare; the heuristic can miss some), 90% are not; 59% compare against a register, 11% against a constant.
* **Rust** (six parsers generated by hbnf from the project's grammars, 250,882 instructions on x86-64; rustc 1.93, `-C opt-level=3 -C overflow-checks=on`; `rustcheck.py`, data in `arch-data/rust/`): **7,275 check sites, 2.90 for each 100 instructions** on x86-64 (AArch64 2.24 and LoongArch 2.09, the IR of rustc compiled by clang). By kind on x86-64: **bounds 58%**, arithmetic overflow 27%, slice range 13%, unwrap 0.2%, other 0.9%. The cold blocks hold **7,671 instructions: 3.1% of the code, 1.1 for each site** (AArch64 0.4 and 0.8% of the code, LoongArch 1.5 and 3.0%): far fewer than Ada's 3.0 for each site, because LLVM merges the panic blocks of a function and keeps the arguments in registers. So the stubs that a table would remove are about **a third of Ada's share** in Rust. The RISC-V figures are not used: its short branches turn a check into a skip over a jump, which the scan does not follow (1,504 sites found against about 5,000 on the other targets). The code is machine-generated parsers (byte buffers, slices, counters), not hand-written Rust; a hand-written crate is still to be added.
* **C with the bounds sanitizer** (`loongarch.md`): 834 checks in 840 files, 0.28 for each 100 pdp64 instructions, an order of magnitude fewer than Ada (3.18), because only arrays of known size are checked; LoongArch's output costs 4.5 instructions a check (`bgeu`, a trap block, an `ori` for a constant bound, and the rest), and its -Os build has 508 trap instructions for the 834 sites counted in the -O2 IR (about 0.6 a site, the two levels mixed).

The savings that matter are **cold code**: a trap that finds its failing site in a table, so that the check needs no cold block that sets up arguments; the compare itself is not where the instructions are. Whether cold code is worth saving is a judgement: it costs nothing in time and, being cold, little in cache; it costs bytes in the file, in memory and in the instruction cache of the surrounding hot code when the cold block sits in line. 9.5% of the Ada run-time's code is what the table would remove.

### 4.1 Do they make safe code as fast as unsafe code, and do they reduce its size?

**Size: yes, by a part; speed: no, they narrow the gap and do not close it.** The instruction cannot make a check free: it still executes, once for each access that is checked, and only the compiler can remove a check it can prove. What the instructions remove is the check's extra instructions and its failure code. The measured floor, on the corpora of this record:

| | unchecked | checked, as compiled (x86-64) | with a one-instruction check and no stub | what remains |
|---|---:|---:|---:|---|
| Ada run-time library: instructions | 481,454 | 584,061 (+21.3%) | 500,010 (+3.9%) | one instruction for each of 18,556 checks |
| of which in the code that runs (compare, branch, bias) | | 46,871 (+9.7%) | 18,556 (+3.9%) | the stubs (55,736, 9.5% of the code) are gone |
| Rust, generated parsers | not measurable (bounds checks cannot be switched off) | 250,882 instructions, 7,275 checks | about +2.9% | one instruction for each check (2.90 for each 100 instructions) |
| C with the sanitizer | 296,059 (pdp64) | +834 checks | +0.28% | |

* **Code size.** The stubs are what goes: 9.5% of the code in Ada, 3.1% in Rust, 0.17% in the sanitized C. The checked Ada code goes from +21.3% over the unchecked to about +3.9%. That needs the table (section 5.0); without it the stub stays.
* **Speed.** In the code that runs, a check costs the compare and the branch: two instructions on x86 and one on the pdp64 (`CBHIS`). A compare-and-trap executes one instruction as well, so on the pdp64 **the hot cost does not change** (about 18,556 instructions for the Ada library, 3.9% over unchecked, either way); on x86-like machines it falls from about 2.5 to 1 a check. Each check still takes an issue slot and a compare, and the value it tests must be ready before the access it guards can be committed: the floor is about 3% more instructions executed for code with 2 to 3 checks in each 100 instructions, and whatever the dependency costs in time, which was not measured.
* **What closes the rest of the gap is not an instruction:** the compiler proving the check unnecessary (a loop whose index is bounded by the array's length needs one check before the loop, not one in it); and, on the pdp64, the **`vec` region prefix** (errata 139), whose region `[Rs, Re)` can be checked **once** against the array's bounds for the whole loop instead of once for each element. A fused check makes a check cheap; hoisting or vectorizing makes most of them vanish.
* **Not measured:** executed instructions and cycles of checked code on any pdp64 (there is no compiler for Ada or Rust for it); the figures above are static counts of the code, with the hot and cold parts told apart.

## 5. What to add to the pdp64

**Decided by the author (2026-11-17, errata 144 and 145): a compare-and-trap with a table of check sites (item 1, approved after section 5.0 explained it), a trap-if-zero (item 2), a two-bound check (item 3) and the pcc path first (item 4); details to be determined.** The rest of this section is the assistant's analysis.

### 5.0 What "a compare-and-trap with a table of check sites" means

**The problem it answers.** Today a bounds check on the pdp64 is `cbhis i, n, fail`: compare `i` with `n` and branch to `fail` if `i` is out of range (an unsigned compare-and-branch, one instruction). The branch goes to a little piece of code, a **stub**, that says *which* check failed and calls the panic routine: in Ada it loads the file name and the line and calls `__gnat_rcheck_CE_Index_Check`; in Rust it passes the index, the length and the source location to `panic_bounds_check`. That stub is about 3 instructions, and **every check has its own**, because each has a different line number. In Ada's run-time library the stubs are 9.5% of all the code, and they are never run unless a check fails.

**The idea.** Replace the pair "compare-and-branch plus its stub" by **one instruction that compares and, if the value is out of range, raises a trap (a processor exception) itself**: `chk i, n`. There is no stub and nothing to branch to; the failing path is the trap.

**The catch, and the table.** A trap by itself cannot say *which* check failed, and an error message that says "index check failed" with no file or line is little use. So the assembler writes a small record for each `chk` instruction into a separate section of the object file: *the address of this instruction, the kind of check (index, null, range), and the file and line*. That list of records is **the table of check sites**. The section is not loaded into memory when the program runs; it sits in the file. When a `chk` fails, the processor delivers the trap to the kernel or the runtime with the **address of the instruction that trapped**; the handler looks that address up in the table (a binary search, because the table is sorted by address), finds the file and line, reads the values of the registers that the instruction named (it can decode the instruction to learn which) to report "index 7 out of range 0..3", and raises the language's exception or panic. The table is consulted only when something has already gone wrong.

**Where this is already done.** This is how the Linux kernel's `BUG()` works: it executes an instruction that always traps (`ud2` on x86) and puts a record with the file and line in a table (`__bug_table`); the trap handler looks the faulting address up to print the "kernel BUG at file:line" message. It is also how C++ and Ada exceptions find their handlers: tables searched by address, not code that runs. Java's HotSpot does the same for null and range checks on PowerPC (unverified, general knowledge).

**What it costs and what it saves.**
* **Saves:** the stubs: about 3 instructions of every check in Ada, 0.6 in the sanitized C (which shares its stubs), and with them the branch target (a cold block that sits near hot code). On Ada's run-time library that is 55,736 instructions, 9.5% of the code. It saves **nothing in the time a program runs**: a check that passes executes one instruction either way.
* **Costs:** the table (8 to 12 bytes a check, 150 to 220 KB for the 18,556 checks of the Ada run-time, in the file but not in memory), the handler that searches it, an assembler and linker that build it, and a decision about what a trap reports when the registers have changed. And without the table the instruction cannot replace the stub, and saves nothing.
* **Not the same as the trap-if-zero and the two-bound check** that the author decided: those save an instruction in the check itself (the two-bound form saves the `lea` of a biased index; the trap-if-zero saves nothing in the instruction count and is the cheapest form of the null check). They still need to say which check failed, so the decision on the table is not independent of them: a trap-if-zero without a table is a plain trap that reports nothing, and with a branch to a stub (`cbeq r, #0, stub`) it already costs 2 bytes. The table decides whether the new instructions can drop the stub.

**The choice in front of the author:** (a) keep the stubs (compare-and-branch, as now) and add the decided instructions as one-instruction checks that branch to a stub, or (b) add the table and let the decided instructions trap directly. (b) buys the 9.5% of cold code on Ada-like programs at the price of the table, the handler and the tool support; on C-like programs it buys 0.17%.

In the order the data asks for them; every item stands or falls on the compiler path (section 1, step 5).

1. **A one-sided unsigned compare-and-trap, `CHK rs, rb | #imm`, with a table of check sites (decided, details to be determined; section 5.0 explains it).** It executes as many instructions as `CBHIS rs, rb|#imm, stub` and saves the stubs. To replace the argument-carrying cold block of Ada and Rust it must find the site in a table: the assembler writes one entry per `CHK` (its address, the kind, the file and line or an index into the compiler's string table) into a section that the linker keeps (`.chktab`); the trap handler looks the faulting address up (a binary search, as exception tables work). Without the table a trap can only say "a check failed" and the cold block stays. J.9.13's option 2, which errata 85 decided against, with its measured value: about 500 instructions of 296,059 on C (0.17%), up to 9.5% of the code on Ada-like code.
2. **A trap-if-zero (decided, details to be determined)**, `TRAPZ rs` (one parcel) or a `CHK` form against zero, for the null checks, the largest class in Ada (44.6%). `CBEQ rs, #0, stub` already does the check in 2 bytes; the form removes the stub as item 1 does.
3. **A two-bound `CHK2 rs, rlo, rhi` (decided, details to be determined)** for an index whose lower bound is not zero (Pascal, Ada: about 10% of Ada's index and range checks; 21% of the sanitized C checks, signed index plus offset): it saves the `lea`, one hot instruction at each biased site; 0 patterns in the three-register group (51 of 128 words used). Smaller than items 1 and 2; worth it if Ada, Pascal or Rust are targets.
4. **A compiler path before any of them (decided: first)**: pcc has no sanitizer and no checked-language front end; an explicit built-in (`__builtin_chk(index, length)`) or a post-register-allocation fusion pass as LLVM's SystemZ has (a branch to a trap block fused with the compare) is the cheapest route; LLVM needs patterns for the new instructions, which no backend but s390x has.
5. **Not recommended**: LoongArch's fused check-and-access (the census has no address-against-limit checks; no compiler or kernel uses it; 26 encodings); bounds in registers as MPX had them (a new register file, saved at every context switch, removed from every toolchain that had it); a check whose bounds are a pair in memory (`BOUND`, `CHK2` of the 68020: a load and a hot memory operand for what two immediates or registers do); the VAX `INDEX` (the indexed mode already folds the scale).
6. **Keep** `CBHIS` and `TRAPCC` as they are: they cover every case until the table exists, and a compiler can emit them today.

## 6. How the Linux kernel would use it

The author's question: the kernel already does something similar, so how does it use the new instructions? **It already uses exactly this mechanism, and a pdp64 port can use it with almost no new kernel code.**

**What Linux already has** (all read in the kernel tree on the author's machine):
* **A table of check sites.** `include/asm-generic/bug.h` defines `struct bug_entry`: the address of the trapping instruction (`bug_addr`), optionally a format string, the file and the line, and flags (`BUGFLAG_WARNING`: report and carry on; `BUGFLAG_ONCE`; a taint). Every architecture's `BUG()` puts one entry in the section `__bug_table` (`.pushsection __bug_table` in `arch/x86`, `arch/riscv`, `arch/loongarch` `asm/bug.h`; the generic form on arm64) next to an instruction that always traps. The trap handler calls `report_bug(address, regs)` (`lib/bug.c`), which finds the entry with `find_bug()` (a linear scan of `__bug_table`, then of each module's table: `module_bug_finalize` registers it at load), prints the file and line, and returns "a bug" or "a warning".
* **A compare-and-trap already, on PowerPC.** `arch/powerpc/include/asm/bug.h`: on ppc64 `BUG_ON(x)` is `tdnei x, 0` (trap if the register is not zero) with a `__bug_table` entry, and `WARN_ON(x)` the same with `BUGFLAG_WARNING`, so that the kernel resumes after the instruction. One instruction, no stub, no branch: the form the pdp64 has just approved. Everywhere else `BUG_ON(x)` is a compare, a branch and an always-trapping instruction (`ud2` on x86, `brk` on arm64, `ebreak` on RISC-V, `break` on LoongArch) with the table entry.
* **The kind of check carried in the trap.** For the compiler's checks (`CONFIG_UBSAN_TRAP`, `CONFIG_UBSAN_BOUNDS`) x86 uses `ud1` whose displacement holds the check kind (`arch/x86/kernel/traps.c`: `report_ubsan_failure(ud_imm)`) and arm64 uses `brk #0x55xx` (`UBSAN_BRK_IMM` in `brk-imm.h`, `ubsan_brk_handler` in `traps.c`); `lib/ubsan.c` turns the kind into the message, and `lib/test_ubsan.c` exists to test it.

**What a pdp64 port does:**
1. **`arch/pdp64/include/asm/bug.h`**, written like the PowerPC one: `BUG()` is an unconditional trap plus an entry; `BUG_ON(x)` is the compare-and-trap against zero (trap when not zero) plus an entry; `WARN_ON(x)` the same with `BUGFLAG_WARNING`. Both polarities of the compare-against-zero are needed, since `BUG_ON` traps on non-zero and a null check on zero: the details left to be determined include that.
2. **The assembler's table is `struct bug_entry` in the section `__bug_table`** (the assistant's proposal; the format is not decided): then the kernel's `report_bug()`, `find_bug()` and the module loader are the pdp64's handler and table, with no new kernel code, and the same section serves the compiler-emitted checks. For user programs (Ada, Rust) the same entries are read by the language runtime from its own ELF file.
3. **`arch/pdp64/kernel/traps.c`**: on the check trap, `report_bug(regs->pc, regs)`; if it says "warning", resume after the instruction. The pdp64's instructions are 2, 4 or 6 bytes, so the exception entry must give the length of the trapping instruction (or the handler must decode it from the prefix code): a detail for the trap frame that the exception chapter has to settle.
4. **The compiler**: the kernel is built by LLVM (errata 137) or GCC; with the trap-based UBSAN modes (`-fsanitize=bounds -fsanitize-trap=bounds`) clang emits a branch to a block that calls `llvm.ubsantrap(kind)`; the pdp64 back end needs the pass that SystemZ's has (a post-register-allocation fusion that turns `br (icmp), trap block` into one compare-and-trap) and writes the entry with the kind. This is the "pcc first" item, for LLVM. For pcc the path is started (errata 146): the built-ins `__builtin_chk`, `__builtin_chkz` and `__builtin_chk2` exist on the branch `chk-builtins` of the pcc clone and compile to one compare-and-branch on the path of a passing check (the two-bound form to `lea` and one compare-and-branch: the `lea` is what the instruction will save).
5. **The kind of check**: in the table (a field of the entry or the high bits of its flags) or in a field of the instruction as x86's `ud1` and arm64's `brk` do; the kernel's `report_ubsan_failure()` takes either. The table keeps the instruction short.
6. **What the kernel does not change**: `array_index_nospec` stays (it masks an index after a check against Spectre v1, a different job), `access_ok` stays (it returns an error to the caller and must not trap), the exception tables of `get_user` stay (they are for faults). `FORTIFY_SOURCE` and `CONFIG_UBSAN_BOUNDS` gain a one-instruction check.
7. **To test**: `sim64` and the pdp64 QEMU deliver the trap and the address; a kernel module with `BUG_ON`, `WARN_ON` and `lib/test_ubsan.c` exercises the path; the Ada and Rust corpora (`corpus-ada.txt`, `corpus-rust.txt`) are the test of the tool support (assembler, linker, the table's size).

**What this costs the kernel:** the lookup is a linear scan of the table in `lib/bug.c`: fine for the few hundred `BUG` sites of a kernel and too slow for the 18,556 checks of a program that checks every index; for those the linker sorts the table by address and the handler searches it by bisection (the kernel already does that for its exception tables, `sort_extable`). The table is in the file and in memory only as the kernel already has it for `BUG`.

## 7. What was not measured

* **Executed instructions** of checked code: no pdp64 compiler for Ada or Rust; static counts only. The dynamic saving of every form above is 0 or 1 instruction a check.
* **Rust**: generated parsers only (no hand-written crate); the other targets are LLVM's lowering of rustc's x86-64 IR (rustc here has only the x86-64 library); overflow checks were switched on, as in a checked build, though release builds leave them off; RISC-V's count is not usable.
* **Ada** is GCC's x86-64 output (2 instructions for a compare and branch); the counts of cold instructions carry over as an estimate of the pdp64's, where a stub is probably 2 instructions (a kind and a call).
* **The check-site table** was not built; its size (one entry of 8 to 12 bytes a site) is not charged in section 4: for 18,556 sites it would be about 150 to 220 KB against the 55,736 instructions saved (about 223 KB at 4 bytes), so a table that is not compressed would about equal the saving in file size; it lives in a section that is not loaded until a trap, so memory and cache are not affected.
* **Loongson MIPS and IA-64 semantics** are unverified (no manual here).
