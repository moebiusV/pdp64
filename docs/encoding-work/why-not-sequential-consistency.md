# Why almost nobody ships sequential consistency, what it costs, and what that means for the pdp64

I wrote this because the owner asked: "there is a reason sequential consistency hasn't been done before. find out what it is," and then added: "we can't be slow as a dog." I opened and read each paper and manual I cite (the list of what I did not open is at the end), and I marked every claim from memory as "from memory, not verified". Those claims are kept out of the conclusions.

## 1. The answer in plain words

**Terms first.** A **store buffer** is a small queue inside a core. When the core stores a word, the word waits in the queue and the core carries on; the queue pushes it out to the cache later. **Speculation** means guessing and running ahead: the core executes instructions before it knows it should, keeps a way to undo them, and undoes them if the guess was wrong. **Coherence** is the hardware rule that keeps every core's cached copies of a memory line from disagreeing; a core that wants to write a line must first make the others throw their copies away. A **litmus test** is a tiny two-core program with one interesting outcome, used to find out which orderings a machine allows. **Sequential consistency** (SC) means the result of any run is as if all the loads and stores of all the cores happened one at a time, in one order, and each core's own instructions appear in that order in their program order.

**The reason.** SC was not avoided out of ignorance. In the 1980s and early 1990s a core that obeyed SC literally had to finish each store, which on a machine with many caches means waiting until the other cores have been told, before it began the next load. That wait is long (tens to hundreds of cycles) and there was no cheap way to hide it. The store buffer hides it, but a store buffer makes a core's store visible to the others late, so loads can pass stores. Designers therefore wrote the weaker behaviour into the architecture (SPARC, x86, Alpha, POWER, Arm, RISC-V), and every vendor documents speed as the reason or leaves the reason unsaid. Once binaries and operating systems existed that depended on the weaker rules, nobody could go back.

**What it costs today, on the evidence.** From 1991 on, researchers showed that the speed can be got back by speculation: let loads run early, and undo them if another core touches the line before the load would have been legal. One shipping core did exactly this, the MIPS R10000 (1996), and it was architecturally and in practice sequentially consistent. On simulated cores of 1997 to 2009, the gap between SC (with that speculation and with prefetching of store ownership) and the relaxed models was **about 10% to 38% in run time with the simple techniques** (a typical figure: 10% to 18%), and **a few percent with heavier techniques** that cost a kilobyte or so of extra state or a chunk-commit mechanism. Those are simulations, mostly of server and scientific work on 4-wide cores with a 64-instruction window; I found no measurement on a modern core and I did not get one. On the machine I have (an x86 core that is TSO), the cost of forcing the store-to-load order with a full fence is anywhere from 1.4 ns to 12 ns per store-then-load pair against 0.4 ns without, and 138 ns against 6.5 ns when the store misses the cache. That is a data point from another machine, not a pdp64 number.

**What it means for the pdp64.** I recommend keeping SC, **with conditions**: an in-order first core pays nothing for stores that hit lines it already owns and a stall only for stores that miss; an out-of-order core uses the R10000 method (loads run early, replay on snoop) and adds store-ownership prefetch; and a measurement with a stated margin decides, with a named fallback (TSO as the architectural model, which keeps one binary on every implementation) if the margin cannot be held. Section 7 gives the numbers.

Two things stand out. First, the only reasons the vendors write down are speed and "implementation freedom": the right to build a weaker (faster or simpler) core later. Second, the architectures that are weak are written so that a stronger core is always allowed: SPARC requires TSO "or a more strongly ordered model, for example, Sequential Consistency", and PA-RISC's CPUs ran fully ordered. That is the compatibility mechanism the pdp64 needs, and it is old.

## 3. The technical reasons, by question

### 3.1 Store buffers and write latency

A core that writes memory must, for SC, make the write visible to all other cores before it lets a later load run. In a cache-coherent machine that means obtaining ownership of the line (asking every other cache to drop its copy and waiting for the answers). On a single bus that is a few tens of cycles; on a many-core or NUMA machine it is hundreds. Adve and Gharachorloo's tutorial (Western Research Laboratory report 95/7, Sept 1995) says SC "greatly restricts the use of many performance optimizations commonly used by uniprocessor hardware and compiler designers", and shows the exact case: with a write buffer that lets reads bypass writes, two cores that each store to their own variable and then read the other's can both read the old value (Figure 5(a) in that report). Hill (IEEE Computer, Aug 1998) puts it as: "SC, for example, makes it hard to use write buffers, because write buffers cause operations to be presented to the cache-coherence protocol out of program order."

I measured that outcome on this host's x86 core. The test is: core A stores 1 to X then loads Y; core B stores 1 to Y then loads X. SC forbids both loading 0. Without a fence, both loaded 0 in 35,063 of 2,000,000 runs; with a full fence (`mfence`) in 0 of 2,000,000. The store buffer is real and visible on the most common machine in the world.

### 3.2 Load speculation and replay; coalescing and forwarding

Gharachorloo, Gupta and Hennessy (ICPP 1991, "Two techniques to enhance the performance of memory consistency models") proposed two tricks that keep the model but hide the delay: a hardware **prefetch** of ownership for a delayed store (so the line is already ours when the store's turn comes), and **speculative loads** (run the later load now, and if the line it read is invalidated before the load would legally have run, undo it and the instructions after it). Their abstract says the pair "equalized" the models: the performance of different models "is equalized, thus reducing the impact of the consistency model on performance". The Adve and Gharachorloo tutorial notes that the rollback "is suitable for dynamically scheduled processors since much of the roll back machinery is already present to deal with branch mispredictions."

The R10000 does exactly that. Yeager's paper says the address queue compares each outside invalidation to its pending loads: "the queue creates a soft exception on the load instruction", which flushes the pipeline from that load and restarts; forward progress is guaranteed because "the oldest instruction graduates immediately after completion". Stores write the cache only when they graduate (retire in program order). Nothing visible to software is out of order.

**Coalescing and forwarding** are what a store buffer does that SC dislikes. Merging two stores to one line (the tutorial notes the Digital Alpha did this) can make a later store become visible together with an earlier one, or make two stores to different words appear in another order. Forwarding a buffered store to the same core's later load is harmless alone (every model allows it for the same address), but forwarding is also what makes the store-buffering outcome above possible if the load of a different address runs before the buffered store is visible. My reasoning, not a quoted result: an SC implementation may still forward from its own store buffer when the load's address matches an older buffered store, provided the buffered stores become visible in order and loads of other addresses do not pass them.

### 3.3 Non-blocking caches, coherence at many cores, NUMA

Gharachorloo and colleagues (ISCA 1990, the DASH project paper) introduced release consistency for "scalable shared-memory multiprocessors" where "memory accesses are cached, buffered, and pipelined to bridge the gap between the slow shared memory and the fast processors". There the cost was acute: the Gniady, Falsafi and Vijaykumar paper (ISCA, May 1999) says conventional SC "would be prohibitively slow especially in distributed shared memory (DSM) where remote memory accesses can take several times longer than local memory accesses." The same paper also says what limits speculation at scale: the speculative state has to be large enough to cover a remote miss, and every incoming invalidation must be checked against it (their section on SC++: "the queue may be too large to allow a fast associative search"). InvisiFence (Blundell, Martin, Wenisch; ISCA, June 2009) says the same from the other side: the store-miss latency "can be fully tolerated only by deep speculation, leading to high storage" for per-store schemes. So scalability does not break SC, but it makes the machinery grow with latency and core count.

### 3.4 The cost of enforcing store-to-load order

This is the one thing TSO and SC differ on. TSO lets a load pass an older store to a different address; SC does not. A core that wants SC without speculation must stall the load until older stores are visible. Section 5 gives the published numbers; section 6 gives my x86 numbers for the same stall.

### 3.5 Hardware complexity of speculative SC

Ceze, Tuck, Montesinos and Torrellas (BulkSC, ISCA 2007) summarise the earlier schemes: SC++ "is nearly as fast as RC", but the schemes "increase hardware complexity substantially because they require (i) associative lookups of sizable structures and/or (ii) tight coupling with key processor structures such as the load-store queue, ROB, register files, and map tables." Their opening line: "SC implementations are considered either too slow or — when they can match the performance of relaxed models — too difficult to implement." Arm's authors give the same kind of reason for dropping non-multicopy atomicity: complexity "of implementation, validation and reasoning". Verification is the cost nobody puts in a table: a speculative SC core must be proved to replay in every corner (a load that was forwarded, an invalidation that arrives between a store's retirement and its commit, forward progress under contention). The R10000 solves forward progress with one rule (the oldest instruction always completes), which is a model to copy.

### 3.6 The academic arguments

Hill (Aug 1998, "Multiprocessors should support simple memory-consistency models") changed sides from advocate of relaxed models: "Multiprocessor hardware should implement SC or, in some cases, models that just relax the ordering from writes to reads." His claim: "the future performance gap between the aggressively relaxed models and SC will be in the range of 20 percent or less" and that this does not "justify their complexity". Gniady and colleagues (ISCA 1999) went further: SC++ reaches RC speed in all six applications they studied, using a 512-entry history queue and a 64-entry table of speculatively accessed blocks. Their abstract: SC implementations "can perform as well as RC implementations if the hardware provides enough support for speculation".

I record the counter-arguments as I found them: the same papers say the result depends on rare rollbacks ("well-behaved applications incur infrequent rollbacks"), the evidence is simulated, the structures are not free, and no vendor adopted SC++, InvisiFence or BulkSC in a shipping product (my search found none; I did not check each vendor's roadmap).

## 4. The compiler side

Weak models do not only free the hardware. The Adve and Gharachorloo tutorial says SC's program-order requirement "directly restricts any uniprocessor compiler optimization that can result in reordering memory operations", naming "code motion, register allocation, and common sub-expression elimination", and software pipelining. A compiler can hold a shared variable in a register, move a load above an earlier store, or merge two loads, none of which changes a one-core program and all of which can change what another core sees.

The C and C++ answer (Boehm and Adve, PLDI 2008) is to promise SC only to programs with no data race, "we give sequentially consistent semantics to programs that do not contain data races", and to give atomic operations explicit ordering levels. That has two consequences for the pdp64:

- **The compiler is not slowed by SC hardware.** C and C++ already let the compiler reorder ordinary accesses; the language model is weaker than any hardware, SC included. So hardware SC does not take away optimisation that C programs enjoy, and the compiler need not insert anything for ordinary loads and stores.
- **The default atomic is already SC in the language.** C++ `seq_cst` atomics are the default. On x86 a `seq_cst` store needs a locked instruction or `mfence`; on Arm and RISC-V it needs a special store or a fence (from memory, not verified here; the annex entry on sequential consistency counted the instructions); on an SC machine it is an ordinary store.

What is lost: a program written in the C++ "relaxed" style gets no benefit from an SC machine (the compiler may still reorder it), and there is no way to ask for a cheaper ordering for speed. That is the "no relaxed load" cost in the annex.

How to read the table.

- **Caveats.** Four of the five sources are simulations of 1997 to 2009 on 4-wide cores with windows of 32 to 64 instructions, which are small by today's standard. The workloads differ: scientific loops have more overlap for a relaxed core to exploit than servers do (Hill says so: "Relaxed models are designed for the instruction-level parallelism of scientific workloads"). Memory latency measured in instruction slots has grown since, which widens the gap (Hill's own warning), and larger windows narrow it. I cannot say which wins today.
- **The range.** With only the old simple techniques (store-ownership prefetch and speculative loads, which are what the R10000 had), SC was 10% to 38% slower than release consistency, with a typical figure of 15% to 20% and server work at the low end. TSO sits between: on the scientific set the TSO-class model took 11% off SC's run time against 20% for release consistency (about half the gain), and in the 2009 mix TSO was **24% faster than SC** while RMO was 34% faster (TSO took about three quarters of the gain), which suggests TSO captures most of what relaxing buys. With the heavier schemes the gap falls to 2% (InvisiFence) or "comparable" (BulkSC, SC++).
- **My own x86 numbers show two things.** A full fence is expensive in its worst form (the 30-fold slowdown of `mfence` in the hot case, 21 times when stores miss), and a modern core makes the same ordering cheap when it speculates: `lock addl` is a full barrier and costs 3.4 times the unfenced loop in the hot case and 1.9 times when stores miss, because the core runs ahead and checks later. That fits the idea that the cost of ordering is mostly an implementation choice, but I cannot prove the lock instruction's mechanism from here, and a store buffer drained before every load is exactly what an in-order SC core would do.

## 7. What it means for the pdp64

The owner's principles are: safety first (ordering errors cannot arise), speed measured by run time, one binary on every implementation, measure rather than guess. I read them as: the program-visible model is SC; the **implementation** may be anything whose visible results are SC. The old veto says a core that is faster by being weaker must still show SC to software.

### 7.1 In-order first cores

An in-order core with a store buffer: **SC costs nothing when the store hits a line the core already owns (modified or exclusive state).** Such a store reaches the L1 cache in a cycle or two and is visible to every core at that moment, so a later load may go straight on. The store buffer is then only a pipeline stage, and the store-buffering outcome cannot happen. The cost appears **only when a store misses** (line not owned): the later load must wait until the store has obtained ownership and been written, unless the core speculates. That is my reasoning, not a published figure.

How large is it? I cannot say from evidence. My x86 test is a bound on the worst case: when every store misses and a full wait follows it, the time per store-then-load pair was 20 times that of the unfenced loop (6.5 ns against 135 ns). That is the cost of a **fully serialising** wait, and it only occurs on code that stores to cold lines and then loads, such as copy and clear loops over cold memory. Two mitigations are cheap, in order: (a) ownership prefetch when the store's address is computed, so the wait is shorter than a full miss; (b) let a younger load run when its line is held and delay the **commit** of its result until the older store completes, which is a small version of the R10000 replay, needed only if (a) leaves a measurable loss. I would build (a) and measure before adding (b).

### 7.2 Later out-of-order cores

Use the R10000 method: loads run early from the cache, the load queue is watched for outside invalidations (and for evictions of the line), and a hit flushes from that load and re-executes. This was shipped in 1996 on a four-wide core; the R10000 paper describes the whole mechanism in under a page. Add ownership prefetch of stores (the 1991 technique). On the evidence, this gets to within **about 10% to 20% of release consistency** (1998 and 1999 simulations); in the 2009 simulation the corresponding core (in-window speculative loads and store prefetch) was still **24% slower than TSO** in run-time speed terms (TSO was 24% faster), which is the largest TSO gap I found with these techniques. If the measured gap on pdp64 workloads is larger than the margin below, the next step is post-retirement speculation (InvisiFence), about one kilobyte of state and 2% of RMO in simulation. BulkSC and SC++ cost more and I would not start with them.

### 7.3 Many cores, devices, IOMMU and DMA

SC is a promise about the **cores' ordinary cacheable memory**. For many cores the promise holds as long as the coherence protocol makes each store visible to all other cores at one moment (the "multicopy atomic" property that Arm adopted in 2018 and POWER lacks); the pdp64 should require that of every interconnect. A machine with pairs of cores sharing a store buffer or a cache would need either a proof that it still looks SC or must not be built.

For devices and DMA agents I would **not** promise SC. The Alpha manual says the same: "The order of accesses by those agents is not completely specified in this document", with a few guarantees that hold everywhere. The pdp64 already orders device accesses with `FENCE`, and the IOMMU's table walks are decided to be coherent. That is the right split: SC for cores, a few stated completion rules for devices.

### 7.4 Options between full SC and TSO, and the fallback

- **Full SC (current decision).** Safe by construction. Pays the store-to-load wait where the store misses.
- **TSO as the architectural model** (x86's rule, RISC-V Ztso, SPARC V9's required model). A load may pass an older store to a *different* address; everything else is in order. Programs for SC work unchanged **except** those that rely on store-then-load order: Dekker and Peterson mutual exclusion, some lock-free structures that publish and then check, and anything like the store-buffering litmus test. They need one fence, or a read-modify-write (which on x86 already is a full barrier). This fallback **keeps one binary on every implementation**, because an SC core is also a TSO core: SPARC V9 says "TSO or a stronger model", and the RISC-V manual says a binary that needs Ztso should be marked, because a weaker core "can simply refuse to run" it. For the pdp64, TSO would be the *architecture* and cores could be SC inside; software written for TSO runs everywhere.
- **Anything weaker than TSO** I reject on the evidence: relaxing the rest (RMO against TSO) gave 8% on average in the 2009 mix, and what it costs in rules, in compilers and in validation is the reason Arm withdrew part of its freedom.

### 7.5 Recommendation: keep SC, with conditions

**Keep sequential consistency as the architecture**, with these conditions, in order:

1. **First, in-order cores:** SC is free when the stored line is owned; otherwise the load waits for ownership. Prefetch ownership at store issue. **Measure before anything else** (section 8).
2. **A stated margin.** I propose, as my own figure that the owner should correct: SC is kept if, on the pdp64's benchmark set, the same core run as TSO is **no more than 10% faster** on an in-order core, and **no more than 5% faster** on an out-of-order core after the R10000 method plus ownership prefetch. Why those numbers: 10% to 15% is what the best 1998 results left against release consistency with simple techniques (so against TSO it should be less), and 2% is what the 2009 post-retirement scheme left against RMO. They are choices of threshold, not findings.
3. **Out-of-order cores:** the R10000 method first; add post-retirement speculation only if the margin is missed.
4. **If the margin cannot be kept:** change the *architectural* model to TSO, not to anything weaker, and say so before any software depends on SC. This keeps one binary on every implementation. The cost to software is a handful of fenced idioms and a measured saving of at most the gap above. I would take that step only on a measurement, never on this report alone.

On the principles: SC costs a bounded, measured amount of speed (safety first, speed measured by run time); every implementation can be at least as strong (one binary); and the check is a measurement (measure, do not guess). The published evidence does not show that SC is "slow as a dog": the worst numbers I found, 24% to 38%, are for plain SC against the weakest models on cores that speculate only a little, and the best-case numbers are within 2% to 15%. The evidence does show that **speed is bought by the machinery of section 6, and I cannot yet say what it costs in gates on a pdp64 core**.

## 8. What measurement would decide it, and what the repository's tools can do now

1. **A trace analysis on the existing timing model.** The `sim64 --timing` model is trace-driven, in order, single core, with an optional data cache; it records each instruction's loads and stores (and says plainly that it has no store buffer and no memory dependences). A small addition to it, counting for each store that misses the data cache the cycles until the next load and charging the part of the miss latency not yet hidden, gives the **in-order SC stall** of every benchmark in the repository: an upper bound on what SC costs an in-order pdp64 core on its own data. That is one core with no coherence misses, so it undercounts sharing, but it measures the capacity-miss part on the actual instruction set. I did not write or run it; I was asked not to change the repository.
2. **Litmus tests on two cores** (already in the plan): store-buffering, message-passing, and the rest of the standard set, to show the cores obey SC. I ran the store-buffering test on this host to show it can be seen: both-zero 35,063 times in 2,000,000 without a fence on an x86 core.
3. **Many-core coherence cost** cannot be got from the repository's tools. It needs a many-core simulator with a coherence protocol. The papers above used RSIM, SESC, and Flexus; I would use one of those or similar (not checked).
4. **An Arm or RISC-V machine** for the same two micro-tests: I did not look for one and none was reached. The data above come from an x86 TSO machine only.

## 9. What I could not verify

- **Lamport 1979.** I opened only the second page of the PDF (the reference list); the text of the definition, the two requirements and the year come from memory, not verified. The definition I give in section 1 is my own wording of the textbook form.
- **SPARC V9 year (1994), Alpha first edition year (1992), the dates of the x86 manual's first TSO text:** from memory, not verified. I read the V9 manual's text and the fourth edition of the Alpha manual.
- **MIPS architecture-level SC.** I verified that the R10000 is SC by Yeager's paper. I did not check whether the MIPS *architecture* documents promise SC to software or whether other MIPS cores were SC.
- **PA-RISC.** I did not open the PA-RISC 2.0 architecture manual; the statement that the architecture permits reordering while the CPUs run ordered rests on one secondary article. The PA-8000 paper I opened (a trade-press article) said nothing on memory order.
- **IBM z and POWER.** I did not open IBM's manuals. The statements are from the Arm paper and the Linux Journal article only.
- **Ranganathan, Pai and Adve (SPAA 1997).** I did not open it; the numbers come from Hill's article, which I did open, and from the 1998 report by the same group, which I also opened.
- **Cain and Lipasti (ISCA 2004).** Not opened (error page).
- **Gharachorloo et al. 1990 (DASH, release consistency).** I read the abstract and introduction only; I did not extract its performance results.
- **Why Intel chose TSO.** The Intel manual states the rules and gives no reason. Sewell and colleagues describe the vendor text but not the decision. I have no verified account of why x86 is TSO beyond "store buffers".
- **Anything on a modern out-of-order core.** All the SC-versus-relaxed gap figures are from simulators of 1997 to 2009 with small windows. I found none from a shipping 2020s core, and no published area or power number for SC against TSO.
- **x86 numbers.** One AMD Zen 4 desktop core, one thread pinned, fence times in this single configuration. They show the shape of the cost; they do not predict a pdp64 number.
- **Whether any vendor ever shipped a post-retirement-speculation SC core:** I did not find one; I did not search each vendor.
