**Terms.** A **microkernel** is an operating-system kernel reduced to the few things that must be privileged: address spaces, threads, message passing and the delivery of interrupts; drivers and file systems run as ordinary programs. **seL4** is such a kernel, about ten thousand lines of C (S6, introduction: "on the order of 10, 000 lines of C code"), written to be **formally verified**: a machine-checked mathematical proof, in the theorem prover **Isabelle/HOL**, that the C code does what its specification says. A **capability** is an unforgeable token that names a kernel object and the rights to it; a program can act only through capabilities it holds. **Untyped memory** is raw memory that a program turns into kernel objects by the `Retype` call; every object has a power-of-two size (S6, 2.3 and 2.4.2). An **ASID** is an address-space identifier, a tag that lets the translation buffer (**TLB**, the cache of address translations) keep entries of several address spaces. An **IOMMU** is the page-table unit that translates the addresses a device uses for DMA (direct memory access). **EL2** is the ARM privilege level reserved for a hypervisor. **Refinement** is the proof method: show that each lower description (C code) can only behave in ways the higher one (the specification) allows. **Translation validation** is a proof that one compiled binary has the behaviour of its C source, checked after the fact for the particular compiler output, instead of trusting the compiler.

## 1. Headline findings

1. **What already fits best.** The pdp64 gives a verifier fewer things to model than any of the verified seL4 architectures: sequentially consistent memory (7.5.1, 9.2.8), precise exceptions with no hidden instruction state in the scalar core (9.2.6, 6.4.1), exception entry that writes only registers (6.3.1, 6.13.3), banked stack pointer and per-core pointer (6.2.4, 7.8), page tables whose walker never writes (6.8.1), a kernel half of the address space that user mode never walks (6.9.1), coherent caches with uncached DMA (7.6.1, 7.6.2), an IOMMU that is blocked at reset and has no bypass (2.11.1, 2.11.3), and all illegal encodings defined (9.1.5). The page-table shape (three levels of nine bits over 4 KB pages, 6.6.1) is the shape of the 64-bit RISC-V configuration that seL4 has verified (S6, 7.1.1.6; S10).
2. **The largest gaps** are not in the ISA's good ideas but in what is unwritten. (a) **No interrupt-controller programming model** (J.6.3): seL4 cannot be written without "which interrupt is pending", "mask this one" and "acknowledge" (S4 Figure 7 lists `getActiveIRQ` and `maskInterrupt`; S13 says the kernel needs an interrupt controller driver). (b) **The atomic instructions have no operand layout and no implementation in the executor** (J.7.3, J.9.3; 48 of 286 core mnemonics are `H_UNIMPL` in `spec/facts/core.toml`, including every atomic), so nothing about locks, and so nothing about seL4's multicore kernel, can be run or modelled. (c) **There is no formal semantics**: the grammar fixes only the encoding; the meaning is a C program whose memory, translation, interrupts and bus are supplied by a host (`common/pdp64exec.h:52-66`). seL4's binary proofs sit on a machine-readable, validated ISA model (S4 section 4.7; S5 chapter 3). (d) **TLB maintenance has no invalidate-by-ASID** and `TLBI` acts on the current address space only (6.8.3, J.6.8); seL4's machine interface invalidates by address and by ASID (S4 Figure 7: `invalidateMVA`, `invalidateHWASID`). (e) **The hypervisor mode (6.14) is designed to host guest kernels, not to be a kernel's own home**: it has no stated translation regime of its own and the guest-tag width is open (2.11.8).
3. **seL4 has no verified SMP, no verified IOMMU and no verified hypervisor configuration on RISC-V or x86-64** (S1, S2, S7). The pdp64 should therefore aim first at the verified shape that exists today: a single core, no hypervisor mode, no IOMMU, no floating point in the kernel, kernel in the privileged mode of the machine (S1, S10). Everything else the pdp64 offers (four cores, hypervisor mode, IOMMU) is outside what seL4's proofs cover on any architecture, so the pdp64 neither gains nor loses proof coverage by having it, but must not make the single-core, non-virtualised case harder.
4. **Top recommendations** (section 6): R1 write the interrupt-controller model (smallest useful form); R2 fix and implement the atomics; R3 make the executor total and put the translation walk in it; R4 build a formal ISA model for the kernel-relevant subset (Sail, generated decoder, hand-written semantics, tested against the executor); R5 add invalidate-by-ASID; R6 fix the system-call register convention so it matches seL4's message registers. None conflicts with a recorded decision; three touch an open item where the assistant's earlier leaning differs (said plainly in section 6).
5. **A statement in the manual contradicts another:** 9.2.6 says "the machine has no hidden instruction state"; 6.14.9 and errata 172, 186 decide hidden vector-block state (restarted from entry, naming cleared at entry and at `RTI`, `common/pdp64exec.c:355` and `:490`). A verifier needs the sentence restricted to the scalar core (decision D11).

## 2. Part 1: seL4

### 2.1 What seL4 is and what the proofs cover today

* **The proofs.** "The formal proofs for seL4 are hosted at https://github.com/seL4/l4v. They are written in the Isabelle/HOL theorem prover." (S1, first paragraph). The proof layers (S4 abstract; S5): functional correctness of the C code against an abstract specification, an IPC fast path proof, **binary correctness** by translation validation, access-control (integrity and availability) and information-flow (confidentiality) proofs, a worst-case-execution-time (WCET) analysis of the binary (S4 abstract: "a sound worst-case execution time analysis of the binary"), and an initialiser for user-level systems.
* **Which configurations (S1, read 2026-11-19).** The table below is S1's, condensed. "FC" is functional correctness of the C code.

| configuration | what S1 lists as verified |
|---|---|
| `ARM` (AArch32, ARMv7-A, kernel at EL1, no floating point, no hypervisor mode) | FC including the fast path; integrity and availability; confidentiality; **binary correctness**; correctness of the capDL user-level initialiser; "Proofs for all other `ARM_*` configurations are completed." |
| `ARM_HYP` (AArch32, kernel at EL2) | FC including the fast path only; S1: "The seL4 kernel runs as hypervisor in EL2" |
| `AARCH64` (ARMv8-A, kernel at EL2, floating point yes, hypervisor mode yes) | FC including the fast path; integrity and availability; confidentiality; "Further properties are under development." |
| `RISCV64` (no floating point, no hypervisor mode) | FC, **no fast path**; integrity and availability; confidentiality |
| `X64` (Intel, no VT-x mode) | FC, **no fast path** |

* **What is not covered.** S1: "none of our verified configurations take into account address translation for devices (System MMU or IOMMU)", and, in the same sentence, debug and profiling interfaces and boot. The verified configurations all set `KernelMaxNumNodes` to 1, that is **one core** (S10, all three files read), and the `AARCH64` file sets `KernelArmSMMU OFF` (S10). S2: "Multicore is presently supported on x64, ARMv7, ARMv8, and RISC-V. Verification of the multicore kernel is in progress for static multikernel configurations in the seL4 roadmap" (the text says this after a line break; the quotation is joined); S2 also says "The SMP kernel uses a big-lock approach" (one lock around the whole kernel). S7 (roadmap): multikernel verification "scheduled to complete Q3/28". S2 and S3 say the confidentiality proof does not cover timing channels: S2 "the confidentiality proof makes no guarantees about the absence of covert timing channels".
* **MCS** (the mixed-criticality extension: scheduling contexts, budgets, a tickless real-time scheduler; S6 "seL4 uses a preemptive, tickless scheduler"). S1: its proofs "are in progress". S8 (29 Jun 2026): "Functional correctness proof for MCS seL4 completed on RISC-V", to be ported to AArch64. S7: "C verification completed for RISC-V, to complete for AArch64 Q3/27". The two pages differ in date; S1 appears to lag S8.
* **Binary correctness: a discrepancy.** S1 lists binary correctness under `ARM` only. S2 says "On the ARM and RISCV64 platforms, there is a further proof that the binary code" is a correct translation of the C code, and S9 (the RISC-V International announcement) reports it for RISC-V ("RISC-V is the first 64-bit architecture" for which it was done). S10 sets `KernelBinaryVerificationBuild ON` in the `RISCV64` and `ARM` verified files and does not in the `AARCH64` file. I read these as: binary verification exists for ARM (32-bit) and RISC-V (64-bit); S1 does not list it for RISC-V. Not resolved further.
* **AArch64 status.** S8 (24 Aug 2026): "seL4 security proofs now complete on AArch64" (FC, integrity and now confidentiality). A 2021 comment under S9, signed "Gernot" (the blog's author), says that doing the translation-validation part on AArch64 "wouldn't be too bad".
* **Size of the thing.** S4: about 10,000 lines of C (S6 agrees); proofs 480,000 lines of Isabelle (S4 introduction, "480 000 lines of Isabelle proofs and specifications"); the fast-path proof alone is 5,913 lines (S4, the fast-path section: "The total size of the fastpath proof is 5913 lines").

### 2.2 The assumptions the proofs make about hardware

From S3 ("What the Proofs Assume"), S2, S4 sections 4.4 and 4.8:

* **Assembly is assumed correct.** S3: "about 340 lines of ARM assembly in our case"; "this concerns mainly entry to and exit from the kernel, as well as direct hardware accesses." S4 4.8: the proof does not cover "the register save/restore and the potential context switch on kernel exit".
* **Hardware is assumed to work as the model says**, and the model is small. S3: the proof "abstracts from cache consistency, cache colouring and TLB (translation lookaside buffer) management" and assumes they are implemented correctly in that assembly and "do not have any effect on the behaviour of the kernel". S4 4.4: "For the parts that we do not model, such as the TLB, we leave the corresponding type unspecified"; the machine interface is a list of operations (S4 Figure 7: `configureTimer`, `resetTimer`, `setCurrentPD`, `setHardwareASID`, `invalidateTLB`, `invalidateHWASID`, `invalidateMVA`, `cleanCacheMVA`, `cleanCacheRange`, `cleanCache`, `invalidateCacheRange`, `clearExMonitor`, `getIFSR`, `getDFSR`, `getFAR`, `getActiveIRQ`, `maskInterrupt`), specified with "maximal underspecification": in the extreme it may change its part of the machine state arbitrarily.
* **Boot code is assumed**: S3 "This leaves out about 1,200 lines of the code base".
* **Virtual memory is the weakest assumption.** S3: "you have to trust us that we got all necessary conditions and that we got them right." The reason (S4 section 4.4 text on in-kernel memory): "all kernel reads and writes are performed through a constant one-to-one virtual memory window which the kernel establishes in every address space", a consistency argument made "only informally". S4, the overview of kernel objects, also says address spaces have no kernel-defined structure "except for a protected region reserved for the seL4 kernel itself".
* **DMA is assumed off.** S2: "the proof assumes that DMA is off"; DMA devices may be used only if they are separately assured, because without an IOMMU they can overwrite kernel memory (S2, "What about DMA?").
* **Uniprocessor.** S4, the concurrency discussion in the kernel-design section: "we focus on uniprocessor support where the degree of interleaving of execution and nondeterminism can be controlled" (the PDF breaks the words "nondeter-minism" at a line end; the quotation is joined). The kernel is "event-based ... with a single kernel stack, and a mostly atomic application programming interface", and interrupt points are "implemented ... via polling, rather than temporary enabling of interrupts": the kernel runs with interrupts mostly off and polls for a pending interrupt at a few preemption points (S4, same section).
* **The ISA model for the binary proof** is separate and has its own gaps: S4 4.7: on ARM, "the Cambridge ARM semantics" in the HOL4 prover, which "has been extensively validated by comparing its behaviour to that of real hardware"; the machine-interface functions "make reference to co-processor instructions that are not part of the Cambridge ARM ISA model", so they, and the fast path that inlined them, were validated separately. S5 chapter 3: "we use an L3 formalisation of the RISC-V ISA, as well as the extensively tested L3 Arm ISA formalisation" (the quotation joins a line break). **System instructions are therefore outside the ISA model and inside the assumed assembly layer on both architectures.**

### 2.4 Porting, and what a new architecture costs

* **A platform port** (a new board of an existing architecture) is documented (S13): a boot loader, a device tree, drivers for timer, serial, interrupt controller and, if enabled, IOMMU, a platform header and a CMake file, and the test suite `seL4test` must pass. S7 lists "Automated Platform Port Verification", whose stated aim is "reducing the need for verification experts for new platform ports" (project to complete Q3/27; "Verification support for all Arm and RISC-V platforms ... now available").
* **A port to a new instruction-set architecture** is **not documented** in anything I read. The only costs stated are indirect: the original proof took about 20 person-years in total and "the total effort for the seL4-specific proof was 11 py" (S4 section 7.2.3); a single API change, the reply capabilities, "took about 1 py or 17% of the original" proof (S4, the passage on reply capabilities in the section on maintaining the proofs); for AArch64 functional correctness, the blog's author, in a comment signed "Gernot" in 2021, wrote that it was "a few person-years of (highly specialist) time" (S9 comment; a blog comment, not a plan); and the proofs are organised per architecture (`L4V_ARCH` in S12 takes `ARM`, `ARM_HYP`, `X64`, `RISCV64` or `AARCH64`; "ARM has the most complete set of proofs, the other architectures tend to support only a subset"). From this I **infer** (not a sourced statement) that a new ISA costs, for the proofs, the architecture-specific part of the specification and of the C-level proof, plus the binary-level ISA model and its validation; and that experts in the seL4 proofs, not the ISA owner, would do most of it.
* **RISC-V.** The RISC-V 64-bit port was verified at C level first and to binary later (S9 text: seL4 on RISC-V "verified to binary code"; the binary toolchain "converts both the C code as well as the binary into an intermediate language ... then uses SMT solvers to prove equivalence of the two programs, one short code sequence at a time"). S9: taking the tool chain "to a 64-bit architecture" needed overcoming "significant scalability challenges", because the state space grows with the word size. The pdp64 is 64-bit.

### 2.5 The ISA specification and the compiler for the verified binaries

* **ISA models used.** HOL4 (the "Cambridge") ARM model and an L3 RISC-V model (S4 4.7; S5). **L3** is a specification language for instruction sets (I did not read its documentation; known only through S5's use of the name). **Sail** is another: "a language for defining the instruction-set architecture (ISA) semantics of processors" (S14), which can "generate theorem-prover-definition versions of the ISA specification, in Coq, Isabelle, or HOL4" and has been used for Arm-A and RISC-V models ("In most cases these are full definitions", S14). **I found no source that seL4's proofs use Sail**; a search result suggested the RISC-V binary proof could use another model, and the whitepaper (S5) names L3. Whether a Sail model could be used by seL4's binary tool chain is therefore *unverified*.
* **What a new ISA must provide** (my reading of S4 4.7 and S5 chapter 3, labelled as inference): a model of every instruction that the compiler emits into the kernel binary, precise, deterministic (S5: "what the compiler does is deterministic enough to make the problem tractable" is about the compiler; the tool "will reject any behaviour in the binary that is not exhibited by the semantic representation of the C program", S4 4.7, so unspecified instruction behaviour would make the check fail or be unsound), and validated against real hardware or a reference simulator (S4: "extensively validated by comparing its behaviour to that of real hardware"). The privileged instructions need not be in that model: they are inside the assumed assembly layer (2.2).
* **Compiler.** The original proof used "GCC 4.5.1 using the -O1 optimisation level" (S4 4.7); GCC at -O2 needed changes to the tool. The verified configurations now use `-O2` (`KernelOptimisation "-O2"`, S10), `KernelOptimisationCloneFunctions OFF` (RISC-V and ARM files) and, for RISC-V, `KernelClzNoBuiltin ON` and `KernelCtzNoBuiltin ON` (S10: the kernel does not use the compiler's count-leading-zeros built-ins, which an ISA model without that instruction would otherwise have to cover). The l4v setup list names `gcc-10-riscv64-linux-gnu`, `gcc-aarch64-linux-gnu` and `gcc-arm-none-eabi` (S12 `docs/setup.md`); the exact compiler version of the RISC-V binary proof is *unverified*. S4: "porting" seL4 to CompCert made the code "cleaner, less GCC dependent, and more likely to run unchanged with other compilers"; and S2 says that on binary-verified architectures "the compiler does not have to be trusted", because the output is checked. So the verified artefact is the binary of a particular compiler run, and **any** compiler may be used if its output passes the translation validation, but the tool was tuned to GCC output (S4: compiler optimisations make "the stack heuristics" harder) and the kernel source relies on GCC extensions (S4: "we make assumptions about the compiler (GCC) that go beyond the standard").
* **For the pdp64:** the compilers that exist are pcc (the working compiler, `handoff.md` section 5) and an LLVM back end that "is to become the standard compiler for development" (`handoff.md` section 4, step 5, quoting errata 159 and R453). I did not test either on seL4's C source. Whether the seL4 source builds with pcc is *unverified*; with clang it is plausible (the seL4 source is portable C with GCC extensions), also *unverified*. The ABI (appendix D, D.1) gives `R0`-`R5` as argument registers, `R0`/`R1` as results, LP64, no red zone, stack aligned to 8 (open: J.D.1).

## 3. Part 2: what the pdp64 offers, from the local sources

### 3.1 The grammar as a specification

* **What it specifies.** `spec/grammars.d/` is the encoding: forms, leaves (prefix, sub-opcode, operand pieces), operand shapes, register tables, mnemonic numbers (`spec/README.md`, "The grammars of the new encodings"), the system-register numbers (`41-sysreg.hbnf`: 13 registers, 0 to 12), the status-word fields, vector numbers, page-table entry fields, memory types, the QEMU machine's memory map and timer (`50-system-v1.hbnf`). `tools/` reads it to generate the assembler, the decoder tables and checks. It is machine-readable and drives a decoder, so a **decoder** for an Isabelle, Sail or HOL model could be **generated** from it.
* **What it does not specify.** Anything about what an instruction *does*. The meaning is in `common/pdp64exec.c` (813 lines), `common/pdp64exec_vec.inc` (1,022 lines), `common/pdp64exec_enc.inc` (297 lines) and `spec/facts/core.toml` (1,115 lines; which handler runs each mnemonic, and which are not implemented) and `spec/facts/vec.toml` (847 lines).
* **Counts disagree.** The manual (9.1.2) says 207 forms and 268 leaves and (9.1.5) 3,278 illegal first parcels; errata 160 says the new grammar has 159 forms and 217 leaves and one illegal first parcel; the generated `spec/pdp64/tables.md` says 182 forms and 240 leaves. I did not resolve this (the generated file may count the vector family and the other two may not); it matters because a formal model must be generated from one stated version.

### 3.2 The executor as a precise semantics

I read the header and the parts of the executor named below; I did **not** audit all 2,300 lines, and said so in section 9.

* **It is usable as an executable oracle for the scalar integer and control instructions.** Cases an ISA model needs defined are defined: division by zero takes vector 12 (`pdp64exec.c:590`), the signed-division overflow case `INT64_MIN / -1` returns the dividend and `MOD` by -1 returns 0 (`:591-594`), shift counts of 64 or more are handled explicitly, with the carry flag defined for every count (`:421-427`); a NaN result is always the canonical quiet NaN (`:126-127`); every error path inside an instruction becomes the illegal-instruction vector (`die`, `:37`); a reserved system register or read-only write is illegal (`:539-542`); a reserved status-word mode is illegal (`:488`, `:557`). (Line numbers are those of the file as read at 12:40 on 2026-11-19; the file was being edited while this review was written, so lines near the end of the file may have moved.)
* **It is not yet a specification.** (1) The meaning of memory, translation, alignment, the bus, interrupt priority between instructions and the instruction fetch is *delegated to the host* through `struct pdp64_env` (`common/pdp64exec.h:52-66`: "ld and st move 1, 2, 4 or 8 bytes, little-endian, and check alignment and mapping themselves"). The translation walk lives only in the QEMU target, `qemu/target-pdp64/mmu.c` (131 lines; three levels only, `docs/implementation-status.md`, "Chapter 6, 6.6"); sim64 has no MMU and no translation buffer (errata 178). (2) **48 of the 286 core mnemonics are `H_UNIMPL`** (`spec/facts/core.toml`), among them `cas`, `casdb`, `ll`, `sc`, `swap`, `xadd` and every other atomic, the AES and SHA words, `mval`. The executor traps them as illegal (`pdp64exec.c:582`, "unimplemented system instruction", and the corresponding messages for the other groups). (3) The split root `KTBR` and the direct-mapping window are not implemented (`docs/implementation-status.md`, the entries on 6.9.1 and 6.9.2). `UA`, `STUA`, `CLUA` and the `.U` moves **are** now implemented in the shared executor and the QEMU walker, with a QEMU test (`docs/implementation-status.md`, entry "6.10.4 and 6.10.1 user guard (errata 43, 190, 192)"; the executor lines 352-353, 506-508); in sim64 the bit exists but the guard has no effect, because sim64 has no MMU. I first read the executor before this change and the matrix below is corrected. (4) `ICINV` is a no-op in the executor (`:580`), `MTDMW` stores only (`:579`), and a write to `PTBR`, `ASID` or `MTASID` flushes the whole TLB (`:545`, `:577`), stricter than the rule of 6.8.4, which is allowed. (5) Floating point uses the host's `double` arithmetic, `sqrt`, `fma` and the host's exception flags (`:126-135`, `:679-693`); a formal model needs bit-exact IEEE arithmetic instead. (6) Global state (`static` `C` and `E` pointers, `:17-18`) and the interleaving of exception entry with the vector-block restart (`:778-805`) are fine for a simulator, not for a pure function.
* **Where behaviour is implementation-defined or unspecified** (decided or open, with citations): the TLB size, organisation and which entries survive a register write (6.8.4 (c) and (d), "no program may depend on an entry surviving"); the `LL` reservation granule (7.4.1, "a size the implementation chooses and not smaller than 8 bytes", J.7.5); the order of accesses inside a block operation (7.5.8, "unordered with respect to one another", J.7.6); the strip of a vector block (implementation's choice, invisible by decision, errata 173; `pdp64exec_vec.inc:6-7`, `:21`); physical address width 40 to 64 bits and 3, 4 or 5 levels, not discoverable (J.6.1); imprecise machine checks for posted-write timeouts and uncorrectable errors (2.9.2, 6.4.3); `WFE` may return with no event (7.10.1); `MFCPUID` and the sizes of the hypervisor's registers (6.14.11, 6.14.3). Everything else I read is defined, including reserved `HINT` numbers (no-ops, 7.10.1; `pdp64exec.c:496`) and reserved page-table bits (a page fault, 6.7.1).

### 3.3 What is decided, implemented and open for the topics seL4 touches

The matrix of section 4 gives each topic with its citation; two overall facts first.

* **Almost nothing is built in hardware.** There is no silicon; there are the simulator sim64, the QEMU target, the executor and the assembler/linker; no pdp64 kernel exists (`docs/implementation-status.md`, entry on 6.1). Statements tagged *(D)* in the manual are decisions whose details may be pending ("Details to be determined"); a statement with no tag "describes the architecture as it is built and tested" (`docs/manual-src/README.md` lines 28 to 32). The appendix pages of the manual are assembled from fragments in `docs/design/src/appendix-parts/` (the appendix source files hold only a placeholder); I read the open items (J) of chapters 2, 5, 6, 7 and 9 and appendix D there, and the headings of the proposed and deferred fragments of chapters 2, 6, 7 and 9.
* **The hypervisor mode is a decision with almost no detail**: 6.14.1 to 6.14.14 are decided; 6.14.3 ends "Details to be determined: the registers, and the sequence that enters a guest and returns from it", 6.14.4 ends "Details to be determined". Errata 181: "no design of the hypervisor mode, the second stage, the virtual interrupt lines or the IOMMU exists" (the IOMMU has since been designed, errata 187 to 190; the other three have not, as far as 6.14 shows).

## 5. What works against verification (plainly)

* **Hidden state exists, though the manual says it does not.** 9.2.6: "the machine has no hidden instruction state". 6.14.9, errata 172, 173, 186: a vector block has a hidden copy of the naming of its accumulators, restarts from its entry after an interrupt, and "a world switch, and every exception entry, clear the naming of the vector accumulators and any `LL` reservation". The clear is implemented (`pdp64exec.c:355`, `:490`); no proof is claimed (errata 181: "the manual may not claim that nothing hidden is observable across a world switch until it exists"). A kernel that never executes `vec` is unaffected; the kernel's user context still has to include or clear it. *Cost to a proof:* the machine model needs these two variables or a rule that the kernel never reads them.
* **Implementation-defined parameters** (3.2) make the model nondeterministic in a bounded way: the TLB retention (benign: the model is a cache, S4's own approach leaves the TLB unspecified), the `LL` granule (matters only to code that depends on an `SC` succeeding), the strip (invisible by decision). Only the **block-operation order** (7.5.8, J.7.6) may be visible: the order and tearing that another observer sees while a `MCPY` or `MSET` runs is unspecified. If the compiler emits `MSET` for `seL4`'s memory-clearing loops (the kernel clears memory when retyping; I did not read that code) the proof needs a model of it. If the kernel only runs them on memory no one else can see, "unordered inside" is harmless; this must be shown, not assumed.
* **Imprecise events.** A posted-write time-out and an uncorrectable memory error are machine checks (2.9.2, 6.4.3). That is outside seL4's model too (S3: hardware "is assumed not to be tampered with, and working as the formal model predicts").
* **Reserved and undefined behaviour in the kernel subset.** I found none that is unspecified: every unused first parcel, sub-opcode and hot-register index is an illegal instruction (9.1.5, D.3.3), reserved PTE bits fault (6.7.1), reserved status-word mode is illegal (6.2.1), reserved `HINT` numbers are no-ops (7.10.1), reserved system registers are illegal (`41-sysreg.hbnf`). `ISYNC`/`HINT` pad bytes must be zero (the executor, `pdp64exec.c:495-511`, makes a nonzero pad illegal; the manual text of the pad was not checked).
* **The check instructions** (`CT<cc>`, `CHK2`, `ADDV`, `TRAPCC`, vector 16; `docs/encoding-work/check-instructions.md`, 6.13.8): when `pcc -xchecks` or the LLVM pass emits them they add an exception that the C source's semantics does not have. For translation validation this is an extra obligation: show that every check can never fire in the verified kernel (seL4's functional-correctness proof already implies it, S2: "freedom from buffer overflows, null pointer exceptions ..."). Build the verified kernel without them; they stay useful for the user-level programs.
* **No formal model** (3.2) and **no hardware**: nothing has been validated against silicon, so S4's "validated by comparing its behaviour to that of real hardware" has no pdp64 counterpart yet; the QEMU target and sim64 share one executor source, so they are not independent witnesses (`handoff.md` section 2; errata 178).
* **The manual is a moving target for a proof**: the form counts above disagree; 9.1.5 says 3,278 illegal first parcels and errata 160 says one. A formal model must be generated from the grammar, not from prose.

## 7. What already helps (keep it)

Each is a decided statement or an implemented fact; the "why it helps" is my reading, with the seL4 source that makes it matter.

1. **Sequential consistency** (7.5.1, 9.2.8, 7.13.1: "no weak ordering"). seL4's SMP verification is unfinished and S2 says it is "in progress" for multikernel only; a weak memory model would make it much harder (my inference). Keep the rule that the store buffer must not let a load pass an older store to another address (7.5.2).
2. **Registers-only exception entry, precise faults, no hidden scalar state** (6.3.1, 6.4.1, 9.2.6). The kernel entry cannot itself fault in a way the proof must model; the "event-based, single kernel stack" design of S4 fits.
3. **Banked `SP` and per-core `DP`** (6.2.4, 7.8): no stack switch in assembly, a per-core pointer without a trick.
4. **Software A/D and a read-only walker** (6.8.1): page tables change only by the kernel's own stores, so the proof's memory model does not need hardware writes to page tables.
5. **Kernel half walked only in kernel mode** (6.9.1): the kernel window is a hardware property.
6. **Tagged TLB with stated flush rules, broadcast and `TLBSYNC`** (6.8.3 to 6.8.5, 7.9): no shootdown protocol for the SMP kernel.
7. **Coherent caches, uncached DMA, memory types per page** (7.6, 6.7.4): the cache part of S3's assumption list shrinks to the instruction cache.
8. **IOMMU blocked at reset, no bypass, fail closed** (2.11.1, 2.11.3, 2.11.6): the DMA assumption of S2 is made true in hardware. seL4 itself has no verified IOMMU support (S1), so this is a head start.
9. **Total, simple decoder** (9.2.1, 9.1.5, 9.2.12, 9.2.4): length from the first parcel, no partial-register writes, no unlisted flag effects.
10. **Machine-readable grammar and facts, one executor shared by sim64 and QEMU** (`spec/`, `common/`): the right starting point for R3 and R4.
11. **Tickless main cores** (5.7.1) and a 64-bit timer shape (`50-system-v1.hbnf`): seL4's scheduler is tickless (S6).
12. **Page-table shape of the verified RISC-V configuration** (6.6.1; S6 7.1.1.6): the abstract specification's VSpace objects map directly.
13. **No floating-point or vector register file in the user context** (9.2.7): the verified RISC-V build turns floating point off (S10); here there is nothing to turn off.
14. **In-order, non-speculative first implementations** (7.5.4): fewer channels in the model and a feasible WCET analysis (S4 did the WCET for ARM1136; not repeated here).

## 8. Decisions for the owner, each with a recommendation

*Each can be answered **accept / change / not decided**. Nothing is recorded as decided until you answer.*

1. **Is seL4 a design target at all, and which configuration first?** *Recommendation:* yes as a reference target; first configuration: one core, kernel in the plain kernel mode, no hypervisor mode, no IOMMU, no floating point, no fast path (the shape of S1's `RISCV64` row). Later: multicore (big lock), then the hypervisor configuration. This costs the design nothing it has decided.
2. **Interrupt controller (R1; J.6.3).** *Recommendation:* decide the smallest controller now (mask, acknowledge, pending register, IPI register, per-core timer) and leave the remapping unit for later; write it in 5.9 and 7.10 and implement it in QEMU.
3. **Atomics (R2).** *Recommendation:* fix the operand layout and the `SC` result with the "three registers, fourth reserved zero" leaning of J.7.3, implement them, run the litmus tests before a second core exists.
4. **Invalidate by ASID (R5).** *Recommendation:* add `TLBIAS` (invalidate by ASID) and the "never stale" sentence; this **reverses the assistant's leaning in J.6.8** but not a decision.
5. **Formal model (R4).** *Recommendation:* build a Sail model of the kernel-relevant subset (decoder generated from the grammar) and test it against the executor; accept that the manual and grammar rule "nothing written by hand twice" bends for the semantics until the executor can be generated from the model.
6. **Executor to a reference (R3).** *Recommendation:* implement the missing instructions that the kernel uses and put the translation walk in the shared core; keep the host hooks for devices only.
7. **System-call convention (R6).** *Recommendation:* capability address `R0`, message info `R1`, message registers `R2` to `R5`, MCS registers `R6`, `R7`, syscall number in the `TRAP` number, IPC buffer in user `DP`.
8. **Hypervisor mode (R8).** *Recommendation:* add one statement: the hypervisor level has its own translation roots and tag; guest-tag width at least 16 bits. Do not design more until the non-hypervisor kernel runs.
9. **Block operations (R9).** *Recommendation:* add a sentence that for a single observer a block operation is a loop in ascending order with its progress in the registers; keep 7.5.8 unchanged for concurrent observers. Ask the compiler not to emit them in the verified kernel if they cannot be modelled.
10. **Kernel window and boot (R10).** *Recommendation:* give `KTBR` register number 13 and a one-page root (the J.6.4 leaning) and decide J.6.6 as "the kernel maps itself at its physical address first"; state that seL4 needs no direct-mapping window.
11. **Wording of 9.2.6 (R11).** *Recommendation:* "the scalar core has no hidden instruction state; the hidden state of a vector block is defined in 6.14.9".
12. **Toolchain (R7).** *Recommendation:* use the LLVM back end for the first seL4 build (clang accepts GCC extensions), pcc as a check; do not choose CompCert (it has no pdp64 target, and I did not research one).
13. **Keep `UA`/`.U`.** *Recommendation:* keep as decided (errata 190); seL4 does not use them.
14. **Keep the check instructions out of the verified kernel build.** *Recommendation:* build the verified kernel without `-xchecks`; keep the instructions for user code.
