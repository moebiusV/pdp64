# frag-timing: sim64 timing model (STEP 3 support) -- PARTIAL, stopped after validation and first sweeps

Worktree <worktree>, branch enc-tm, 3 commits on enc-prefix (2a7b55a model, eb6cb8e docs+tools/timing.py, then fused-instruction test). tools/check-all.sh green at the first two (the third only ran check-timing). Nothing pushed.

## Done
- `sim64 --timing=SPEC` (repeatable, up to 32 models per functional run; --timing-out, --timing-pc, --timing-help). common/timing.c/.h; the shared executor is untouched: tools/mk-exec-tm.py generates build/pdp64exec_tm.c (logs register/flag/DP accesses in order).
- Model: W-byte aligned fetch window, N-byte prefetch buffer with back pressure, optional I-cache, decode (iw, decw, ldec = length-decode latency, 0 for r20 and ldecp=1 for /16 /32 by default), dq queue, in-order scoreboard issue (iw, mem ports, 1 branch/cycle), latencies per class, D-cache optional, non-pipelined dividers, count-based block ops, bimodal/static/perfect predictors, BTB, RAS, indirect table, fused instructions as one slot with in-order latency walk. Idle cycles are charged to fetch-wait (start/seq/imiss/taken/misp/dec) or execute-wait (by producer class); identity cycles = active + fe + ex + occ checked in tests.
- Validation: tests/timing/check_timing.py, 128 exact hand-derived checks in 3 encodings (dependent chain, independent adds iw 1/2, load-use chain, mul chain, divider, taken/mispredicted loops, fetch-limited stream W=2..16, BTB loop, mov2 chain). Honest limit: it validates that the code implements the stated pipeline, not that the pipeline resembles hardware. docs/timing-model.md has the exact command lines, parameters and errata-style assumptions (in-order toy; OoO not modelled; no wrong path, no store forwarding, etc.).
- tools/timing.py: table over presets / parameter sets / sweeps for images. Use: `tools/timing.py -p scalar -p dual -s W=2,4,8,16 image.x...` (build with `CFLAGS="-O2 -w" tools/build-sim64.sh` for speed: ~35 ns/insn/model).
- Six programs built with current pcc-enc (abacdf17; ccom built into scratchpad/tm/pcc), variants base and ssa; scripts scratchpad/tm/{build6.py,runtm.py,agg.py}, results scratchpad/tm/res/VARIANT/*.tm.

## First results (base variant, ideal memory, iw=1, no BTB; ALL = sum of lz4 zlib lua bs_hash bs_sym bs_ec; LUA r20 IS TRUNCATED at 200M steps in these numbers -- rerun with -n 4e9 was queued, not finished, so ALL r20 is not comparable yet; use per-program rows for the others)
Cycles for ALL (r20 / 16 / 32): W=2: 1238M/1078M/1070M; W=4: 1077M/968M/892M; W=16: 1075M/964M/888M; wide: 1068M/936M/854M. fetch-wait share at W=8: r20 1.6%, /16 5.0%, /32 6.5% (the prefix encodings pay ldec=1 on every taken branch/refill); at W=2 r20 22.8%, /16 18.6%, /32 26.8%. Execute-wait is 25-31% (load-use dominates, e.g. bs_hash ex_load 20M of 86M cycles). Preliminary reading: at W>=4 the programs are execute-bound and the denser encodings win only through fewer instructions (/16 vs r20 about -10% cycles; /32 about -17% on the partial totals); at W=2 all are fetch-limited and the byte savings of /16 count; the length-decode latency costs /16 and /32 about 3-5% fetch-wait at W>=8. Crossover W and the dual-issue (iw=2) picture (cycles ~-13% vs iw=1, ex-wait share rises to 31-38%) need the corrected data before being quoted.
