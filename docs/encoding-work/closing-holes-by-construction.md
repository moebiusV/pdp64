# Closing three holes by construction: stale translations after a guest reset, kernel registers after a return, floating-point flags between processes

*For the owner to read. Nothing here changes the manual, the grammar, the tools, the executor, the QEMU model or a test. It answers the owner's questions on the three holes that the security corpus found and left to him (the corpus index lists them as the guest reset in place, the kernel's registers after a return, and the floating-point flags). The rule it follows: start from what other architectures do, change as little as possible so that the hole closes by construction, and judge by safety first, then speed, then fewer instructions, then a set a programmer can keep in their head.*

*How to read the labels.* Every figure is one of three kinds and says which. **Measured**: I ran a program or a synthesis tool (the method is in section 1). **Counted**: read from a manual sentence or from code (file and line given; line numbers are those of the repository today). **Estimate**: my judgement, with the reason. A statement about another architecture or operating system is either **verified** (one short quotation with its source, read on 2026-11-19) or marked **unverified** and kept out of the conclusions. Gate counts are NAND2 equivalents (a two-input NAND is 1, an inverter one half, a flip-flop 6, a flip-flop with a clear 7), the unit of the earlier gate records. The scalar core is 220,000 to 310,000 of them (the gate record's table), so 1,000 gates is about 0.4% of the core.

## 1. Method

* **Gates.** The repository's method (yosys 0.52, `synth -flatten`, `abc -g NAND`; the gate record's flow). I wrote a small Verilog model of each block, synthesised it, and subtracted the same model without the change. I reproduced the references first: the 32-entry translation buffer (no tag) came to 7,581 gates of logic and 2,048 flip-flops against the record's 7,589 and 2,048; adding a 16-bit tag with a valid bit and an invalidate by tag cost +8,799 against the nested-virtualization estimate's +8,828 (the guest tag, +0.3% apart). The register file came to 32,150 (record: 32 k) when written as a memory array. The synthesiser's result moves by about 4,500 gates between two ways of writing the same register file (an array or one register at a time), so **every comparison for the register file below uses the same way of writing both sides** (27,593 for the base). A difference under about 10 gates is noise. The models are scratch files and are not in the repository; the gate counts are reproducible from the descriptions in each section, and I can add the Verilog to `tools/gates` if the owner wants it.
* **Cycles for the hypervisor.** I ran the repository's four hypervisor programs (`hv-first`, `hv-stage2`, `hv-timer`, `hv-vtimer` in `tests/qemu`) on the QEMU model under a debugger and logged every entry into a guest (`GENTER`), every exit, every translation request of a guest, and every invalidate the model performed. The QEMU model keeps an architectural cache of translations keyed by the guest tag (`qemu/target-pdp64/mmu.c:150-212`) and empties QEMU's own buffer at every `GENTER` (`qemu/target-pdp64/op_helper.c:203-216`), so a log of the guest's translation requests is a log of first touches of each page after each entry. I replayed the log under each rule. **Limits:** it counts first touches only, so the capacity misses of a 32-entry buffer are not counted (a lower bound for every rule alike); the guest tag is not in the log, so an invalidate is treated as emptying every guest (more than the model does); the programs are tests, not workloads. A walk costs `nm + n + m` table reads (manual 6.14; 15 for three levels in each stage, 3 for one stage), and I charge 3 cycles a read, the load-use latency of the repository's timing model (`sim64 --timing-help`, `ld 3`), an **estimate**: a read that misses the cache costs more.
* **Cycles for the kernel.** The timing model of `sim64` refuses kernel mode (`sim64: --timing does not work with -K`), so I counted instructions with the simulator's trace (`sim64 -K -t`) on a loop of 1,000 system calls (user program, `TRAP`, a handler of 8 instructions, `RTI`) in six variants, and charge one cycle for a simple instruction and one cycle a register for a multiple push or pop (the timing model's count-based rule, `docs/timing-model.md`: **estimate**). The cost of the exception entry and of `RTI` themselves is not modelled anywhere in the repository and is not claimed.

## 2. Hole 1: a guest reset in place leaves old translations

### 2.1 The hole in plain words

A **translation buffer** (TLB) is a small cache of the results of page-table walks, so that the processor does not read the tables at every access. A guest has two sets of tables: its own (stage 1: guest-virtual to guest-physical) and the hypervisor's (stage 2: guest-physical to real). The buffer holds the combined result, tagged with a 16-bit **guest tag**. If the hypervisor rewrites a stage-2 entry, or reuses the same stage-2 root for a freshly reset guest, and enters the guest again, the guest can still read the **old** page through a cached entry. The hypervisor must remember to flush. The corpus probe is `tests/sec-open/qemu/sec-hv-reset-inplace.S`; the model discards a guest's entries only when the root or the enable bit of the guest register `GTBR` changes, on a write of `MMUCTL`, `PTBR` or `ASID`, or on `TLBI` and `TLBIA` (`common/pdp64exec.c:476-477`, `qemu/target-pdp64/mmu.c:192-212`, manual 6.8.4 and 6.8.5). This is the class of the stale-translation bug of the Linux KVM CVE the repository calls CVE-2026-99312 (errata, number 178).

### 2.2 What other architectures do (verified unless marked)

* **Software flushes after editing a table, everywhere.** RISC-V: "SFENCE.VMA is also used by higher privilege levels to synchronize page table writes and the address translation hardware." (RISC-V privileged specification, version 20260120, supervisor chapter, read 2026-11-19). The base design has no hardware coherence between a page-table store and the cache; the fence is software's job.
* **RISC-V adds fine-grained fences, and hardware updates of accessed and dirty bits, but not coherence.** Quote: "The Svadu extension adds support and CSR controls for hardware updating of PTE A/D bits." (same document and date). Svinval only "splits SFENCE.VMA ... into finer-grained invalidation and ordering operations" for speed.
* **AMD makes the flush a field of the entry into the guest.** The control block that `VMRUN` loads has a TLB control field with the values `TLB_CONTROL_DO_NOTHING` (0), `TLB_CONTROL_FLUSH_ALL_ASID` (1), `TLB_CONTROL_FLUSH_ASID` (3) and a local variant (7) (Linux `arch/x86/include/asm/svm.h` lines 183 to 186, read 2026-11-19), and Linux sets it before entering (`arch/x86/kvm/svm/svm.c` lines 4330, 4655, 4749). So the hardware can flush at the entry, but the hypervisor still chooses the value: forgetting is still possible. This is rule (a) below with a switch.
* **Arm numbers the guest and lets software bump a generation.** Linux's Arm KVM keeps a generation counter for the guest identifiers: "We're out of VMIDs, so increment the global generation count" (`arch/arm64/kvm/vmid.c` line 116, read 2026-11-19); the flush happens when the identifiers run out, not at a reset. This is rule (b) below, in software.
* **A hardware design that keeps the cache coherent with page-table stores exists in research, not (as far as I read) in a product.** The ISCA 2017 paper on HATRIC: "HATRIC extends translation structure entries with coherence tags (or co-tags) storing the system physical address where the translation entry resides." (abstract as returned by a search on arXiv 1701.07517, read 2026-11-19; I did not read the paper, so its numbers are not used). It reports an area of under 2% of a CPU. The idea is rule (c) below: tag each cached translation with where it came from and let the cache-coherence traffic kill it.
* **Unverified, and kept out of the conclusions:** that x86 gives no hardware coherence between page-table stores and its translation buffer (I did not read the Intel manual); Arm's rule of "break before make" and the features FEAT_BBML1 and FEAT_BBML2 (QEMU's list names them, `docs/system/arm/emulation.rst` lines 31 and 32; I did not read Arm's text); IBM's z/Architecture instruction `IPTE`, which I recall invalidates the translation as part of editing the entry (not read).

**The finding:** every product I could verify leaves it to software, and the hardware that helps (AMD) only offers a switch. None closes the hole by construction. So the pdp64 would be first, and the owner's question has a real answer only in rules (a) and (c).

### 2.3 The four rules, each in a few words

**(a) Discard the guest's entries at every entry into the guest (`GENTER`).**
*What it does:* hardware empties the entries of the guest tag about to run, always. *Hole it closes:* all of it, for every cause (a rewritten stage-2 entry, a reused root, a forgotten flush, stage-1 tables rewritten in guest memory): the hypervisor cannot forget because it is not asked. *What we lose:* every entry the guest had built, at every exit and entry, including an exit for a console character. *Gates:* measured −9 (noise; by hand one OR gate and one select that the base already has). *Cycles:* see 2.5.

**(b) A generation number in the guest tag, so that a reset makes a new tag value.**
*What it does:* the buffer's tag grows by 8 bits that name a generation; an entry of an old generation never matches. *Hole it closes:* only if something changes the generation. Hardware cannot see a reset (there is no such event), so the hypervisor has to write a new generation or a new tag at each reset: it still has to remember, only a different thing (the Arm KVM code does exactly this in software, and bumps only when the numbers run out). A counter in hardware that bumps at each `GENTER` is rule (a) with a delayed sweep. *What we lose:* storage in every entry, and the old entries stay as dead weight until replaced. *Gates (measured, 32-entry buffer):* +4,225 for an 8-bit generation written by software; +2,973 for an 8-bit counter in hardware that software can only bump; ×1.5 for the core's two buffers (estimate): about +6,300 and +4,500. *By construction:* no, the dependence on software remains (what remains: the hypervisor must write the new value). It is a faster flush, not a safer one.

**(c) Hardware notices stores to table pages that were walked, and discards the affected entries.**
*What it does:* a small directory remembers the pages the walker has read as tables (stage 1 and stage 2); a store by the core, or a DMA write, into one of them discards the entries made through it. *Hole it closes:* all of it, including a table edit done with no flush at all: the page-table store itself is the flush. *What we lose:* gates (a content-addressed store is large), a store port that every core's stores must reach (other cores' stores too: more wiring), and a rule for what happens when the directory is full (discard what it points to). *Gates (measured, directory plus its kill, per core):* 8 entries one store port 6,030; 16 entries one port 12,120; 16 entries two ports (the core's stores and DMA) 14,338; 32 entries two ports 28,757. A 32-entry buffer can hold entries made from many more than 16 table pages, so a small directory discards too much; 28,757 is more than three times the guest tag itself (8,799). The variant that follows the HATRIC idea, a bit in each data-cache line that the walker read, plus the table page's address in each buffer entry, is **estimated** at 8,000 to 11,000 (512 line bits at 6, 48 entries of 28 bits at 6 each, a compare) and was not synthesised. *By construction:* yes. *Cycles:* a stage-2 edit discards what it must; false discards come from a full directory.

**(d) The cheap amendment of the MMU review: a flush bit in the guest register `GTBR`, so a reset is one write.**
*What it does:* a write of `GTBR` with the bit set discards the entries of the tag written, whether or not the root changed. *Hole it closes:* it makes the correct reset one instruction; the hypervisor can still leave the bit clear. *What we lose:* one bit of the register. *Gates:* measured +7 (the base's "root or enable changed" test, 29 bits wide, is already there). *Cycles:* none. *By construction:* no.

### 2.4 A fifth rule that the numbers suggested: an arena for the stage-2 tables, and a flag (what I recommend)

Rule (c)'s directory is large because it must remember any page. If the hardware is told **where** the stage-2 tables are, it needs two comparators, not a directory.

**(e) The arena and the "tables changed" flag.**
*What it does:* the hypervisor writes two page registers that bound one range of real memory, the **arena**, and every stage-2 table must lie inside it; the walker refuses (an exit with its own cause) a table outside. A store by the core or by DMA into the arena sets a flag `S2DIRTY`; so does any write of a translation register of a guest at the hypervisor level (`GTBR`, `PTBR`, `ASID`, `MMUCTL`), even with the same value. `GENTER` discards the guest's entries if the flag is set, and clears it. With no arena set, the flag is treated as always set, which is rule (a): the default is safe, and the fast path is opted into. *Hole it closes:* a stage-2 entry rewritten with no flush, a reused root with no flush, and a guest reset (a reset must write the guest's `MMUCTL` and `PTBR` or it is not a reset; that write sets the flag). The hypervisor cannot forget, because there is nothing to remember: the store itself arms the flush. *What we lose:* the hypervisor must allocate stage-2 tables from one contiguous pool (whether the usual hypervisors can do this is **unverified**; Linux's Arm KVM draws its tables from a general pool, which I did not check); a store of any kind into the pool flushes at the next entry, including setting up a new table (one flush, not one per store); and it needs the snoop of other cores' stores when there is more than one core (the same comparator on the coherence port; not built, so **estimated**). The stage-1 tables of a guest live in guest memory and are not in the arena (see 2.6).
*Gates:* measured **1,072** for the two range comparators on two store ports and the refuse test, **+93** per 32-entry buffer for a clear-all input to the buffer (so about 1,260 for the core's two buffers), plus the flag, its wiring and the second port's OR (**estimated** 20): **about 1,300 in all, 0.5% of the core**. *Cycles:* an exit that changed nothing keeps every entry (measured in 2.5); an exit that edited stage 2 discards what the software `TLBIA` would have discarded anyway.

### 2.5 Cycles, measured on the hypervisor tests

Entries into a guest (`GENTER`) and the table reads a rule costs, from the replay described in section 1 (the first column is today's behaviour):

| program | entries | walks today | walks, rule (a) | extra reads, rule (a) | per entry |
|---|---:|---:|---:|---:|---:|
| `hv-first` (a guest that prints through 79 hypercalls, takes a page fault in stage 2 and a timer tick) | 79 | 15 (165 reads) | 113 (1,431 reads) | +1,266 | 16.0 reads, about 48 cycles |
| `hv-stage2` (stress test of stage 2, tags and resets) | 38 | 68 (300 reads) | 85 (351 reads) | +51 | 1.3 reads, about 4 cycles |
| `hv-timer`, `hv-vtimer` | 1 | 0 | 0 | 0 | none (the guest barely runs) |

Rule (e) discards at an entry only when the flag is set; in these programs the only flagged entries are the ones where the hypervisor already executes `TLBIA` (the demand fill in `tests/qemu/hv-first.S:94-115`, the resets in `hv-stage2`), so **its extra reads are 0 in all four** (it replays as today). Rules (b), (c) and (d) also add no reads in a hypervisor that does its flushes. The hypercall round trip of `hv-first` is 8 instructions of hypervisor code (counted, `tests/qemu/hv-first.S:79-89`) plus the hardware exit and entry; the repository has no cycle count for those (the nested-virtualization estimate says the same), so taking the timing model's flat 20 cycles for each of two events (**estimate**) gives about 48 cycles, and rule (a) adds about 48: **it about doubles the cost of a hypercall that changed nothing**. For a timer tick every millisecond, a guest that has to refill all 48 entries of its two buffers costs at most 48 × 15 reads × 3 cycles = 2,160 cycles (**estimate**, an upper bound), 0.2% of a 1 GHz core; for an exit rate of 100,000 a second the same bound is about 20%. That is why the fast path matters for a hypervisor that serves a device, and why rule (e) is worth 1,300 gates.

### 2.6 What each rule leaves open

* **(a)** nothing, at the cost above.
* **(b)** the hypervisor must write a fresh tag or generation at every reset.
* **(c)** nothing, at the cost in gates.
* **(d)** the hypervisor must set the bit.
* **(e)** a guest's own stage-1 tables are in guest memory, not in the arena: a hypervisor that wipes guest memory in place and enters without writing the guest's translation registers would leave combined entries made from the old stage-1 tables. A reset writes those registers (that is what makes it a reset; manual 6.14.8 and the table of reset state), and the write sets the flag, so this is closed by the same rule. The case that is not closed is a hypervisor that edits guest memory that holds the guest's page tables while the guest is stopped, **not** as a reset: but the guest must then execute its own `TLBI` as it must after editing a table itself, or the hypervisor is changing the guest's tables behind its back, which no architecture protects against.

### 2.7 Recommendation for hole 1

Adopt rule (e). It costs about 1,300 gates, loses nothing on an exit that changed nothing, and removes the dependence on the hypervisor's memory for stage 2 and for a reset. If the owner would rather build nothing, rule (a) alone is a handful of gates and closes the same hole completely at the cost of about 16 table reads at each entry. Keep (d) out: with (e) or (a) it adds a way to forget, not a way to remember. Rule (c) with a directory is the cleanest idea and the most expensive (6,000 to 28,757 gates, or 8,000 to 11,000 estimated for the cache-line version); it is worth a second look only if the owner wants the same guarantee for a kernel's own tables (stage 1), where it would make `TLBI` and its broadcast unnecessary: a bolder change (it is what HATRIC proposes), which I do not recommend for a first version.

## 3. Hole 6: the kernel's registers are visible to the user after a return

### 3.1 The hole in plain words

Only `R14` (the stack pointer) and `DP` (the direct-page register) are banked by mode (manual 6.2). `R0` to `R13` and `R15` to `R31` are one set. A system call or an exception handler uses some of them as scratch and returns; whatever it left in a register it did not restore, the user can read. The probe is `tests/sec-open/sim/sec-regs-carry.S`.

**The catch.** A blind clear of the registers at the return would be wrong: on the way back the kernel puts the user's own values back into the registers it saved (`popm` in `tests/qemu/mini-kernel.S`, lines 79, 104 and 118), and a system call's result must be in `R0` (the ABI table, `docs/abi.md` line 11: results in `R0` and `R1`). A clear that runs at the return wipes both. A clear at the **entry** is no use either, since the kernel must see and save the user's registers at the entry. So any hardware scheme must either (i) know which registers hold the user's own values at the moment of the return (a mask, or a marker per register), or (ii) mark, at the time of each write, whose value it is. The kernel's `popm` and a `movq` of a result into `R0` are ordinary writes; the hardware cannot tell them from a scratch write unless the kernel says.

The ABI helps in one way: `R0` to `R7` and `R12` are caller-saved (`docs/abi.md` line 11), so a kernel need not restore them across a system call; the user already assumes they are clobbered; the hole is that they are clobbered **with the kernel's data**, not with zeros.

### 3.2 What other systems do (verified)

* **Restore every register from the saved frame.** OpenBSD's amd64 return path reloads the registers from the trap frame (`movq TF_R8(%rsp),%r8` and the lines around it, `sys/arch/amd64/amd64/locore.S`, lines 595 to 612, read 2026-11-19). On processors that need the mitigation for the "MDS" leaks it first runs `xorl %edi,%edi; xorl %esi,%esi; xorl %r11d,%r11d; xorl %eax,%eax; xorl %ecx,%ecx` (lines 616 to 620, the same file and date), which zeroes five registers (**it is not a general rule of clearing what was not restored**: I looked for one and did not find it). Linux x86 does the same: `POP_REGS` at the return (`arch/x86/entry/entry_64.S` line 139) and, at the entry, a macro whose lines are `xorl %esi, %esi /* nospec si */` and so on (`arch/x86/entry/calling.h`, lines 109 to 115: clears registers so that speculation cannot use them). Linux arm64 restores from its frame (`arch/arm64/kernel/entry.S` line 424, `ldp x0, x1, [sp, #16 * 0]`). So the common design is "save everything, restore everything", which costs a store and a load for every register, at every system call. It leaks nothing by construction of the habit (every register is overwritten), not of the hardware.
* **Hardware clears by instruction, in the compiler or in software:** the Linux option `CONFIG_ZERO_CALL_USED_REGS` and the Arm "clear multiple registers" instruction of the Armv8.1-M profile come to mind; **unverified** (not read).
* **A second register set for the kernel.** The PDP-11 itself had it: "To speed up context switching, some PDP-11 models provide dual R0–R5 register sets." (Wikipedia, "PDP-11 architecture", read 2026-11-19; the handbook was not read). It is the oldest answer and the one nearest to the owner's taste.

### 3.3 The options, each in a few words

**(a) The kernel clears what it did not restore (the software baseline).**
*What it does:* before `RTI` the handler executes a clear for each register it dirtied and did not restore. *Closes:* the hole, if the kernel is careful on every path (system call, fault, timer, new process, signal); nothing checks. *We lose:* instructions at every return. *Measured* (instruction counts of 1,000 system calls on `sim64 -K -t`; the handler is 8 instructions, using `R1` to `R5` as scratch):

| variant | instructions per system call, handler | extra | cycles extra (estimate) |
|---|---:|---:|---:|
| lazy kernel, clears nothing (the hole) | 8 | 0 | 0 |
| clear `R1`-`R5` (what this handler dirtied) | 13 | +5 | +5 |
| clear `R1`-`R7`, `R12` (all caller-saved) | 16 | +8 | +8 |
| clear all of `R1`-`R7`, `R12`, `R16`-`R31` that are not callee-saved | 32 | +24 | +24 |
| save and restore `R1`-`R13` with `pushm` and `popm` (the Linux and OpenBSD way) | 10 | +2 (26 words moved) | +30 |
| save and restore `R1`-`R5` (the mini-kernel's way) | 10 | +2 (10 words moved) | +14 |

*By construction:* no. A new path that forgets is the hole again. The cost is large against an 8-instruction null call: a careful clear of the caller-saved set makes it 16, twice as long.

**(b) A marker bit per register that says "a more privileged mode wrote this" (the owner's taint bit).**
*What it does:* each register has one bit; a write made in kernel mode sets it; in user mode a register whose bit is set reads as zero; a write in user mode clears it. The kernel's restores must use a write that does not set it (a mode bit in the status word like the user-access guard `UA`, set with one instruction and cleared by every exception entry and return; or a distinct form of `popm` and of a move). *The flaw I found:* it is not enough. The user reads zero, but the register still **holds** the kernel's value; at the user's next system call the kernel saves it (kernel-mode reads are not gated), and later restores it with the untainted write, which gives the secret to the user. So at every entry to the kernel the hardware must also clear every register whose bit is set (and reset the bit): that is a flash clear as well as the bits. *We lose:* the kernel must say, with every user-visible write (the result in `R0`, the restores), that the write is the user's: one more instruction at each return (the mode bit), or new forms. *Closes the hole by construction?* Yes once the entry clear is added; a kernel that forgets to say it loses its program's registers (reads zero), loudly. *Gates (measured, same style on both sides):* base 27,593; with 32 bits, the read gating and the entry clear **30,771: +3,178**, and one more gate delay on each read path (an estimate: the reads are gated after the mux).

**(c) A return with a mask of the registers to keep, and a flash clear of the rest.**
*What it does:* one instruction, `RTI` with a 32-bit mask (an immediate: a 16-bit opcode and a 32-bit mask, six bytes; the minimum is one new encoding of the existing instruction with an immediate field, no new mnemonic, spelled `RTI #mask`). When the return goes to a **less privileged** mode, hardware clears, in the same cycle as the mode change, every register whose bit in the mask is zero; a return to the same mode (a nested interrupt) clears nothing. The plain `RTI` with no mask **does not exist**: the architecture has no way back to the user that does not say what the user may see. *Closes:* the hole by construction: the clear is not a kernel duty. A kernel that returns with the mask `-1` (everything) is making an explicit, greppable claim; a kernel that returns with too small a mask gives the user zeros where it should have given values, which the first test shows. *We lose:* four bytes at each return site; that the kernel must know, at each return, which registers hold the user's values (it does: it wrote the `popm` three instructions earlier; a mask is a constant per return path); and the old unmasked `RTI`, whose users (the kernels and the repository's tests) must be changed (the tests `sec-*` and `mini-kernel` use `RTI` throughout; a transition period could keep the plain form meaning "mask zero" and make that the default of the assembler). *Gates (measured):* the flash clear, a clear on each flop of 31 registers (`R14` is banked) gated by the mask and the return: **+2,112 (+7.7% of the register file)**; the lazy version (one bit a register, set by the return, a register with the bit set reads as zero in every mode, a write clears it, which also avoids the second flaw of (b)): **+1,147 (+4.2%)** but one more gate on each read path. *Cycles:* the clear runs inside the return's own pipeline restart (an **estimate**: the instruction was not run, and nothing models it); zero extra instructions; against the 5 to 24 of (a), a system call return is **5 to 24 cycles faster than doing it by hand, and safe**. The same mask on `GENTER` closes the same hole between the hypervisor and its guest (the hypervisor's registers visible to the guest at entry); there the hypervisor restores all of the guest's registers anyway, so the mask is cheap there too.

**(d) Others, from the baseline.**
* *A second set of registers for the kernel (the PDP-11/45 way).* Closes the hole completely and with no help from the kernel's care (the user's set is never written by the kernel; a system call's result and arguments cross by two new instructions, move from the other set and move to it). *We lose* 39,112 gates (**measured**: 66,705 against 27,593, +142%, about 12% to 18% of the core), one instruction per argument and result (about 4 per system call, **estimate**) and 30 more at each context switch (**estimate**) for saving the user's set. It buys the cleanest picture, the one a PDP-11 programmer already has, at a large price in silicon: I do not recommend it for the gates, though it is the best on the last principle.
* *Hardware save and clear at the entry, as a hardware stack frame:* every exception would store the registers (cycles at every entry, not only at the return): rejected on speed; **unverified** what Arm's M profile does.

### 3.4 What it does to the speed of a system call

Safety first: (a) leaves the hole open on every path the kernel's author forgets; (b) and (c) close it. Then speed: (a) adds 5 to 24 cycles, **more than doubling** the 8-instruction call at the high end; (b) adds one instruction (the mode bit); (c) adds none, and one more entry decode; the bank adds about 4. The mini-kernel's own handlers (`h_write`, `h_pf`) already save and restore what they use, so they leak nothing today: the leak is in a kernel written in the lazy, caller-saved style that the ABI allows, which is exactly the fast style, and the one hardware (c) makes safe.

### 3.5 Recommendation for hole 6

Option (c), the return with a mask and a flash clear: +2,112 gates (about 0.8% of the core), no extra instruction, no extra cycle, and no way back to user mode without naming what the user may see. Keep the lazy version in reserve if the read path is not the critical one. Do not take (b): it needs the same flash clear and, in addition, a way to mark every write.

## 4. Hole 7: the floating-point flags carry from one process to the next

### 4.1 The hole in plain words

`FPSR` is five sticky flags (invalid, divide by zero, overflow, underflow, inexact; manual 9.12.3); no operation traps; `FSFLAGS` reads and clears them (the corpus test also writes them with a second register). They are per core. A process that makes the flags depend on a secret (a branch on a secret that decides whether an operation overflows) leaves one bit per flag for the next process, if the kernel does not swap them. The probe is `tests/sec-open/sim/sec-fpsr-carry.S`.

### 4.2 What other systems do (verified)

* **RISC-V:** the flags are part of `fcsr`, which the kernel saves with the floating-point registers: `__fstate_save` reads it with `frcsr t0` (Linux `arch/riscv/kernel/fpu.S` line 27, read 2026-11-19). Kernel duty.
* **Arm:** Linux keeps `fpsr` in the thread's saved state: `task->thread.uw.fpsimd_state.fpsr = 0x0800009f;` (`arch/arm64/kernel/fpsimd.c` line 706, read 2026-11-19). Kernel duty.
* **Order in a context switch.** Linux's generic scheduler switches the address space first and the registers after: `switch_mm_irqs_off(prev->active_mm, next->mm, next);` (`kernel/sched/core.c` line 5563) before `switch_to(prev, next, prev);` (line 5584), both read 2026-11-19. A clear on the address-space write therefore comes **before** the kernel restores the incoming flags, which is the order option (b) needs; I read only the generic scheduler, not each architecture's floating-point switch, so that every architecture restores its flags inside `switch_to` is **unverified**.

### 4.3 The options

**(a) Kernel duty.** *What it does:* the kernel saves the outgoing flags and writes the incoming at each switch: with `FSFLAGS`, read-and-clear plus a store, then a load plus the write: **4 instructions** per switch (counted from 9.12.3 and the corpus test). *Closes:* if the kernel does it on every path. *We lose:* nothing; *gates:* 0; *cycles:* 4 per switch.

**(b) The hardware clears the flags when the address-space number is written** (and, for the same reason, when the guest register `GTBR` or the page-table base is written: any write that changes whose space runs). *What it does:* the old process's flags cannot be seen by the new one. The kernel still restores the incoming process's flags afterwards (so the correctness of the flags per process is the kernel's, as now; the safety is the hardware's). *Closes:* the leak between address spaces by construction; a careless kernel that forgets to restore gives the new process **cleared** flags, a lost "sticky" bit, which is a wrong value but not a secret. *We lose:* the order (restore after the write of the number; the common order, section 4.2) and the sticky flags of a kernel that restores the flags *before* the write, which are lost; and threads of the same process do not get a clear (the same address space, the same trust domain). Also not covered: the kernel's own floating-point arithmetic between the user's instructions, which sets user-visible flags (option (c) covers it; a kernel with no floating point does not need it). *Gates (measured):* base 58 (5 flip-flops and the sticky logic); clear on `ASID` write **63 (+5)**; on `ASID` and `GTBR` writes **65 (+7)**; the page-table base adds one more OR (estimate: +1). *Cycles:* none.

**(c) Banked by mode.** *What it does:* the kernel's floating-point work sets its own five flags; the user's are untouched in kernel mode. *Closes:* only the kernel-to-user direction, not process to process: the kernel must still swap on a context switch. *We lose:* a second set. *Gates (measured):* **126 (+68)**. Not enough alone.

### 4.4 Recommendation for hole 7

Option (b): +5 to +7 gates, no cycles, and the leak across address spaces is closed by the write the kernel has to make anyway. The same clear on a write of the address-space number could serve other per-context hidden state that is not already handled by the resume design (the vector accumulators and the resume record are, in `vector-resume-design.md`; I do not repeat them): the one candidate I see is the **load-linked reservation** (the hardware's note that a `LL` is outstanding), which manual 6.14.9 already clears at every exception entry and return, so it needs nothing.

## 5. What I could not verify

* Intel's manual, Arm's reference manual, and IBM's z/Architecture text were not read: nothing is said about x86 coherence, Arm's break-before-make behaviour, or `IPTE` except as a name or an "unverified".
* The HATRIC paper was not read; only its abstract as a search returned it. The OpenBSD, Linux, and RISC-V quotations are from the files and the specification as fetched on 2026-11-19; Linux line numbers are those of the master branch of that day and will drift.
* OpenBSD's practice: I found no general clearing of the registers it did not restore, only the five `xorl` of the MDS mitigation and a restore of every register. If the owner remembers a general rule, it is not in the file I read.
* Arm's M-profile clearing of registers at a security transition, the Linux zeroing option, and the Arm clear-multiple instruction: not read.
* The cycle numbers of the hypervisor are a replay of first touches of QEMU's software translation cache, not of a hardware buffer; the cost of a read (3 cycles) and of an exit and an entry (20 each) are estimates; the repository has no measured exit or entry cost. The kernel's numbers are instruction counts (the timing model refuses kernel mode), and the cost of the exception entry and `RTI` is unknown.
* The flash clear, the arena and the flag, the clear on the address-space write were synthesised as small models, never run as hardware or in the simulator: whether the instruction `RTI #mask` fits the encoding (the grammar has not been consulted for a free six-byte form) is open.
* The gates of the arena version leave out the wiring of other cores' stores, and the cache-line variant of rule (c) was not synthesised.

## 6. Decisions for the owner, each with a recommendation

1. **How should a guest reset in place be made safe: by hardware that cannot be forgotten (rule e, or the simpler rule a), or by one more bit for the hypervisor to set (rule d), or by a generation number (rule b)?** *Closes:* the stale-translation hole. *We lose* (e): about 1,300 gates and the need to keep stage-2 tables in one pool. *Recommendation:* (e), with (a) as the default whenever no arena is set. Not (d) and not (b): both leave the hypervisor something to remember.
2. **Is the hypervisor allowed to be forced to keep stage-2 tables in one contiguous pool?** *Closes:* what makes (e) cheap (two comparators instead of a 6,000 to 28,000-gate directory). *We lose:* freedom of the hypervisor's allocator; a hypervisor that cannot do it falls back to (a). *Recommendation:* yes; a first hypervisor of our own can pool them, and one that cannot falls back to discarding at every entry.
3. **Does a write of a guest's translation register at the hypervisor level always arm the flush, even with the same value?** *Closes:* the hole of the reset that "changes nothing". *We lose:* a few refills when the hypervisor rewrites the same value for no reason. *Recommendation:* yes (it is how a reset is recognised).
4. **If the owner wants no new hardware at all for hole 1: is discarding at every `GENTER` acceptable?** *Closes:* the hole completely, for a handful of gates. *We lose:* about 16 table reads (about 48 cycles) at each entry of a small guest, which about doubles a hypercall that changed nothing, and up to a fifth of a core at 100,000 exits a second. *Recommendation:* acceptable for a first version only; take (e) when a guest does device work.
5. **Is a hardware directory of walked table pages (rule c) wanted for a kernel's own tables, to drop `TLBI`?** *Closes:* every stale-translation bug of a kernel (a bolder change). *We lose:* 6,000 to 28,757 gates (or 8,000 to 11,000 estimated by the cache-line version) and store ports on every core. *Recommendation:* no for now; revisit with the multi-core design.
6. **Should every return to a lesser mode carry a mask of the registers to keep, with a flash clear of the rest, and no unmasked return?** *Closes:* the registers-after-a-return hole by construction. *We lose:* four bytes at each return site, the old unmasked `RTI`, and +2,112 gates (about 0.8% of the core). *Recommendation:* yes. It saves the 5 to 24 instructions a careful kernel would spend, and a careless kernel's mistake is a lost register that shows at the first test, not a leaked secret.
7. **Spelling of the mask: an immediate in the instruction, or a system register written before the return?** *Closes:* the same hole. *We lose:* the immediate makes the instruction six bytes and the mask a constant of the code (good: reviewable); the register costs two instructions at each return and can be left stale. *Recommendation:* the immediate; if the encoding has no room, the register, cleared by every return.
8. **Does the same mask apply to `GENTER`, so that the hypervisor's registers are not visible to a guest?** *Closes:* the same hole one level up. *We lose:* the same four bytes in the hypervisor's entry code. *Recommendation:* yes.
9. **Flash clear, or the lazy version (one bit a register, reads as zero until written)?** *Closes:* the same hole. *We lose:* the flash clear costs +2,112 gates and none on the read path; the lazy version costs +1,147 and one gate delay on every register read. *Recommendation:* the flash clear (the read path matters more than 965 gates); revisit if the read path has slack.
10. **Should the second register set for the kernel (the PDP-11/45's) be built?** *Closes:* the registers hole without any care by the kernel and gives the cleanest picture. *We lose:* 39,112 gates (about 12% to 18% of the core), about 4 more instructions at each system call, 30 more at each context switch. *Recommendation:* no; the mask costs a twentieth of it.
11. **Should the floating-point flags be cleared when the address-space number, the page-table base or the guest register is written, with the kernel restoring the incoming flags after the write?** *Closes:* the leak of the flags between address spaces by construction. *We lose:* 5 to 7 gates, the order "write the number, then restore the flags" (the order of Linux's generic scheduler), and the sticky flags of a kernel that restores first. *Recommendation:* yes. Not banking by mode (68 gates and it does not close process to process); record in the manual that threads of one process share the flags.
