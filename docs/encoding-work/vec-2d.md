# The 2D (tile) form of the vec block: prior art, design, security, measurements

**Status (2026-11-18): implemented, tested and measured; the compiler does not emit it.** The owner asked (2026-11-18): "i want to know ... is it possible to set up the instructions once then just keep reading in tiles and rerunning it? ... about the scalar loop; if its running millions of times as the outside loop not the inner loop, its ok; what efficiency gain is there with the 2d block? not code size. execution speed/efficiency? now if it makes it easier to do things more securely without bounds checks... excellent. go ahead and design the 2d block; you sure noone else has done this before? measure and find out why not. and yes, i do want you to rerun the graphics shaped kernels with and without the 2d block form at both strips." (R483). The design details below are the assistant's, decided by the owner's standing criteria (the most work for the fewest instructions; reasonable performance for minimal silicon; safety and security; precise exceptions and clean restarts; hidden state is ok if exceptions stay precise and restarts clean) and recorded as errata 176 and R483 to R489. **What is built:** the words `vec2` and `vskip` (grammar, `as64`, `sim64`, the QEMU copy, the manual entries, the LLVM name tables), the executor, both cycle models with the row advance as a stated parameter (`sim64 --vrow=N`), the test `tests/sim/vec-2d.S` (117 cases, strips 16, 32, 64; sim64 and QEMU), 16 hand-written kernels and 4 checked ones (`arch-data/vec-forms/tiles/`), the rerun script `tools/gates/run-2d.sh`. **What is not built:** a hardware bounds operand (costed, section 5), a row-packing strip (analytic only, section 6.5), a compiler pass (section 3.9), blocks with accumulators in 2D (refused). **Evidence grades used throughout:** [M] measured by the assistant in this work (sim64, yosys, enumeration); [A] analytic (arithmetic from measured parameters, not a run); [R-source] read in a source that was fetched in this work (the notes of the prior-art study, a subagent's, with the URL named); [S] seen only in a search result summary (a lead, not a read); [Mem] from memory, not checked now. **Thin evidence:** most of section 1 below the AMX, Xe, TMA, SME and RVV entries is [S] or [Mem]; the cycle numbers are of the two models of `docs/sim64.md` (no hardware), the scalar baseline is compiler-made scalar code at one cycle an instruction, and the row cost is an assumption.

**Related:** `vec-isa.md` (semantics; section 9 is the 2D block), `vec-strip.md` and `vec-latency.md` (the cycle models), `vec-silicon.md` (the silicon of the family), `docs/errata.md` 176, `docs/decision-register.md` R483 to R489, `tools/gates/run-2d.sh` (the rerun), `tools/gates/2d-results/summary.md` (every table).

**The premise "no one has done this" is false in part.** Someone has done a 2D load: AMX (`TILELOADD` with a stride, a start row for restart), Intel Xe (2D block messages), Hopper TMA (box copies), SME (slices), MOM (matrix registers, 1999 to 2001), AltiVec `dst` (a 2D prefetch hint), and every DSP with nested zero-overhead loops. What is not found in any of them is the *shape chosen here*: a loop of the unchanged one-dimensional block over rows, with the registers of the block as the progress, for general-purpose code with ordinary pointer registers and no new register state. AMX is the closest in the restart idea (progress held in an architectural register, resume at the row); its tile is a fixed 16 x 64 byte register file, ours is no state at all. What we borrow: **start-row restart from architectural state (AMX, RVV `vstart`), the descriptor as the bounds (Xe, TMA), and the DSP's separation of "counter" from "modifier"** (our `vskip` is a post-modify register per stream, applied at the end of a row). What the others did not need and we do: nothing hidden at all across a context switch.

**Why general-purpose vector ISAs mostly have none (what the sources support, what is inference).** Supported: restart needs architectural progress state and bounded work per instruction (AMX 16 rows, `start_row`; RVV `vstart`) [R]; where 2D exists in a CPU it is a small fixed tile and its state forced OS machinery (AMX permission and XFD, SME clear-on-enable) [R]; GPUs avoid faults with a bounds descriptor and a defined out-of-bounds fill, landing data on chip [R]; RVV declined strided first-fault for encoding space [R]; the production vectoriser is innermost-only and the outer-loop path is unfinished [R]; the 2D idea that shipped widely was the prefetch hint [R]. Inference [Mem]: a multi-row operation touches many pages and lines per instruction, so its TLB and cache cost is unbounded unless the rows are capped; strides that share factors with the bank count conflict; two strides and two counts do not fit a 32-bit encoding, so designs use a configuration register (AMX `tilecfg`) or a descriptor (TMA tensor map). Section 2 tests these against pdp64 with measurements.

## 2. Why not for the pdp64: the measured answers

**(a) How many pages does a tile touch?** Measured by enumeration (`tools/gates/pages2d.py`; the tile base at every 4-byte-aligned offset of a page, bytes per pixel 1) [M]. The pdp64 page is 4 KiB with 2 MiB mappings (the leaf sizes the tests build). A 16 x 16 tile touches, on average, **3.35 pages at pitch 640, 5.69 at 1280, 8.03 at 1920, 10.38 at 2560, 15.07 at 3840, exactly 16 at 4096** (not 16 at pitch 1920: a 4 KiB page holds two rows of 1920). 8 x 8: 2.09, 3.19, 4.28, 5.38, 7.56, 8.00. 64 x 64: 10.86, 20.70, 30.55, 40.39, 60.08, 64.01. **A row straddles a page boundary in 0.3% of the rows of a 16-wide tile and 1.5% of 64-wide** (so about one tile in 20 of 16 x 16 has a row whose strips need two translations), and a row of 16 bytes touches 1.19 64-byte lines on average (8 bytes: 1.06; 64 bytes: 1.94). With 2 MiB mappings a tile of 64 x 64 touches 1.02 to 1.12 pages. **What a precise per-row fault costs:** nothing extra in this design: the fault is per strip (the same strip of the 1D block), the strip's accesses are all checked before it does anything (`vec-isa.md` 8.6), so a tile of 16 pages can fault 16 times and each restart re-issues the block header (the `vec2` and its `vskip` words and the `vend`: 1 + n + 1 slots, 5 for a three-stream block in the model) and no strip is done twice. **The thing that is expensive is the TLB, not the architecture:** a 16 x 16 tile at pitch 4096 needs 16 translations per stream, and two streams need 32; an implementation with a small data TLB will thrash exactly as the loop of 1D blocks does; the 2D block neither adds nor removes that (it makes it visible: the hardware knows the footprint at the `vec2` and could prefetch the translations; not built).

**(b) The restart cost of a fault in row r.** The pointers, `Re` and `Rn` are committed with each strip (the row advance with the last strip of its row), so after a fault the block restarts **at the faulting strip of the faulting row**, with no work repeated [M: the test counts 913 rows executed for 117 cases whose tiles have 913 rows in all, with 93 restarts: a repeated row would show]. The cost of a restart is the re-issue of the header, 5 slots here [A]. The rows before are not redone (contrast AMX, which restarts at a row boundary of its own `start_row`, and a hidden-accumulator block of the 1D family, which restarts from its entry: those cost the work so far). A block with accumulators would lose the whole tile on a restart, which is why it is refused in 2D (section 3.7).

**(c) Could LoopVectorize or the LLVM pass emit the form?** Measured (`tools/gates/nests2d.py` over the C sources of `llvm/bench` and the tiles; the IR after opt -O2 with LoopVectorize) [M]: 150 scalar loops (this count includes the remainder loops the vectoriser leaves) and 85 vectorised loops in 8 sources; **18 loops contain a loop; all 18 have a countable trip count (SCEV); 15 contain a loop that was vectorised**; of the 10 nests outside `tiles.c` 9 have a vectorised inner loop under a countable outer loop (`kernels.c` 2 of 2, `blas.c` 5 of 5, `newk.c` 1 of 1, `gaps.c` 1 of 2). So **in the benchmark kernels a countable outer loop around a vectorised inner loop is common wherever a nest exists, but nests are few (10 loops that contain a loop among the 134 non-vectorised loops of the pre-existing sources; the count includes the remainder loops the vectoriser leaves)**, and in tile code it is the rule (8 of 8 countable, 6 of 8 with a vectorised loop inside: `gray` and one more are not vectorised). What the compiler would need: the outer loop's stride of each pointer as an invariant (SCEV gives it), the proof that the streams of the nest do not overlap across rows (the same disjointness proof the 1D pass needs, but across rows), no calls and no other work in the outer body, and the vskip count (at most four streams advanced). **LoopVectorize itself cannot: it vectorises the innermost loop and leaves the outer loop scalar** [R-LLVM docs]; the lowering pass `PDP64VecLoop` recognises only an innermost loop. **Not done:** a recogniser that takes the `.preheader` loop of the nest in `tiles.c`'s IR (an inner `vector.body` loop inside a counted outer loop whose only other work is pointer increments) and emits `vec2`; the work is about the size of the 1D pass's block lowering plus the disjointness check across rows (not estimated further).

**(d) Silicon.** Measured with yosys and the flow of `tools/gates/gates.sh` (synth, abc to NAND2, flip-flops apart; `tools/gates/tile2d.v`) [M]: the row advance of four streams, with four 64-bit adders (the pointers), the 3-input adder of `Re`, the row counter (a decrementer and a zero test) and the row-end compare: **4,617 NAND2 equivalents**; the same with one shared adder for the pointers (the pointer updates take four cycles instead of one): **2,030**; one 64-bit adder alone 660; the decode latches (four pairs of 5-bit register indices, valid bits, a 2D flag: 45 flip-flops, about 270 NAND2 at 6 for a flip-flop). Against the measured family (263,000 to 291,000 NAND2 for wave 1 with 16 integer lanes, `vec-silicon.md`): **4,900 is 1.7 to 1.9%, the shared-adder version 0.8%**. The registers are the machine's own: the row count, the end, the width and the gaps are ordinary integer registers read and written through the ports the strip commit already has (the strip commit already writes the pointers of the block). A hardware bounds comparator for four streams (not built): **3,999** more.

## 3. The design

### 3.1 The words

```
vec2   Rs, Re, Rn, Rw      begin a 2D block: Rn rows, each the region [Rs, Re) of the pointer register Rs, a row being Rw bytes of the first stream
vskip  Ra, Rg              (zero to four, directly after vec2) at the end of each row, Ra += Rg
  ... the body: the instructions of a 1D block, unchanged ...
vend
```

The `vec2` word is a new form (`VBEG2`: four 5-bit registers, a 12-bit prefix: **16 first-parcel patterns of 65,536, 0.024%**); `vskip` has the free sub-opcode of the form of `vec` (**no pattern**). The grammar goes from 181 forms and 239 leaves to 182 and 240; the words from 363 to 365 (base mnemonics 63 to 65, forms of the family 23 to 24); the illegal first parcels 911 to 926 (the optimiser's layout was run again, as at each wave: **every encoding moved**, the golden vectors, 8 `tests/asm` word files, the linker's expected words and the checksums were rewritten; encodings stay provisional, errata 161).

### 3.2 What a 2D block does

For each row (while `Rn` is not zero): the strips of the 1D block over the region `[Rs, Re)` of the first stream (the stream of the first instruction that has `(Rs)+`); a strip never spans rows, the last strip of a row is short. When a row ends: every `vskip` pointer is moved, `Re` moves by `Rw` plus the gap of the first stream's pointer, and `Rn` falls by one, **all committed with the last strip of the row**. At the end `Rn` is 0, each pointer that has a `vskip` is at its entry value plus rows x pitch, `Re` at its entry value plus the row's width plus rows x the first stream's pitch, and a pointer with no `vskip` is where the strips left it (the stream is contiguous: a packed tile, the case of a SAD against a 16-byte-pitch current block needs no declaration). A `d(Ra)` stream does not move unless it has a `vskip` (a per-row base: a row of coefficients). A reduction register (`vsad`, `vacc`, `vdacc`, ...) accumulates over **the whole tile** (it is an ordinary register that each strip adds to when it commits): for a SAD, `r6` is the sum over all rows. A zero `Rn` or a zero `Rw` does nothing and changes nothing; an empty row (`Re` not above `Rs`) is only the advance; `Re - Rs` and `Rw` must be whole numbers of elements of the first stream (else the illegal-instruction exception). The block ends with `vend`; **the one-instruction prefix has no 2D form**; nested blocks are refused.

### 3.3 Decisions (each by the owner's criteria; the options not taken are in section 4)

1. **Spelling: `vec2 Rs, Re, Rn, Rw` and per-stream `vskip Ra, Rg`.** Fewest instructions (one setup instruction for each stream's gap, no new memory operand form: the 120-odd load and store words keep their forms), the same body as 1D, the pitch of a stream named once, a stream with no declaration free; silicon: a decode latch per declaration.
2. **The pitch of a stream is held as a gap** (the pitch minus the bytes the row used), the DSP's post-modify convention, **not as a pitch.** With a pitch the hardware would need the row's start address of every stream, which is hidden state (lost at a context switch) or an extra register; with the gap the pointer itself is the only state and the add is `Ra += Rg`. The price is one `sub` per stream in the setup (for streams of different element sizes the gap is in bytes of that stream).
3. **Where the row counter lives: `Rn`, an ordinary integer register; the row's end is `Re`, another; the row's width is `Rw`, a constant register.** All four are architectural: a fault, an interrupt or a context switch leaves them where the last committed strip left them, and the same `vec2` executed again continues. Four registers because a restart in the middle of a row must know both where the row ends (`Re`) and how wide the next rows are (`Rw`); there is no way to recover the width from `Rs` and `Re` after the first strip. `Rs`, `Re`, `Rn`, `Rw` must be four different registers (refused by the assembler and by the executor); `Rw` and the gap registers are read only in the block and may be shared by streams, `Ra` of a `vskip` is not `Re`, `Rn`, `Rw`, a reduction target is none of the registers the block names.
4. **A strip never spans rows (first design).** A narrow row (8 or 16 bytes) at a 32-byte strip leaves half the strip empty; section 6.5 evaluates the packed alternative.
5. **At most four `vskip` per block**: four adders (the silicon of 3.2d). A block that needs a fifth stream falls back to the loop of 1D blocks.
6. **The invisible strip holds** (`vec-isa.md` 8): results, EPC, EVA and ECAUSE do not depend on the strip. EVA is the first faulting access in the order of the elements, where the element index runs row after row; the progress of the pointers and of `Rn` at a fault is opaque (an element boundary, no later than the faulting element): the operating system restarts by returning and never interprets them.
7. **Blocks with accumulators (`vclr`, `vfmab`, `vfin`) are refused in 2D** (the assembler: an error; the executor: the illegal-instruction exception). Such a block restarts from its entry (`vec-isa.md` 4.1) and a 2D one would lose the whole tile; a micro-kernel has its own loops. Hidden state of any other kind does not exist in 2D.
8. **Overlapping streams are unpredictable, as in 1D** (`vec-isa.md` 8.8): a store over another stream's element at a different row or column. The same element of the same stream (read then write: an in-place update through two pointers) is defined, as in 1D; the test has it.
9. **The compiler does not emit the word.** The LLVM name tables know it (`tools/gen-llvm-td.py` writes `vec2` and `vskip` into the mnemonic list); no pattern, no pass. Section 2(c) says what a pass would take.
10. **The cost of a row in the models is a parameter**, `sim64 --vrow=N`, default **1 cycle for each row advance** (the pointer updates and the count in parallel; an ASSUMPTION for an in-order unit with four adders: one shared adder makes it up to 4); each `vskip` and the `vend` take one decode slot, once per block; sensitivity 0 and 2 is in the tables. Both models add the row cost between the last strip of a row and the first of the next (in model 2 it also delays the next strip's issue and completion).

### 3.4 An example (SAD of two 16 x 16 tiles of bytes, the current block packed, the reference with a frame pitch)

```
k_sad:	clr	r6
	movq	r3,r11 ; sub r4,r11	; gap of b = b stride - w          (a is packed: no vskip)
	lea	(r0)(r4),r7		; Re
	vec2	r0,r7,r5,r4		; Rs, Re, Rn = h, Rw = w
	vskip	r2,r11
	vld.bu	v0,(r0)+ ; vld.bu v1,(r2)+ ; vsad.bu r6,v0,v1
	vend
```
The loop of 1D blocks needs, for each row, `lea, vec, add, add, dec, cbgt` (6 scalar instructions) and a `vend`; the 2D block has `vec2`, 2 `vskip` and a `vend` once. Counts (sim64, measured): the loop form executes about 14 + 6 x h scalar instructions for h rows (110 for 16 rows; 13 + 6h at 256 rows), the 2D form 16.

### 3.6 What the test proves

`tests/sim/vec-2d.S`, from a model in Python written from the definition: four kernels (a reduction, a store, a widening store with a 2-byte element and its own pitch, an in-place update through two pointers) with the tile shapes 40 x 9, 5 x 3, 64 x 2, 16 x 1, 130 x 4 and 33 x 0 (no rows) and no fault (final memory by checksum, the scalar, the final `Rs`, `Re`, `Rn` and the pointers), and a page fault at the first, a middle and the last row (0, 4, 8) and at the first element of a row, one in the middle of a strip and the last element (0, 16, 39), on each stream of each kernel: exactly one fault, EPC the address of the `vec2`, a load or store fault, EVA the address named, the handler reading EPC, EVA and ECAUSE only and returning, the restarted block giving the result of the run with no fault; and 12 cases with a handler that saves the registers: `Rn` fell by the rows completed r' no later than the faulting row, the pointer of stream A at row r' and a column no later than the faulting one. 117 cases, strips 16, 32 and 64 on sim64 (`-K -x`), the same file on QEMU. **Non-empty:** three mutations of the test (a wrong gap register for each of three streams) fail at checks 9, 10 and 11. Not covered: faults on `vfir` halo reads, segment loads or `vtbl` in a 2D block (the 1D test covers them in 1D; the 2D block adds no new access).

### 3.7 Nested blocks and the other refusals
Nested blocks are refused; a `vskip` after the body began, a fifth `vskip`, a repeated pointer, `Rw` or a gap that the block writes, a reduction that targets `Rn`: all illegal (`as64` says why; the executor raises the illegal-instruction exception).

## 4. The options not taken

| option | pros | cons | why not |
|---|---|---|---|
| a pitch operand on every memory operand (`vld.bu v0,(Ra)+,Rp`) | the pitch next to the use; no declaration words | a second register field in about 120 load and store words: new forms for all of them (the first-parcel patterns of two register fields, 4 forms of the family become 8); four-byte words become six | the most encoding for the least gain; the pitch is a property of the stream, not of the instruction |
| the pitches in the block header (`vec2 Rs,Re,Rn,Rw,Rp0,Rp1,Rp2,Rp3`) | one word | eight register fields: a three-parcel form; unused fields still cost | `vskip` is free of patterns and a stream with no pitch costs nothing |
| the pitch as a pitch (not a gap) | no `sub` per stream | needs the row start of each stream: hidden state or another register | restart cleanliness |
| a hidden row counter (hardware keeps it) | no `Rn` | not saved at a context switch: a restart would have to repeat the row | the owner: the row counter must be architectural |
| restart at the row (hardware rolls pointers back to the row start) | no `Re` | repeats the strips of the row already done: wrong for in-place updates (blend) | clean restarts |
| a wrapper instruction `vrep Rn` before `vec` | no change to `vec` | does not say how the pointers advance | no pitch |
| accumulators across rows | GEMM tiles | the restart from entry would lose the tile | refused (3.3, item 7) |
| strips packed from several rows | fills the strip of a narrow tile | section 6.5 | analytic only: needs two cache accesses per strip |
| a hardware bounds operand | one precise check | section 5 | costed, not justified |

## 5. Security: bounds checks

**What the 2D block gives.** A tile is declared once: base (`Rs`), width (`Rw`), rows (`Rn`) and a pitch for each stream (the gap). So the whole footprint of a stream is known before the first strip: **one check of the first and the last row of the stream, instead of one at every row.** What the machine has: `chk2 r, rlo, rhi` (trap unless `rlo <= r < rhi`, signed; one instruction; vector 16 `check`, EPC the check) and `ct<cc> r, rb` (`docs/encoding-work/check-instructions.md`); both execute in sim64. **The idiom** (`k_sad.vec2d.chk.s`, `k_mblend.vec2d.chk.s`): per stream, with the bound `hi - w + 1` made once, `chk2` of the first row start, then the last row start `Rs + (h-1) x pitch` (`movq, dec, mul, add`) and `chk2` of it: 6 instructions per stream, **22 for the SAD (two streams), 41 for the four-stream mask blend**, whatever the tile. In the loop of 1D blocks the check is one `chk2` for each stream and row (the row end is already made for the block): 2 for each row for the SAD, 4 for the blend, plus the setup of the bounds (10 and 16). With two checks per stream a negative pitch (a bottom-up bitmap) is covered, because the rows between the first and the last lie between them.

**Measured** (sim64, strip 16, port 16, model 1, `tools/gates/2d-results/summary.md`; cycles added by the check):

| tile | SAD, loop of blocks | SAD, 2D | blend of 4 streams, loop | blend, 2D |
|---|---:|---:|---:|---:|
| 8 x 8 | +26 (25.5%) | +22 (37.3%) | +49 (33.3%) | +41 (45.6%) |
| 16 x 16 | +42 (22.1%) | +22 (22.2%) | +81 (28.6%) | +41 (25.3%) |
| 64 x 64 | +138 (9.3%) | +22 (2.0%) | +273 (10.4%) | +41 (1.9%) |
| 256 x 256 | +522 (2.9%) | +22 (0.1%) | +1041 (3.0%) | +41 (0.1%) |

Scalar instructions with the check (16 x 16): SAD 152 loop, 38 2D (unchecked 110 and 16); blend 220 and 54 (139 and 13). **So the per-tile check costs a constant (22 and 41 cycles) and the per-row check grows with the rows (setup 10 plus 2 a row for the SAD, 16 plus 4 a row for the blend): they are equal at about 6 rows, and from 8 rows the per-tile check is cheaper (8 x 8: +22 against +26 and +41 against +49 cycles).** In relative terms the check is 22 to 46% of a small tile in either form, because the unchecked 2D block is itself cheap there. The check is not free and the 2D block does not remove it.

**A hardware bounds operand** (not built): a per-stream limit register, `vlim Ra, Rlo, Rhi`, with the block faulting precisely (the check trap, before any access of the strip) when a strip's first or last byte is outside `[Rlo, Rhi)`. **What it buys:** a check that cannot be forgotten or skipped by a compiler; **overflow-safe by construction** (the comparison is of real addresses; the software idiom's `(h-1) x pitch` must be known not to wrap, true for 32-bit sizes in 64-bit arithmetic and an extra `mulh` and a compare for 64-bit ones); no instructions at all (22 and 41 become 0). **What it costs:** silicon, measured **3,999 NAND2 equivalents for four streams** (two 64-bit compares each), 1.4% of the family; **two more registers for each stream** (4 streams: 8 registers beside the pointers, gaps and the four of the header: 16 of 32 registers for a four-stream block), or a shared window for all streams (one pair) which only suits blocks whose streams share an allocation; and another decode-time table. **Decision: not built.** The software idiom costs a constant 22 to 41 cycles per tile, 2% at 64 x 64, 0.1% at 256 x 256, and works with the checks the compiler already emits (`.chk`, `__bug_table`); the hardware form costs 1.4% of the vector unit and the registers. What would change this: a security rule that no vector block may touch memory it was not given (a capability machine), or a compiler that cannot hoist the check; then `vlim` is the first thing to add and its silicon is here. The 2D block makes the software check cheaper to write and to prove (one place, the whole footprint); it does not make bounds checks unnecessary.

### 6.3 The owner's question: "if the scalar loop runs millions of times as the outside loop, is that ok?"

The loop of 1D blocks pays, per row, 6 scalar instructions and a `vend` (7 slots) against the 2D form's 1 (the row advance): the gain is `(7 + c·s) / (1 + c·s)` for `s` strips of a row each costing `c` cycles (c = 4 for the SAD: 3 vector instructions and the commit, memory 2). **It is ok when a row has many strips: the overhead is under 10% from 16 strips a row and under 5% from about 30 (480 bytes at strip 16, 960 at strip 32) [A, confirmed by the 256 x 256 runs: 1.09].** Measured, SAD, 16 rows, model 1, strip 16 (the gain of 2D over the loop; strips of 16 bytes a row in brackets): W = 8 (0.5): 1.92; 16 (1): 1.92; 32 (2): 1.56; 64 (4): 1.31; 128 (8): 1.17; 64 x 64 (4): 1.34; 256 x 256 (16): 1.09. For kernels with more vector work per strip the gain is smaller (blend, 16x16: 1.27; `put8h`, 8 taps: 1.10; 64 x 64: 1.07 and 1.03). **Graphics tiles (8 to 64 pixels wide, 1 to 4 strips a row) are in the region where the loop is 1.3 to 1.9 times slower than the 2D block** (SAD, average, blend of masks, threshold), 1.1 to 1.3 for the heavy kernels. In model 2 (latencies, vmemlat 4) the gain is smaller (SAD 16x16: 1.56) because the strips' latency is paid either way. Sensitivity (SAD 16 x 16, 2D/loop): row cost 0 / 1 / 2: 2.29 / 1.92 / 1.65 (model 1), 1.73 / 1.56 / 1.42 (model 2); vmemlat 2 / 4 / 8 (model 2): 1.69 / 1.56 / 1.40 (model 1 does not see the latency).

### 6.4 Does the 256-bit strip gain on a 16-wide tile? (the owner's suspicion: it is half empty)

**Confirmed, for byte kernels: no gain at all.** Cycles at strip 16 over cycles at strip 32 (port 16, model 1): `sad`, `avg`, `mblend`, `thresh` on 8-wide and 16-wide tiles: **1.00 in both forms**; 32-wide: 1.19 to 1.63; 64-wide: 1.27 to 1.70; 128-wide: 1.33 to 1.73 (the 2D form gains more than the loop form because the loop overhead is a larger share at the short strip). **Not for kernels that widen** (the strip counts the widest lane, so 16 pixels widened to 16-bit lanes fill 32 bytes): 16 x 16: `blend` gains 1.57 (loop) and 1.86 (2D), `gray` 1.53 and 1.80, `put8h` 1.76 and 1.91, `quant` 1.56 and 1.82; 8-wide, where bytes widen to 32-bit lanes: `put8h` 1.61 and 1.83, `quant` 1.39 and 1.69 (`blend` and `gray` at 8-wide: 1.00). Against no vectorisation (2D form, 16 x 16): strip 16 gives 27.1 (`sad`), 19.5, 15.2, 8.8 (`blend`), 17.2, 10.7, 19.6, 6.8 times; strip 32 the same for the byte kernels and 16.4, 32.8, 19.3, 12.4 times for `blend`, `put8h`, `gray`, `quant`; on 64 x 64 strip 32 gives 57.3 (`sad`), 34.1, 30.4, 18.2, 35.3, 22.5, 40.4, 14.1 times [M, model 1, hand 2D form against compiler-made scalar].

### 6.5 Row packing (analytic, not modelled)

A strip filled from several rows for rows narrower than the strip (two 16-byte rows in one 32-byte strip). **What it would need:** two cache accesses per strip for each stream (two rows are two lines, usually two cache lines and possibly two pages), an address generator that produces two addresses and a lane assembly (a 16-byte half from each), the stores in the same way, `vskip` gaps applied between the halves, and in the precise-fault rule, the first faulting access in element order spans two rows. **What it would give, SAD 16 x 16 at strip 32 (model 1, [A]):** the unpacked 2D form costs 3 (header) + 16 (rows) + 16 strips x 4 cycles = 83 vector cycles plus 16 scalar = 99; packed, 8 strips each needing two 16-byte reads on each of two streams (4 port cycles at 16 bytes a cycle, 5 with the commit): 3 + 16 + 8 x 5 = 59 + 16 = **75, 1.32 times faster than 99** (1.68 if the row advance overlapped the strips). It would make a 256-bit strip pay on 16-byte rows; it would not help a 128-bit strip. Not built: the gain is bounded by 1.3 to 1.7 on the narrowest tiles, the cost is a second address stream per strip in every implementation.

## 7. Why has no one done this? (what is read, measured and remembered)

* **Read:** they have, as 2D loads with a fixed small tile or a descriptor (section 1): AMX restarts at the row from `start_row` and bounds the work to 16 rows; the GPUs avoid faults by a bounds descriptor and on-chip destinations; the DSPs have 2D address generators and nested hardware loops; AltiVec `dst` shipped as a hint. General-purpose vector ISAs with page-faulting memory and no new state did not, and the sources point to state size (AMX 8 KB, SME's SVL squared), encoding space (RVV) and the absence of a compiler that nests (LLVM's outer-loop path is unfinished).
* **Measured here:** the reasons that bind a general machine do not bind this one: no new state (all in four ordinary registers and the pointers, which the context switch already saves); no restart problem (strip precise, the row advance committed with the strip; 117 cases); no extra translation cost beyond the loop of blocks (section 2a); the encoding is 16 patterns; silicon is 0.8 to 1.9% of the vector unit. What the 2D block is worth is the loop overhead only: 1.9 times on the smallest tiles, 1.1 to 1.3 on the heavy kernels, 1.09 on a 256-wide frame.
* **Remembered, not checked:** that Cray-class vector machines and the DSPs treated the nest as a compiler problem and strides as the tool [Mem]; that SIMD ISAs added 2D prefetch before 2D loads [R-AltiVec]; that the main reason for the lack of general 2D is that the compilers vectorise only the innermost loop, so that no hardware feature of the outer loop would be used (supported by [R-LLVM], not shown by a survey of compilers).
* **A fair answer to "why not":** the 2D block is a small gain (at most about 2 times, at the tile sizes of a codec, in the loop overhead) for a small price (16 patterns, 1% of the vector silicon); machines that did more paid more state. Its use is in hand-written kernels of fixed tile sizes (video, blending), where the alternative is unrolling the rows (code size, which the owner does not weigh).

## 8. Recommendation

Keep the form (`vec2`, `vskip`) as built. Use it in hand-written tile kernels (SAD, average, blend, filters on 8 x 8 to 64 x 64 tiles); do not take the compiler work until a kernel set shows the loop of blocks costing more than 10% (the measured crossing is about 16 strips a row). Do not build the hardware bounds operand or the row packing now; keep the software idiom (22 to 41 instructions a tile, a check of the first and last row) and the sums above. Re-open if the owner wants a 256-bit implementation to pay on 16-byte rows (row packing, 1.3 to 1.7 times on those tiles), or the compiler gets the outer-loop recogniser (section 2c).

## 9. What was not verified

Hardware: nothing here is a measurement of silicon or of a real memory system (no cache, no TLB model; the models count a strip's port cycles and latencies). The scalar baseline is compiler-made at one cycle an instruction. The row cost is an assumption (0, 1, 2 shown). The prior art of section 1 below the first six rows is mostly from search summaries and memory. QEMU executes the same shared executor as sim64 and the test passes there; no other implementation exists. `tools/encopt/addforms.py` writes a grammar with outdated boilerplate; the encodings are provisional.
