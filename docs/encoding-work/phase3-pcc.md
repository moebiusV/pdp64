Worktree <work>/pcc-enc, branch enc-prefix, 11 commits on top of d44d98a4 (none pushed; <work>/pcc and <repo> untouched; pdp64-enc only read, its as64/ld64/sim64 builds copied).

## 1. Targets and ABI (done)
* `ccom -m pdp64/r20|pdp64/16|pdp64/32` (same spelling as `as64 -m`).  pdp64/r20 is the default and its output is byte-identical to the old compiler on all 841 files (instruction bytes 1,083,870 reproduced exactly) and 516 tests.
* The register file is a build table (mip/mkext.c), so pdp64/32 is a second build of the same sources, `-DPDP64_REGS32` (MAXREGS 32, RSTATUS/ROVERLAP, rnames, COLORMAP limit 29 via NALLOC, prologue/epilogue save set, pushm/popm masks printed unsigned, peep.h masks 64 bits with r16-r23 clobbered by a call and r24-r31 read by ret).  A ccom refuses a target it was not built for.  `arch/pdp64/test/build-ccom.sh DIR` builds `DIR/ccom` (16 registers: r20 and pdp64/16) and `DIR/ccom32`.
* ABI split of r16-r31 as the draft: r16-r23 caller-saved, r24-r31 callee-saved (r24-r26 are in the 4-bit hot table).  Allocation prefers the hot registers (PICKCOLOR, `pdp64_pick`, `-m hot=N`).  Measured effect: at most 0.03% (r0-r3 and r8-r10 were already what the old order used first, and coalescing hints win).  Kept as default, honestly a wash.
* Driver: the pcc driver `cc/cc` does not build for pdp64 at all (no CPPMDADD), so every tool calls ccom.  I added mach_pdp64 to its `-O` table (ccomflgcheck: -xdmr on, -xssa off) and the project's usual selection is ccom's `-m`.  Edits the pdp64 repo needs (I could not touch it): tools/build-pcc.sh should build both variants (see build-ccom.sh: CFLAGS +`-DPDP64_REGS32` into a second directory, link as ccom32); tools/pdp64size.py `ccomflags('pdp64')` for the new targets is just `-m pdp64/16` (or /32): the defaults turn on all the flags; tools/pdp64test.sh and pdp64test-all.sh need `as64 -m MODE` (mine, in arch/pdp64/test, do).

## 2. Flags found, and optimizations
The ccom -x flags (cc/ccom/main.c): ssa, scp, ccp, tailcall, temps, deljumps, dce, inline, dmr, c2, noregvars, noframeless, llib, llall, abs, gnu89, gnu99, uchar.  There is NO flag named for Johnson ("sj"): his pcc is what is left with all of them off (`-xno-dmr -xno-temps -xno-deljumps -xno-inline -xno-dce`).
* On by default for the new targets (so the "driver" enables them): dmr (also gates the text peephole peep.h, where the cbCC fusing, the tail call `call;ret -> jmp`, dead-instruction and copy-propagation rewrites live), temps, deljumps (looprot, cross-jumping/tail merging), inline, dce.  `-xno-NAME` turns one off (new in main.c).  Ablation (bytes, pdp64/16, alone off): dmr +25.6%, temps +66.9%, deljumps +6.0%, inline +0.4%, dce +16.2%; all five off: 2,356,392 (+147%).
* Not enabled: `-xssa` is correct (all tests, all 841 files) but +0.44% bigger (957,568); `-xssa -xscp` fails 2 files (`bad xasm node type`) and is +0.51%.  `-xccp` and `-xtailcall` are parsed and never read by any pass (no effect).  c2, llib, llall, noframeless, abs are pdp11/amd64 options with no effect here.
* Broken, found and fixed for the new targets only: with `-xtemps`, `char c = -3; return (unsigned char)c;` returned -3 (local.c retyped a TEMP, a register, like memory).  The bug is in the baseline too; pdp64/r20 keeps it (its output must not change); test/c/avail_volatile.c finds it.
* Added (all new targets only; each switchable with `-m no-NAME`): fusion (below); a call reads only the argument registers it passes (`; args:N` written by zzzcode G from lastcall's count of the argument registers; the peephole's liveness took every call to read r0-r5); block-local value availability (redundant clr/movq #k/lea sym/loads, loads turned into register moves, a store forwarded to a following load of the same place; volatile functions excluded by a `; vol` note; labels nothing refers to do not end it); jump threading of a condition made into a value and tested again; pushm/popm understood by the liveness model (they were barriers: everything live before every epilogue); `movq a,b; add #k,b -> lea k(a),b`; arranging a register move next to its call; switch dispatch by halves (mygenswitch; cgram.y's switch is a chain of n compares).
* Static ablation, pdp64/16 (each alone off): avail +0.77%, arrange +0.31%, thread +0.06%, leafold +0.02%, fuse +4.16%; switch dispatch costs 0.27% static (no-switch is 950,800, default 953,370) but cuts lua from 225.1 M to 148.7 M instructions and 724.8 M to 425.3 M bytes executed.  Cumulative path: 1,016,238 (old compiler, assembled pdp64/16) -> 978,086 fusion -> 965,296 call args -> 955,682 avail/thread/popm -> 951,734 arrange/forwarding -> 950,800 lea/labels -> 953,370 switch.
* Not done (said in the doc): loop-invariant motion, strength reduction, live-range splitting, jump tables for dense switches (8 bytes a case), load CSE across blocks, store elimination.  The two biggest remaining costs are not the compiler's: external `call` (6 bytes, 14,853 in the corpus, 9%) and `lea sym` of a data symbol (6 bytes, 12,775, 7.8%) wait for linker relaxation in ld64 (the encoding has the 4-byte forms).

## 3. Fusion (done)
`pp_fuse` in peep.h, run last on each function: `pop r;ret -> popret r`, `popm #m;ret -> popmret #m` (m a mask of r8-r15 only: the field is m/256 in 8 bits, so r24-r31 saves cannot fuse), `movq a,b;call f -> movcall a,b,f`, `movq a,b;movq c,d -> mov2` (all four in r0 r1 r8 r2 sp r3 r9 r10).  A run of moves before a call is matched by dynamic programming (maximum matching, two bytes per pair).  Pairs are arranged: a register move earlier in the block that commutes with what follows is moved next to its call.
Counts over the corpus: pdp64/16 movcall 10,785, popmret 2,261, popret 2,601, mov2 4,045 = 19,692 pairs; static effect 993,044 -> 953,370 = 39,674 bytes = 4.16% (two bytes a pair; no-fuse measured, popmret 4,522 / popret 5,202 / mov2 5,472 / movcall 21,452 individually).  pdp64/32: 11,539 / 1,614 / 2,581 / 4,073; no-fuse costs +40,224 bytes (+4.07%).  Nothing fusable is left in the pdp64/16 output (no adjacent pop;ret, popm;ret or movq;call); 1,334 adjacent move pairs are not all in the 3-bit table.

## Not done / limits
* ld64 was used only for the six programs and the test programs, not on the corpus.  The pcc driver is not built for pdp64.  The pdp64 repo's tools were not edited (not allowed); what they need is listed above.
* hbnf/other implementations are not involved; sizes come from the real as64 (phase 1), executed counts from the phase-2 sim64.
* cbCC for a far target is expanded by as64 to cmp+bCC, which writes the codes; the peephole only forms a cbCC where the codes are dead after the branch, so this is safe; the 9,000-instruction limit on the wide cbCC (r20 heritage) is unchanged.
* No assembler-level check that popmret/movcall/mov2 forms assemble was needed beyond the corpus (all assemble); movcall to an external symbol is a 6-byte instruction as far as as64 goes.
