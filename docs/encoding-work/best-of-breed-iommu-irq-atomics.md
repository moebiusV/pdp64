# Best of breed for the IOMMU, the interrupt controller and the atomics: the baseline, our design against it, the holes, the amendments

Review for the owner, 2026-11-19. It applies errata 198 (R521) to three areas: (A) the IOMMU, DMA and the bus; (B) the interrupt controller and the timer; (C) the atomics and the memory model. It changes nothing; it proposes, and every proposal that would reverse a recorded decision is put as a question in section 6.

Plain words used throughout. A **core** is one processor. An **IOMMU** (input-output memory management unit) is the translator and guard between a device's memory accesses (DMA, direct memory access) and memory. A **device entry** is the IOMMU's per-device record. A **stage** is one table walk; two-stage translation walks a guest's table, then the hypervisor's. An **MSI** (message-signalled interrupt) is an interrupt that a device raises by writing a value to an address. **IPI** is an inter-processor interrupt. An **atomic** is a memory operation that no other core or device can see half done. **LL/SC** (load-linked, store-conditional) is the pair that takes a reservation on a piece of memory and writes only if nobody else wrote it meanwhile. **CAS** is compare-and-swap. **Forward progress** is the promise that a loop built from these eventually finishes. **ACS** (access control services) is the PCI Express feature that forces a switch to send device-to-device traffic up through the IOMMU.

### 1.2 The IOMMU

**RISC-V IOMMU (open specification, designed with virtualisation from the start).**

* One device identity, one table per identity: "A radix-tree data structure called device directory table (DDT) that is traversed using the device_id is used to locate the DC." The table has 1, 2 or 3 levels; a non-leaf entry is 8 bytes; "In base-format the DC is 32-bytes. In extended-format the DC is 64-bytes." (the device context, DC, is the per-device record; the extended form adds the MSI fields). Source 3.1, 3.1.2. From these sizes and 4 KiB pages a 16-bit identity needs two levels of 9 and 7 bits (my inference from the sizes, not a quotation).
* Two stages: a first stage the guest owns (device address to guest-physical) and a second stage the hypervisor owns, each selectable as Bare (off); 16-bit guest and 20-bit process context numbers (GSCID, PSCID), each of which "facilitates invalidation of cached address translations" per virtual machine or per address space (3, 2.4).
* A process directory table (PDT) selects a per-process address space for devices that tag requests with a process number (3.2). Optional.
* The mode register `ddtp`: Off (nothing allowed), Bare ("No translation or protection. All inbound memory accesses are passed through."), 1LVL, 2LVL, 3LVL; "All IOMMUs must support Off and Bare mode"; the reset value "must be either Off or Bare" and "is recommended to be Off" (6.5, 6.2).
* Guest-owned devices: "The hypervisor may provide a virtual IOMMU facility, through hardware emulation or by enlightening the guest OS" (2.2.3). The real tables stay the hypervisor's.
* MSIs of a guest-owned device: "An IOMMU must recognize certain incoming writes from such devices as MSIs and convert them as needed for the real machine." The extended device context holds an MSI page-table pointer, an address mask and an address pattern (3.3.3, 3.1.3.5, 3.1.3.6).
* The command queue, in memory, each command 16 bytes, four opcodes: IOTINVAL (page-table cache invalidation, by guest or address space or address), IOFENCE (the fence and completion command, optionally writing a data word to an address), IODIR (device or process directory cache invalidation) and ATS (PCI Express translation commands); an illegal command stops the queue until software clears the error (4.1).
* Ordering and in-flight requests: "The IOMMU fetches commands from the CQ in order but the IOMMU may execute the fetched commands out of order." and the fence only covers requests "already processed by the IOMMU"; for a device's requests not yet seen the text says software "must perform an interconnect-specific fence action" (4.1.2). `IODIR.INVAL_DDT` "guarantees that any previous stores made by a RISC-V hart to the DDT are observed before all subsequent implicit reads" (4.1.3). A change of `ddtp` to Off guarantees that in-flight transactions are "either be processed with the configurations applicable to the old value ... or be aborted" (6.5).
* The fault queue (called fault/event queue), in memory, "Each fault record is 32 bytes", and a per-device bit DTF that stops fault reports ("A hypervisor may set DTF to 1 to disable fault reporting when it has identified conditions that may lead to a flurry of errors"); a refused read gets an error completion, a refused posted write is discarded (4.2, 3.1.3.1, 8.3).
* The page-request queue, 16-byte records, for PCI Express page requests (4.3), and the ATS controls: "If EN_ATS is set to 1, IOMMU supports the following inbound transactions; otherwise they are treated as unsupported requests." The option T2GPA exists because "The T2GPA control enables a hypervisor to contain DMA from a device, even if the device misuses the ATS capability" (3.1.3.1).
* The register map (6.1) is a fixed table: `capabilities` at 0 (8 bytes), `fctl` 8, `ddtp` 16, `cqb` 24, `cqh` 32, `cqt` 36, `fqb` 40, `fqh` 48, `fqt` 52, then the page-request queue, control and status registers, performance counters, a translation-request debug interface, `icvec` and an MSI configuration table. "Features supported by the IOMMU may be discovered using the capabilities register" (6.3): version in bits 7:0, then one bit per feature (Sv39, Sv48, Sv57, the guest-stage forms, ATS, T2GPA, MSI forms, hardware A/D update, process-number widths, physical address size, QoS).
* Alignment with the processor: the IOMMU uses "Page based virtual-memory system as specified by the RISC-V Privileged specification ... to allow software flexibility to either use a common page table for the CPU MMU as well as the IOMMU or to use a separate page table" (2.4).
* QEMU: `hw/riscv/riscv-iommu.c` is 3,039 lines plus 383 (counters), 220 (PCI wrapper) and 262 (platform wrapper); it includes `riscv_hart.h` and `cpu_bits.h`, so it is tied to the RISC-V target.

**Arm SMMUv3 (D.a).**

* Stream table (indexed by a device's stream number), stream table entry (STE) and context descriptor (CD): "A Stream table entry (STE) contains stage 2 translation table base pointers, and also locates stage 1 configuration structures". Linear or two-level stream table (3.3.1).
* Queues: "All SMMU queues for both input to, and output from the SMMU are arranged as circular buffers in memory." One command queue, one event queue, optionally a page-request queue, indexes PROD and CONS with a wrap bit (3.5).
* Commands: configuration invalidation (CMD_CFGI_STE and others), TLB invalidation by stage, address space and virtual machine (VMID), ATS and PRI commands, CMD_SYNC: "Any operations made observable by the completion of the synchronization operation are observable before the interrupt or event is observable" (4.3, 4.4, 4.6.3).
* Default deny: for the global bypass register the text notes "An implementation can reset this field to 1, in order to implement a default deny policy on reset." (SMMU_GBPA.ABORT). A stream may also bypass by configuration (STE.Config == 0b100); a disabled SMMU can pass traffic (3.4).
* Virtualisation: "The SMMU does not provide programming interfaces for use directly by virtual machines." The hypervisor emulates a virtual SMMU; extra hardware interfaces for guests are implementation defined (3.8). Devices under guest control with stage 2 only need no guest interaction.
* Capabilities: the SMMU_IDR0 register has one bit or small field each for stage 1 and stage 2 support (S1P, S2P), ATS, PRI, MSI, hypervisor support (Hyp), 16-bit address-space numbers (ASID16), two-level stream table (ST_LEVEL), stall and terminate models, coherent access (COHACC), broadcast TLB maintenance (BTM) (register diagram, 6.3.1).
* Interrupts of devices are not in the SMMU: they go through the GIC's translation service (1.2 below).
* QEMU: `hw/arm/smmuv3.c` 2,290 lines, `hw/arm/smmu-common.c` 1,051.

**Intel VT-d (Rev 4.0).**

* Root table, then context table: "The root-table is 4-KByte in size and contains 256 root-entries to cover the PCI bus number space (0-255)." Each context table has 256 entries, one per device and function; the scalable mode splits the context table in two halves of 128 entries and adds a PASID directory and PASID tables for per-process address spaces (3.4, 3.4.3, chapter 9).
* An abort mode: "hardware will abort all DMA operations without the need to set up a root-table with each entry marked as not-present." (3.4.4, Abort DMA Mode, the Translation Table Mode field set to 11b).
* Fault recording: "The primary method for logging non-recoverable faults is through Fault Recording Registers." (7.2.1; a register array rather than a ring in memory).
* Invalidation: a register interface and a queued invalidation interface (6.5.2) with wait descriptors for completion.
* Interrupts: "The interrupt-remapping architecture enables system software to control and censor external interrupt requests generated by all sources". "Interrupt requests appear to the Root-Complex as upstream DWORD sized memory write requests to the interrupt address range FEEx_xxxxh." (5.1). Posting: "Interrupt-posting enables a remappable format interrupt request to be posted (recorded) in a coherent main memory resident data-structure" (5.2).
* QEMU: `hw/i386/intel_iommu.c` 5,727 lines.

**AMD-Vi.** Not read from the specification. QEMU's model (`hw/i386/amd_iommu.h`) shows a device table of 32-byte entries (`AMDVI_DEVTAB_ENTRY_SIZE`), 16-byte commands, 16-byte events, a page-request log, and the commands COMPLETION_WAIT, INVAL_DEVTAB_ENTRY, INVAL_IOMMU_PAGES, INVAL_IOTLB_PAGES, INVAL_INTR_TABLE and INVAL_ALL. That is the same family: a table, a command queue, an event log, a wait command.

**What the four have in common, and so what "best of breed" means here.** (1) A per-device record found by the device identity. (2) Two stages, guest then hypervisor, and a hypervisor-emulated unit for the guest. (3) Command queue, fault or event queue, both in memory, with a completion command that writes to memory. (4) Cached translations that are only discarded by a command, so a missing invalidate is a bug the hardware does not hide. (5) A separate table or a remapping step for interrupts. (6) A capability register. (7) A mode that blocks or aborts all DMA before the table is set up (RISC-V Off, Arm GBPA.ABORT, Intel TTM = 11b). RISC-V and Arm keep a bypass or pass-through mode (Intel and AMD: not checked); ours is the one that does not.

### 1.3 The interrupt controller

**Arm GICv3 and GICv4 (IHI 0069G).** A distributor routes shared interrupts; each core has a redistributor and a CPU interface read and written by system registers (ICC_*), so acknowledging an interrupt is a read of a register (ICC_IAR1_EL1). "Priority values are an 8-bit unsigned binary number" (4.8) with at least 16 levels. Message interrupts are LPIs: "Locality-specific Peripheral Interrupts (LPIs) are edge-triggered message-based interrupts" with configuration and pending state held "in tables in memory" ("at least 8192 LPIs are supported", 5.1). The interrupt translation service (ITS) turns a device identity and an event number into an LPI through tables (5.2, 5.3). Software-generated interrupts are the IPIs: "SGIs are typically used for inter-processor communication, and are generated by a write to an SGI register in the GIC." (4.4). Virtualisation: hypervisor-written list registers: "Each entry in the list corresponds to either a pending or an active interrupt" with the virtual interrupt number, state and virtual priority; the guest has its own virtual priority mask, acknowledge and priority drop (6.2); GICv4 adds direct injection of virtual LPIs (7.2, ITS mandatory). QEMU: `hw/intc/arm_gicv3_its.c` 2,037 lines, `arm_gicv3_cpuif.c` 3,204.

**RISC-V AIA (2025-03-12).** The incoming MSI controller (IMSIC) gives each core an **interrupt file** per privilege level: "the hart's IMSIC contains a separate interrupt file", and extra **guest interrupt files** for virtual machines (3.1). The MSI is a 32-bit write to a register in the file's page, and "The MSI write data is simply the identity number of the interrupt to be made pending in that interrupt file" (3.2). "Within a single interrupt file, interrupt priorities are determined directly from interrupt identity numbers." (3.3, lower number higher priority). A threshold register masks identities from a number up. Taking an interrupt is a read-and-claim of a CSR: "i=read CSR mtopei or stopei, and write simultaneously to claim the interrupt" (3.10). The IPI is the same message: "an IPI can be sent to a hart by writing to the destination hart's IMSIC, the same as a regular message-signaled interrupt (MSI)" (7). The APLIC converts wired interrupts into MSIs (1.1). With the IOMMU: "maximize the opportunities and ability for a guest operating system running in a virtual machine to have direct control of devices" (1.1), by redirecting guest MSIs to guest interrupt files (3.2, chapter 8). Two things the AIA states it does *not* define: "automatic preemption (nesting) of interrupts at a hart, based on priority" and a separate trap entry for each interrupt (1.1). So the threshold is the only priority control and nesting is software's job. Hypervisor CSRs `hvien`, `hvictl`, `hviprio1/2` and `hvip` inject virtual interrupts (2.3). QEMU: `hw/intc/riscv_imsic.c` 538, `riscv_aplic.c` 1,158.

**x86 (SDM, VT-d).** Vectors are 8-bit values and the priority is part of the number: "Each interrupt vector is an 8-bit value. The interrupt-priority class is the value of bits 7:4 of the interrupt vector." Vectors 0 to 15 are never delivered and 0 to 31 are reserved for the architecture (SDM Vol. 3A, local APIC, interrupt priority); the task-priority register blocks classes (CR8: "all interrupts in this and lower priority classes are blocked"). An MSI is a write to the address range FEExxxxx (VT-d 5.1); interrupt remapping puts a table between the write and the target; posting records the interrupt in a memory descriptor and notifies the core if it runs a guest (VT-d 5.2). IPIs are writes to the local APIC's command register (SDM; unverified text, not quoted). QEMU: `hw/intc/apic.c` 1,193, `ioapic.c` 518.

**What the three have in common.** (1) A device interrupt is a memory write whose address selects the target core and whose data selects the interrupt. (2) The pending and enable state is per core, in the controller. (3) Priority is either part of the number (x86, AIA) or a field per source (GIC). (4) The IPI is the same kind of write. (5) A remapping or translation table sits between a device's write and the target (Intel interrupt remapping, GIC ITS, RISC-V IOMMU MSI page tables), so a hostile or guest-owned device cannot raise any interrupt it likes. (6) A wired source is converted to a message (APLIC, the GIC distributor, the I/O APIC). (7) Virtual interrupts have hardware help.

**The timer.** RISC-V's base timer is memory-mapped, `mtime` and `mtimecmp`; the Sstc extension (in the ISA manual read) gives "supervisor mode with its own CSR-based timer interrupt facility" (`stimecmp`) and the hypervisor form `vstimecmp`, "thus eliminating the large overheads for emulating S/HS-mode timers". x86's local APIC timer has a deadline mode: "TSC-deadline mode allows software to use the local APIC timer to signal an interrupt at an absolute time." (SDM, Vol. 3A, local APIC timer). Arm's generic timer: **unverified** (not read).

### 1.4 The atomics and the memory model

**RISC-V A, as ratified (ISA manual 20261119).**

* AMOs (Zaamo): three registers, destination, source, address; `rd = old, mem = op(old, rs2)`; operations swap, add, and, or, xor, signed and unsigned max and min; doubleword and word. "AMOs can either operate on doublewords (RV64 only) or words in memory." Alignment: "an address-misaligned exception or an access-fault exception will be generated" unless a platform's misaligned-atomicity granule says otherwise (5.6). Each has two ordering bits, acquire and release (`aq`, `rl`).
* Zabha adds byte and halfword AMOs because emulating them by LR/SC "introduces issues related to scalability and fairness" (5.8).
* Zacas: compare-and-swap word, doubleword, quadword; the expected value is in `rd` and the old value replaces it (`X(rd) = temp`), the new value in `rs2`, the address in `rs1` (5.9).
* LR/SC (Zalrsc): the reservation set may be larger than the word; an SC may succeed only if no other store or device write to it was seen; "SC.W ... writes zero to rd" on success and "a nonzero value" on failure. "The platform should provide a means to determine the size and shape of the reservation set." Device writes: "writes from devices other than RISC-V harts are only required to invalidate reservations when they overlap the bytes accessed by the LR". Reservation at a context switch: software, "A store-conditional instruction to a scratch word of memory should be used to forcibly invalidate any existing load reservation ... during a preemptive context switch" (5.2).
* Forward progress is stated by a syntactic rule, the **constrained LR/SC loop** (at most 16 instructions placed sequentially; between LR and SC only base-integer instructions, no loads, stores, backward jumps or taken backward branches, FENCE or SYSTEM; the same address and size; the region has the eventuality property), and then: "the execution environment must guarantee that one of the following events eventually occurs": a successful SC to the set, another hart's or a device's store to the set, the loop exits, "H traps". "Unconstrained LR/SC sequences might succeed on some attempts on some implementations, but might never succeed on other implementations." The rationale: "The main disadvantage of LR/SC over CAS is livelock, which we avoid, under certain circumstances, with an architected guarantee of eventual forward progress" (5.2.1). Za128rs bounds the reservation set at 128 bytes (5.3).
* Atomics against memory type: the platform attributes say which atomics a region supports: "Main memory and I/O regions may only support a subset or none of the processor-supported atomic operations" (AMONone, AMOSwap, AMOLogical, AMOArithmetic, then CAS levels) and a reservability level (RsrvNone, RsrvNonEventual, RsrvEventual) (Volume II 3.6.3).
* Zawrs: a wait on a reservation: "the hart to temporarily stall execution in a low-power state until a store occurs to the reservation set or an interrupt is observed" (5.5).
* Memory model: RVWMO (weak, with explicit annotations); Ztso: "All AMOs behave as if they have both acquire-RCsc and release-RCsc annotations", meant for porting from x86 (3.2).
* QEMU (`target/riscv/tcg/cpu_helper.c`, the trap-entry function, lines 860 to 869): the reservation is cleared at every trap, with the comment that version 2.2 of the ISA "explicitly requires this behaviour, while later revisions say that the kernel 'should' use an SC instruction ... As a result, do both." `target/riscv/tcg/insn_trans/trans_rva.c.inc` line 37 makes every AMO and LR/SC require natural alignment (`MO_ALIGN`).

**Arm.** The memory model: "Armv8-A implements a weakly-ordered memory architecture" and "The Armv8-A memory model is described as Other-multi-copy atomic" (Learn the architecture - Memory Systems, Ordering, and Barriers). The large-system-extension atomics are in QEMU's decoder (`target/arm/tcg/a64.decode`): `CAS`, `CASP` (pair), `LDADD`, `LDCLR` (and-not), `LDEOR`, `LDSET`, `LDSMAX` and the rest, `SWP`, each with a 2-bit size field and acquire and release bits (`@atomic sz a r`). QEMU's model clears the exclusive monitor on exception return (`target/arm/tcg/helper-a64.c` line 634, `arm_clear_exclusive`) and has a `CLREX` instruction. The Arm text on forward progress, the exclusives reservation granule and alignment: **unverified** (the Architecture Reference Manual was not read).

**x86.** "Locked operations are atomic with respect to all other memory operations and all externally visible events." The prefix works on almost any read-modify-write, on any alignment ("The integrity of a bus lock is not affected by the alignment of the memory field", though aligned is recommended); a locked instruction is "guaranteed to lock only the area of memory defined by the destination operand"; locked instructions have a total order. The model is total store order: "Reads may be reordered with older writes to different locations but not with older writes to the same location." (SDM Vol. 3A, chapter 11, multiple-processor management).

**The interaction of atomics with devices.** RISC-V names AMOs in the IOMMU's fault causes ("Write/AMO access fault", 4.2) so a device atomic is a write to the IOMMU; and writes by devices clear reservations only on byte overlap. PCI Express atomic requests: **unverified** (the specification was not read; the appendix J.7.4 text says only fetch-and-add, swap and compare-and-swap exist on the bus, which I have not re-checked).

## 2. Our design against the baseline

Citations: "m" is the manual statement, "e" errata, "J" appendix J, files as named. "Deviation justified by" is my reading; "none" means I found no principle that justifies it.

### 2.1 Area A: the IOMMU, DMA and the bus

| Design point | What we do | What the baseline does | Deviation, and what justifies it |
|---|---|---|---|
| Identity | 16-bit requester identity, one space (m 2.11.1; e 187) | RISC-V up to 24 bits; Arm stream number; Intel bus-device-function | none needed: PCI Express's own identity; the segment is not modelled (one root complex) |
| Device table shape | directory of 512 x 8 bytes, leaf page of 128 x 32 bytes; mode: blocked, one level, two levels (m 2.11.1; `qemu/hw-pdp64/iommu.c`) | RISC-V base format: 8-byte non-leaf entries, 32-byte device context, 1 to 3 levels (3.1) | none: identical to the RISC-V two-level directory for a 16-bit identity (inference in 1.2) |
| Reset and "off" | blocked at reset (m 2.11.1) | RISC-V Off "recommended" at reset; Arm may reset to abort ("default deny"); Intel abort mode | none: this is the baseline's recommended form; P9 |
| Bypass | no bypass mode at all (m 2.11.3, e 187) | RISC-V requires the unit to support Bare; Arm and Intel have pass-through | deviation, justified by P1 and P9: "the device sees physical addresses" is a one-leaf 1 GB table instead |
| Device entry | 32 bytes: V, MUTE, STAGES, LEVELS_A, LEVELS_B, DOMAIN, GUEST, two roots, a reserved word (`iommu.c:410-449`) | RISC-V base DC: translation control (V, ATS enables, DTF...), second-stage root and mode, translation attributes (process context number), first-stage or process-directory pointer | field by field in 2.3 below |
| Reserved bits | any set reserved bit refuses the device (`iommu.c:419`) | RISC-V: a valid device context with any reserved bit set is "misconfigured" and reported as cause 259 (3.1.4) | none: the same rule |
| Process or per-address-space tables | none | RISC-V PDT, Intel PASID tables, Arm substream | deviation, justified by P3 and P7: needs ATS and page requests to be useful, which we refuse |
| Two-stage translation | level A (guest) then level B (hypervisor), every level-A table pointer sent through level B; the real table is the hypervisor's; the guest sees a trapped virtual unit (m 2.11.2) | RISC-V 2.2.3 and Arm 3.8: the same split, hypervisor-emulated virtual unit | none: this is the baseline |

So the custom design is already a subset of the RISC-V IOMMU in shape. The differences are three decisions of ours (no bypass, no ATS, no process contexts), a thinner capabilities register, a different register map, a fixed-value sync, and the missing interrupt part.

### 2.4 What a wholesale adoption of the RISC-V IOMMU would change

**What it would save.** (1) The specification: a ratified text of about 100 pages in place of the eleven statements of 2.11 and the 315-line proposals document; the manual could cite it and list deviations. (2) Verification: a differential test against QEMU's own RISC-V IOMMU model (3,039 lines), which already implements the commands, queues, two stages, ATS and MSI translation; the two units could be driven by the same test tables. (3) Software: an existing driver model (a Linux driver for the RISC-V IOMMU is believed to exist; **unverified** here); for OpenBSD none is known to me (**unverified**), so the saving there is a spec to port from, not a driver. (4) The interrupt part comes with it: the MSI page tables, which already solve H2, but only together with the AIA interrupt files (section 1.3).

**What it would change.** (1) Bare mode: "All IOMMUs must support Off and Bare mode" (6.5), against our decided "no bypass" (e 187 decision 3). A unit can reject a write of Bare (the field is WARL, write-any-read-legal), but then it is not strictly conformant. (2) The page-table entry: the RISC-V IOMMU uses the RISC-V entry; ours keeps the processor's entry "in place" (page number at bit 12, memory type at bits 8 and 9, m 6.7.1), RISC-V's has the page number at bit 10 and two software bits at 8 and 9; the first eight bits (V, R, W, X, U, G, A, D) agree (ISA manual, Sv32 entry figure and the Sv39 text, "Bits 9-0 have the same meaning as for Sv32"). Adopting wholesale would either change the processor's entry (a decision of the MMU, e 85 "bits 40 to 63 free" and m 6.7.1) or leave the IOMMU with a second format. (3) The register map, the command encodings and the queue discipline replace ours (grammar part `51-iommu-v1.hbnf`, `iommu.c`, seven tests, manual 2.11). (4) The tags and sizes: 24-bit device identity, 20-bit process number; ours decided 16-bit. (5) The model: QEMU's RISC-V IOMMU is tied to the RISC-V target headers (`riscv_hart.h`, `cpu_bits.h`); using it for pdp64 means factoring or copying.

**What in it contradicts our principles.** Bare mode (P1, P9). Optional process contexts, ATS, page requests, hardware A/D update, performance counters and QoS identifiers are features we would leave at capability 0 (P3, P7); that is allowed, so it is not a contradiction, but the text and the model carry them. The AIA coupling of the MSI part (the guest-physical address of a guest interrupt file as the MSI target) assumes one page per file, which fits the interrupt-file design of 4.5 but not a vector-table controller that identifies the vector by data alone. Nothing in the RISC-V IOMMU contradicts sequential consistency or the hypervisor decisions.

**Conclusion of 2.4.** Wholesale adoption is close to free in structure and costs three recorded decisions (no bypass, the 16-bit identity, the page-table entry); an adoption that keeps those three as listed deviations is the bold alternative B1 of section 5. The amendment path of 4.1 gets most of the saving without reversing anything but the register map.

## 3. The holes found after the fact

Cause means the place in the design where the hole came from; "closed by construction" says how a baseline design makes it impossible rather than detected. Sources: the seL4 review (`docs/encoding-work/sel4-fit.md`, rows 5, 6, 16, 18 and R1, R2), implementation status, and my own reading. H2, H8, H9, H10 to H12, H16 and H18 are new here.

| # | Hole | Cause in the design | How a baseline closes it by construction |
|---|---|---|---|
| H1 | **No interrupt-controller programming model** (seL4 review R1; J.6.3). MSI-X is decided as the device interrupt, but nothing receives the write; the model has 32 wired lines to the core. | MSI-X was chosen at the device edge (e 95) and the processor edge was left open; the old slot-derived vectors were retired first (e 29, 49, 75) | every baseline defines the receiving page or register: an AIA interrupt file (a write sets a pending bit, one read claims), a GIC redistributor with LPI tables, a local APIC; per-core pending and enable state is part of the architecture |
| H2 | **A device assigned to a guest can raise any interrupt.** To let the device interrupt at all, the unit must map the interrupt controller's page for it; the data of the write then names any vector the file accepts, including the timer, the IPI and the unit's own. | H5 | **The IOMMU guard and in-flight invalidation are untested**, and untestable in the model: the executor is synchronous, "no request of a device is ever in flight while a command runs" (`iommu.c:25-30`). | H6 | **ATS is refused (m 2.11.9) with no way for software to see it.** The model's translated-request path (`iommu.c:572-575`) has no test and no capability bit names it. | the refusal is a rule of the unit, not a capability | RISC-V per-device EN_ATS and a capability bit; "otherwise they are treated as unsupported requests"; the refusal is discoverable and a later version adds the feature by capability |

Nothing states that the unit sees the stores. | the unit was specified as a device, and 2.5.2 applies to its buffers, not to its tables | RISC-V: the invalidate command is the point of visibility: IODIR.INVAL_DDT "guarantees that any previous stores made by a RISC-V hart to the DDT are observed before all subsequent implicit reads" |

| H15 | **No `TOP` or which interrupt is pending** that a kernel can read at priority 7 (seL4 gap, row 5). | the entry sets priority 7 and delivers a vector; there is no polling interface | AIA `*topei`; GIC `ICC_HPPIR`; x86 reads the pending-register arrays |
| H16 | **The DMA coherence rule is a convention.** Nothing stops a kernel mapping a DMA buffer cached; the unit's leaf must have memory type 0 ("DMA goes around the cache"), but cannot know the processor's mapping. | cheapness (P4): no snooping | x86 DMA is coherent; RISC-V's capability bit lets a system say whether the IOMMU path is coherent; Intel has snoop control |
| H17 | **Discovery is provisional**: the memory map of ECAM, windows, the unit, the timer is "one place" in the grammar and J.2.1 is open. | e 97 retired the bit-39 rule before its replacement | QEMU's Arm and RISC-V machines describe these in a device tree; a boot-information block would play that part |
| H18 | **A device atomic (PCI Express atomic request) through the unit** has no stated permission rule. | the unit checks R for reads and W for writes; an atomic is both | RISC-V names the cause "Write/AMO": an atomic needs write permission (and, as our W needs R, read) |

## 4. The proposals: amendments that close each by construction

For each: the change, the principle, what it costs, what exists now that would change, and whether it reverses a record. "Estimate" marks my labelled guesses; nothing here is measured.

### 4.1 The IOMMU

**A1. Take the RISC-V IOMMU's register map, queue discipline, command names and capability bits for everything we have in common, and keep our three deviations as a written list** (no Bare, no ATS or process contexts in version 1, the processor's leaf entry). Principle P5, P6, P12. Change: the grammar part `spec/grammars.d/51-iommu-v1.hbnf` (registers, bits, command encodings), `qemu/hw-pdp64/iommu.c` (the register decode `:800-903`, the commands `:738-766`, the queue pointers), the seven tests (`tests/qemu/iommu-*.S`, `pcie-dmatest.S`), the constants page of the manual, and 2.11.10, 2.11.3 to 2.11.7 reworded as deltas against the cited text. Cost: no new hardware and no new instruction; the unit gets simpler to state and a little bigger (a capabilities register of about 40 bits, a version field, IOFENCE data). Effort (estimate): a few days of work in the model and tests, a rewrite of 2.11. Verification gain: a differential run against QEMU's RISC-V IOMMU on the shared parts. **Reverses:** the register layout of e 187 decisions 2, 3 and 11 (accepted), though not their substance; and e 194's grammar part. Put as question 1.

**A2. Interrupt filtering by construction: define word 3 of the device entry as a pointer to a per-device interrupt table** (H2). Entry per MSI-X vector index (a PCI Express function has up to 2,048, m 2.6), 8 bytes: valid, target core, vector, plus level when the level is not derived (see 4.2). The device's MSI-X write carries the index in its data; the unit looks up the entry, forwards the write to the controller as the controller's own message, and refuses a write whose index has no valid entry. One new command (invalidate interrupt table, as AMD-Vi's INVAL_INTR_TABLE in QEMU's model) and a new fault cause. Principle P1, P5, P8. Cost: a table read per interrupt write (cached by the unit), a state of the entry cache; qualitatively small next to the 3-level walk already there; a broken unit silences interrupts (a dependency J.6.3 already noted). Exists now: the reserved word (`iommu.c:419-425` requires it zero), the command and fault sets, tests to add (a device with no entry raises nothing; an entry retargeted by an atomic store; invalidation). Does not reverse a record; it fills a reserved word and settles J.6.3 option 2, which the assistant had leaned to as the end state. Question 2.

**A3. A capability bit for each optional feature, set to 0 where refused: ATS and page requests, process contexts, interrupt remapping (1 after A2), coherent DMA.** Principle P5, P12; closes H6 and part of H16. Cost: zero hardware, a few bits. Exists: `caps_value` (`iommu.c:792`). No reversal.

**A4. State the invalidation guarantee as a point in time, and make it testable.** "After `invalidate device` and `sync` complete, every request of that device that the unit accepted before the command was completed under the old tables or refused; every request accepted after uses the new tables; for requests still in the device or on the link, the bus's ordering rules apply and the kernel orders them first as RISC-V requires" (4.1.2). Keep the guard for guest invalidation. Principle P1, P5. Cost: hardware counts requests the unit has accepted and not completed (one counter per unit), qualitatively small; the model needs a two-phase request, in `qemu/hw-pdp64/dmatest.c` rather than the QEMU generic DMA helpers, which are synchronous (`iommu.c:25-30`). Reverses: not a record, but it rewrites m 2.11.7's third sentence (a decided statement) to the weaker precise one. Question 3.

**A5. Every invalidate command is also the point of visibility of earlier table stores** (H8), after RISC-V `IODIR.INVAL_DDT`; and name `FENCE` before the command. Principle P1. Cost: none in hardware beyond a flush of the unit's own caches (which a unit that reads RAM already needs). Changes: m 2.11.7 gains a sentence. No reversal.

**A6. The group rule becomes detection plus refusal** (H7): at enumeration the kernel reads each downstream port's ACS capability; a function behind a port that cannot redirect peer-to-peer requests joins its group, as now; a function behind a port that has the capability with redirection on is assigned alone. Principle P1, P5. Cost: nothing in hardware; an enumeration step (m 2.4); the rule 2.11.5 gets a precondition. **Partly reverses** m 2.11.5, which says peer-to-peer is invisible and that such devices form a group; the group stays as the fallback. I did not read the PCI Express text for ACS, so the bit names are **unverified**; the idea is verified in the RISC-V text. Question 4.

**A7. A device atomic through the unit needs W (and so R)** (H18), logged with a cause "atomic"; and a coherent-DMA capability bit that, when set, lets the leaf's memory type allow cached buffers (H16). Principle P1. No reversal; the second half is optional and costs nothing until implemented.

### 4.2 The interrupt controller and the timer

**B1. A per-core interrupt file, as J.6.3 option 1, with the AIA's two best ideas and none of its priority rule** (H1, H15). One 4 KB page per core at `base + 4096 x core`. A 32-bit write of a vector number to the set register makes that vector pending in that core's file (the MSI, the IPI, the converter's output are all this write). Pending and enable bits for vectors 32 to 255; the core takes the highest pending, enabled vector whose level exceeds `PRI`, clears its pending bit at delivery and enters through the vector table as today (`ECAUSE` = the vector); a read-only `TOP` register returns the highest pending enabled vector (readable at priority 7, the seL4 need), with no side effect. A wired-to-message converter for the timer, console and the unit's own line (the APLIC's role). Principle P5 (AIA's interrupt file and the IPI as the same write), P4 (no claim read, `SPL` stays an instruction), P6 (MSI-X has a receiver). Cost: about 1,300 bits of state per core by the multiprocessor record quoted in J.6.3, a few hundred lookup tables or a small RAM per core on an FPGA (that record's estimate, not mine); no instruction; a manual section (5.9, 7.10). Exists: the 32 wired lines (`cpu.c:112`), `pdp64_irq_deliverable`, `pdp64_cpu_set_irq`, the vector and level rules, the timer and console wiring (`virt.c`), the hypervisor's `VIRQ` path. Tests to add: a write sets pending on the right core; mask and level; the IPI; `TOP` at priority 7. Reverses nothing: m 6.3.7 and 6.13.4 stay. Question 5.

**B2. Derive the level from the vector number** (the x86 rule; the AIA derives priority from the identity). Level = vector divided by 32, for vectors 32 to 255, giving levels 1 to 7 exactly, and the file needs no per-vector level register (about 670 bits less state: my arithmetic, 224 vectors x 3 bits). It closes by construction the mismatch of a vector and its level, and it makes the hypervisor's seven virtual lines the same seven groups. Cost: the present fixed assignments (timer vector 32 at level 6, console 33 and 34 at level 4, PCIe pins 35 to 38 at level 5, the unit 39 at level 5; the rules `vector` and `irq-level` of the grammar part `50-system-v1.hbnf`) are renumbered so that vector and level agree; tests that name them (`tests/qemu/timer.S`, `con-*.S`, `hv-timer.S`, the PCIe tests) change. m 6.3.7's "the timer is at level 6 and the console at level 4" stays true. **Reverses** no record but fixes what J.6.3 option 1 left as a 3-bit level for each vector; and moves wiring decided in errata 194 (the four pins go to vectors 35 to 38 at level 5). Question 6.

**B3. State how a guest's interrupt arrives: unchanged.** The physical interrupt always exits (e 186 decision 1), the hypervisor sets a `VIRQ` line, one line for each level (e 195). Record the consequence H13 in 6.14.5: two virtual vectors at one level are delivered one after the other, and a multi-queue assigned device raises one virtual vector per level at a time. Principle P4, P8. No cost, no reversal. Reopen if the OpenBSD guest needs more.

**B4. Make the timer per core, with the shape of the virtual timer page** (H14; J.5.1). One core-local timer page with counter, compare and control, the same three registers; the virtual page of e 195 is the second instance (a counter that is the real counter minus `VTOFF`). No `RDTIME`: that keeps m 6.14.2's rule that no unprivileged instruction reads a clock (decision 14 of e 186). Principle P5 (Sstc and x86 per-core compare), P3 (one timer shape), P8. Cost: a per-core compare and comparator; the counter is shared. Exists: `qemu/hw-pdp64/timer.c`, `vtimer.c`. Changes: the timer's address becomes per core. This settles J.5.1's timer half in favour of its option 2's per-core compare without the instruction; the console and entropy halves stay open. Question 7.

### 4.3 The atomics

**C1. Operand layout from the baseline: three register fields for every atomic; `CAS` takes the expected value in `rd` and returns the old value in `rd`.** `XADD Rd, Rs, (Ra)`: old value to `Rd`, `Rs` added, address in `Ra`; `CAS Rd, Rs, (Ra)`; `SC Rd, Rs, (Ra)` with `Rd` = 0 on success and nonzero on failure (RISC-V's meaning, verified). The retry loop of a compare-and-swap uses the returned old value as the next expected value, so overwriting `Rd` costs nothing in the usual loop (the C11 call writes the observed value into its expected-value argument on failure; **general knowledge, unverified here**). It removes the four-register leaf of J.9.3 option 1 (six bytes). Principle P5, P4 (shorter code, one leaf shape), P3. Changes: grammar leaves in `30-mn-core.hbnf` (`atom` words), `as64`, `sim64`, QEMU decode, the executor (22 `H_UNIMPL` words), LLVM name table, the manual 9.13 entries, J.7.3 and J.9.3. **Departs from** the leaning of J.9.3 (the assistant's, not a decision) and from the grammar's present assumption (e 87 assumption 4). Question 8.

**C2. Size: 4 and 8 bytes for every atomic (the width in the sub-opcode as the baseline does), no byte or halfword atomic in version 1.** Zabha exists because emulating subword atomics by LR/SC is unfair on large machines; for four to sixteen cores the emulation by `CAS` is acceptable. Principle P3, P7. Changes: m 9.13.2 extended to all atomics. Question 9 (with C1).

**C3. Naturally aligned or a precise alignment fault, for every atomic and `LL`/`SC`** (H11). Principle P1; matches RISC-V and QEMU's RISC-V decoder; differs from x86, which allows split locks. Changes: m 7.4 gains a statement; the executor checks. No reversal.

**C4. Define the constrained `LL`/`SC` loop as RISC-V does** (H12): at most 16 instructions placed sequentially; between `LL` and `SC` only register instructions, no loads or stores, no backward branches; the same address and size; on memory of the eventual class (C5). The guarantee: one of four events eventually occurs. Outside the definition, no promise. Reservation set 8 to 128 bytes, discoverable (J.7.5 option 3; Za128rs). Principle P1, P5. Cost: a manual statement, the compiler's and the kernel's loops obey it, and a litmus test. Replaces the prose of m 7.4.2.

**C5. Atomics by memory type, as the RISC-V PMAs do** (H10, H9). All atomics and reservations are defined on normal cached pages; on normal uncached and device pages an atomic or `LL`/`SC` raises a precise access fault (J.7.4 options 1 and 4 together); a device atomic is forwarded only where a function advertises it (J.7.4 option 3), as an extension. This also removes H9: the pages that devices write (DMA buffers, uncached by 2.5.2) are the pages where no reservation can exist, so a device write never has to clear one; m 7.4.4 and 2.10.2 are restated: a write by a device to a reserved granule clears it where the path is coherent. Principle P1, P7. Cost: a check at the memory-type lookup the MMU already does; no hardware beyond that. **Reverses** the plain reading of m 2.8.1 ("atomics that can reach device memory", decided, D) and m 2.10.2 and 7.4.4 (D). Question 10.

**C6. Keep sequential consistency and the `_DB` variants; add the litmus tests and the `WFE`-on-reservation wake of J.7.1 option 2.** The comparison: RVWMO, Ztso and Arm are weaker (1.4); a weak model gives a core freedom to reorder and gives the kernel and compiler barriers to place; the owner's principle P1 ranks errors that cannot arise first, and m 7.13.1 says no weak ordering. The one cost of SC is replay on a speculative core (m 7.7.3), which the first implementations do not have. Principle P1, P10. No reversal.

**C7. Order of work, so that every decided rule gets a test.** Implement `LL`/`SC` and the 20 read-modify-write words (C1 to C5), then the reservation clear at exception entry and world switch (H4) with a test (interrupt between `LL` and `SC` fails the `SC`), then the litmus tests of J.9.11 (store buffering, message passing, load buffering, IRIW), then the first lock in `tests/qemu`. Nothing in the architecture changes.

## 5. Bold alternatives

**B1 (bold): adopt the RISC-V IOMMU architecture wholesale in place of the custom unit.** Win: the specification and its cross-checks (2.4); the interrupt part with it (MSI page tables); the model could be tested against QEMU's. Cost: Bare mode and its unit-wide switch (reverses e 187 decision 3 unless kept as a listed deviation); the 24-bit identity; the page-table entry (change ours "in place" to RISC-V's, or keep two formats); the register map (already A1); the AIA coupling; a larger text and model (3,000 lines against 973) carrying features we refuse. Risk: the guest-physical MSI conversion presupposes AIA's one-page-per-file layout; the model's reuse needs target decoupling. **Recommend amend (A1), not adopt** now: it takes the shape and the names and leaves the three deviations; revisit adopting wholesale if the OpenBSD or Linux port finds the driver shape matters more than the three deviations.

**B2 (bold): adopt the RISC-V AIA (APLIC and IMSIC) as the interrupt controller.** Win: a finished, ratified architecture with an existing OpenBSD driver (375 + 228 lines per J.6.3, **from that appendix, not re-checked here**), guest interrupt files for direct delivery (no exit per interrupt, and more than seven virtual vectors), the IOMMU's MSI tables, IPIs and wired conversion. Cost: it uses RISC-V CSRs (`siselect`, `sireg`, `stopei`) and an interrupt file per privilege level and per guest: new instructions or system registers for the pdp64 (J.6.3 would no longer be "no instruction"); identity is priority and the threshold register is the only mask, with "automatic preemption (nesting) of interrupts ... based on priority" explicitly not defined (1.1), so `SPL` would become a register write to the controller on every call, which contradicts P4 (the instruction `SPL`) and m 6.3.7, 6.13.4; and it conflicts with the decision that a physical interrupt always exits (e 186 decision 1) since the AIA's win is direct delivery to guests. **Recommend amend (B1 above, our 4.2 B1 and B2), not adopt**: take the interrupt file and the single-write IPI, keep `SPL` and the vector table.

**B3 (bold): adopt the RISC-V A extension and RVWMO's rules, with Zacas (and Zabha).** Win: ratified semantics, text, litmus suites, compiler mappings (C11 atomics map onto the acquire and release bits); a weaker model lets a large out-of-order core drop the replay of m 7.7.3. Cost: `aq` and `rl` bits on all 22 words (so the `_DB` doubling goes; the encoding needs two bits per leaf); a weak model, which m 7.13.1 refuses and the seL4 review counts as the best case lost (`sel4-fit.md`: "the SC model (7.5.1) is the best case for the lock proof"); barriers in every kernel and driver; races that appear once a week (P1). **Recommend the instruction half, not the model:** adopt the A extension's layout and the Zacas form (C1, C2) and keep sequential consistency (C6); the weak model is a question for the day an out-of-order core needs it, which m 7.7.2 keeps open.

**B4 (bold, for the record): Arm's SMMUv3 as the IOMMU.** Nothing in it fits better than the RISC-V unit for us: it has no interrupt translation of its own (the GIC does it), it reaches guests by hypervisor emulation as ours does (3.8), and its text is older in this review (D.a). Not recommended.

## 6. Decisions for the owner, each with a recommendation

Each is one question; answer accept, change, or not decided.

1. **Amend the IOMMU toward the RISC-V IOMMU architecture (A1)?** Take its register map, command and queue formats and capability bits where we have the same thing, keep as listed deviations: no Bare mode, no ATS or process contexts in version 1, the processor's leaf entry, 16-bit identity. This changes the register layout of errata 187 decisions 2, 3 and 11 and 194, not their substance. *Recommendation:* accept; do not adopt wholesale (B1) now.
2. **Define interrupt filtering in the IOMMU now (A2)?** Word 3 of the device entry points to a per-device interrupt table; a device with no entry raises nothing. It fills the reserved word of errata 187 decision 12 and settles J.6.3 option 2. Needed before an assigned device exists, which errata 181 decided. *Recommendation:* accept.
3. **State the in-flight invalidation guarantee as a point in time, testable (A4)?** This replaces the third sentence of m 2.11.7 ("does not complete until the device's requests in flight are finished or refused") with the weaker and precise one, and the model gets a two-phase request. *Recommendation:* accept.
4. **Require ACS-style redirection for assignment and keep the group only as the fallback (A6)?** It adds a precondition to m 2.11.5. *Recommendation:* accept (the PCI Express bit names are to be checked in the specification before the text is written).
5. **Define the interrupt controller as a per-core interrupt file with a set register, a read-only `TOP`, a converter for wired sources and the IPI as the same write (B1 of 4.2)?** It closes J.6.3 in the form of its option 1 with the AIA's two ideas and not its priority rule. *Recommendation:* accept.
6. **Derive the level from the vector number (B2 of 4.2)?** Levels 1 to 7 are vectors 32 to 255 divided by 32; the present timer, console and PCIe vectors are renumbered, changing the wiring of errata 194 and the tests that name it. *Recommendation:* accept (the alternative, a 3-bit level per vector, costs state and allows a vector and level to disagree).
7. **Make the physical timer per core with the virtual timer's shape, and no `RDTIME` (B4 of 4.2)?** It settles the timer half of J.5.1. *Recommendation:* accept.
8. **Fix the operand layout of the atomics as the baseline has it (C1)?** Three register fields for all, `CAS` with the expected value in `rd` and the old value returned there, `SC` result 0 for success; this departs from the assistant's earlier leaning in J.9.3 (the four-register form). *Recommendation:* accept.
9. **Fix the atomic sizes at 4 and 8 bytes for all, with natural alignment or a precise alignment fault (C2, C3)?** *Recommendation:* accept.
10. **Restrict atomics and reservations to normal cached memory and make any other use a precise fault (C5)?** This reverses the plain reading of m 2.8.1 and restates 2.10.2 and 7.4.4, and settles J.7.4 (options 1, 3, 4 together). *Recommendation:* accept, with device atomics left as an extension; if you want the promise of 2.8.1 kept in full, say so and J.7.4 stays open.
11. **Define the constrained `LL`/`SC` loop syntactically as RISC-V does, with a reservation set of 8 to 128 bytes, discoverable (C4; J.7.5 option 3)?** *Recommendation:* accept.
12. **Keep sequential consistency and reject RVWMO and Ztso for now (C6, B3)?** *Recommendation:* accept: keep it.
13. **Make every invalidate command the point of visibility of earlier table stores, and state that a device atomic needs write permission (A5, A7)?** *Recommendation:* accept.
14. **Add capability bits to the unit for each refused or optional feature, including ATS, process contexts and coherent DMA (A3)?** *Recommendation:* accept.
15. **Do the atomics first: the order of work of C7, then the tests (H4)?** Atomics (22 words) and the reservation clear have no implementation and no test; the seL4 review, the interrupt controller and the hypervisor all wait on them. *Recommendation:* accept.
16. **Adopt wholesale, instead of amending: the IOMMU (B1), the AIA (B2) or RVWMO (B3)?** *Recommendation:* not now for each; for B1 revisit when the first OpenBSD or Linux driver is attempted; for B2 never as long as `SPL` and the vector table stand; for B3 only the layout.

## 7. What could not be verified

* **The AMD I/O Virtualization specification** (download timed out, not retried). AMD-Vi is described from QEMU only.
* **Arm Architecture Reference Manual**: the exclusives monitor's forward-progress rules, its granule size, alignment of LSE atomics, the memory model's formal statement, the generic timer: **unverified**. What is said about Arm atomics rests on QEMU's decoder and exception code and on two Arm "Learn the architecture" guides.
* **Arm SMMU and GIC specifications are older issues** (D.a, 2020; IHI 0069G, 2021) than the current ones; features added since (for example the confidential-compute and virtual-LPI changes) are not covered. The STE and CD sizes and the SMMU register offsets were not extracted.
* **The PCI Express specification**: ACS bit names, atomic request types, the rules of posted and completion ordering, the memory-write form of MSI-X (the manual's own list marks several as unverified, 2.12). The statement that an AtomicOp is one of fetch-and-add, swap or compare-and-swap is from J.7.4 and is not re-checked.
* **RISC-V IOMMU figures**: the bit positions of the device context and registers are in images in the PDF and were not extracted; none is claimed. The reset values other than `ddtp` and the performance-counter, QoS and debug chapters were not read in detail.
* **x86**: the local APIC's command register for IPIs and the I/O APIC are not quoted (the SDM covers the first; the second is in separate datasheets that were not read).
* **OpenBSD and Linux drivers**: the line counts quoted in J.6.3 are that appendix's and were not re-counted; whether a Linux or OpenBSD driver for the RISC-V IOMMU exists was not checked.
* **Counts**: `spec/facts/core.toml` has 46 `H_UNIMPL` mnemonics, 22 of them atomics; the brief said 48. I did not reconcile the difference (three `SYSPG` words and the user-qualified forms were implemented since). No tests in this repository were run for this review.
* **My own inferences**, marked in the text: the 9 and 7 bit split being RISC-V's two-level case; the 1,300-bit state figure (J.6.3's, not mine); the 670-bit saving of B2 (224 x 3, my arithmetic); every effort statement (estimates).
