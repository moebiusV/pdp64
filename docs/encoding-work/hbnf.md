## 1. hbnf

* Fetched github.com/moebiusV/hbnf origin/main: **dd34982ab66ad47312e57b92eb25b4ece75ed57d** (2026-11-03, "The C tree is smaller ..."). Built with the project recipe, `tools/build-hbnf.sh`
  (Alpine rootfs under bwrap, GNAT 15); the commit is written to `$W/hbnf.commit`; `HBNF_REF=<commit>` pins another one.
* **No local patch.** The recipe still applied `tools/hbnf-numbers.patch`, which had been deleted when upstream took the change (c99c7cc), so the recipe was broken; it now builds plain upstream.
  (The `libhbnf.gpr` source-list workaround is still needed: upstream's gpr lists 14 sources, the tree has 36.)
* Two consequences of the new hbnf for the old grammars, both fixed in the first commit: (a) upstream's 2026-11-03 notation change refuses ABNF's `%x41`/`%x30-39` in hbnf's own notation; I ran upstream's
  `tools/hbnf_modernize.py` over `spec/ascii.hbnf common.hbnf pdp64-asm.hbnf pdp64.hbnf.in` (pure respelling, `0x41..0x5A`); (b) upstream's C parsers now default to compact, overlaid nodes, which
  breaks `as64/asmp.c` (it reads the old node layout); the as64 and asm-syntax parsers are generated with `--no-compact --no-overlay` (documented flags). Everything else, formats, sim64, ld64, qemu, llvm, passes unchanged.
* The scripts now default to a scratch hbnf build (`hbnf`, `hbnf-templates`) (what the recipe builds; I installed my build there). I did **not** overwrite the other agents' hbnf build, which the other
  agents' branches (old notation) run. After merging, `tools/build-hbnf.sh` must be run once (or copy that directory) on any other machine.
* What hbnf can express now and what I used: bit rules (fields `name:N`, `:Ns` signed, constants as wide as their digits `0b0010`, `bits(0)` for an operand with no bits, 64-bit fields), enum numbers
  (`"x"@N`), `?(expr)` checks, 281-alternative choices, `include` relative to the file; it generates a complete decoder and encoder (`parse_bits`, `emit_bits`) from them in 0.7 s.
* **Capability gaps found. None blocks; each is worked around inside the grammar, so no hbnf patch was needed or written** (option b of the task). Proposals for the author, none urgent:
  1. A bit field cannot be typed by an enum: `sub:mn-x` makes the file text-mode. So `sub:4` and the list of mnemonics `sub-FORM-K = "movq" | ...` are two rules joined by name, plus `?(sub < N)`
     for the unused numbers. Proposal: `sub:4 of sub-FORM-K`/`sub:enum-rule` (width from the enum, value must be a member, the generated struct gets the enum type) would remove the convention and the check.
  2. Rule names cannot contain `.` or `/` (the optimiser's form names are `LDU.B28`, `LDI12/a`, `CBI4_8/a`): the exact names are literals of the catalogue `forms = "LDU.B28"@13 | ...`, the rules use the spelling with `-`.
  3. A rule that is only a choice of bit rules (`insn = a | b`) is not a bit rule; it needs a field (`insn = leaf:( a | b )`), and the grammar is read as bits-only (so `parse_bits` is generated) only
     if that rule is the first. A text rule listed first (an enum) turns the whole file into `parse_text`. Proposal: `--root=RULE` should be honoured for bits-only reading too (today it is not).
  4. No hbnf template produces a *table*. What the codec needs (leaf table, runs of bits, candidate forms per mnemonic in assembler order, hot tables, spec pool) is generated by a small program that reads the grammar:
     `tools/mkenc.py` via `tools/encgram.py`. This is the one permitted exception ("a small generator that READS THE GRAMMAR"); no data file stands beside the grammar.

## 2. The grammars (spec/)

* `spec/pdp64-enc.hbnf` (167 lines): the vocabulary (a header that documents every name), the operand **shapes** (`reg4 = r:4`, `b4d28s-x1 = base:4 d:28s`, `pc16-u2`, `k-sp = sp:bits(0)` ...; width and signedness are in
  the fields, the attributes a field cannot carry (scale, unit, absent displacement) are in the name), the access sizes of the moves (`acc-8 = "movq"` ...), and `mn-ext`, the 70 numbered words only the new encodings have.
* `spec/pdp64-16/pdp64-16.hbnf` (1744 lines) and `spec/pdp64-32/pdp64-32.hbnf` (1725): `insn = leaf:( ... )` first (a bit rule), the name, the register file `regs` (r0-r15 / r0-r31), the hot tables
  `hot3` (and `hot4` in /32), `fused`, the **catalogue** `forms = "SYS0"@0 | ...` (index = the order the assembler tries them), then the leaves **grouped by instruction family** (comment banner per family, one block per
  form): `form-X = o1:shape o2:shape` (the operand syntax), `leaf-X-K = 0b<prefix> sub:J <pieces of operands in bit order> ?(sub < N)`, `sub-X-K = "mnemonic" | ...` (numbered by position).
  Illegal patterns: a first parcel no prefix matches (3,277 of 65,536 in both), an unused sub-opcode (`?(...)`). A register field narrower than the file is a hot index (`hot3`/`hot4` by width).
* Conversion: `docs/codegen-data/encoding/write_hbnf.py`, run once on forms.json (commit 24276e1); `tools/encgram.py` reads the grammar back into the dict forms.json held. **Lossless check:** forms, leaves (prefix, L, off, j,
  subbits, every place), hot8/hot16, fused, name, registers all equal for both encodings (script comparison against the old JSON). Names follow the existing grammar: `mn-`-style enums, `reg`, `hot`.

## 3. What is generated from the grammars

* `tools/mkenc.py` reads only the grammar: `build/pdp64-NN-tab.c` (codec tables), `build/pdp64-NN-hbfields.h` (new: accessor over hbnf's record), `build/x/*` (assembly grammar incl. group mn-ext and r16-r31 taken from
  `regs`, `pdp64-groups.h`, `pdp64-extnames.h`, `pdp64-mnnames.h`), `spec/pdp64-NN/tables.md`. sim64/ld64/as64 use the same tables (no separate decode tables exist). Drift-test inputs (`check-drift-enc.py`,
  `check-enc.py`) and the vector/corpus generators (`mk_vectors.py`, `mk_asm_tests.py`, `mk_ld_tests.py`, `asm_vs_model.py`) read the grammar through `encgram`.
* **hbnf's own generator is used for the decoder**: `hbnf spec/pdp64-NN/pdp64-NN.hbnf --backend=c` gives `parse_bits`/`emit_bits`; `tests/enc/hbdec.c` runs it against the codec (below).
* `forms.json` x2 deleted (git rm); nothing reads the optimiser's data. The optimiser (`docs/codegen-data/encoding/`) stays as oracle (`check-enc.py` still lays the forms out with `enc.py`) and as design tool:
  `export_forms.py OUTDIR` now writes the three grammars via `write_hbnf.py`. **I re-ran it on the corpus: the grammars it writes are byte-identical to the committed ones** (closed loop).
