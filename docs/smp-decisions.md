[← pdp64 index](../README.md)

For the author's annotation. Two parts, each section with the question, the state of the repository, the history (PDP-11, VAX, early Unix), what other systems do, the pain points already collected, several options with a one-line summary each, a recommendation with its reasons, and what you must decide. Priorities are those of errata 83: security and safety first, then opcode choice and encoding, speed and power, compiler target, assembler; beside them out-of-order readiness, the soft-rule test and hot-loop weight.

**Decisions already made that frame everything below** (errata 92):

* At least **4 cores** must work in iteration one; **16 or more** is the preferred architectural ceiling, which no decision may preclude.
* The **initial device has 4 cores**, hoped to fit the FPGA.
* **In-order and out-of-order cores may share a die**, provided software can tell which is which (the core-class register of manual 7.8.3); the architectural memory model and the ISA semantics are identical on every core.
* The dedicated-core proposal (graphics, network, audio) is a proposal (errata 76); the secure core class (in order, fixed latency, private caches, no periodic tick) is approved (errata 85, 86).

**Part A** (atomics, memory model, coherence, TLB, devices ordering) and **Part B** (interrupts, inter-processor interrupts, starting cores, idle, timers, dedicated and mixed cores, the operating-system view, tools) were written separately; where they touch each other (for example the reservation that wakes `WFE`, the write-back behaviour of stop-and-drain, the coherence limit at 16 cores) each says so.

**Figures that need care.** The FPGA fit of 4 cores differs between the parts, because the plan's own figures conflict: by the plan's ratio of 16,000 LUTs to "about 15% of a DE10-Nano" that board would hold about 6 cores, but the DE10-Nano has about 41,000 ALMs, roughly 82,000 LUT-equivalents, which gives 2 to 3 cores with the FPU, or 4 without it at 64% nominal (89% at the +40% end). 16,020 LUTs is the plan's figure for a complete core (integer core, MMU, FPU, L1 caches, bridge) before the 600 LUTs per core for snooping; it is a paper estimate at ±40% for the old encoding, and no core has been synthesised. Both parts agree on the conclusion: 4 cores fit only the Kria KV260 class with the FPU, and 16 cores fit none of the boards in the plan.

**Where the code is.** The new encodings and the tools mentioned (pdp64/16 and pdp64/32, `sim64` for them, the timing model, linker relaxation) were on the branches `enc-prefix`, `enc-hb`, `enc-ld`, `enc-tm` and `enc-cb` when this was written (not yet merged then) and are merged in the integrated tree (branch `enc-int`); references to `spec/pdp64-16`, `spec/pdp64-32` and errata 87 to 90 mean entries 87 to 91 of the integrated numbering (87 phase 1, 88 sim64, 89 grammars, 90 cbCC reach, 91 linker relaxation; the old "89" of enc-ld).

The repository tree has no `spec/pdp64-16` or `spec/pdp64-32` directory in this checkout; the encodings are taken from `docs/encoding-proposal.md`. `docs/errata.md` ends at entry 86 in this checkout; an entry 88 (sim64 traps every `ATOM` word) is not in it, and the only trace read is that `common/pdp64exec.c` has no `ATOM` case (read: grep of `common/pdp64exec.c`, no hit) and the errata entry 62 says the reference executor does not implement the atomic group (read: `docs/errata.md:212`).

**Design targets in force for every section** (the author's later decisions, folded in): at least 4 cores must work in iteration one, and 16 or more is the architectural ceiling that no decision may preclude, dedicated cores included; in-order and out-of-order cores may share one die, provided software can tell which is which (the core-class register of manual 7.8.3 is specified in another part). The consequence for this part is one rule, stated here once and used below: **there is one architectural memory model, one reservation rule, one translation-visibility rule and one device-ordering rule, and every core obeys all of them regardless of its microarchitecture; a core class may differ in speed, never in what a program may observe.**

## 1. ATOM instructions: operand placement

**Question.** The atomic group `ATOM` (opcode `0x11`) has 22 words whose operand placement was never fixed: which register holds the address, which holds the value to add or the new value, which receives the old value, where the compare value of `CAS` goes and where the size (4 or 8 bytes) is encoded. The placement decides how many instructions an atomic costs, how many bytes it takes in each of the two encodings, and what OpenBSD's `atomic_*` and mutex code compiles to.

**Current state.**
* The 22 words (read: `spec/pdp64-mnemonics.hbnf:239-262`), with their 8-bit sub-opcodes: `cas` 0x00, `casdb` 0x01, `swap` 0x02, `swapdb` 0x03, `xadd` 0x04, `xadddb` 0x05, `xand` 0x06, `xanddb` 0x07, `xor_` 0x08, `xor_db` 0x09, `xxor` 0x0A, `xxordb` 0x0B, `xmax` 0x0C, `xmaxdb` 0x0D, `xmin` 0x0E, `xmindb` 0x0F, `xmaxu` 0x10, `xmaxudb` 0x11, `xminu` 0x12, `xminudb` 0x13, `ll` 0x20, `sc` 0x21. Bit 0 of the sub-opcode is the `_DB` flag (a full barrier folded into the atomic) for the first twenty; `LL` and `SC` have no `_DB` form. Sub-opcodes 0x14 to 0x1F and 0x22 to 0xFF are unassigned.
* Semantics in the manual: `CAS` operates on 4 or 8 bytes and the 8-byte form may span two adjacent 4-byte fields (read: `docs/manual/09-isa.md:3047`, "The encoding of the `CAS` size is unspecified"); the syntax is given as `CAS expected, new, (address)` with the placement "unspecified" (read: `docs/manual/09-isa.md:3053-3066`); the operation is `old <- M[address]; if old = expected then M[address] <- new; result <- old` (read: same file, Operation block); all forms trap on a misaligned address (read: `docs/manual/09-isa.md:3084`).
* Present format in the old encoding: `ATOM` is one of the six escape groups, four bytes minimum; parcel 0 carries `reg` and `low` as two 4-bit register fields ("in this group `low` is a register, never a mode"), parcel 1 is `sub:8 t:4 x:4` (read: `spec/pdp64.hbnf.in:44-48`, `docs/manual/09-isa.md:3059`). That is four 4-bit fields of which `t` and `x` have no assigned meaning.
* New prefix-coded encodings assume 20 words in group `R3` (three registers) and `cas`, `casdb` in `R4` (four registers) with the address in a register (read: `docs/encoding-proposal.md:96`). `R3` uses 52 of 256 sub-opcodes, `R4` uses 16 of 16 and has no spare (read: `docs/encoding-proposal.md:83,88,228`). The byte length of an `R3` or `R4` instruction was not read.
* Errata 86 item 18: "atomics take the user form once `ATOM`'s operand placement is fixed" (read: `docs/errata.md:236`), that is, the `.U` user-qualified access applies to atomics once their operands are fixed; a kernel `copyin` that must `CAS` a user word needs it.
* Errata 45 fixes the semantics on a monitor; `LL` reserves a naturally aligned granule of at least 8 bytes (read: `docs/errata.md:195`).

**History.**
* PDP-11: no atomic instructions as such; read-modify-write instructions (`INC`, `BIS`, `BIC` on memory) were indivisible on the Unibus because the processor held the bus between the read (`DATIP`) and the write (`DATO`). `TST`/`TSTSET` arrived on the 11/70-era multiprocessor models (from memory, not confirmed: the 11/74 added `TSTSET` and `WRLCK`/`ASPI`-style instructions for multiprocessing). Unix on one CPU used `spl` for exclusion; the dual-processor Unix ports of the 1970s (Purdue's dual 11/70, and the Naval Postgraduate School's MUNIX, from memory, not confirmed) were master/slave: one processor ran the kernel, the other ran only user code, which needed one lock and no atomics inside the kernel.
* VAX: `BBSSI` and `BBCCI` (branch on bit, set or clear it, interlocked), `ADAWI` (add aligned word, interlocked), and the interlocked queue instructions `INSQHI`, `INSQTI`, `REMQHI`, `REMQTI`, which are whole lock-free queue operations in one instruction, so the ABA problem (a value changes A to B to A between your read and your compare) never appears (read: `docs/decisions-pending.md`, P8 history paragraph, "checked: VAX-11 Architecture Reference Manual 6.1; the 1977 handbook has only `INSQUE`/`REMQUE`"). The VAX-11/782 (1982, from memory, not confirmed) was an asymmetric two-processor machine; the 8300 and 8800 (mid 1980s, from memory, not confirmed) were symmetric, and ran VMS; Berkeley Unix ran on them rarely. What this tells us: DEC's own answer to multiprocessing was large atomic instructions that build queues, not a small general primitive. The 4.3BSD kernel on a uniprocessor VAX still used `spl` (read: `docs/decisions-pending.md` P11 history).
* Unix SMP ports in general (from memory, not confirmed): master/slave (one kernel processor), then a giant lock (one lock around the whole kernel; SunOS 4 MP, early FreeBSD 5, OpenBSD today), then fine-grained locks (SVR4/MP, Solaris 2, FreeBSD SMPng from 2000 to 2003). OpenBSD still has its giant lock in 2026: "Diff below pushes the kernel lock around namei() and vn_stat" (Pieuchot, 6 Jan 2025, read: `docs/kernel-pain-points.md:607`). The lesson for this section: a kernel whose atomics are `cas`, `swap`, `add` and `setbits` is enough to run for decades; the exotic words are for lock-free structures that the BSDs hardly use.

**What other systems do.**
* x86: `LOCK`-prefixed read-modify-write on any memory operand with a full addressing mode, so the address is base+index+displacement; `XCHG` with a memory operand is implicitly locked; `CMPXCHG` compares with `RAX` implicitly and leaves the old value there (486, 1989; `CMPXCHG8B` Pentium; `CMPXCHG16B` x86-64; all from memory, not confirmed). Every `LOCK` operation is fully ordered. OpenBSD amd64 `membar_enter` is `mfence`, the other four are compiler-only (read: `<work>/kernel-src/openbsd/sys/arch/amd64/include/atomic.h:266-270`).
* ARM: ARMv8.0 has exclusive load/store pairs (`LDXR`/`STXR`, with acquire/release forms `LDAXR`/`STLXR`); ARMv8.1 Large System Extensions add `CAS` (`Rs` compared and receives the old value, `Rt` is the new value, `[Xn]` the address: three register fields, no displacement), `CASP` (register pairs), `SWP`, `LDADD`, `LDCLR`, `LDEOR`, `LDSET`, `LDSMAX`, `LDSMIN`, `LDUMAX`, `LDUMIN`, each in relaxed, acquire, release and acquire-release forms and in byte, halfword, word, doubleword sizes (from memory, not confirmed; the Linux file `arch/arm64/include/asm/atomic_lse.h` exists and uses `ldadd` among others, read: `<work>/kernel-src/linux/arch/arm64/include/asm/atomic_lse.h:62`). OpenBSD arm64 builds `atomic_setbits_int` from a `ldxr`/`stxr` loop (read: `<work>/kernel-src/openbsd/sys/arch/arm64/include/atomic.h`, the `ldxr %w0`/`stxr %w1` asm).
* RISC-V: `LR`/`SC` with a constrained loop of at most 16 instructions that is guaranteed to succeed eventually (read in earlier work: RISC-V ISA manual 5.2.1, cited in `docs/decisions-pending.md` P11); AMOs `AMOSWAP`, `AMOADD`, `AMOAND`, `AMOOR`, `AMOXOR`, `AMOMAX`, `AMOMAXU`, `AMOMIN`, `AMOMINU` with address in `rs1` and no displacement, `rd` receiving the old value, `rs2` the operand, and two ordering bits `aq` and `rl` (from memory, not confirmed). Compare-and-swap came late as the Zacas extension (`amocas.w/.d/.q`) and byte/halfword atomics as Zabha; Linux's qspinlock series for RISC-V had to wait for them: "using Zacas and Zabha extensions and finally uses those newly introduced macros to add support for qspinlocks" (Ghiti, 28 May 2024, read: `docs/kernel-pain-points.md:744`; the Linux tree selects them at boot, read: `<work>/kernel-src/linux/arch/riscv/include/asm/cmpxchg.h:139-148`). OpenBSD riscv64 uses `amoor.w`/`amoand.w` for `atomic_setbits_int` (read: `<work>/kernel-src/openbsd/sys/arch/riscv64/include/atomic.h`). The `amocas` register convention (three fields; `rd` is the compare value in and the old value out) is from memory, not confirmed.
* LoongArch: `amswap_db.w/d`, `amadd_db` and the rest, the `_db` suffix meaning the barrier is folded in (read: `<work>/kernel-src/linux/arch/loongarch/include/asm/barrier.h:122,129`); `ll.w`/`sc.w`, `ll.d`/`sc.d` (read: `.../atomic.h:25-34`). This is where pdp64 got the `_DB` idea (read: `docs/pdp64-isa.md:1879`).
* POWER: `lwarx`/`stwcx.` and `ldarx`/`stdcx.` with `sync`, `lwsync`, `isync` and `eieio` for ordering (OpenBSD powerpc maps `membar_enter` to `isync`, `membar_exit` and `membar_producer` to `sync`, read: `.../arch/powerpc/include/atomic.h:279-283`); POWER9 added `lwat`/`ldat` fetch-and-op, `stwat`/`stdat`, (from memory, not confirmed). MIPS: `ll`/`sc` (and `lld`/`scd`), `sync`. SPARC V9: `CASA`/`CASXA`, `SWAP`, `LDSTUB` (a byte test-and-set), memory barriers `MEMBAR` with a mask (from memory, not confirmed). Alpha: `LDL_L`/`STL_C`, `MB`, `WMB`. s390: `CS`, `CDS`, `CSG`, `CDSG` (a double-width compare and swap since S/370, from memory, not confirmed), `LAA` fetch-and-add and friends since z196, and `PLO` for multi-word updates (from memory, not confirmed).

**Pain points.**
* Four registers for `CAS` in a 16-register ISA: address, expected, new, result is four of sixteen live registers at one instruction; the compiler (`pcc`) must reserve them in a sequence where the loop around it already holds a pointer and a counter. This is why ARM and RISC-V both chose in/out compare registers (from memory, not confirmed).
* No displacement means a `LEA` before every atomic on a structure field: the OpenBSD mutex `mtx_owner` and the reference counts `atomic_inc_int(&obj->refcnt)` are field addresses. Rows relevant: lock bouncing and false sharing (read: `docs/kernel-pain-points.md:724`, "lock word and protected data should not share a line"; `:509` OpenBSD's ticket kernel lock, +155% with an Anderson lock).
* RISC-V's missing `CAS` and sub-word atomics held back `qspinlock` for years (read: `docs/kernel-pain-points.md:744`, row 99 at `:1643`). pdp64 already has `CAS` and `XADD`; the open point is byte and halfword sizes.
* Mixed-size atomics: the 8-byte compare-exchange spanning two 4-byte members of Linux's `lockref` is the case that broke the "barriers restore SC" assumption on ARM and POWER (read: `docs/kernel-pain-points.md:1408`, Flur et al., POPL 2017); manual 9.13.2 copies that use deliberately.
* OpenBSD's kernel-side vocabulary (read: `<work>/kernel-src/openbsd/sys/sys/atomic.h`): `atomic_cas_{uint,ulong,ptr}`, `atomic_swap_{uint,ulong,ptr}`, `atomic_add_{int,long}[_nv]`, `atomic_sub_*`, `atomic_inc_*`, `atomic_dec_*`, `atomic_load_*`, `atomic_store_*`, and in machine-dependent headers `atomic_setbits_int` and `atomic_clearbits_int`; all 32-bit ("int") or 64-bit ("long", "ptr"); no byte or halfword atomics. The compare-and-swap is the only conditional one. `mtx_enter` is one `atomic_cas_ulong` on `mtx_owner` followed by `membar_enter_after_atomic()` (read: `<work>/kernel-src/openbsd/sys/kern/kern_lock.c:342-363`); `__mp_lock` takes a ticket with `atomic_inc_int_nv` (`kern_lock.c:170`).

**Options.**

1. **Register-only, address in a register, three register fields (RISC-V/ARM-LSE model).** Each word is `rd, rs, (ra)`: `rd` receives the old value, `rs` is the operand (addend, mask, new value, bound), `ra` holds the address; `CAS` is `rd` = expected in and old out, `rs` = new, `ra` = address; `SC rd, rs, (ra)` where `rd` receives 0 for success and 1 for failure; `LL rd, (ra)`. The size goes in the sub-opcode (new bit 6: 0 = 4 bytes, 1 = 8 bytes), keeping the fourth field free. In the old encoding it is four bytes with the unused fourth nibble reserved zero (a hint nibble for later: acquire/release strength). In the new encodings every word fits `R3`, `cas` and `casdb` leave `R4` (two slots freed in a full group). Costs one `LEA` when the address is a field at nonzero offset. Scoring: (1) safety: good, a misaligned address aborts and no addressing mode can hide a wraparound; the `ra` register holds exactly the address the page walk sees; (2) instructions: +1 `LEA` for field atomics (hot: refcounts, `mtx_owner`); (3) encoding: densest; (4) gates: smallest address path, no adder in the atomic unit; (5) compiler: simplest (RISC-V proves it); (6) assembler: `xadd r1, r2, (r3)`. Out-of-order: the address is known at issue, so the atomic unit sees a finished address with no AGU involved. Mixed cores: nothing core-specific.
2. **Option 1 plus a small scaled displacement in the spare nibble.** The `x` nibble (old encoding) or a nibble of `R3` (new, if one is free; not checked) becomes `d`, address = `ra + d * size`, `d` 0 to 15, so 0 to 120 bytes for 8-byte atomics. Covers the first 16 words of a structure, where `mtx_owner`, reference counts and flags sit in practice (from memory, not confirmed; not measured). Removes the `LEA` for most field atomics. Costs the nibble (no later hint bits), an adder in the atomic unit (small), and in the new encodings possibly a bigger group. Scoring: (2) better than 1 by the number of `LEA`s removed; (3) same density; (4) one small adder; (1) address overflow past the end of a page is a normal alignment/page fault, no special case.
3. **Full memory operand modes, as in loads and stores (x86 model).** The atomic names its address with the standard mode field. 6 bytes for base+displacement-16; the escape group `ATOM` would drop out of the "low is a register" rule, which is the property that keeps its decoder trivial (read: `docs/manual/09-isa.md:3059`). Gains: nothing that Option 2 does not give, except indexed atomics, which no OpenBSD or compiler path uses. Costs: a general address generator in the atomic unit; mode-dependent side effects (autoincrement) in an atomic are a fault-restart hazard (`pdp64-isa.md` 7.2 undo journal). Rejected on priorities 1, 3 and 4.
4. **CAS in the x86 style, with fixed registers** (expected in `R0`, old value out in `R0`). Two register fields freed. Rejected: the register file is 16 registers, a fixed register is a permanent compiler constraint, and the new encodings gain nothing since `R3` has the room.
5. **Double-width `CAS` (P8) as a register-pair form** (`CASP`-style, 16-byte aligned). Defer, as P8 recommends (read: `docs/decisions-pending.md:338-360`). At 16 cores the lock-free structures that need it (a free list with a tag) become more attractive; the tagged-pointer pattern (25 spare bits of the 64-bit pointer) delivers the version counter without an instruction. Reserve sub-opcode `0x02` mod size bits for it now so that it can be added without moving anything: a cost of zero.

**Lean.** Option 2 in spirit but decided in two steps: fix **Option 1** now (three register fields, address in a register, size in the sub-opcode, the fourth field reserved zero), because it is what both encodings already assume and what costs nothing; leave a **scaled displacement** as the one reserved use of the spare nibble, to be taken only when the OpenBSD port is compiled and the `LEA` count in front of atomics is measured (the author's priority 2 is instructions executed; the measure exists once `pcc` compiles `kern_lock.c`). Byte and halfword atomics: not added (OpenBSD has none; Linux needs them, RISC-V paid for the omission); keep the sub-opcode bit pattern able to hold them (size field of two bits instead of one: 4, 8, and two reserved). `CAS` in the in/out form (three fields) moves out of `R4`. Add the user form (`.U`) for atomics at the same time (errata 86). Say in the manual that `rd` and `rs` or `ra` may be the same register (the result written last), and that `rd = R0`-style discard is not special: a fetch-and-op whose old value is unused is still an atomic read-modify-write, no cheaper unless the implementation knows (RISC-V's `rd = x0` lets a far atomic skip the return; the same trick here would need a "no-return" convention, to be chosen with the far-atomic question of section 2).

**What the author must decide.**
(a) Placement: Option 1 now with the nibble reserved, or Option 2 now.
(b) Sizes: 4 and 8 only, or reserve byte and halfword.
(c) `CAS` as in/out compare register (three fields) so that `R4` gets its two slots back: yes or no.
(d) A "no-return" convention for fetch-and-op words whose result is discarded.
(e) Whether `_DB` stays one bit pair on all twenty words, or becomes a two-bit strength field (none, acquire, release, full) as on ARM and RISC-V; under SC they are all equivalent for cores (section 3) and differ only for devices, so the single bit is enough today.

## 2. Forward progress and the constraints on LL/SC

**Question.** Errata 45 says a constrained `LL`/`SC` sequence "must eventually succeed when no other initiator keeps writing the granule" (read: `docs/errata.md:195`). What exactly does the architecture promise when other initiators do keep writing, as they will at 16 cores, and what stops a livelock (two sequences that keep cancelling each other so that neither finishes)? What does the OpenBSD kernel need?

**Current state.**
* The promise is conditional: success is guaranteed only if nobody else writes the granule, which is vacuous under contention (read: `docs/errata.md:195`; manual 7.3.2 repeats it, `docs/manual/07-smp.md` 7.3.2).
* "Constrained" means short, with no intervening memory access or exception (read: `docs/errata.md:195`); the length bound is not given. Manual 7.3: the `LL`/`SC` loop "must be emitted in the constrained form, with no other memory access between the two" (read: `docs/manual/07-smp.md`, 7.3 Impact).
* The read-modify-write atomics "may be built from an exclusive access with hardware retry" (read: `docs/errata.md:195`), which says nothing about fairness or a bound.
* The reservation granule is "of the implementation's choice, not smaller than 8 bytes"; granule discovery in the feature registers is pending (P4) (read: `docs/errata.md:195`). `pdp64-ooo-readiness.md` decision 7: write the reservation rules, the forward-progress guarantee, `SC`'s result and what `_DB` adds (read: `docs/pdp64-ooo-readiness.md:33`) and says atomics "execute at commit" (`:173`).
* A device that writes shared words clears reservations (read: `docs/manual/07-smp.md` 7.3.4).
* Livelock/fairness verdict in the pain-points table: "MITIGATED BY DESIGN, constrained-sequence guarantee in E45; unmeasured, and only when a second initiator exists" (read: `docs/kernel-pain-points.md:338`, the LL/SC row). Hardware-vulnerabilities notes atomics' timing depends on contention (read: `docs/hardware-vulnerabilities.md:119`).

**History.**
* The Unibus lock made the PDP-11 read-modify-write trivially live: whoever held the bus finished. It also made every other device wait, which is why it did not scale beyond a few processors. VAX interlocked instructions were retried by the instruction in microcode under a bus or memory interlock, with the queue instructions failing visibly (the condition code reported "secondary interlock failed") so that the programmer retried with a bounded count (from memory, not confirmed). Lesson: a primitive that can fail visibly has to say how often, so that a loop around it can be bounded.
* The ticket-lock, MCS-lock and queued-lock lineage was driven by exactly this contention: Linux went test-and-set, ticket (2008), queued (`qspinlock`, 3.15) (read: `docs/decisions-pending.md` P11 paragraph citing LWN 590243; Piggin's report of unfairness "up to 1 000 000 (!) times" on an 8-core machine, read: `docs/kernel-pain-points.md:723`).

**What other systems do.**
* RISC-V: a constrained loop (at most 16 instructions of the base ISA, no loads or stores other than the `LR`/`SC`, no backward branches other than the retry) "eventually succeeds" provided the hart is not interfered with indefinitely; the guarantee is a system-wide progress statement and not per-hart fairness (from memory, not confirmed; wording in the P11 record is "eventual success for constrained loops: checked, RISC-V ISA manual 5.2.1").
* ARM: the exclusive monitor is cleared by any store to the granule (the "exclusive reservation granule", 8 bytes to 2 KB, implementation-defined, discovered in `CTR_EL0.ERG`) and by exception return; an exclusive pair that is too long or contains a memory access "may never succeed"; the architecture mentions a bounded-retry implementation hint but no guarantee (from memory, not confirmed). ARM added the single-instruction atomics of LSE precisely because LL/SC loops degrade under contention (from memory, not confirmed). `WFE` is woken by the clearing of the exclusive monitor, which lets a spinlock sleep instead of poll (from memory, not confirmed).
* POWER: `lwarx` takes a reservation on a cache-line-sized granule; a store by anyone cancels it; hardware holds the line for a short window after `lwarx` (from memory, not confirmed). Alpha: `LDx_L`/`STx_C` with a defined rule of 16 instructions between and no memory access, otherwise "may never succeed" (from memory, not confirmed). x86 has no LL/SC and so no such case, and its `LOCK` operation holds the cache line in the core for the instruction's duration (from memory, not confirmed).
* A real erratum of this kind exists: the ARC kernel panics at boot on an SMP configuration with atomics but without the "llock/scond livelock workaround" for a named silicon erratum (Gupta, commit `4d0cb15fccd1`, 25 Jul 2016, read: `docs/kernel-pain-points.md:513`); the forward-progress rule is a hardware obligation and not only text.
* Linux's own view: if a `cmpxchg` fails a lot, "your cache coherency is simply bad" and a Marvell part measured "~25x retries for one cmpxchg" (read: `docs/hardware-vulnerabilities.md:249`).

**Pain points.** At 16 cores a hot lock word is contended almost always, which makes the conditional promise empty. OpenBSD's `__mp_lock` waits on a ticket and spins with a count `__mp_lock_spinout` initialised to `1L * INT_MAX` (read: `<work>/kernel-src/openbsd/sys/kern/kern_lock.c:40,134-149`), so a kernel that livelocks is eventually detected in software by a panic or a "spun out" message, but only after billions of iterations. The mutex path `mtx_enter` is `atomic_cas_ulong(&mtx->mtx_owner, 0, self)` with a spin and a "park" structure (`mtx_enter_park`, `kern_lock.c:319-336`) added by recent OpenBSD to avoid contended spinning, evidence that contention on real machines was bad enough to restructure the code. The Guzik report on ticket-lock scaling: +155% with an Anderson lock (read: `docs/kernel-pain-points.md:509`).

**Options.**

1. **System-wide progress with a bounded hold-off, and read-modify-write words that cannot fail.** The architecture promises: (a) if any initiator executes `LL ... SC` as a constrained sequence, then in any interval in which one core attempts it repeatedly, at least one core's `SC` succeeds (lock-freedom, not wait-freedom); (b) on `LL`, the core's cache holds the line exclusive and the coherence protocol defers (holds off) snoops of that line for at most N cycles or until the `SC`, whichever is first, N being an implementation parameter reported in the feature registers and not less than the number of cycles the core needs to retire the maximum constrained sequence (sixteen instructions); (c) the twenty read-modify-write words are performed by the memory system as one atomic action on a line held exclusive, so they never fail and never visibly retry; `CAS` returns the old value, a mismatch is a normal result, not a failure of the mechanism. Per-core fairness is not promised; software uses `XADD` tickets or `SWAP`-based queues. Scoring: (1) safety: an error that cannot arise for (c), easy to detect for (a) because `SC` returns a status and a bounded retry count can trap; (2) instructions: none added; (3) none; (4) holds a line N cycles, no new storage beyond the reservation tag; (5) the compiler emits `LL`/`SC` loops only where a word does not exist; (6) none. Out-of-order: `LL` and `SC` execute at commit, so the hold-off clock counts from commit and a wrong-path `LL` can neither take a reservation nor hold off a snoop (a speculative LL would be a probe of other cores' lines, hardware-vulnerabilities rule C-class cross-core channel; read: `docs/hardware-vulnerabilities.md:119,123`).
2. **Option 1 plus a hardware retry counter visible to software.** The `SC` failure result distinguishes "reservation lost" from "gave up" so a loop can back off. Costs a result code and a counter; gains only a diagnostic. Defer.
3. **Far atomics (atomics performed at the memory controller or L2, AXI5-style).** The 20 words become messages to the home node; no line bounce at all, constant cost under contention, a core sends the operation and gets a reply (read: `docs/decisions-pending.md` P11 option 4 and its note "not better than far atomics"). Gains at 16 cores: a contended counter costs a round trip, not an ownership transfer per update. Costs: the home node needs an ALU, and every word needs a defined far form (min/max and the barrier-fused ones included), the interaction with `LL`/`SC` reservations on the same line, and cached-copy invalidation. Optional and invisible to software if Option 1(c) is the contract: any implementation may perform the 20 words near or far. Recommend leaving the door open and not specifying it.
4. **Mandatory exponential backoff in hardware after a failed `SC`.** Keeps a core out of the fight; costs a hidden timer, nondeterministic latency (priority 1 "strange side effects"). Rejected.
5. **Keep errata 45 as written.** Vacuous under contention; the first 16-core run will find it. Rejected.

**Mixed cores (the author's same-die decision).** The guarantee is stated in committed instructions and in the definition of "constrained", never in cycles, so it holds on the slow in-order core and on the fast out-of-order one alike. A fast core must not starve a slow one: the hold-off bound N is per core (the holding core's own N) and the requesting core's retries are paced by the protocol, which in a directory protocol queues requests per line in arrival order (a hardware queue gives per-line fairness for free; a snoop bus does not). Differences in speed change fairness in practice, so spin locks need a ticket or queue (section 1's `XADD`/`SWAP`) which the OpenBSD kernel already uses. The core class register gives N and the granule so software can adapt without any core being allowed to differ in meaning.

**Constraints on the sequence to write now** (each is cheap and closes a silent failure): exception entry and `RTI` clear the reservation, so a context switch cannot leave a thread with another thread's reservation (safety: an error that can never arise); `SC` to a different address than `LL`'s granule fails; an `SC` without a preceding `LL` fails; a second `LL` replaces the first; a store by the same core to the granule clears it (the RISC-V rule differs; the lean is the conservative one); `MBLK`, `PUSHM`, `POPM` and any other multi-access instruction in the sequence void the constraint; a page fault between them clears the reservation; the maximum sequence is sixteen instructions and no taken backward branch except the retry.

**Lean.** Option 1, with far atomics left as an invisible implementation choice (Option 3's door open). Write the system-wide-progress statement and the sixteen-instruction constraint into errata 45's follow-up; add granule size and the hold-off bound to P4's feature registers. For the kernel: `atomic_cas_*`, `atomic_swap_*`, `atomic_add_*_nv` and `atomic_inc/dec` map to the single words (no `LL`/`SC` loop at all); only `atomic_setbits_int`/`atomic_clearbits_int` (a fetch-and-or and fetch-and-and with a discarded result) also have single words (`xor_`, `xand`). The OpenBSD kernel needs no `LL`/`SC` loop on pdp64; `LL`/`SC` remains for user-level libraries and for ABA-sensitive code, which the manual says (read: `docs/pdp64-isa.md:841`).

**What the author must decide.**
(a) System-wide progress with a bounded hold-off (Option 1) as the promise.
(b) Whether the architecture names far atomics (leaning: no).
(c) The constraint list above, in particular the maximum length (sixteen) and that a same-core store cancels the reservation.
(d) Whether `SC`'s failure code distinguishes "lost" from "gave up" (Option 2).

## 3. The memory model (Q5)

**Question.** Sequential consistency (SC: the result is as if all cores' accesses occurred in one order that respects each program's order) is declared. Out-of-order readiness is a standing constraint, 4 cores must work and 16 or more must not be precluded, and in-order and out-of-order cores may share one die. Is SC still the contract, what is the retreat, and what do the compiler and OpenBSD need?

**Current state.**
* "pdp64 is sequentially consistent. Stated here, once, and not revisited." (read: `docs/pdp64-isa.md` 17.1, `docs/pdp64-isa.md:1937-1945`). Out-of-order keeps SC by early loads re-checked against other cores' writes before retirement, with stores buffered and drained in program order (read: same section). Per-byte SC, single-copy atomic aligned accesses, and the rule for a load overlapping a buffered store of a different size (read: `docs/manual/07-smp.md` 7.2.6).
* Q5 options 1 to 5 and the view: "Keep while the cores are small and in order. Revisit when an out-of-order core is really planned: total store order (option 2) would be the least painful retreat." (read: `docs/decisions-pending.md:774-800`). The ooo-readiness review rates SC "AWKWARD: speculative loads with snoop-and-replay, in-order store release; known cost, defined; two spec holes (decisions 8, 9)" (read: `docs/pdp64-ooo-readiness.md:174`). The two holes: device loads must not be speculative (decision 8) and the order of the accesses inside `MBLK`, `PUSHM`, `POPM` is unstated (decision 9) (read: `:34,35`).
* `FENCE` "orders nothing for normal memory under SC; its job is device memory and posted writes. Drain the store buffer" (read: `docs/pdp64-ooo-readiness.md:230`).
* `_DB` atomics: "under sequential consistency, are a convenience" (read: `docs/errata.md:195`).

**History.**
* PDP-11/VAX: one processor, so "the question did not arise"; the Unibus and VAX interlocks provided device ordering; the VAX multiprocessors (782, 8800) shared memory with interlocked instructions for locks (read: `docs/decisions-pending.md:774-800` history). Early Unix SMP ports kept all kernel data under one lock, so ordering inside the kernel was implied by the lock acquire and release; the first need for explicit barriers came with lock-free code and with weakly ordered hardware in the 1990s.
* The industry sequence (from memory, not confirmed): the DEC Alpha (1992) shipped the weakest model, including reordering of dependent loads; MIPS R10000 (1996) was out-of-order and SC, implemented with speculative loads and invalidation checks (from memory, not confirmed); the Intel P6 (1995) was out-of-order with TSO and a "memory ordering machine clear" on snoop hits to speculatively loaded lines (from memory, not confirmed); SPARC V8/V9 offered TSO, PSO, RMO; POWER and ARM are weak. Mark Hill's 1998 argument ("Multiprocessors should support simple memory consistency models", IEEE Computer, from memory, not confirmed) was that speculation closes most of the gap between SC and relaxed models, and the Gharachorloo, Gupta and Hennessy techniques (1991: hardware prefetch of the line for a store waiting its turn, and speculative loads with rollback) are what an SC machine uses (from memory, not confirmed).

**What other systems do.**
* x86 and SPARC (TSO) and s390 (a strong model, from memory, not confirmed): stores drain in order, a load may pass an earlier store to a different address (store buffering), loads are not reordered with loads, and the barrier is `MFENCE` or a locked operation. OpenBSD amd64: all five `membar_*` are compiler barriers except `membar_enter` and `membar_sync` which are `mfence` (read: `<work>/kernel-src/openbsd/sys/arch/amd64/include/atomic.h:266-270`).
* ARM, POWER, RISC-V RVWMO: weak. ARM's model took years to formalise; ARMv8 later became "other-multi-copy atomic" (a store becomes visible to all other cores at once), a restriction after earlier ARMv7 and POWER permitted non-multi-copy-atomic behaviour (from memory, not confirmed); the ARM and POWER mixed-size result shows barriers do not restore SC for overlapping accesses of different sizes (read: `docs/kernel-pain-points.md:1408`). RISC-V has the optional Ztso extension for TSO (read: `docs/decisions-pending.md` Q5 "RISC-V RVWMO with optional Ztso: checked"). OpenBSD's barrier set per architecture, riscv64: `enter` = `fence w,rw`, `exit` = `fence rw,w`, `producer` = `fence w,w`, `consumer` = `fence r,r`, `sync` = `fence rw,rw` (read: `.../riscv64/include/atomic.h:10-14`); arm64: `dmb sy`, `dmb st`, `dmb ld` (read: `.../arm64/include/atomic.h:10-14`). OpenBSD also has `virtio_membar_*` that are real barriers "even on SP kernels" (read: `.../riscv64/include/atomic.h:18`), which matters for the section 7 interplay.
* Alpha: dependent loads reorder, so `READ_ONCE` carries a barrier only on Alpha (read: `<work>/kernel-src/linux/Documentation/memory-barriers.txt:237-238,570-571`; the cause was split cache banks, `:629`); regret of the Linux community recorded in `docs/kernel-pain-points.md:750` (Paul McKenney on `smp_read_barrier_depends`). Linux's operations are by default "fully ordered" for value-returning RMW and "relaxed" for the rest (read: `<work>/kernel-src/linux/Documentation/atomic_t.txt:169-184`).
* C11 `<stdatomic.h>`: `memory_order_seq_cst` is the default; on an SC machine every order degenerates to a compiler barrier; `atomic_thread_fence` likewise.

**Pain points.** The documented overhead of weak ordering is software: 5,596 lines of ordering vocabulary in Linux plus 3,016 lines of `memory-barriers.txt` (read: `docs/manual/07-smp.md` 7.2 Benefits; `docs/kernel-pain-points.md:206`); the BSDs have a smaller set (`membar_*`, `atomic_*`). OpenBSD's mutex code uses five different barrier forms in a single file, including a comment-marked "StoreStore | StoreLoad" `membar_enter()` before a `cas` that sets the wait bit (read: `<work>/kernel-src/openbsd/sys/kern/kern_lock.c:450-452`), and `membar_producer()` at `:523`, `membar_consumer()` at `:465`: evidence that OpenBSD developers think in SC-minus terms and would get them for free. The hardware cost is real: speculative load replay on a core where another core's write hits a line that an early load already used; an SC stall when a store miss blocks later stores (read: `docs/pdp64-isa.md:1944`).

**Litmus tests the model decides** (each: the result forbidden under SC, and where it appears): *store buffering (SB, Dekker):* `T0: x=1; r0=y` / `T1: y=1; r1=x`, `r0=r1=0` forbidden under SC, allowed under TSO and weaker (this is the one reordering TSO adds; mutual exclusion algorithms without a locked operation break). *Message passing (MP):* `T0: data=1; flag=1` / `T1: r0=flag; r1=data`, `r0=1, r1=0` forbidden under SC and TSO, allowed under weak models unless fenced or ordered by dependencies. *Load buffering (LB):* `T0: r0=x; y=1` / `T1: r1=y; x=1`, `r0=r1=1` forbidden under SC and TSO, allowed on ARM and POWER (a speculative store before the load completes). *IRIW (independent reads of independent writes):* two writers to x and y, two readers reading in opposite orders, disagreement forbidden under SC and TSO (multi-copy atomicity), allowed on POWER and old ARM. *WRC (write-to-read causality)* and *2+2W*, *CoRR/CoWW* (coherence per location). *Dependencies:* address dependency (`r0=ptr; r1=*r0`), data dependency, control dependency: under SC all are ordered; under ARM, POWER and RISC-V they are ordered except through a control dependency to a load; Alpha is the exception (no ordering for an address dependency), so a weak pdp64 would need an RCU-style `membar_datadep_consumer`, which OpenBSD already has as a hook (read: `<work>/kernel-src/openbsd/sys/sys/atomic.h:272-281`).

**Options.**

1. **Keep SC as the architectural contract on every core (current), and implement it per microarchitecture.** In-order core: stores drain in program order from a store buffer with load forwarding, loads wait for older loads; the store's line is fetched exclusive early (prefetch for ownership) so the miss latency overlaps; no replay. Out-of-order core: loads execute early, enter a load queue, and are checked against invalidations (and evictions) of their lines until retirement; a hit replays from that load; stores retire to a post-commit store buffer that releases in order; the store buffer sits behind the load queue. A speculative-load check on a mixed machine is internal to the out-of-order core and visible to the others only as an extra invalidation response delay; the other cores see ordinary snoop traffic. Scoring: (1) safety: nothing for software to get wrong, no fence-omission bugs ("reproduce once a week", read: `docs/pdp64-isa.md:1970`); an error that cannot arise in software; hardware errors detected by litmus tests (below); (2) instructions: no barriers in any code; lock acquire is one `_DB` word or one atomic; (3) encoding: no fence encodings other than the device `FENCE`; (4) speed/power: the load queue replay and the in-order store release cost gates and power on the big core (the mechanism exists in every Intel core for TSO, so the added cost over TSO is the load-load order check on loads, which TSO also needs; the difference between SC and TSO is only that stores cannot be passed by later loads: the core must either wait for the store buffer to drain before a load can complete or speculate past it and check; the second is cheap with the load queue already there; from memory, not confirmed); (5) compiler: free; (6) none. Speed ground truth: Hill's argument and the R10000 experience say the gap is a few per cent on typical code with speculation (from memory, not confirmed; no number read in the repository). OoO readiness: "awkward but defined".
2. **TSO as the contract.** Store buffer with forwarding; loads may pass earlier stores to different addresses; a `FENCE`-class barrier (full) and the atomics restore order; `_DB` then means something for cores. Gains: the in-order and OoO cores need no store-to-load ordering check (the one thing SC adds to the load queue); software: the SB litmus test now allowed, so Dekker/Peterson breaks and mutual exclusion needs a locked operation, which all OpenBSD locks already use. Costs: the compiler must treat atomics as seq_cst with a fence on stores (as GCC does on x86: `mov; mfence` or `xchg` for a seq_cst store); `membar_enter` and `membar_sync` become real instructions (`mfence`-like), as on amd64 (read: `amd64/include/atomic.h:266-270`); the SC claim in the manual (7.2.1, 9.x) goes; the ABI says something about ordering. Irreversible in one direction only: software written for TSO is correct on SC.
3. **A weaker model with fences** (ARM, RISC-V RVWMO). Fastest hardware (stores may leave in any order, loads reorder), needs the full barrier vocabulary (producer, consumer, acquire/release flavors, data dependency barrier or a dependency rule) and compiler work in every C11 atomic and in OpenBSD's 5 `membar_*` per mutex; a decade of formalisation and errata to follow. Rejected by priority 1 (an error in software that can arise and is hard to detect) and 5.
4. **SC by default, weaker by page type or by core class** (Q5 option 4). A page attribute "relaxed" (say for graphics buffers) or a core class (the OoO cores run TSO and the in-order run SC). Rejected firmly under the author's same-die decision: it makes two models, and the mixed-machine verification (below) becomes a product of cases; a per-core mode changes the program's observable behaviour, which the standing rule forbids. A weaker model for *device* pages already exists (uncached, strongly ordered, F14) and is a property of the page, not a core; keep it.
5. **SC now, with an announced, machine-wide, one-way switch to TSO written into the architecture as a reserved system-register bit** (`MMUCTL`-style, set once at boot, readable in the feature registers; the author's soft-rule 42 allows a mode bit that is machine-wide and set once). All cores in the machine would switch together; software built for TSO runs on both. Gains: the door Q5 calls "least painful" is written down and costs only a reserved bit; costs: a second model to specify, test and verify, and the temptation to use it; if the switch exists, kernel code that needs `membar_enter` must be compiled with it. Lean: write the retreat down, do not implement it.

**Cost in the fused instructions and in prefetching.** Under SC every access of a multi-access instruction is ordered after the previous and before the next. The compiled corpus has 1,924 load-op instructions, `PUSHM`/`POPM` (4,836, 3.70 registers each, 17,900 loads and stores), `CALL`/`RET` (read: `docs/pdp64-ooo-readiness.md:197,217`); the readiness review (decision 9) proposes that the accesses *inside* `MBLK` are unordered with respect to one another and only the final result is defined (read: `:35`). That is the one SC exception to write down: what another observer may see in the middle of `MCPY` (read: `docs/pdp64-ooo-readiness.md:221`) and of `PUSHM`/`POPM`. Lean: `PUSHM`, `POPM`, `CALL`, `RET`, `PUSHX`, `POPX` access in the architecturally stated order (stack grows down, ascending register order) and are visible to other cores in that order, because the stack is private in practice and the cost is nothing; `MBLK`/`MCPY`/`MSET` are explicitly unordered within the block and ordered as a whole before and after (as x86 fast-string moves are, from memory, not confirmed); a `FENCE` or an atomic after `MCPY` publishes it. Prefetching: hardware prefetch and the `HINT` prefetch are not architectural and may fetch any line; a store's line may be fetched exclusive as soon as the store's address is known, which is what lets SC hide store latency (prefetch-for-ownership); a prefetched line is subject to invalidation like any other and so cannot create a stale read; no rule is needed.

**Mixed cores (the author's same-die decision).** One architectural model, enforced by the machine and tested by the machine's litmus plan, not by documentation. The litmus plan for a mixed machine: (i) run the standard suites (`litmus7`/`herd7` families; the existing plan item is read: `docs/pdp64-fpga-plan.md:224` and ISA open item 11) with every pair-wise placement of threads over core classes (in-order with in-order, in-order with OoO, OoO with OoO, and a thread migrating between them mid-test); (ii) test with at least three and four cores for IRIW and WRC (they need three or four threads and any of them may be on a different class); (iii) include mixed-size and overlapping-access tests (`CAS` 8 bytes over two 4-byte stores, byte stores into a word being added to, read: `docs/manual/09-isa.md:3047`); (iv) include device-ordering tests (section 7); (v) run each with random delay injection on the snoop network, replay forcing on the OoO core (the invalidation arrives one cycle before retirement) and store-buffer full conditions; (vi) a machine-checked model of the protocol (a TLA+ or Murphi model of the directory protocol of section 4 with both core types' load queue behaviours as obligations) before RTL, because simulation of litmus tests samples interleavings and a model enumerates them (from memory, not confirmed: the practice of vendors). **Per-core features that change memory-model-visible behaviour are not allowed.** The rule: a feature register may report capacities and speeds (store buffer depth, granule, hold-off N, cache line size is *not* varied, see section 4), never ordering; no mode, bit, page type or instruction may make one core observe a different order from another; verification is the litmus run above, repeated by the core-class register's value, plus a check in the test harness that any two cores' feature registers agree on every field that is an architectural parameter (line size, granule, page size, memory model version). A mixed machine whose registers disagree on such a field fails its boot self-check.

**Lean.** Option 1 as the architectural contract. Keep Q5's retreat as Option 5: a paragraph in the ISA text that says what would change under TSO (SB permitted; `FENCE` and atomics restore it; `membar_enter` and `membar_sync` become real) and that it would be a whole-machine decision made before any software depends on the stronger rule. Do not build a weaker mode. Reasons: priority 1 (no software-visible ordering bug can arise), priority 2 (no barrier instructions executed or fetched in a lock path: the `membar_enter_after_atomic()` after OpenBSD's mutex `cas` is empty), the standing constraint (OoO core pays by replay, a defined cost), and the mixed-core rule (one model is the only verifiable case). Also write the `MBLK`/`PUSHM` ordering rule now.

**What the author must decide.**
(a) SC stays the contract (Option 1) at 4 and at 16 cores, mixed cores.
(b) Whether to write the TSO retreat now (Option 5) as a reserved bit or only as prose.
(c) The ordering inside `PUSHM`/`POPM`/`PUSHX` (ordered) and `MBLK` (unordered inside, ordered at the ends).
(d) The litmus plan above as a gate before any second core is trusted, extended to mixed pairs.
(e) That per-core ordering features are forbidden and the self-check at boot.

**Your annotations:**

## 4. Cache coherence (R3)

**Question.** Snooping MSI for two to four cores is specified. The target is now 4 cores minimum and 16 or more at the ceiling, with dedicated graphics, network and audio cores, a secure core class with private caches, and a mix of in-order and out-of-order cores. What protocol, what states, what topology, and what is architectural?

**Current state.**
* Snooping MSI for two to four cores; "directory-based coherence scales further and is not needed below about eight cores"; MESI's benefit judged small at this core count; coherence "transparent to software" (read: `docs/pdp64-isa.md` 17.3, `docs/pdp64-isa.md:1968-1974`). Cost estimate: about 500 LUTs per snoop port plus a state machine and about 600 per core (read: `docs/manual/07-smp.md` 7.7).
* R3's five options and the lean "keep snooping, record the limit" (read: `docs/decisions-pending.md:1137-1161`); ISA open item 12 ("if the target is eight or more, that is the wrong protocol", read: `docs/pdp64-isa.md` open items, item 12).
* The dedicated-core proposal: errata 76; F16 to F21; F18: "general cores stay coherent with each other; the graphics, network and audio cores are message-passing partners using uncached rings and `FENCE`, the same rule as a DMA device" (read: `docs/decisions-pending.md` F18; `docs/errata.md:226`). F19: a complete core is about 16,000 LUTs (±40%), the DE10-Nano fits a few (read: `docs/decisions-pending.md` F19).
* DMA: software-managed first (F5): uncached pages (`MT = 01`) and `FENCE` at the doorbell (read: `docs/decisions-pending.md` F5; ISA 17.3 second half).
* Secure core: "private cache lines", every timing channel removed (read: `docs/errata.md:235`, entry 85; entry 86 approves the design).

**History.**
* PDP-11: Unibus devices and CPUs shared core memory with no cache coherence problem for most models; the 11/70 had a cache that the processor and the Unibus Map kept coherent by write-through and invalidation by DMA writes (from memory, not confirmed). The multiprocessor 11/74 (1976, from memory, not confirmed) shared multiport memory and used write-through caches with cross-invalidation. VAX 8800 and 8300 shared memory over the "SBI/NMI" interconnect with caches coherent by snooping a write-through bus (from memory, not confirmed). The record is consistent: coherence was provided by the memory system under the interlocked instructions (read: `docs/decisions-pending.md:1137` history paragraph, same statement), never by software cache flushes.
* Industry: bus-snooping SMPs (Sequent Symmetry, Sun Enterprise, 1980s to 1990s) topped out near 16 to 64 processors because every cache sees every transaction; directory machines (Stanford DASH 1992, SGI Origin 1996, from memory, not confirmed) scale by sending messages to the sharers only; modern x86 uses a home-agent or snoop filter inside a die and directories across sockets; ARM coherent interconnects (CCI, CMN) use snoop filters or directories (from memory, not confirmed, read only for ARM in `docs/decisions-pending.md` R3 "what current systems do").

**What other systems do** (all from memory, not confirmed): x86 Intel uses MESIF (Forward state) with an inclusive L3 acting as a snoop filter in client parts and a directory/home snoop across sockets; AMD uses MOESI with probe filters; ARM ACE/CHI use MOESI-class states (UniqueClean, UniqueDirty, SharedClean, SharedDirty, Invalid) with directory-based snoop filters (CMN-600/700 "SF"); RISC-V TileLink and CHI-based designs use MESI/MOESI with a directory in the L2/L3 (SiFive, Rocket tiles); POWER uses an extended MESI family (many states) with a snoop bus on the chip and a directory-less broadcast to groups; SPARC (Oracle M7) uses directories. A 16-core cluster with a shared inclusive L2 and snoop filter is the common design point; beyond 32 cores everyone uses directories.

**Pain points.** Lock-word bouncing is the cost the protocol must absorb: "lock fairness and cache-line bouncing: 2 to 4 cores snooping MSI keep it small; beyond that R3 and queued locks return" (read: `docs/kernel-pain-points.md:339`); OpenBSD's per-CPU structures false-share (8 CPUs per cache line, read: `docs/kernel-pain-points.md:509`). Atomic timing depends on coherence state (read: `docs/hardware-vulnerabilities.md:119`), which matters for the secure core. Coherence adds a covert/side channel: cache-line ownership transfer time is observable across cores (Flush+Reload, Prime+Probe cross-core on a shared L3; read: `docs/hardware-vulnerabilities.md:81`; rule C9 "caches and TLBs are flushed or partitioned at a privilege change when shared", `:160`).

**What the FPGA can hold** (read: `docs/pdp64-fpga-plan.md:17-22,69`; a core is about 16,000 LUTs, ±40%, near 15% of the DE10-Nano by the plan's own arithmetic). The plan's four boards: DE10-Nano (about 110K LE, about 41K ALM; at 16K LUT per core by the plan's own ratio about 6 cores of logic with nothing left, and by the ALM count about 2 to 3 cores: the two readings of the same board differ by a factor of two and the plan does not say which is right); Zybo Z7-20 (Zynq 7020, 53K LUT: 3 cores of logic before any cache controller or peripherals); Kria KV260 (ZU5EV, about 117K LUT: 7 cores of logic, about 4 with caches' control logic and the interconnect, BRAM-limited); ULX3S (ECP5-85F, 84K LUT: 5 cores of logic, about 3 usable). **Four cores therefore fit the KV260 and not the DE10-Nano or the Zybo, and 16 cores (256,000 LUTs for the cores alone, before caches, coherence logic and peripherals, at ±40%) fit none of the four.** Board classes that could hold 16 (from memory, not confirmed): a Xilinx UltraScale+ part of roughly 400K to 600K LUT, such as the Kintex KU15P or Zynq ZU9EG/ZU15EG, or a Virtex UltraScale+ VU9P (about 1.2 million LUT) or Alveo-class card, at the price of an order of magnitude more than the plan's boards; a smaller core (a 2-wide in-order with no FPU, or the dedicated cores built without `MBLK`, UTF-8 and crypto, the plan's own large items) to bring the per-core figure down; or sim64/QEMU for functional verification of 16-way behaviour with an FPGA of 4 to 8 for timing and a multi-FPGA or ASIC for the ceiling. BRAM is the scarce resource at any count (read: `docs/pdp64-fpga-plan.md:79,279`): 16 L1 pairs of 8 KB each already take 256 KB of a Cyclone V's roughly 5.5 Mbit (about 690 KB) of BRAM. This section therefore recommends that the 16-core protocol be proven by model checking and in simulation, and that the 4-core protocol be the one built first.

**Options.**

1. **Keep snooping MSI, 2 to 4 cores, say so (current R3 lean).** Gains: smallest; fits the FPGA. Costs: violates the new target of 16+ cores at the ceiling. Rejected as the only protocol; remains valid as the 4-core iteration-one build.
2. **Snooping MESI/MOESI within a cluster of up to 4 cores (shared L2 as the home), a snoop filter at the L2, and a directory protocol between clusters.** Hierarchy: 4 clusters of 4 cores gives 16; each cluster is a snooping MESI group on a bus or crossbar with a shared L2; the L2 keeps a directory (one presence bit per cluster plus state, 4 bits per 64-byte line, under 1% of storage) for lines held by other clusters. A 4-core machine is exactly one cluster: nothing is wasted, and iteration one builds the cluster and nothing else. Gains: 4 cores need no directory; the ceiling is reachable by adding the inter-cluster layer without changing the cluster; snooping only broadcasts within 4. States: MESI in the L1s (Exclusive avoids a bus transaction for a private write, which at a 4- to 16-core mixed workload dominates: most lines are private; unlike the "small benefit" estimate for two cores in ISA 17.3, which was for 2 to 4 cores), and a clean/dirty owner state (MOESI's Owned) only if cache-to-cache dirty transfer is wanted (skip: a write-back to the L2 is simple and the L2 is close). Costs: two protocols; the directory is the part most likely to hide a deadlock (message classes, virtual networks to avoid protocol deadlock; from memory, not confirmed: three or more virtual channels for request, forward and response). Scoring: (1) safety: coherence is a hardware property software cannot misuse; detect with the protocol model checker; (2) no instructions; (3) no encoding; (4) gates: cluster snoop only; directory is on the L2; (5) compiler: free; (6) none. Out-of-order: the invalidation reaches the L1 in a bounded number of cycles and the load queue checks it; the directory sends invalidations and waits for acknowledgements before granting exclusive, which is what SC needs (a write completes when all invalidations are acknowledged; the "early acknowledgement" optimisation of weak models is forbidden under SC unless the L1 also holds younger loads, see the mixed-core rule below).
3. **A flat full directory** (one home node per line, a sharer bit-vector of 16 to 64 bits; 16 bits per 512-bit line is 3% of storage at 16 cores and 12.5% at 64, from first principles). Simplest to reason about, scales to 64; the home latency penalty for the common case of a line held by one core is two hops instead of a snoop; for a 4-core iteration-one this is more than needed. Scoring as 2 but heavier for the minimum. Keep as the form of the inter-cluster layer, not the whole machine.
4. **No hardware coherence across clusters; explicit cache operations between them** (R3 option 4). Cheap to scale; contradicts Q5 (the SC contract would have to say "within a cluster") and the "bugs reproduce once a week" argument (read: `docs/pdp64-isa.md` 17.3); the soft rules allow it, but the dedicated cores already use the non-coherent partner model, and making the *general* cores non-coherent would put a cache-flush discipline into OpenBSD's whole kernel. Rejected for general cores.
5. **Dedicated cores as DMA-like partners (F18), the general cores coherent** (the author's proposal). The graphics, network and audio cores keep their own memory (or uncached regions), communicate by rings in uncached or write-combining shared memory with a doorbell, order with `FENCE`, and their device-like DMA is handled as in F5 (software-managed, or I/O-coherent through an IO port on the L2 that only snoops and invalidates, a "coherent DMA port" with no cache of its own). Gains: the number of coherent cores stays at the general count (4 to 16) and the dedicated cores do not enlarge the directory; isolation (F20) follows: they are separate IOMMU domains. Costs: the network core's data is not coherent with the kernel's mbufs without a copy or a flush; it is exactly the F17 problem. At 16+ cores, "the dedicated cores need not participate in the directory" is the cheapest way to keep them in. A dedicated core *may* choose to be a coherent member if its class register says so; the architecture then needs the one protocol only. The word to avoid: "cluster" for something non-coherent.

**Coherence between in-order and out-of-order cores (mixed).** The protocol sees only an L1 per core; the L1 behaviours that differ are: (i) the out-of-order core may hold lines read by speculative loads that never retire, so a speculative load's line fill must not change the coherence state visibly to other cores in a way an attacker reads (this is the cross-core speculative probe; the rule: a speculative load may fetch a line in Shared but a speculative store never takes Exclusive; the Exclusive request is issued at commit or from the store buffer; cf. hardware-vulnerabilities rules on speculative cache state, `docs/hardware-vulnerabilities.md:150-160`); (ii) on an invalidation, the OoO core must replay any retired-pending load that read the line, which delays only its own retirement, not the invalidation acknowledgement, provided the acknowledgement is sent when the L1 line is invalidated and the load queue is checked at the same time (the replay window is internal; this is the standard design, from memory, not confirmed); (iii) a snoop response never depends on the core class; the in-order core holds an L1 with an in-order store buffer and no speculation, so for it (ii) is vacuous. The architecture states: a write is complete when every other L1 has acknowledged invalidation and every acknowledging OoO core has placed the line's loads under the replay check; this is a hardware obligation checked in the protocol model and not a visible feature.

**Instruction-cache coherence** is section 6. **PCIe/DMA:** F5 stays: software-managed first; the root complex's DMA writes invalidate lines they hit only if it is an I/O-coherent port (leaning: a later feature announced by capability, errata 81). **Secure core (errata 85, 86):** private caches, no shared structure. The protocol must therefore let a core class declare "no sharing": its lines are never in the directory as shared with another core, its L2 slice is private (way partitioning or a separate cache), its coherence traffic carries constant latency (no snoop-dependent timing), and it communicates through uncached messages like the dedicated cores. Atomics on its shared words are handled as device-style messages; a `LL`/`SC` loop on shared memory would expose coherence timing (read: `docs/hardware-vulnerabilities.md:119`) and is not offered to it. This fits Option 5: the secure core is a partner, not a coherent member.

**Lean.** Option 2 as the architectural direction, built in two steps: iteration one builds a single cluster of 4 snooping MESI cores with a shared L2 and snoop filter (the 4-core minimum), with the L2 designed so a directory can be added to it, and the architecture text states "coherent, sequentially consistent, line size 64 bytes, transparent" and nothing about the protocol (so 16+ cores in clusters is an implementation, not a change). The dedicated and secure cores are Option 5 partners. MESI over MSI: the Exclusive state is worth its gates once the target is 4+ cores because it removes the upgrade transaction for private data; the earlier judgement of ISA 17.3 (MSI) was for 2 cores and is superseded by the target change. Fix the cache line size as an architectural constant (64 bytes), because the reservation granule, false-sharing rules, `ICINV` granularity and the per-CPU alignment all hang from it; a mixed machine cannot have core classes with different line sizes.

**What the author must decide.**
(a) The cluster-then-directory direction, with the single 4-core cluster as iteration one.
(b) MESI (leaning) or MOESI.
(c) The dedicated and secure cores as non-coherent partners (F18) or as optional coherent members.
(d) Line size 64 bytes as an architectural constant.
(e) The FPGA plan: 4 cores on the Kria-class board (not the DE10-Nano or Zybo), and 16 by model checking and simulation until a larger part is bought.

## 5. TLB coherence

**Question.** `TLBI`, `TLBIA` broadcast and `TLBSYNC` waits (ISA 17.2). At 16+ cores, with out-of-order cores that speculate on translations, is broadcast still the right choice against interrupt-based shootdown, and what is the by-ASID form (P5), the completion semantics and the OpenBSD pmap's need?

**Current state.**
* `TLBI` (SYS class 5, takes a register operand) invalidates by address, `TLBIA` all, both broadcasting; `TLBSYNC` waits for completion everywhere; 16-bit ASID, `G` entries and direct-mapped windows keep kernel mappings out of the path (read: `docs/pdp64-isa.md:790,799,1947-1957,1976-1984`). Broadcast chosen over shootdown for 2 to 4 cores: "far faster for two to four cores" (read: `docs/manual/07-smp.md` 7.5 Trade-offs).
* P5: add `TLBIASID` (recommended; "medium priority", then "ranks above medium" under the priorities) (read: `docs/decisions-pending.md:252-290`). Pain-points: "Flush a range: SAME PROBLEM, only `TLBI rN` (one page) and `TLBIA` exist; a 33-page ceiling policy and a loop of broadcasts" (read: `docs/kernel-pain-points.md:300-305`).
* The readiness review: "younger speculative translations must be discarded or replayed; `tlbsync` must wait for the other cores to complete or squash older accesses that used the old translation. The ISA does not say which" (read: `docs/pdp64-ooo-readiness.md:228`); `ISYNC` makes writes to `PTBR`, `ASID`, `MMUCTL`, `VBR` take effect (read: `docs/pdp64-isa.md:813` text of `ISYNC`).
* The ISA text claims the kernel's mappings "are never invalidated by an address-space change" (`G` and windows). Software-managed accessed and dirty bits, so a write through a stale clean entry faults (read: `docs/kernel-pain-points.md:521`, the guarantee Gorman asks for).

**History.**
* PDP-11: no translation cache; the kernel reloaded the relocation registers on a context switch. VAX: `TBIA`, `TBIS` through `MTPR`; no address tags; on a VAX multiprocessor the other processors' translation buffers were invalidated by an interprocessor interrupt (software shootdown; VMS and the 782/8800, from memory, not confirmed) (read: `docs/decisions-pending.md:252-290` for the uniprocessor facts). Unix MP ports always needed shootdown code once the TLB was tagged, and the early NetBSD Alpha port reported shootdown IPIs "as frequent as the clock interrupt on a 2-CPU Alpha" (read: `docs/kernel-pain-points.md:840,1685`).

**What other systems do.**
* x86: `INVLPG` is local; remote invalidation is an IPI with a software handshake (OpenBSD amd64 has `pmap_tlb_shootpage`, `pmap_tlb_shootrange`, `pmap_tlb_shoottlb`, `pmap_tlb_shootwait` driven by `x86_ipi` (read: `<work>/kernel-src/openbsd/sys/arch/amd64/amd64/pmap.c:362-368,537-538,1872-1874,1936-1941` and `ipi.c:54-90`)); AMD added a broadcast `INVLPGB`/`TLBSYNC` pair late (the repository names the AMD instruction, read: `docs/decisions-pending.md:252-290`), Linux uses it (`x86/mm/tlb.c`, same record); `INVPCID` invalidates by PCID. Cost: "was interrupted roughly 900K times per second" by flush IPIs on 48 CPUs, 180K with one IPI per CPU (Gorman, read: `docs/kernel-pain-points.md:521`).
* ARM: `TLBI ...IS` (inner-shareable, broadcast) by VA, ASID, VA+ASID or all, followed by `DSB ISH` to wait; the broadcast goes over the coherent interconnect (distributed virtual memory, DVM, messages) (from memory, not confirmed). OpenBSD arm64 `ttlb_flush` uses `cpu_tlb_flush_asid` / `_all_asid` (read: `<work>/kernel-src/openbsd/sys/arch/arm64/arm64/pmap.c:41-55,330-331`). Linux arm64 "batched and deferred shootdown (2023)" for ranges (read: `docs/kernel-pain-points.md:516`). Broadcast TLBI latency grows with the number of cores and clusters (DVM messages cross the interconnect), a known problem on large ARM servers (from memory, not confirmed).
* RISC-V: `SFENCE.VMA` is local; remote invalidation is by IPI, usually through the SBI call `sbi_remote_sfence_vma` (OpenBSD riscv64 `pmap.c:75,112` read: `<work>/kernel-src/openbsd/sys/arch/riscv64/riscv64/pmap.c`). Newer RISC-V work (Svinval, a batched form; hardware broadcast not standard) (from memory, not confirmed).
* POWER: `tlbie` broadcast with `tlbsync` and `ptesync` (from memory, not confirmed). SPARC: demap operations with cross-calls. s390: `IPTE` with hardware broadcast and purge.

**Pain points.** Shootdown completion windows violate lock-protected reads in practice (Rabe on FreeBSD, read: `docs/kernel-pain-points.md:758`); NetBSD's deadlock in the shootdown IPI (read: `:516`); each FFS block mapped and unmapped paid a shootdown (read: `:649`). OpenBSD reworked shootdown information transfer in Dec 2025 (read: `:516`). The reverse risk: a broadcast per page over 16 cores costs a bus transaction to every core's TLB even those that never ran the address space; x86's `mm_cpumask` optimisation exists to skip such cores (read: `docs/kernel-pain-points.md:295`).

**Options.**

1. **Broadcast `TLBI`/`TLBIA` + `TLBSYNC` as specified; add nothing.** Gains: no handler, no IPI deadlocks. Costs at 16+: every `TLBI` is a message to all cores or all clusters; a mass unmap is N broadcasts (the 33-page policy); ASID rollover with `TLBIA` flushes every process on 16 cores. Fine at 4, weak at 16.
2. **Option 1 plus `TLBIASID` (P5 option 1) and a scoped broadcast.** `TLBIASID rN` invalidates every entry with the ASID in the register, on all cores. Gains: process exit and rollover cost one broadcast, not a flush of everything (priority 2: fewer instructions executed in the hot context switch/exit path). At 16+ cores add a *scope*: the broadcast goes only to cores whose "currently or recently running ASID set" contains the ASID, held as a per-ASID core mask in the directory/interconnect, a hardware version of Linux `mm_cpumask` (from memory, not confirmed) (read: `docs/kernel-pain-points.md:295`). Costs: a core mask per ASID in hardware, for 65,536 ASIDs a table of 16 bits each = 128 KB (too big; a Bloom or per-cluster bit is used instead: 4 bits per ASID = 32 KB), or let software supply the mask (a second register operand: `TLBIASID rASID, rMask`, a core bitmap), which moves the bookkeeping to the kernel where `mm_cpumask` lives. Recommend the software-supplied mask as an optional operand form; default all.
3. **Ranged `TLBIR rStart, rEnd`** (ARM `TLBI RVAE1IS`, RISC-V Svinval). One broadcast for a range. Gains for large unmaps. Costs: an instruction, a range compare in every TLB, interruption/restart semantics. Defer until the OpenBSD port shows `pmap_remove` ranges are common; the compiled corpus is the wrong place to measure it.
4. **IPI shootdown as the mechanism (x86/RISC-V).** The primitive exists already (IPIs, R2); no new broadcast hardware. Costs: handlers, deadlock cases, per-CPU pending lists, interrupts delivered to idle cores (read: `docs/kernel-pain-points.md:301`, the designed-away list). Rejected as primary, but **kept as the fallback**: a core that is parked, in `WFE`, or unreachable (hot-unplugged, secure) needs a software path, and the dedicated/secure cores (non-coherent partners) have their own TLBs and are *not* in the broadcast group by default: shared kernel mappings do not exist for them (separate address spaces, F20), so no `TLBI` need reach them.
5. **Hardware shootdown that avoids broadcasting to cores that never loaded the entry** (a TLB directory): too large. Rejected.

**Completion semantics for speculating cores (mixed cores).** Write the rule: (a) `TLBI` executed on core A is performed on every core B in the broadcast group in program order with respect to B's own *retired* instructions, and B discards or replays any younger instruction whose translation used the old entry before acknowledging; the acknowledgement thus says "no instruction that has not yet retired on B can complete using the old translation"; (b) an in-order core satisfies this trivially at the next instruction boundary; an OoO core must flush speculative uses (the TLB entry is invalidated, in-flight loads and stores that already translated are re-executed or squashed if they have not yet committed; a store already committed is older and complete); (c) `TLBSYNC` on core A completes when all acknowledgements arrive and A's own older loads and stores have retired (the readiness question: the ISA does not say which of "wait" or "squash"; the rule above picks "wait for acknowledgement, and each remote core did the squash"); (d) memory accesses *after* `TLBSYNC` on A are ordered after the invalidation on every core (the SC contract for translation: no core uses the old translation once `TLBSYNC` completes on the initiator). The page-table store, the `TLBI` and the `TLBSYNC` form the update sequence; the page-table store itself is an ordinary store, visible before the `TLBI` under SC. The hardware walker's reads must observe the latest stores (the walker uses the data cache or its own coherent path); the Rabe-style window (read: `docs/kernel-pain-points.md:758`) is closed by the rule that a core does not act on the old translation after its acknowledgement, and the remote window before acknowledgement is bounded by the completion latency which `TLBSYNC` exposes. A privilege change or `MTASID` needs no broadcast; `ISYNC` orders the local pipeline.

**What OpenBSD pmap needs.** `pmap_update`/`pmap_remove` call `pmap_tlb_shoot*` on amd64 and wait with `pmap_tlb_shootwait`; on arm64 the pmap issues `tlbi ... is` and a `dsb`; on pdp64 the pmap needs: a per-page `TLBI rN`, `TLBIASID` (pmap_destroy, ASID reuse), `TLBIA` (rollover fallback) and `TLBSYNC` before freeing the page or reusing the frame (the pmap equivalent of `pmap_tlb_shootwait`); no handler and no IPI vector for flushes; kernel mappings are `G` or window-mapped and need no flush on context switch. A pmap that wants to skip idle cores keeps its own `pm_cpus` mask, as OpenBSD amd64 does (from memory, not confirmed in the lines read), and passes it as the optional mask operand of Option 2.

**Lean.** Option 2 with the ranged form (Option 3) deferred and IPI (Option 4) kept as a software fallback for cores outside the broadcast group; write the completion rule above into the ISA text (it closes readiness item "does not say which"); make the broadcast group a property of the machine, discoverable in the feature registers (the cores that hold coherent translations). Scores: priority 1 gets the "stale translation cannot be used after TLBSYNC" guarantee (easy to detect by a litmus test with page-table updates; cannot arise in software that follows the sequence); priority 2 gets `TLBIASID` (one instruction instead of a loop or a full flush); 3 one `SYSX` word; 4 a mask compare per TLB entry in the broadcast receiver. For the machine at 16+ cores, measure before adding a scope mask: broadcast latency over the cluster interconnect is the number that decides it.

**What the author must decide.** (a) `TLBIASID` yes (P5), (b) optional core-mask operand, (c) ranged form now or later, (d) the completion rule, (e) the broadcast group's definition for dedicated and secure cores (not members by default).

## 6. Instruction-cache coherence, self-modifying code and JIT

**Question.** Instruction caches are not coherent with data caches; `ICINV` (a line) and `ICINVA` (all) exist and are unprivileged (read: `docs/manual/07-smp.md` 7.5.2). What does a JIT or module loader do on 4 and on 16 cores, how does cross-modifying code (one core writes, another executes) work, and what must a speculating, out-of-order fetch do?

**Current state.**
* "`ICINV` exists because instruction caches are not coherent with data caches... a JIT, a trampoline, a loaded module, a Lisp runtime" (read: `docs/pdp64-isa.md:1960`); "coherent instruction caches" listed as avoided (`:1994`). Neither `ICINV` nor `ICINVA` states whether it applies to other cores, or how a core that has already fetched stale bytes is made to refetch. The readiness review: "`ICINV` as written cannot be implemented correctly on a core with an instruction queue without an unwritten rule" and the architecture "has no instruction that makes younger instructions come from the new bytes" (read: `docs/pdp64-ooo-readiness.md:229`); `ISYNC` was added to make `ICINV` take effect (read: `docs/pdp64-isa.md:813`; the manual 7.5.3 and 7.9.3 write the sequence "write, `ICINV`, `ISYNC`").

**History.** PDP-11 and VAX had no instruction cache coherence issue for most models because writes went through to a unified or snooped cache; the PDP-11/70 had a unified cache (from memory, not confirmed). VAX had `REI`-based synchronisation: self-modifying code required an `REI` or similar to flush the instruction stream buffer (the VAX Architecture Reference Manual says "the effect of an instruction modifying the next one is undefined unless an REI intervenes"; from memory, not confirmed). Unix on these did not need it.

**What other systems do.** x86: instruction and data caches are coherent; self-modifying code works, cross-modifying code requires a serialising instruction (`CPUID`) on the executing core after the write becomes visible (Intel SDM cross-modifying-code protocol, from memory, not confirmed). ARM: `DC CVAU` (clean data to the point of unification), `DSB ISH`, `IC IVAU` (invalidate instruction cache by VA, broadcast to the inner-shareable domain), `DSB ISH`, `ISB` on every core that executes it; if the processors are `IDC`/`DIC`-capable the first steps can be omitted (from memory, not confirmed). RISC-V: `FENCE.I` is local; cross-hart requires an IPI and `FENCE.I` on the receiving hart (Linux `flush_icache_all` via SBI remote fence.i, from memory, not confirmed); a later `Zifencei` split. POWER: `dcbst`, `sync`, `icbi`, `isync`. MIPS: `SYNCI`. The common shape: write data, make the data visible, invalidate the instruction side, serialise the fetching core.

**Pain points.** x86's cross-modifying protocol took years to specify (from memory, not confirmed); ARM's four-instruction JIT sequence is a frequent bug source (from memory, not confirmed); RISC-V's local `FENCE.I` forced SBI IPIs (from memory, not confirmed). At 16 cores a broadcast `ICINV` of every line of a loaded module goes to 16 instruction caches; `ICINVA` is one broadcast.

**Options.**

1. **`ICINV`/`ICINVA` are local to the executing core's I-cache; the kernel IPIs the others.** Smallest hardware; software cost in `mprotect(PROT_EXEC)`, module load, JIT. Rejected for 16 cores: the user JIT cannot IPI (the instructions are unprivileged).
2. **`ICINV`/`ICINVA` broadcast to all coherent cores' instruction caches (like `TLBI`), completed by `TLBSYNC` (or an `ISYNC`-like completion), and the executing core executes `ISYNC` before it runs the new code.** The sequence for the writer: stores, then `ICINV` per line (or `ICINVA`), then `TLBSYNC`-style wait for completion (a new wait word is not needed: define that `TLBSYNC` also waits for outstanding `ICINV` broadcasts, one completion instruction for both); for each core that will execute: an `ISYNC`, which discards its fetched but unretired instructions and refetches. How does core B learn that it must `ISYNC`? By the same mechanism that tells it the code exists: a flag, a lock release, a system call return or an IPI; `ISYNC` is unprivileged for this purpose? Currently privileged (read: `docs/pdp64-isa.md:813`): a user JIT must be able to run it. Decide: `ISYNC` unprivileged (it is harmless: it only discards speculative state of the core running it). Gains: one hardware broadcast path shared with `TLBI` (priority 4 Occam), safety: the dangerous case "core B executes stale bytes" is avoided by the rule "after the initiator's wait completes, no core fetches old bytes once it has executed an `ISYNC` afterwards". Costs: a message per line to all instruction caches (use `ICINVA` for big ranges; add a ranged form later, same as TLBI Option 3).
3. **Hardware-coherent instruction caches (snooping I-cache, as x86).** Removes `ICINV` for software; costs a snoop port per I-cache (the ISA's stated reason for refusal, `docs/pdp64-isa.md:1994`), and with an out-of-order fetch queue it still needs a serialising instruction for the cross-modifying case, so the software sequence does not disappear. Rejected on cost, as the ISA already decided; becomes cheaper with a directory-based L2 that already tracks sharers (a code line is a sharer): reconsider only if the directory exists.
4. **Unified L1 for code and data on small cores.** No problem at all on cores whose L1 is unified; a variant not worth a protocol. Skip.
5. **A write to an executable page traps** (W^X by hardware for JIT). OpenBSD enforces W^X (read: `docs/errata.md:189` mention "OpenBSD defaults to PIE and enforces W^X"), so a JIT already maps the page writable, writes, then remaps executable by `mprotect`: the kernel's `mprotect` path can carry the `ICINV` and the TLB shootdown, so a W^X JIT needs no user-visible `ICINV` on OpenBSD; the unprivileged `ICINV` serves Lisp runtimes with other policies. Keep `ICINV` unprivileged; teach the OpenBSD `pmap_protect` / `pmap_enter` with execute permission to issue `ICINVA` plus the completion wait when a page changes from writable to executable.

**Mixed cores.** An in-order core with a short fetch buffer and an out-of-order core with a deep fetch queue, trace cache or branch-predicted prefetch both obey the same rule: the `ICINV` broadcast invalidates the line in the I-cache and marks any fetched-but-unretired instruction from it as invalid *at the next `ISYNC`* (the architecture promises the effect only after the next `ISYNC`, read: `docs/pdp64-isa.md:813`; an implementation may apply it at once and software may not rely on that). That wording stays; it is the right freedom for both classes. A speculative fetch on the OoO core must not have a side effect on a device page (readiness decision 8, read: `docs/pdp64-ooo-readiness.md:34`).

**Lean.** Option 2: broadcast `ICINV`/`ICINVA`, completion by the same wait as `TLBSYNC` (rename to "synchronise broadcasts" in the text, keep the mnemonic), `ISYNC` unprivileged, the four-step sequence written once in the manual: (1) store the code, (2) `ICINV` (or `ICINVA`), (3) `TLBSYNC`, (4) on every core that will run it, an `ISYNC` before the first jump to the new code; in the kernel W^X path the `mprotect` return performs step 4 implicitly (return to user is an exception return, and exception return is defined to discard the fetch queue; verify that statement in the exception text, not read here). Scores: priority 1 (the unsafe case is detected by definition and closed by one rule), 2 (no extra instruction in the common case), 4 (reuse of the broadcast), 5 (the JIT library calls one function), OoO (the rule is the minimal one every OoO ISA has).

**What the author must decide.** (a) Broadcast `ICINV` (Option 2). (b) `ISYNC` unprivileged. (c) One completion wait for `TLBI` and `ICINV`. (d) That an exception return is defined to refetch.

## 7. Ordering with devices and MMIO

**Question.** PCI Express writes are posted (the sender does not wait for completion) while the machine is sequentially consistent. How do cores order writes to devices, and how do devices order their DMA writes and interrupts against what a core reads?

**Current state.**
* F14 lean: "device pages strongly ordered and uncached, with a barrier before every doorbell write" (read: `docs/decisions-pending.md` F14). F24: "an interrupt (MSI-X) write cannot pass the DMA writes that precede it", many vectors per core, atomically retargetable entry, mask while changing (read: `docs/decisions-pending.md` F24); errata 71 applies it as manual 2.5.4 and 5.9.4 (read: `docs/errata.md:221`). `FENCE` orders device accesses (read: `docs/manual/07-smp.md` 7.12.4; `docs/pdp64-ooo-readiness.md:230`). ISA §16: "the architecture owes devices a memory type, an ordering instruction and atomics" (read: `docs/pdp64-isa.md` §4.11.1 `RESET` paragraph). Memory type field `MT`: `01` uncached, `10/11` device types (read: `docs/pdp64-ooo-readiness.md:34`, "a load from an `MT = 10/11` page is performed only when it cannot be on a wrong path"). DMA caches: F5, software-managed.
* IOMMU: F25 accepted (translation on by default, one domain per device, no kernel pointers in descriptors, permanent ring mappings, bounce copies for small buffers) (read: `docs/decisions-pending.md` F25 and `docs/errata.md:235`).
* Atomics against devices: the monitor design says devices that write shared words clear reservations; the Q64 bus mapping is R4/P11 (UNKNOWN) (read: `docs/kernel-pain-points.md:340`).

**History.** PDP-11 Unibus: processor and device accesses were non-posted bus cycles; a device register read or write completed on the bus before the instruction finished, so program order was bus order by construction, and the `DATIP`/`DATO` pair held the bus. VAX: the Synchronous Backplane Interconnect and later buses posted writes in places; the VAX provided `MTPR`-type serialising operations and `REI` as barriers, and drivers on the UNIBUS adapter had to read a status register to flush the adapter's write buffer (from memory, not confirmed: the classical "read back to flush" idiom). Unix drivers carried the idiom of reading a device register after writing a command.

**What other systems do.** x86: UC and WC memory types; UC accesses are strongly ordered and non-speculative; PCIe posted writes are ordered with each other and loads to the device flush them (the "read-to-flush" idiom); Linux has `mmiowb` (read: `docs/kernel-pain-points.md:1911`, the barrier-ordering expression includes `mmiowb`). ARM: Device-nGnRnE (no gathering, no reordering, no early write acknowledgement) and `DSB` before a doorbell; Linux `writel` includes the barrier (`__iowmb`) and `readl` includes a read barrier (from memory, not confirmed). RISC-V: I/O ordering bits in `FENCE` (`fence io,io`, `fence w,o`), PMAs for strongly ordered regions (from memory, not confirmed). OpenBSD riscv64's `virtio_membar_*` uses real fences "even on SP kernels" for exactly this: the device is another observer (read: `<work>/kernel-src/openbsd/sys/arch/riscv64/include/atomic.h:18-21`; arm64: `dmb st`/`dmb ld`/`dmb sy`, `:18-21`; amd64: `mfence` for `virtio_membar_sync` only, `amd64/include/atomic.h:285-287`).

**Pain points.** The ordering of a doorbell against the descriptor that precedes it, and of an MSI-X write against its DMA data, are the classical bugs ("the interrupt write cannot overtake the data writes", read: `docs/errata.md:221`). Speculation reading a side-effecting register (a KL11-style FIFO pop on read) is the out-of-order hazard (readiness decision 8). Thunderclap showed an IOMMU alone is not enough (read: `docs/decisions-pending.md` F25); SRBDS/MMIO stale data shows device register reads leaking internal buffers (read: `docs/hardware-vulnerabilities.md:67`).

**Options.**

1. **F14 as proposed: device pages (`MT = 10/11`) strongly ordered, uncached, non-speculative, and `FENCE` before a doorbell.** The rule stated in full: accesses to device pages are performed in program order, one at a time, never speculatively and never merged; a store to a device page is non-posted from the core's point of view in the sense that the core's next access to *any* page is ordered after the device-page store reaches the root complex's ordering point, *or* the store is posted and `FENCE` waits for it. Choose one. The cheaper for the core is "posted, and `FENCE` drains the posted queue and waits for the root complex's acknowledgement"; the cheaper for software is "non-posted, no `FENCE` needed", which makes every register write stall the core for a PCIe round trip (microseconds); drivers that write many registers (NVMe queue doorbells are one write per batch; xHCI one) pay little. With 16+ cores, one core stalling does not stall the others. Lean: posted plus `FENCE`, with `FENCE` defined as "all earlier loads and stores of this core, to any memory type, are performed with respect to all observers, including devices, before any later access of this core". Under SC for normal memory `FENCE` orders nothing among cores (read: `docs/pdp64-ooo-readiness.md:230`), so its cost is the drain of the posted device writes.
2. **A "write-with-completion" store type or a doorbell instruction** (`MOVQ.D`: store to a device page and wait for completion). Gains: one instruction for the common "register write then wait" pair; costs an opcode and a new store form. Defer: `FENCE` after the write measures the same.
3. **Read-back idiom required by the manual** (as x86 and old VAX): a load from the same device flushes posted writes. Makes the rule device-specific; PCIe guarantees a non-posted read pushes earlier posted writes to the same device only. Not general enough; mention as a fallback, do not rely on.
4. **Interrupts and DMA:** the rule (F24) "an MSI-X write is ordered after the DMA writes of the same device that precede it" is a requirement on the root complex (PCIe ordering already gives this for posted writes on the same path from the same requester, from memory, not confirmed), and on the *core* side: when a core takes the interrupt and reads the data, the read must not be satisfied from a stale line. With software-managed DMA (F5) the buffer is uncached, so no stale line exists; with a coherent DMA port (future), the DMA write invalidates the L2/L1 copies before the MSI-X write is delivered, which the directory (section 4) provides by ordering invalidations before the interrupt message in the same virtual channel. The interrupt entry itself must be ordered after the data on a mixed-core machine: an OoO core that took the interrupt must not have speculatively loaded the data buffer *before* the interrupt arrived and kept it: a speculative load before the interrupt is replayed on invalidation (the load queue rule of section 3) when the DMA write invalidates the line, or, for uncached buffers, speculation past an uncached load is not performed; a rule is needed: an uncached normal-memory (`MT = 01`) load that is not yet retired when an interrupt is taken is re-executed after the handler. Say so (the readiness review's decision 8 covers device pages; extend it to `MT = 01`).
5. **IOMMU interplay (F25).** IOMMU updates (map, unmap, invalidate the IOMMU's TLB) are device operations, not core TLB operations: they are posted writes to the IOMMU's registers or command queue, and the "unmap complete" is a completion event the driver waits for (as `TLBSYNC` for the core TLBs, a separate wait for devices). A device must not DMA to a page after unmap completes: this is the Thunderclap-class window and the same shape as the Rabe window of section 5. Rule: IOMMU invalidation has a status the kernel polls or an interrupt; the kernel does not free or reuse the page until it reads "complete". One completion mechanism per domain (core TLBs: `TLBSYNC`; IOMMU: its own), not merged.

**Mixed cores.** Device accesses go through the same strongly ordered path from every core class; no OoO core issues a device access speculatively; a core's `FENCE` has the same meaning on both classes; the secure core never has a device mapping except through its own queue.

**Lean.** Option 1 (posted, `FENCE` drains and waits for acknowledgement), with the `MT = 01` interrupt-replay extension of item 4 and the separate IOMMU completion of item 5. Write these four statements into the bus chapter; no new opcode.

**What the author must decide.** (a) Posted-plus-`FENCE` against non-posted device stores. (b) The `FENCE` definition. (c) The `MT = 01` replay rule at interrupt entry. (d) IOMMU invalidation completion kept separate from `TLBSYNC`.

## 8. Per-CPU data and the thread pointer

**Question.** How does the kernel find "this core's" data, what do `MFCPUID`, `DP` and the per-mode stack pointers give, how does OpenBSD's `curcpu()` look, and does it still work at 16+ cores with cores of different classes?

**Current state.**
* `DP` has three copies (kernel, supervisor, user): in kernel mode it is the per-CPU pointer, `MOVQ d(DP), Rd` is one four-byte instruction with a 12-bit displacement; in user mode it is the thread pointer (TLS local-exec `MOVQ off(DP),Rd`) (read: `docs/pdp64-isa.md:108,121,1976-1980,2054,2075`; `docs/abi.md:20`; `docs/pdp64-system-architecture.md:18,131`).
* `MFCPUID Rd` returns the core number; "there is no way to synthesize it" (read: `docs/pdp64-isa.md:1951`); the system architecture says it reports only the core number and identification beyond that is open (read: `docs/pdp64-system-architecture.md:59`); a per-core identification register giving class and capacity is decided (read: `docs/manual/07-smp.md` 7.8.3). The stack pointer is banked by mode, so an interrupt from user mode finds the kernel stack (read: 7.4.4).
* `MFDP` and `MTDP` are `SYS` classes 9 and 8, two bytes (read: `docs/pdp64-isa.md:795-799`); `MFCPUID` is class 11, two bytes.

**History.** PDP-11 and VAX had one processor; Unix kept `u.` (the user area) at a fixed virtual address mapped to the current process's kernel stack page (V6/V7 `u` at a fixed address), the VAX `P0BR`/`P1BR` held per-process mappings: both were the first generation of "per-context data at a fixed address", which on an SMP is replaced by "per-CPU data at a base held in a register". VAX multiprocessors had a per-CPU slot in the system's `SCB`-related structures (from memory, not confirmed).

**What other systems do.** x86-64: `GS` base plus `swapgs`, with the entry code needing the kernel `GS` before it can find anything; ARM64: `TPIDR_EL1` (read: OpenBSD `arm64/include/cpu.h:209-212`: `mrs %0, tpidr_el1`), and `TPIDR_EL0` for user threads; RISC-V: the `tp` register holds `curcpu` in the OpenBSD kernel (read: `riscv64/include/cpu.h:148-150`, `register struct cpu_info *__curcpu asm ("tp")`, and `cpu_number()` is `curcpu()->ci_cpuid` at `:170`), with `sscratch` swapped on entry; OpenBSD amd64 `curcpu()` is an inline asm (read: `amd64/include/cpu.h:302`; the `%gs`-relative form is from memory, not confirmed). The repository's kernel survey: seven architectures pay for the problem of no free register at entry (read: `docs/manual/07-smp.md` 7.4 Precedent); `swapgs` is itself a speculation gadget (read: `docs/kernel-pain-points.md:722`); Linux x86's stack protector shares the per-CPU segment (read: `:595`).

**Pain points.** None in the base design; the open points are (i) whether `DP` in kernel mode is correct at the first instruction of every entry (it is: switched with the mode, no swap instruction), (ii) the user `DP` thread pointer is also used for TLS, so the kernel needs a separate way to know user `DP` at entry (it is saved as part of the user context; `MFDP` reads the *current* mode's copy; a way to read the other mode's copy is `MFSR`/`MTSR` and not specified for `DP`, see item 9 of section 9), (iii) a core migrating a thread: the user `DP` is part of the thread's saved state and is restored on switch.

**Options.**

1. **Current design: `DP` = `struct cpu_info *` in kernel mode; `curcpu()` = `MFDP` (2 bytes, one instruction), `cpu_number()` = `MOVQ ci_cpuid(DP)` (4 bytes) or `MFCPUID` (2 bytes); `ci_curproc`, `ci_schedstate` etc. as `d(DP)`.** In OpenBSD `curcpu()->field` is the most common per-CPU access; the displacement 12 bits reach 4 KB of `cpu_info`, which is large enough for the hot fields if the structure is laid out with the hot ones first (it is a kernel layout choice). Cost: zero in the encodings, and the OpenBSD `cpu.h` `curcpu()` is a three-line port. Scoring: (1) safety: no swap instruction, no window in which the pointer is the user's (the failure mode of `swapgs`); a corrupted user `DP` cannot affect the kernel because the kernel copy is separate; (2) fewest instructions: one for a field access; (3) no new encoding; (4) one extra register copy (three `DP` copies); (5) compiler: `curcpu` global register or an intrinsic; OpenBSD's riscv64 uses a global register variable for it (`tp`), which GCC and clang support (read: `riscv64/include/cpu.h:148`); on pdp64 the global register would be `DP`, which is not in the general register file, so the compiler needs an intrinsic or a special address class for `d(DP)` (the existing direct-page mode); (6) assembler: `d(DP)` exists.
2. **Reserve a general register for `curcpu` (MIPS/RISC-V style).** Costs a register of sixteen; rejected, `DP` already exists.
3. **`MFCPUID` only; per-CPU tables indexed by core number.** One more load and a shift per access; supplanted by Option 1. Keep `MFCPUID` for `cpu_number()` where it is cheaper than a load.
4. **Per-CPU stacks and the exception stack:** the banked `SP` gives the kernel stack at entry on a user-to-kernel transition; an interrupt that arrives while already in kernel mode uses the same kernel stack, as on the PDP-11 (the nested case), and a double fault or a kernel stack overflow has a stack-limit register (errata 84 approves the stack limit register, read: `docs/errata.md:234`). Per-CPU interrupt stacks (OpenBSD amd64 has per-CPU `ist` stacks and `ci_intrstack`, from memory, not confirmed) are not required.

**Mixed cores and 16+ cores.** The core number is a small integer assigned at start (R2); the class comes from the identification register (the other part of the document). `ci_cpuid` and the class are stored in `cpu_info`, so the kernel's code is class-agnostic. The kernel must be able to ask "which core number am I" in any state (including the start-up path before `DP` is set): `MFCPUID` does this, and the boot code sets `DP` from the core number (start register convention, appendix H, 7.8.1). At 16+ cores false sharing of per-CPU state (OpenBSD's "8 CPUs per cache line" report, read: `docs/kernel-pain-points.md:509`) is a layout matter: `cpu_info` aligned to the 64-byte architectural line (section 4). A stack-limit register and `DP` copies are per core.

**Lean.** Option 1; fix the ABI statement that kernel `DP` is the `cpu_info` pointer (a convention, not hardware); add `MFDP`-from-another-mode access only if the context switch needs it (the saved user context is in memory). No new encodings.

**What the author must decide.** (a) The kernel `DP` convention as an architectural recommendation. (b) Whether a core can read the other modes' `DP` copies (`MFSR` register numbers for `udp`, `kdp`), needed for ptrace-like debugger code and for saving the user `DP` at a context switch.

## 9. Other open questions in the atomics, memory and coherence area

Each item: **Question**, **Current state**, **Lean**.

1. **Atomics on non-cacheable and device memory.** *Question:* what does `CAS` or `XADD` do on a page with `MT = 01` (uncached) or a device page, and on the secure core's private memory? *Current state:* "the access is atomic with respect to every initiator" (read: `docs/manual/09-isa.md:3084`); the bus mapping is open (R4, P11). *Lean:* atomics to device (`MT = 10/11`) pages are an abort (illegal access) because PCIe cannot guarantee atomicity of arbitrary read-modify-write (it has AtomicOps only on some devices, from memory, not confirmed); atomics to uncached normal memory are performed by the memory controller (far atomics, section 2 Option 3) or abort, decided with R4. A fault that is easy to detect beats a silent non-atomic update (priority 1).
2. **Reservation granule and false cancellation.** *Current state:* granule of the implementation's choice, at least 8 bytes (read: `docs/errata.md:195`), discovery in P4. *Lean:* the granule is the cache line, 64 bytes, an architectural constant; software must not share a lock word with data it also writes (OpenBSD's comment: lock word and data not in a line, read: `docs/kernel-pain-points.md:724`); the compiler aligns lock words with `__aligned(64)` attribute in a structure's layout.
3. **Core-to-core wake-up at 16 cores: `WFE`/`SEV`.** *Question:* `SEV` is a broadcast to all waiting cores (read: `docs/pdp64-ooo-readiness.md:231`); at 16 cores a thundering herd. *Current state:* P1 recommends wake on a pending interrupt and `SEV` sticky for one wait. *Lean:* `WFE` also wakes when the exclusive monitor/reservation line the core holds is written (ARM's behaviour, from memory, not confirmed), which makes a ticket-lock waiter sleep on the lock line with no `SEV` at all; add this as a clause of P1 (priority 4: no spin power); `SEV` stays a global event, and targeted wake-up is the IPI (R2).
4. **Mixed-size and overlapping accesses** (CAS over two 4-byte fields, byte store into an atomically updated word). *Current state:* manual 7.2.6 and 9.13.2. *Lean:* keep: SC is per byte and the cache performs all atomics on the line, so mixed sizes cost nothing here; the litmus plan includes them (section 3). This is where ARM and POWER fail (read: `docs/kernel-pain-points.md:1408`).
5. **Order inside multi-access instructions** (`MBLK`, `PUSHM`, `POPM`, `PUSHX`): section 3 lean.
6. **Livelock/interrupt latency of long `LL`/`SC` sequences and `MBLK`.** An interrupt cancels the reservation (section 2); `MBLK` is bounded by its granularity (ISA open item 5, read: `docs/pdp64-isa.md` open item 5, "an implementation claiming an interrupt-latency figure must state its block granularity"). Nothing to add at 16 cores except that the granularity statement belongs in the class register for the same reason as the granule.
7. **Open item 4 (bus lock against monitor):** closed by errata 45; remaining work: the ISA text of 17.6 still reads as open (read: `docs/pdp64-isa.md:2000`); the reservation tests in sim64 (no `ATOM` in the executor), QEMU and the litmus suite. The simulators cannot test any of this until `ATOM` is implemented, which depends on the placement of section 1: the placement is therefore on the critical path of SMP verification.
8. **Hardware vulnerabilities rules for SMP.** *Current state:* no SMT is a design property (rule C6, read: `docs/hardware-vulnerabilities.md:157`), the TLB is per core (TLBleed), atomics timing depends on contention, `TLBI` broadcast cost depends on other cores (read: `:119,123`). *Lean:* SMT stays absent for every core class (an SMT core would fall under C6 and multiply the memory-model cases); cross-core channels (coherence timing, shared L2 and directory) are handled by the secure core's no-sharing rule (section 4); speculative coherence side effects (section 4, mixed-core paragraph) are covered by the existing speculation rules; add to the vulnerabilities document a rule "a speculative access never changes another core's cache line state" so that an out-of-order core joining the machine cannot be a probe of an in-order core's lines.
9. **Core hot-unplug and stop-and-drain.** *Current state:* stop-and-drain register (7.8.3); pain-points row 240 (CPU hotplug for RAS) is OPEN (read: `docs/kernel-pain-points.md:1813`). *Lean:* a stopped core's cache must be written back and its TLB and reservation cleared, and it must leave the broadcast group and the directory before the register says stopped; state it with 7.8.3.
10. **Boot-time consistency of core classes.** The boot code reads each core's identification register; any difference in an architectural parameter (line size, granule, page size, memory model version, ASID width) is a fault, section 3.
11. **Debugging and the memory model.** A breakpoint or single-step must not change the order other cores see; the debug interface of the FPGA plan (halt, single step, read registers) halts a core at an instruction boundary after its store buffer has drained (stated here as a rule for the debug unit, from design reasoning, not from a source).

## 1. R1: the interrupt controller and routing to cores

**Question.** How does an interrupt reach one of four to sixteen-plus cores: wired lines or messages, how many vectors per core, how are priorities kept, how is a device's interrupt moved from one core to another without losing or doubling one, and what is done about spurious interrupts and non-maskable interrupts?

A **message-signalled interrupt** (MSI-X on PCI Express: the device does an ordinary memory write whose address and data say "interrupt this core with this vector", so the interrupt is a store and needs no wire). **Affinity** (which core a given interrupt is delivered to). **Remapping** (a table in the IOMMU between the device's write and the core, so the device never knows the real core number).

**Current state.**
- The PSW has eight priority levels; `SPL #n` sets the level; exception and interrupt entry set level 7 (read: docs/decisions-pending.md Q4 around line 748, errata 36 and 40; P14 at line 506 asks the author to confirm 7 on interrupt entry).
- R1 (interrupt controller, line 1083) was recommended as option 1 (wired lines plus messages, per-core threshold) and revised to option 2 (wired lines to core 0 with a per-line target register, messages later). Part F then made MSI-X standard: F2 (decided in outline by errata 80: standard enumeration and MSI-X replace slot vectors), F24 (the interrupt write cannot pass the DMA writes before it; many vectors per core; an atomically retargetable entry; a mask while an entry changes; lean: write all three into the bus chapter), F25 (IOMMU hardening, accepted by errata 85), F12 (fixed non-PCI devices: timer, interrupt controller, UART, through a small device tree). (read: docs/decisions-pending.md:1563-1600)
- Errata 71 applied 2.4.4 and 5.9.4 (the interrupt write cannot overtake data writes; a moved interrupt target is masked and read back or written atomically). Manual 7.8.2 says routing is device-side and unspecified. (read: docs/errata.md:221; docs/manual/07-smp.md 7.8.2)
- The revised R1 lean (wired lines to core 0) predates the author's 4-minimum, 16-preferred decision and the standard NVMe, virtio-net and xHCI devices, all of which are MSI-X devices that want a vector per queue. The revised lean is therefore out of date.

**History.**
- PDP-11: no controller. A device raised one of the bus-request lines BR4 to BR7 and supplied its own vector; the processor arbitrated by priority. Eight levels in the PSW is the heritage the PDP-11 gives us (read: docs/decisions-pending.md:1103).
- PDP-11/74 and the multiprocessor 11/70 family: shared memory with a second processor on a multiport memory; interrupts were per processor, with no common controller (from memory, not confirmed). Unix on them was a research port, not a product.
- VAX: 32 priority levels (IPL), vectors through the System Control Block. The VAX-11/782 attached processor and the 8300 and 8800 families were asymmetric or symmetric depending on the model; on the 11/782 the attached processor had no I/O and the primary took all device interrupts (from memory, not confirmed). On the VAX multiprocessors the "interprocessor interrupt" was a write to a per-processor interrupt-request register at a software IPL (the `SIRR` register requests a software interrupt at a level, and an interprocessor interrupt at IPL 14 on some models) (from memory, not confirmed). The lesson that matters: the machine that routed every device interrupt to one processor was the simplest and became the bottleneck.
- Unix: the first multiprocessor ports (Purdue's Unix on dual VAX-11/780, the "master/slave" scheme where the slave runs only user code and calls the master for every system call; Sequent, Encore and others used a giant lock) show that the interrupt side was solved by sending every device to one processor first and spreading later (from memory, not confirmed).

**What other systems do.**
- x86: the 8259 pair, then the APIC (a local APIC per core, an I/O APIC for wired lines) from the Pentium (1990s), x2APIC with 32-bit IDs, MSI/MSI-X for PCI Express devices; interrupt remapping in the IOMMU (VT-d) so a device cannot forge a destination (from memory, not confirmed). Linux: "the interrupt vector space is notoriously low, providing only 256 vectors per CPU" and managed affinity for NVMe's one-queue-per-CPU (read: docs/kernel-pain-points.md:104, 1398 quoting Linux Documentation).
- ARM: the GIC (distributor plus per-core interface, GICv3 redistributors, the ITS for translating messages) with 16 software-generated interrupts per core as IPIs (from memory, not confirmed); OpenBSD's driver `agintc.c` is 2,166 lines (read: sys/arch/arm64/dev/agintc.c).
- RISC-V: PLIC (wired, a priority and threshold per context; OpenBSD `plic.c` 737 lines), then the AIA: APLIC (wired lines turned into messages, 228 lines) and IMSIC (an "incoming MSI controller", one interrupt file per hart, 375 lines) (read: sys/arch/riscv64/dev/). The AIA design is the closest published match to what is proposed below: one file per hart, wired lines converted to messages.
- POWER: OpenPIC, XICS, then XIVE with per-queue notification (read: docs/decisions-pending.md:1101 lists OpenBSD powerpc64 `xics.c`, `xive.c`). s390: the interruption subclasses and the floating interrupt (from memory, not confirmed). MIPS: per-core CP0 interrupt lines plus an external controller. SPARC: the UPA/JBus interrupt dispatch with a mondo vector to a chosen CPU (from memory, not confirmed).

**Pain points.**
- docs/kernel-pain-points.md:98 (shared level lines, "nobody cared", storms: the kernel kills a line after 100,000 interrupts if more than 99,900 are unhandled).
- :100 and :946 (a pin interrupt can arrive before the data; message interrupts fix the ordering problem behind a bridge).
- :104 (vector scarcity and affinity as a mask; suspend moves every interrupt to one CPU and can exhaust vectors).
- :68, :917, :918 (NMI nesting: an `IRET` unmasks the NMI; a 2012 rework by Rostedt; a three-state machine, still in `nmi.c`).
- :941, :945 (boot interrupts and lying firmware in the I/O APIC), :590 (spurious interrupts are device quirks), :1082 (affinity is a mask the controller may ignore).
- docs/kernel-pain-points.md:414-425 (the interrupt section; the pdp64 verdict "spurious/storm handling: same problem, a device property, R7").

**Options.**

1. **Wired lines to core 0 with a per-line target register (the current revised lean).** One wire per device and a table of targets. Gains: smallest; PDP-11 style. Costs: PCI Express devices raise messages, not wires, so this needs an adapter anyway; sixteen cores all interrupted through one front door; a per-queue NVMe interrupt cannot have its own target. Score: (1) safety: retargeting a wired line is a register write the device does not see, good; but legacy shared-line "nobody cared" storms exist (--). (2) ok. (4) smallest gates (++). OoO: neutral. Does not meet the author's MSI-X standard; reject except for the three fixed devices.

2. **Message-signalled only, with an interrupt file per core.** Each core has a 4 KB page in the controller's address range: `base + 4096*core`. A store of a vector number (8 bits, so 256 vectors per core) to the page sets that vector's pending bit in the core's file. Each vector has a 3-bit priority level and an enable bit held in the file. The core takes the highest pending, enabled vector whose level is above the PSW level; the vector number goes into `ECAUSE` at entry (errata 36), so no memory read is needed to learn who interrupted. Gains: scales to any core count; the same write is the IPI (§2); the PSW level remains the only threshold, so there is no per-core threshold register to keep consistent with it; no "claim" read, one memory fetch fewer per interrupt than PLIC or GIC (priority 2). Costs: a legacy wired source needs a converter (below); the file is state per core (256 pending bits + 256 enables + 256 x 3 level bits is about 1,300 bits, a few hundred LUTs or one small RAM). Score: (1) ++ if the rules below hold; (2) ++; (3) n/a; (4) + ; OoO ++ (the pending file is outside the pipeline; taking an interrupt is a precise exception at retire).

3. **Option 2 plus an IOMMU interrupt-remapping table.** The device's MSI-X write carries a table index, not a core number; the IOMMU maps index to (core, vector, level) in a 64-bit entry. Retargeting is one atomic 64-bit store to the entry; no mask-write-unmask dance in the device; a device cannot send an interrupt to any core or vector except those the kernel put in its table (security: F25 L6 "interrupt remapping"). The processor-side table is invisible to cards, so under errata 81 it needs no announcement. Gains: F24's three requirements (many vectors, atomic retarget, mask during change) are met by construction because the entry is 64 bits and written atomically (part A: single-copy atomicity of an aligned 8-byte store, 7.2.3); the kernel can disable one device's interrupts by clearing its table range even if the device is hostile. Costs: an IOMMU table walker for every interrupt write (a small cache of entries; the IOMMU already exists for DMA); another structure to size. Score: (1) ++ (an error that cannot arise: a forged interrupt); (2) +; (4) -; OoO neutral.

4. **A GIC-style distributor with an ITS.** A central block holds all state and forwards. Gains: matches ARM software. Costs: a large block, 2,166 lines of OpenBSD driver for the GIC alone (read: agintc.c), no benefit over option 3 for a design with no legacy. Reject.

5. **No controller; core 0 forwards by IPI.** Costs two interrupts per device interrupt and serialises sixteen cores through one. Reject, kept as the fallback if the controller is late: it works with part of the interrupt file (IPI only).

**Design details for the lean (option 3), the points the author asked about.**
- *Wired to message.* The timer is per core (§4). The UART and the few fixed devices (F12) have level wires into a small converter (the RISC-V APLIC does this) that writes to a configured core's file when a line goes active and again when it is re-armed after being serviced (level semantics: the converter keeps the line "pending-in-flight" until the handler acknowledges by a register write, so a level line cannot flood the file). Edge and level are a property of the converter, not of the core.
- *Vector count.* 256 per core; levels 3 bits; one level can hold many vectors. NVMe wants one completion queue per core plus an admin vector, so 16 cores need 17 vectors from one device; 256 per core is ample (Linux's complaint is 256 total shared by all device classes on x86, read: :104). A MSI-X table has up to 2,048 entries per function (PCI Express specification, from memory, not confirmed), so the remapping table must be able to hold a few thousand entries; a one-level table with 8 KB (1,024 entries of 8 bytes) per device range is enough for iteration one.
- *How a device's write reaches the core.* Device MSI-X write goes up the PCI Express link as a posted write, to the root complex, to the IOMMU (index to entry), to the interrupt file of the target core. F24: the interrupt write may not pass the data writes before it from the same device. PCI Express posted writes from one function keep their order (PCI ordering rule, from memory, not confirmed), so the rule is: the root complex does not reorder the interrupt write ahead of the same device's earlier posted writes to memory, and the file's pending bit is set only after those writes are globally visible (the memory system's completion; part A's device-ordering section F14 owns the exact rule). This is the property that makes it unnecessary for a handler to read a device register to flush (read: pain row :100).
- *Spurious.* In this design a pending bit is set only by a store and cleared only on delivery or by writing the file, so the vector that arrives is always one that was requested; the "spurious" cases left are (a) a vector whose handler is no longer registered (software), (b) a retargeted entry where the old core already holds the pending bit: the kernel clears it by writing the old core's file after masking, and the remaining race is closed by the device-side "mask, read back, retarget, unmask" of F24 or, with remapping, by "invalidate the entry, store a clear to the old file". A device that interrupts without cause is a device bug the kernel can silence by invalidating its entry range (detect and cheap to recover, priority 1).
- *Priority.* Vector to level is a 3-bit field in the file, so eight levels remain. OpenBSD's interrupt priority levels are twelve in the riscv64 port (`IPL_NONE` 0, `SOFTCLOCK` 2, `SOFTNET` 3, `SOFTTTY` 4, `BIO` 5, `NET` 6, `TTY` 7, `VM` 8, `AUDIO` 9, `CLOCK` 10, `HIGH` 11, `IPI` 12; read: sys/arch/riscv64/include/intr.h:45-58), so eight hardware levels need a map; see §8.
- *Level 7 on entry (P14).* Every entry masks everything, so IPIs and device interrupts cannot nest into the entry sequence; the handler lowers the level. This keeps nesting out of the first instructions at the cost of one `SPL` per interrupt.
- *Interplay with idle.* A core in `WFE` wakes when a pending bit becomes visible to it regardless of level (§3). The file raises a wire to the core: the "interrupt pending" signal is the OR over enabled pending vectors above... see §3: the wake is on any enabled pending vector, the take is on level.
- *NMI.* The known pain is that an NMI cannot be masked, so any return instruction that re-enables NMIs lets a second NMI in on a stack already in use (read: pain rows :68, :917-918). Options: (a) no NMI; (b) an NMI vector delivered on a separate register set. Lean: (a) plus a hardware substitute: the stop-and-drain register of 7.8.3 (and its sibling, a freeze request) acts on a core from outside, without an interrupt, so a panicking core can stop its fellows even when they spin at level 7. The debug and panic case needs a register file readable by the stopping core after the stop (a "halted-state window" per core in the controller; details for the author to approve). The cost is that a core hung in a loop with a held lock can be frozen but not made to run a handler. That is the right trade for priority 1 ("an error that can never arise"): no NMI nesting state machine at all.

**Lean.** Option 3, with the interrupt file as the only delivery mechanism (wired lines are converted at the edge, and the earlier revised lean of core-0 wiring is withdrawn), eight levels kept, the vector delivered in `ECAUSE`, no NMI, stop-and-drain as the external stop. It satisfies F24 (all three requirements), F25 L6, errata 81, and is the least new software for OpenBSD because a driver of the shape of `imsic.c` (375 lines) plus `aplic.c` (228) is the model (read: those files) rather than the 2,166-line GIC.

**What the author must decide.**
(a) Confirm that the interrupt file is the single delivery path and the earlier core-0 wiring lean is dropped. (b) 256 vectors per core and 8 levels, or fewer vectors. (c) Whether the IOMMU remapping table is in iteration one (needed for sixteen cores and for hostile devices) or iteration two. (d) No NMI, with stop-and-drain as the external stop: accept, or require an NMI. (e) Whether priority 7 on interrupt entry (P14) is confirmed; this design assumes yes.

## 2. R2: inter-processor interrupts, starting and stopping cores

**Question.** How does one core interrupt another (and many at once), how do the other cores leave reset, what happens at sixteen cores, how is a core taken offline, and how is the secure core stopped without a tick?

An **inter-processor interrupt** (IPI: one core raises an interrupt on another core). A **doorbell** (a register whose write wakes or interrupts the owner). **Parallel secondary-core release** (letting all cores out of reset in one operation instead of one at a time).

**Current state.**
- R2 recommended per-core doorbell registers and cores held in reset released by an entry-address write (option 1); the decision is not recorded (read: docs/decisions-pending.md:1111-1133). B2 in docs/boot.md recommends the same with core number in `r0`, priority 7 (read: docs/boot.md:134-150).
- Appendix H, 7.8.1 to 7.8.3 (moved from chapter 7), is proposed (P): cores other than 0 held in reset, a per-core start register with entry address and argument; an IPI is a write to a per-core register. 7.8.3 is decided (D): read-only class and capacity register, and a stop-and-drain register that finishes outstanding bus transactions and stops the core. (read: docs/manual/07-smp.md)
- The secure core is "stopped or preempted by an inter-processor interrupt from a general core (the doorbell and the stop-and-drain register)"; class selection is writable only while the core is held in reset and locks when the start register is written (read: docs/crypto-secure-core.md:92, 113).
- Translation-buffer shootdown is a broadcast `TLBI` + `TLBSYNC`, so no IPI is needed for it (part A; read: manual 7.5.1). Instruction-cache invalidation `ICINV` is local to the core that executes it unless it is broadcast: cross-modifying code has no rule yet (read: docs/kernel-pain-points.md:458). That is the one place an IPI may still be needed for memory consistency; part A owns it.

**History.**
- VAX: an interprocessor interrupt was a write to a processor register (`IPIR` on some models, `SIRR` for a local software interrupt at a given level) and the secondary processors were started from the console subsystem; the 8800 and the 782 had a console processor that did the start (from memory, not confirmed). The docs record that "those designs relied on the console processor and an elaborate firmware" (read: docs/decisions-pending.md:1131).
- PDP-11: the 11/74 multiprocessor and the dual-processor 11/70 variants signalled through shared memory and a mailbox; the processors were started by front panel or reset (from memory, not confirmed).
- Unix: master/slave (one CPU runs all kernel code, others run user code) and then a giant lock (one lock for the whole kernel, as in the early SMP ports of 4BSD, SVR4-MP and OpenBSD's `KERNEL_LOCK`). The giant lock makes IPIs rare and simple (reschedule and stop); OpenBSD's riscv64 port today needs two IPI kinds, `IPI_NOP` and `IPI_DDB` (read: sys/arch/riscv64/include/intr.h:199-200) and amd64 about a dozen (read: sys/arch/amd64/amd64/ipifuncs.c: halt, nop, reload pctr, reload mtrr, ddb, vmm clear/start/stop, wbinvd, xcall). That tells us that most amd64 IPI kinds exist because of x86 hardware, not because the kernel needs them.

**What other systems do.**
- x86: the ICR (interrupt command register) write sends an IPI to one, to a logical group, to all, or to all-but-self; INIT then two START-UP IPIs release an application processor which wakes in 16-bit real mode (from memory, not confirmed; read: docs/boot.md lists 1,528 lines of x86 start-up code). x2APIC has a single 64-bit MSR write; the logical cluster mode allows 16 targets per message.
- ARM: software-generated interrupts (SGIs) through the GIC with a target list; start is PSCI `CPU_ON` (a firmware call) or a spin table (read: docs/boot.md:55-56 gives 124 and 127 lines). OpenBSD arm64 has four IPI kinds: NOP, DDB, HALT, XCALL (read: sys/arch/arm64/include/intr.h:201-204).
- RISC-V: SBI calls `sbi_send_ipi(hart_mask)` and HSM `hart_start(hartid, start_addr, opaque)`, `hart_stop`, `hart_get_status` (read: sys/arch/riscv64/riscv64/sbi.c:103-123 and intr.c:734-770); newer: ACLINT's MSWI (one memory-mapped software-interrupt register per hart) and IMSIC for message IPIs (from memory, not confirmed). The riscv64 OpenBSD IPI is: set a bit in `ci_ipi_reason`, send SBI IPI; the handler does `atomic_swap_uint(&ci->ci_ipi_reason, IPI_NOP)` (read: intr.c:741-767).
- POWER: `OPAL` start-secondary calls and doorbell `msgsnd` instructions (from memory, not confirmed). s390: `SIGP` instruction with order codes (sense, start, stop, restart, set prefix) per CPU address: an IPI plus start/stop in one architected instruction (from memory, not confirmed). MIPS: cluster power controller `smp-cps.c` 976 lines (read: docs/boot.md:48).

**Pain points.** docs/kernel-pain-points.md:152 and :638 (starting other cores is a polling loop: "polls for up to 10 seconds", 305 to 405 microseconds per core on a four-core desktop, Len Brown 16 Aug 2015; mitigated by an event-based release); :301 (shootdown IPI designed away); :516, :521, :649 (IPI deadlocks and shootdown storms: "interrupted roughly 900K times per second" on 48 CPUs, NetBSD one shootdown per FFS block, NetBSD IPI deadlock); :841-842 (the first NetBSD SMP API left lock ownership and priority undefined; "the overhead to enter a C language context is considerable"); :710 and :1273 row C9b (CPU hotplug with unlike cores: manual has no text); :1435 (hotplug reasons: provisioning and RAS).

**Options.**

1. **The IPI is a message to the target's interrupt file (the lean of §1).** A store of a vector number to `base + 4096*core` is an IPI. Reserved vectors name the reason, so no shared `ci_ipi_reason` word is needed: four vectors cover OpenBSD's four needs (nop/wake, halt, ddb, xcall), and a fifth, "panic stop", costs nothing. Gains: one mechanism for devices and cores; no new register block; the vector arrives in `ECAUSE` so the handler needs no atomic swap of a reason word (one fewer atomic and one fewer cache line to bounce per IPI than riscv64's `ci_ipi_reason`); a core can send itself a software interrupt (needed for soft interrupts, §8). Costs: who may write the page matters (kernel only: the interrupt file pages are device-half addresses never mapped into user space, and the IOMMU does not map them for any device except through the remapping table); IPI latency equals a posted store to the controller plus the pending-to-take path. Score: (1) +: no forged IPI from a device because it can reach the file only through remapping; (2) ++; (4) ++; OoO ++.

2. **Option 1 plus a multicast register.** A 64-bit store of `(mask << 8) | vector` to a controller register sends the same vector to every set core in a group of 56 (a group-select field covers more than 56, so 256 cores = five groups); one store instead of fifteen at 16 cores. Gains: the broadcast cases (halt all, panic stop, xcall to all) cost one instruction rather than N-1; IPI storms like the 900K/s case (read: :521) are less likely because the kernel batches by design. Costs: one more register (a few LUTs). Score: (2) ++ for the all-cores case; (4) +. Recommended as an addition to option 1.

3. **A software-interrupt bit per core in a system register (RISC-V `ssip`).** `MTSR` raises the bit on the current core only; a remote raise needs the controller anyway. Reject as the IPI path; the self-interrupt case is covered by option 1.

4. **SBI-like or PSCI-like firmware.** A call into a monitor to send IPIs and start cores. Gains: the register layout is hidden. Costs: the pdp64 has no firmware layer (P7 option 2 and docs/boot.md recommend against); an extra mode, a trusted component, and the OpenBSD riscv64 port has `sbi.c` and a full `SBI_CALL` machinery only because of that layer. Reject: hardware registers are fewer lines and do not add privilege levels.

5. **Spin table: cores park in `WFE` on a mailbox in memory.** Gains: no release logic. Costs: trust in memory contents that the first stage wrote; secondaries run before the kernel has set protections; polling at boot. Reject as the primary; keep as the fallback for a board whose controller lacks the start register.

**Starting cores (B2) at sixteen.**
- Per-core start register `START[n]` (entry address, argument) plus `STARTMASK`, a mask register: writing the mask releases every core named in it at once, each core reading its own entry and argument. The riscv64 call is serial (one `hart_start` per hart; read: cpu.c:603-625, 630-650); at 305 to 405 microseconds per core (read: :638) 16 cores take 5 to 6 ms serially; parallel release is not about speed at this scale but about having no polling loop to time out. The argument register (`r1`) holds the address of a per-core structure so the core finds its stack with no table lookup; `r0` holds the core number (docs/boot.md B2).
- Reset state of a secondary: kernel mode, priority 7, translation off, `UA` = 0, same as core 0 (read: docs/boot.md:277). Then the secondary must turn translation on with the same page tables: in the riscv64 port `cpu_hatch_secondary` passes a physical start address (read: cpu.c:639-644).
- The class and configuration register is writable only in reset, locked by the start write (read: crypto-secure-core.md:113). A mismatch between requested and capable class sets a status bit and the core does not start: detected, not run.
- A core that never starts is reported by the start register's status (started, in reset, faulted), not by a timeout.

**Stopping and hot-plug.** Stop-and-drain (7.8.3): the kernel writes the register, the core finishes outstanding bus transactions and stops. The sequence to offline core N: (1) scheduler marks it halt-wanted and it idles (OpenBSD does this with `SPCF_SHOULDHALT` and `SPCF_HALTED`, read: kern_sched.c:194-202, and `sched_stop_secondary_cpus` in sched.h), (2) interrupts for it are retargeted away by writing remapping entries (§1), (3) write stop-and-drain, (4) the status register shows stopped. Open: the memory-coherence side of stopping a core with a dirty cache (flush before the stop, or the drain includes a write-back); part A owns it. For the secure core a stop includes zeroization (read: crypto-secure-core.md:115): stop, clear the private window, then the core may be reconfigured. Hot-plug of an additional core after boot is not required by OpenBSD (it has no true CPU hotplug on these ports; the mechanism is "block" a CPU type by `hw.smt`/`hw.blockcpu`, read: kern_sched.c:875-930) (from memory, not confirmed that OpenBSD has no hotplug).

**Secure-core stop by IPI.** An IPI to the secure core is an interrupt, so it is taken at the next instruction boundary (or the next block boundary of an `MBLK`), with the five handler rules of 1.5 (read: crypto-secure-core.md:94-100). Extra rule for sixteen cores: the secure core's interrupt file receives IPIs only from the kernel, and an IPI storm from other cores must not change its timing: section 1.6 of the secure-core document reserves interconnect slots; the file read inside the core is local (no bus), so the cost of an IPI to it is the fixed handler cost.

**Lean.** Options 1 and 2 together: IPI = message into the interrupt file; a multicast register; four architected IPI vectors; start register per core with a mask for parallel release; stop-and-drain as the offline mechanism. No firmware layer. This leaves exactly the IPI set OpenBSD's arm64 port uses (NOP, DDB, HALT, XCALL; read: arm64 intr.h:201-204).

**What the author must decide.** (a) Confirm IPI = interrupt-file store, no separate doorbell register block, no firmware. (b) The multicast register and its group size. (c) The reserved vector numbers for the four IPIs (an ABI item for the port). (d) Whether stop-and-drain writes back dirty cache lines. (e) Whether `ICINV` broadcasts (then no IPI for code patching) or an IPI is the cross-modifying-code answer (part A).

## 3. P1: the `WFE` wake rule and the idle loop

**Question.** What ends a `WFE` sleep, how can an idle loop check for work and sleep with no gap, and can the same instruction make a spin lock sleep instead of burn?

A **lost wake-up** (the event arrives after the check for work and before the sleep, so the sleep never ends). An **event register** (one sticky bit per core that `SEV` sets and `WFE` consumes). **Spinning** (re-reading a lock word in a loop).

**Current state.** `WFE` (kernel only) sleeps until an interrupt is taken; `SEV` sends an event; P1 is open; the proposed rule is "wake on a pending interrupt even if the priority masks it", with the loop `SPL #7`, check, `WFE`, `SPL #0`; `HINT #1` is the pause (read: docs/decisions-pending.md:138-160; manual 7.6.1-7.6.3). The survey adds that `SEV` should be sticky for one wait (read: :160). A verification note says RISC-V `wfi` is weaker than assumed and AArch64 was not confirmed (read: :160 and :1655).

**History.** PDP-11: V7's idle was `wait` at priority 0 in a loop that rechecked the run queue after every interrupt, so a lost wake-up cost one clock tick (read: manual 7.6 commentary). VAX: no idle instruction on early models; VMS and BSD looped on the run-queue summary; later models had a `HALT` equivalent (from memory, not confirmed). Unix on multiprocessors: the idle process spun on the run queue; spinning idle processors starved the memory bus of the busy ones, which is why the Sequent and Encore ports added back-off (from memory, not confirmed).

**What other systems do.**
- ARM: `WFE` sleeps until an event; events are `SEV`/`SEVL`, an interrupt, and the clearing of the global exclusive monitor, which is what lets `LDAXR; WFE` spin-waiters sleep until the lock holder's store (from memory, not confirmed; the idiom is how Linux arm64 spinlocks wait). `WFI` sleeps until an interrupt (read: Linux `arm64/kernel/idle.c` in docs/decisions-pending.md:156).
- RISC-V: `wfi` ends when an interrupt is pending and enabled in its own register, whatever the global enable bit says, and an implementation may treat it as a no-op (read: :156, :160). The `Zawrs` extension adds `wrs.nto`/`wrs.sto` to wait on a reservation (read: docs/kernel-pain-points.md:569).
- x86: `HLT` after `STI` (the interrupt shadow makes `sti; hlt` safe); `MONITOR`/`MWAIT` waits on a write to a cache line (from memory, not confirmed); `PAUSE` is the spin hint with a delay (read: :156 counts hlt 57, mwait 9).
- OpenBSD's own loops: `sched_idle` checks `spc_whichqs == 0` and calls `cpu_idle_cycle()` inside a loop (read: kern_sched.c:192-205). The riscv64 `cpu_idle_cycle` is `intr_enable(); wfi` with a comment `XXX Data Sync Barrier?` (read: sys/arch/riscv64/riscv64/machdep.c:201-206). An interrupt that lands between the loop test and `wfi` is taken, queues work, returns, and `wfi` then sleeps with work waiting. Today the next clock interrupt repairs it, within one tick. On a tickless core there is no next tick. This is the concrete reason P1 matters for the author's tickless direction. `cpu_unidle` sends `IPI_NOP` to a sleeping core (read: cpu.c:687-697).
- OpenBSD's spin loops: `__mp_lock_spin` loops on a ticket with a spin-out counter `__mp_lock_spinout` and `spc_spinning++` (read: kern_lock.c:134-153) and mutexes spin similarly; both use the per-architecture busy-wait hint (from memory, not confirmed which macro).

**Pain points.** docs/kernel-pain-points.md:341 (spin-wait hint, mitigated; the lost-wake race of the idle loop is P1), :424 (lost wake-up in the idle loop: UNKNOWN pending P1), :569 (Zawrs), :830 (contended CAS collapses: "~25x retries" at 28 threads; `cpu_relax` turns into one no-op on ThunderX2), :476 (power management: WFE only).

**Options.**

1. **Wake on any pending interrupt (enabled in the interrupt file, any level); `SEV` sticky for one wait.** Idle loop: `SPL #7`, test, `WFE`, `SPL #0`. Gains: closes the gap with no new instruction; two rules in the core, no opcode. Costs: a core wakes for an interrupt it will not take for a while (it then takes it at `SPL #0`: intended). Score: (1) + (the window cannot arise); (2) ++; (4) +; OoO: the wake is at retire, the sleep a serialising instruction, neutral. This is the current proposal (P1 option 1 or 2).
2. **Option 1 plus: `WFE` also ends when the reservation held by a preceding `LL` is lost** (a write to the granule by any initiator, the same event that makes `SC` fail; manual 7.3.1). A spin wait becomes `LL r, lock; test; WFE`: the core sleeps and wakes when the holder's ordinary release store hits the line. The unlocker executes no `SEV`. Gains: unlock stays one store (priority 2: fewer instructions executed in a hot loop; the Linux arm64 lock idiom) and a lock waiter in a 16-core machine costs no bus bandwidth; the same rule gives a lost-wake-free "wait for a flag". Costs: the monitor must stay armed while sleeping (it holds a granule tag; the cache keeps the line shared and watches invalidations, a few gates); a spurious wake is allowed (so the loop re-reads). Score: (1) + (a waiter cannot miss the release: the same argument as `LL/SC`); (2) ++; (4) + (less spinning traffic is power); OoO +. Needs a statement that the reservation survives the sleep; part A owns the reservation semantics.
3. **`WFE` takes a priority operand** (P1 option 3: sleep then run at level n). One instruction does lower-and-sleep. Gains: no `SPL` around. Costs: new operand form to encode and verify; loses to option 1 where the existing loop is two instructions. Not preferred.
4. **A timeout form `WFE` with a deadline** (like `Zawrs`' `wrs.sto` short timeout). Gains: a waiter cannot sleep forever if the wake source breaks; useful for the secure core's bounded waits and for a watchdog. Costs: an operand. Keep as a later extension.
5. **No `WFE`, poll with `HINT` pause.** Burns power and bandwidth; reject (read: :154).

**Lean.** Option 2 (which contains option 1). In the OpenBSD port, `cpu_idle_cycle` becomes: raise to level 7, test `spc_whichqs`, `WFE`, lower to 0. That is a machine-dependent function that does its own re-test, which the riscv64 version cannot do because it is called after the generic loop's test. The generic loop in kern_sched.c re-tests after return, so the pair is correct. Mutex and `__mp_lock` spin loops use the `LL; WFE` form in the port's `mplock.h`/`cpu.h` macros (10 lines per port in riscv64's `mplock.h`; read: sys/arch/riscv64/include/mplock.h).

**What the author must decide.** (a) Option 1 only, or option 2 (the reservation wake). (b) Whether the wake from `WFE` considers disabled vectors (this design: only enabled vectors in the file wake it; a disabled one does not). (c) Whether a timeout operand is architected now. (d) The spin-lock policy: ticket (what OpenBSD has, read: kern_lock.c:157-175) versus queue, at 16 cores; a pain row shows the ticket lock scaling badly (read: manual 7.3 commentary, "155% worse than an Anderson lock").

## 4. Timers

**Question.** Where do timer interrupts come from on four to sixteen-plus cores, how do cores agree on the time, and how does a core run without a periodic tick?

A **tick** (a timer interrupt at a fixed rate, 100 or 1000 per second, that the kernel uses for scheduling and timekeeping). **Tickless** (the kernel programs the next timer interrupt only for the next needed event, and an idle or single-task core takes none). A **one-shot compare register** (an interrupt when the counter reaches a programmed value).

**Current state.** The System v1 timer interrupts at level 6, vector 32, one core (read: docs/decisions-pending.md:1095 area). P3 proposes `RDTIME rd`, an unprivileged read of the constant-rate counter the timer device uses, with an enable control for side channels and virtualization (read: :200-216, :1285 item (a) says the time counter gets an enable bit or trap). P16 proposes cycle and instruction counters after P3 (read: :560-580). The secure core takes no periodic tick, may read `RDTIME` exactly, and has a cycle counter inside its window (read: crypto-secure-core.md:87, 92, 343). Errata 85 says the secure core "keeps its timer ticks"; errata 86 reverses it. The author says "main cores tickless". The pain-points row says: "A per-event compare register" mitigates tick versus tickless (read: docs/kernel-pain-points.md:101). The timer is a fixed device (F12).

**History.** PDP-11: the KW11-L line clock interrupted at line frequency (50 or 60 Hz) at priority 6, and the KW11-P programmable clock added a counter and a rate; Unix's `clock()` runs on each tick (from memory, not confirmed). VAX: the interval timer (`ICCS`, `NICR`, `ICR` processor registers) ran at 100 Hz with a time-of-year register for wall time (from memory, not confirmed). VAX multiprocessors had one interval timer per processor with a master that kept the time (from memory, not confirmed). 4BSD kept `hardclock` on every tick; tickless is a 2000s idea (Linux dynticks, 2007) (from memory, not confirmed; read: pain-points :101 "dynticks off-case must not slow; timer wheel reworked four times in June-July 2016").

**What other systems do.**
- ARM generic timer: a system counter (`CNTPCT`, `CNTVCT`) read by every core and shared, with a per-core compare register `CNTV_CVAL` and a countdown form; used for tickless in Linux (from memory, not confirmed; read: Linux vDSO uses `cntvct`, docs/decisions-pending.md:216).
- RISC-V: `mtime` (one shared counter) and `mtimecmp` per hart in the CLINT or ACLINT; supervisor mode could not program it without the SBI `set_timer` call until the Sstc extension added `stimecmp` (read: sys/arch/riscv64/riscv64/clock.c:63-70: `if (riscv_hwcap & HWCAP_ISA_SSTC) csr_write(stimecmp, nsecs); else sbi_set_timer(nsecs);`). `rdtime` is the user read (read: clock.c:81, 93).
- x86: the TSC (invariant TSC is constant-rate and synchronised on modern parts) plus the local APIC timer in TSC-deadline mode, a one-shot compare against the TSC; older parts had per-core TSCs that differed and counters that stopped in sleep states; Gleixner: "the stupid hardware is not reliable whether it has some 'I claim to be reliable tag' on it or not" (read: docs/kernel-pain-points.md:729, :1129 and :97 region; the Intel SDM text in decisions-pending.md:216 is read).
- POWER: the time base, synchronised at boot, plus per-core decrementer. s390: the TOD clock and per-CPU clock comparator plus CPU timer.

**OpenBSD timekeeping.** `clockintr` (kern_clockintr.c, 669 lines; read) gives each CPU a set of scheduled events (hardclock, statclock, schedclock) driven by one hardware timer per CPU programmed one-shot through `cpu_startclock_fcn`; the riscv64 backend is 175 lines (read: clock.c) and sets the compare value through `timer_set`; `clockintr_dispatch(frame)` runs at the timer interrupt (read: clock.c:152). OpenBSD runs `hardclock` on every CPU (from memory, not confirmed whether idle CPUs are exempt). So the interface a pdp64 port needs is: read the counter, set a one-shot compare value, take the interrupt, which is exactly the compare-register option. True tickless idle (not re-arming `hardclock` on an idle CPU) is kernel work above the machine-dependent layer and is not done in OpenBSD as far as I know (from memory, not confirmed); the hardware support does not decide it.

**Pain points.** :101 (tick versus tickless, timer wheel rework), :729 (TSC not trustworthy), :97/:424 area (clock watchdog); the VM timekeeping rows in section 0.4 list "the TSC (#3)" and "tick and tickless (#5)" (read: kernel-pain-points.md:1464).

**Options.**

1. **One global constant-rate counter, a one-shot compare register per core, a timer interrupt vector per core in its interrupt file.** The counter is distributed to all cores from one source with a defined skew bound; all cores read the same value, so `RDTIME` on any core agrees within the bound and a thread migrating between cores sees time that does not go backwards by more than the bound. The compare write is `MTSR` on the current core. Gains: closes the x86 TSC problem by construction; tickless is a compare write; no periodic hardware at all; the secure core simply never writes its compare; 16 cores add 16 comparators (a 64-bit comparator each, ~64 LUTs). Costs: distributing the counter on a 16-core die (a counter register per core fed by a broadcast and corrected, or a read through the interconnect: reads must not take microseconds); the skew bound must be written down. Score: (1) ++ (no unsynchronised clock; a timer cannot fire for the wrong core); (2) ++ (a compare write is one instruction; `RDTIME` one instruction); (4) +; OoO: `RDTIME` must be ordered by a stated rule (not speculated earlier than prior instructions retire) or it becomes a measurement channel; note the existing text.
2. **A periodic tick timer per core, fixed rate (PDP-11 line clock).** Gains: simplest. Costs: a tick on every core wakes an idle core a hundred times a second; the secure core cannot have one (errata 86); contradicts the author's "main cores tickless". Reject.
3. **A shared timer with a target register (global timer, interrupts routed by R1).** One comparator queue in the controller delivering to whichever core. Gains: fewer comparators. Costs: every core's next event is programmed through a shared structure, a lock; migration of events when cores go idle. Reject for general use; acceptable as an additional "wall clock alarm".
4. **Option 1 plus a cycle counter per core (P16) and a per-core scaled counter** (frequency scaling later). Keep P16 separate: `RDTIME` is constant-rate; `rdcycle` is for profiling and is disabled for user mode by default (side channels, read: P3 enable control).

**Specific design points.**
- *Reading.* `RDTIME` privileged or user-enabled per P3; the 64-bit counter does not wrap in the machine's life. On the secure core `RDTIME` is exact (read: crypto-secure-core.md:87).
- *Synchronisation.* One source, a defined skew bound of a few counts; no per-core adjustment registers (they would reproduce the x86 problems). Suspend/resume: counter state survives or the kernel re-bases a software offset, not a per-core one.
- *Tickless in OpenBSD.* The port gives `clockintr` a backend whose `rearm` is a compare write. Whether an idle main core suppresses hardclock is a scheduler change, listed in §6; with `LL; WFE` idle (§3) plus no tick, an idle core is quiet.
- *Statclock.* The statistics clock (random-interval sampling) is also a clockintr event; needs the compare, nothing else.
- *Secure core.* No timer interrupt at all; the preemption path is the IPI (§2); its accounting uses `RDTIME`.

**Lean.** Option 1 (with P16 separate). Equivalent in shape to RISC-V Sstc (compare in the privileged mode, no firmware) and ARM's generic timer, which are the two designs with the least kernel code (riscv64 `clock.c` is 175 lines, read).

**What the author must decide.** (a) The skew bound of the shared counter and whether it is guaranteed (stated in the manual). (b) `RDTIME` privileged or user-enabled by default (P3; the five constraints of Part C virtualization item (a) push toward an enable bit). (c) Whether the timer vector is architected the same on every core (this design: a fixed vector per core, level 6 kept). (d) That the wall clock (time of year) is a separate device.

## 5. The dedicated and heterogeneous core design

**Question.** How does an operating system use cores that differ in kind (a graphics core, a network core running the TCP/IP stack, an audio core, a secure core, general cores, some in order and some out of order), what must be the same on all of them, what may differ, and what do the 4-core minimum and the 16-plus target look like on real boards?

**Current state.**
- Errata 76 (proposal): one graphics core (Blit model: the terminal has a processor of its own), one network core running the full TCP/IP stack, one audio core (MIDI, DSP), the rest general. The cores are the same architecture; the class register of 7.8.3 already lets cores differ (read: docs/errata.md:226).
- F16 (iteration one or two; lean: policy by affinity in iteration one), F17 (what runs the stack; lean: OpenBSD's stack as a service, but splitting it out is a port task; affinity captures most of the benefit), F18 (shared memory: general cores coherent with each other; dedicated cores are message-passing partners using uncached rings and `FENCE`, the DMA rule of 7.7.2), F19 (how many cores; two or three general plus the three dedicated on a larger part; one general plus affinity on the DE10-Nano), F20 (each dedicated core its own IOMMU domain and address space), F21 (audio: same ISA, no DSP instruction at first; measure) (read: docs/decisions-pending.md:1599-1612).
- Secure core approved: in order, no speculation, fixed-latency instructions and caches, private window backed by TCM, no tick; the class is fixed by what was built; reserved bus slots (read: docs/crypto-secure-core.md:33-115; errata 86).
- The author, same day as this note: in-order and out-of-order cores may share a die "as long as we can tell which is which".
- Manual 7.8.3: class and capacity register, "defined from the first system although every core is alike". Row C9b of the pain-points matrix: the manual has no text on unlike cores or hotplug (read: docs/kernel-pain-points.md:1273). P4 (feature and identification registers) is open with options for read-only `mfsr` registers (read: docs/decisions-pending.md:226-240).
- Speculation controls: retire-stage candidates 12 (retire-gated visibility, a "strict" domain: study) and 13 (predictor and cache-way isolation by ASID: adopt predictors; the author said "smp is immediate, so don't defer" the ways) (read: docs/retire-stage-candidates.md:31-32; errata 84).
- FPGA: a complete core is about 16,020 LUTs (integer core with MMU about 7,620, plus FPU about 7,000, 8 KB L1 caches and the bridge), plus about 600 per core for the snooping coherence, with 11 BRAM blocks per core; estimates at plus or minus 40%; about 16,000 LUTs is stated as near 15% of a DE10-Nano, which holds only against the 110K LE figure; against the ~41K ALM (about 82K LUT) it is about 20% (read: docs/pdp64-fpga-plan.md:19, 34-69). The plan's phase 8 (SMP) is optional and last (read: :173-177). The earlier F19 lean predates the author's four-core initial device; 5.7 redoes the budget.

**History.**
- Heterogeneous machines before: the PDP-11/74 pairs identical processors; the VAX-11/782 had an attached processor with no I/O of its own (asymmetric); the VAX 8800 had two identical CPUs; the I/O processors of the CDC 6600 (peripheral processors) and the IBM channel processors are dedicated cores for I/O, as is the Blit's separate terminal processor (the terminal has its own CPU and display memory; read: errata 75/76 text on the Blit model) (VAX and CDC from memory, not confirmed).
- Unix on asymmetric hardware: master/slave Unix put all kernel work on one CPU; that is the dedicated-core idea in its crudest form and shows its cost: the master becomes the bottleneck (from memory, not confirmed).
- Offloading the network: the TCP offload engine (TOE) of the 2000s was rejected by Linux (Linux maintainers refused to merge TOE support; reasons: security surface, bugs in firmware stacks that cannot be patched like the kernel, a second stack to keep in step with the first) (from memory, not confirmed). DPDK and netmap run the stack in user space on dedicated cores with the card mapped, the most successful form of "a core owns the network card" (from memory, not confirmed). Plan 9 and microkernels ran network and file services as separate processes; rump kernels run an unmodified NetBSD stack as a library (from memory, not confirmed), and OpenBSD has no rump support (from memory, not confirmed). The "network processor" model (Intel IXP, Cavium Octeon, Mellanox/Bluefield DPUs) puts general cores next to the NIC (from memory, not confirmed).

**What other systems do on unlike cores.**
- ARM big.LITTLE (2011) and DynamIQ: cores of different microarchitecture in a cluster, same ISA; Linux uses an energy-aware scheduler with a per-CPU `cpu_capacity` value normalised to 1024; `sched-capacity.rst` is 442 lines and says capacity-aware scheduling places tasks by compute need (read: <work>/kernel-src/linux/Documentation/scheduler/sched-capacity.rst exists; contents not read in full). Linux gets the capacity from the device tree (`capacity-dmips-mhz`) or measures it (from memory, not confirmed).
- Intel hybrid (Alder Lake, 2021): P and E cores; the Thread Director gives the OS per-thread hints through a table in memory (from memory, not confirmed). OpenBSD's hybrid support is the type mask `sched_blockcpu` with `CPUTYP_SMT`, `CPUTYP_P`, `CPUTYP_E`, `CPUTYP_L` ("Lethargic, Low Power Efficiency core"), with `hw.smt`, `hw.blockcpu` and `hw.perfpolicy` sysctls, so a scheduler can refuse to run work on a type (read: sys/sys/sched.h:185-189; kern_sched.c:875-930). Torvalds on mixed cores: "I'm not convinced we handle the case of hotplug CPU's with different CPU models correctly" (read: docs/kernel-pain-points.md:710).
- Apple: P and E cores, with the QoS class API choosing among them (from memory, not confirmed). RISC-V: each hart has `mvendorid`, `marchid`, `mimpid` and an ISA string; Linux `hwprobe` reports a common subset for "all CPUs" and per-CPU on request (read: Linux Documentation/arch/riscv/hwprobe.rst exists, 425 lines; the sbi.c identify code reads `sbi_get_mvendorid()` etc., cpu.c:179-181). A well-known RISC-V pain point is cores with different extension sets in one system (from memory, not confirmed).
- Heterogeneous in-order and out-of-order, same ISA, on one die: ARM (A55 with A76, A53 with A57) is the large precedent; software sees the same architecture, differing only in the ID registers.

**Pain points.** docs/kernel-pain-points.md:70 (row 10, non-uniform cores and CPU hotplug), :710, :1273 (C9b: OPEN), :1295 (big.LITTLE and CPU hotplug thin rows), :1435 (hotplug reasons), docs/hardware-vulnerabilities.md:156 (C5: no buffer holds data from one domain where another's load can receive it) and :157 (C6: no SMT between mutually untrusting domains; holds because there is none), :80-84 (SMT policy, TLBleed, port contention).

### 5.1 What must be identical on every core, and what may differ

**Identical (the architecture; a program must run correctly anywhere):** the instruction semantics, flags, tags and the 64-bit register file width; sequential consistency, single-copy atomicity, the reservation rules and the atomics (part A) at the architectural level; precise exceptions and the restart contract (errata 84 item 17, decisions-pending.md:450-473); fault behaviour and `ECAUSE` codes; the page-table format and the page-attribute bits, so a process migrated between cores sees the same translation; the privilege model, `PSW`, `UA`, priority levels, interrupt entry; the interrupt-file protocol; `TLBI` broadcast; the 4 KB page and the cache-line size that software sees through the identification register (software that blocks to a line must find one value; if cores differ, the architectural line size is the largest and the smaller is a hint).

**May differ (reported, not guaranteed):** timing and instruction latencies; issue width; caches and TLB sizes; speculation and prediction (but see 5.3); in order versus out of order; the 16- or 32-register member (pdp64/16 against pdp64/32, which differ in the ISA, not just microarchitecture: they must not be mixed in one process, see below); optional extensions (crypto, fused instructions); whether the core is tickless-capable; secure-class properties; clock frequency and capacity.

**Hazards of mixing.**
1. *Migration of a running program between an in-order and an out-of-order core.* Fine for correctness by the identical list. The hazards are timing (a tight loop's cycle count changes), side-channel posture (the OoO core may be exposed to speculative channels the in-order core is not), and a program that caches an identification value read on one core (a cache-line size, the feature bits) then runs on another. Rule: the identification value a user process reads is the intersection over all cores it may run on, or the process is pinned.
2. *Different register-file members.* pdp64/16 and pdp64/32 differ in the instruction encodings (two member variants). A binary for 32 registers cannot run on a 16-register core. Rule: a machine has one member; mixing is not supported; the class register reports the member so a mismatch is a detected start failure.
3. *Speculative side channels.* An OoO core next to in-order cores: a victim on an in-order core is still exposed to shared-structure attacks from an OoO attacker sharing the L2, the bus and the coherence traffic (cross-core channels exist without SMT; read: docs/hardware-vulnerabilities.md:156-157 are about SMT; the cross-core channels are in the same document's cache sections). C5 and C6 become properties of the schedule: the scheduler must keep mutually untrusting domains off cores that share the exposed structure.
4. *The secure core's guarantee next to an OoO core.* The secure core's private window and cache are not shared (read: crypto-secure-core.md:70, 106), its bus use is time-division multiplexed with a reserved slot (read: :105), and nothing of its data enters a shared L2. An OoO core cannot disturb the secure core's timing as long as those three hold and the coherence traffic from the OoO cores cannot reach it. Verification item: the interference test of the secure-core document (a bus saturator, a cache thrasher, an IPI storm; read: :331) must be run with OoO cores present; pass is "deltas unchanged bit for bit".
5. *A strict-domain process on a core that does not honour it.* If retire-gated visibility (candidate 12) or predictor isolation (candidate 13) exist only on some cores, a process that asked for them must be scheduled only on cores whose class register says they are honoured. The scheduler enforces this through the allowed-cpus set, as for the secure core (read: crypto-secure-core.md "one affinity rule").
6. *Pending interrupts and wake behaviour* are identical because the interrupt file and the `WFE` rule are architectural.

### 5.2 What the class register (7.8.3) and P4 must report

The class register should be a short read-only group of `MFSR` registers (P4 option 1), readable from kernel mode on every core, and mirrored for user mode only where P3 permits (an enable bit, same rule as `RDTIME`). Field list, each one a fact software must not guess:

| Field | Values and purpose |
|---|---|
| Core number and the member | `MFCPUID` returns the number; the member (16 or 32 registers) and ABI version |
| Kind | general, graphics, network, audio, secure (a code); reserved codes for later |
| Execution style | in order or out of order; speculation on or off; speculation depth class (none, bounded, deep) |
| Capacity | an integer normalised so the fastest general core is 1024 (the Linux convention), plus a frequency |
| Issue width and the fetch/decode properties | width in instructions per cycle; instruction-length decode window (the two-byte-granule variable encoding is an area where cores differ); mispredict penalty is a hint field |
| Timing class | fixed-latency (secure), variable; whether `DIV` and `MUL` are constant time; whether `DIT` is honoured |
| Isolation properties | honours strict domain (candidate 12); predictor/way isolation by ASID (candidate 13); private caches; has a private window and its size; SMT absent (C6) |
| Optional ISA | feature bitmap: crypto (AES, SHA), fused instructions, `MASKEQZ`/`BSEL`, atomics set, UTF-8 and block-move widths |
| Cache and TLB geometry | line size, levels, sizes, TLB entries |
| Tickless | whether the core supports a timer compare and runs tickless (all except possibly the secure core which never programs one) |
| Coherence domain | which cores it is coherent with (F18: dedicated cores outside the coherent domain use uncached rings) |
| Stop-and-drain | supported, and whether it writes back |

Open design question for the author: capacity is a single scalar on Linux; here a secure core has low throughput but fixed latency, so scalar capacity loses information. Keep a scalar plus the kind and the property bits.

### 5.3 How the operating system uses it (OpenBSD)

- At attach (`cpu_attach`), the port reads the class registers into `cpu_info`: a class code, capacity, flags. The existing hooks are the `ci_flags` field and the `sched_blockcpu` type mask (read: kern_sched.c:875-930, sched.h:185-189). Map: general in-order = `P` or default; a future OoO general core = `P`; a low-power general core = `E` or `L`; dedicated cores get no scheduler type at all and are marked `CPUF_*` flagged "not for general scheduling" so `sched_choosecpu` and `sched_steal_proc` skip them (read: kern_sched.c:428, 495); the secure core is likewise outside general scheduling and reached only by an explicit request.
- Affinity: OpenBSD has per-process CPU affinity through `sched_peg` / `ps_flags` in `sched_choosecpu`, and interrupts are pinned by `intrmap` (read: kern_intrmap.c, 239 lines; the file exists in the tree) (affinity API details from memory, not confirmed). F16's "pin the network card's queue and the graphics driver to a core" is these two mechanisms, not new code.
- Scheduling hints: iteration one needs none beyond the class (no Thread Director).
- `hw.smt`: moot (no SMT, C6); the machinery is the reusable part.

### 5.4 The network core: what splitting the stack costs and buys

OpenBSD's TCP/IP stack is in the kernel, shares `mbuf`s, the routing table, pf and the socket buffers with everything else, and takes the `NET_LOCK` rwlock and, for much remaining code, the `KERNEL_LOCK` (lock count in section 6). Running it "as a service on the network core" means: all network syscalls on other cores become messages over a shared ring to a stack running on the network core; socket buffers are copied or shared between cores; pf and routing live there.

*Buys:* an isolated address space for the exposed stack (F20: a compromise of the stack cannot reach kernel memory directly, with the IOMMU limiting device DMA); fewer lock interactions with the rest of the kernel; deterministic latency for packets because the network core runs nothing else; the NIC's MSI-X queues all point at one core (no spreading, no cross-core cache bounce of descriptors).
*Costs:* a second protocol boundary: every `send`/`recv` crosses cores through uncached rings with `FENCE` (F18), adding a per-message latency that the in-kernel stack does not pay; a new socket layer (copy or zero-copy sharing of buffers); `select`, `kqueue`, `pf`, `bpf`, and every other consumer of mbufs and the routing table either move to the network core or reach it through the message interface. This is a rewrite, not a port: the rump-kernel and TOE precedents above say the protocol logic is reusable but the interface to the rest of the kernel is where the work and the bugs are (rump kernels work because they bring the stack up as a library with a defined hypercall interface; TOE failed on the interface and on update-ability). Sixteen cores do not remove this cost; they change the choice only in that one network core handles about one 10 Gb/s flow set before more are needed (from memory, not confirmed; depends on the in-order core's speed, which on FPGA at 50 to 80 MHz is far below it, read: fpga-plan.md:97).
*Verdict for the plan:* affinity (policy) in iteration one, as F16/F17 lean; the separate stack is iteration two and only after a measurement shows the in-kernel stack on a pinned core is the bottleneck.

### 5.5 Graphics and audio cores

- Graphics (Blit style): the core runs the drawing and compositing work and owns the virtio-gpu 2D queues; the kernel sends it rectangles over a ring and gets frames flushed. Cheap to isolate because the interface is already a command ring. Likely an in-order core (deterministic frame times), with the identical-ISA property letting the same OpenBSD binary toolchain build its firmware.
- Audio: virtio-snd streams in shared-memory queues, MIDI over USB; hard per-block deadline, so an in-order fixed-latency class is ideal and the secure core's design is the same shape (a small in-order core). A DSP loop needs multiply-accumulate; measure on the existing multiplier before any new instruction (F21).
- Both are outside the coherent domain; they use uncached rings and `FENCE`, each its own IOMMU domain (F18, F20). A fault on a dedicated core must not reach other cores: the IOMMU domain bounds its DMA, the page tables bound its CPU accesses, and a crashed core is stopped and restarted with stop-and-drain and the start register (§2), a recoverable fault by design (priority 1).

### 5.6 Core maps

Assumptions: general cores snoop with each other up to four (R3 limits; part A); more than four general cores need a directory or a cluster of four snooping groups, which is R3's decision; dedicated cores are outside the coherent domain. "Tag" = what the class register reports.

**Iteration one, 4 cores (the minimum that must work).**

| Core | Class | Notes |
|---|---|---|
| 0 | general, boot | takes the console, runs the kernel |
| 1 | general | |
| 2 | general | network queue and its interrupts pinned here by affinity (policy, F16) |
| 3 | general | graphics driver thread and audio thread pinned here by affinity (policy) |

No class is built as dedicated. All four cores are one class (general, in order); the dedicated roles are scheduling policy: the stack runs in the kernel, and an interrupt and a process are pinned. A 4-core machine cannot spare three cores for graphics, network and audio and keep a usable general-purpose OS, so the dedicated cores are an iteration-two feature on four cores. The initial device is these four cores (author, this session); whether they fit the first FPGA is 5.7 (they do not with the FPU on the DE10-Nano). A secure core, being a small in-order block (about 5,000 LUTs is my estimate, not a measured figure), is an optional fifth or replaces core 3 (5.7); the machine works without it (the crypto routines run on general cores with `DIT` set and the AES/SHA instructions, read: crypto-secure-core.md:314).

| 12 | network core (or two: transmit/receive or one per card) |
| 13 | graphics core |
| 14 | audio core |
| 15 | secure core (more secure cores are possible: one per domain) |

Beyond 16: more general cores in groups of four; the dedicated roles do not multiply except the secure core and network cores. The architecture's ceiling (the interrupt file, 256 cores by the 8-bit group count, the vector field, the multicast register) allows far more (§1, §2). MAXCPUS in OpenBSD riscv64 is 32 (read: sys/arch/riscv64/include/cpu.h:177), arm64 256 and amd64 255 (read: arm64 cpu.h:237, amd64 cpu.h:296), so sixteen fits without changing the generic kernel.

**In-order and out-of-order tagging in the maps.** Iteration one: every core is in order; the tags still carry in-order/OoO, speculation, member, secure, strict-domain support so software that reads them is correct on day one. Iteration two: OoO cores appear among general cores; dedicated audio and secure stay in order; network and graphics may be either.

- Network: a pinned queue and thread; the standard virtio-net runs in QEMU and `sim64`; on the DE10-Nano the HPS Ethernet is a different path (the plan's HPS bring-up harness).
- Audio: a pinned real-time thread; the audio hardware on the board is the HDMI/I2S path.

Lean: (c) if it fits, else (b), because the secure core is the only dedicated function whose value depends on hardware, and a three-general-core OS is still SMP.
- Dedicated-core roles by class (network core, graphics core, audio core running separate stacks) are an 8-core or larger feature; on a 4-core first device they are not built.

**What 16 cores means on a board that cannot hold it.** 16 full cores are about 266K LUTs (16 x 16,020 + snoop) and 16 FPU-less cores about 154K; neither fits any board in the plan's list. The architecture must not preclude it (§1, §2 are built for 256 cores) and the first device must not depend on it.

**Lean.** Dedicated cores as policy on 4 cores (iteration one); as a class (register reports it, hardware built differently) on 8 and 16; the network core as a user-space program or driver with the card mapped first, an in-kernel-stack split only after measurement; general cores in coherent groups of four; every core tagged. The in-order/OoO mix is accepted with the class register fields of 5.2 and the scheduling rules of 5.1 hazards 1 to 5.

(c) Whether the class registers are readable from user mode (P3/P4 constraint). (d) The rule for mixed members (pdp64/16 with pdp64/32): forbidden in one machine, or supported. (e) Where the coherent domain ends (groups of four, directory) which is R3 in part A. (f) The first board that has more than 4 cores (a bigger FPGA than the DE10-Nano), and whether the FPU-less core is a permitted member. (g) The network split: stack as a user-space program with the card mapped, as a kernel service, or not at all.

## 6. The operating system view (OpenBSD)

**Question.** What does OpenBSD need from the architecture to run on four to sixteen cores, and what machine-dependent SMP work is the port?

**Current state.** Roadmap measured the riscv64 `sys/arch` tree: `riscv64/` core 14,873 lines (pmap.c 2,187, machdep.c 1,082, cpu.c 1,027, intr.c 769, trap.c 289, locore.S 268) (read: docs/roadmap.md:27-37). The pdp64 manual 7.9 lists the kernel view: start a core by a register write, `DP` as the per-CPU pointer, `_DB` locks, `TLBI`+`TLBSYNC`, `WFE` idle. OpenBSD is the target kernel (errata 83 context; `UA` kept until the port confirms, errata 86).

**History.** 4.3BSD on the VAX 11/782 and later VAX multiprocessors: exclusion by `spl`; true SMP BSDs came with the 386 era (BSD/OS, FreeBSD 5 SMPng, NetBSD 5 and the 1990s `big_lock`). OpenBSD added `KERNEL_LOCK` as `mp_lock` in 2004-2005 and a ticket `__mp_lock` in 2016 (the current implementation: read: kern_lock.c:157-175); the lock-unlocking effort has been going since about 2010 and is still in progress (from memory, not confirmed). The NetBSD `tech-smp` list records the first MI SMP API leaving lock ownership and priority undefined (read: kernel-pain-points.md:841-842).

**What other systems do.** FreeBSD and Linux unlocked the kernel in the 2000s (SMPng; the BKL removal "on the to-do list almost since that lock was first added", read: kernel-pain-points.md:910). OpenBSD keeps the giant lock for much of the kernel and unlocks subsystem by subsystem: network (`NET_LOCK` rwlock, parallel softnet), VFS parts, syscalls tagged as locked or not (from memory, not confirmed).

**Pain points.** kernel-pain-points.md:339 (lock fairness and cache-line bouncing: same problem), :656 (an SMP kernel on one CPU pays for its locks), :564 (queue locks needed nine versions), :910.

### 6.1 What the OpenBSD sources show (the sparse tree, read)

- *Giant lock.* In the sparse tree (which may be incomplete) `KERNEL_LOCK()` appears 142 times in 58 `.c` files (counted: `grep -rn "KERNEL_LOCK()"` under sys/); `__mp_lock` is a ticket lock with per-CPU state indexed by `cpu_number()` and a spin-out counter (read: kern_lock.c:64-210). Per-architecture `mplock.h` is 10 lines in each port (read). So at 16 cores the giant lock is the scalability question; the architecture's job is to make a spin on it cheap (§3) and fair.
- *Scheduler.* Per-CPU run queues (`spc_whichqs`, `spc_runq`), CPU choice in `sched_choosecpu` (kern_sched.c:428) and `sched_choosecpu_fork` (:376), stealing in `sched_steal_proc` (:495), idle loop (:192-205), and a type mask for `hw.smt`/`hw.blockcpu` (:875-930). `kern_sched.c` is 938 lines (read).
- *Cross-calls.* `kern_xcall.c` (157 lines, 2025) provides `cpu_xcall_ipi`, implemented by the architecture as an IPI (read: amd64 intr.h:226; arm64 intr.h:207). It is the portable replacement for several of amd64's ad hoc IPI kinds. The port needs: `cpu_xcall_ipi`, halt, nop, ddb.
- *Per-CPU data.* `curcpu()` returns the `cpu_info` pointer (a register or `TPIDR`-like on other ports); the pdp64 `DP` makes it `MOVQ d(DP), Rd` (read: manual 7.4.2). `ci_cpuid`, `cpu_number()` reads `curcpu()->ci_cpuid` (read: riscv64 cpu.h:170).
- *Hatch.* `cpu_hatch_secondary` obtains the physical address of `cpu_hatch` and calls `sbi_hsm_hart_start` (read: riscv64 cpu.c:630-650); `cpu_hatch` sets up the stack and calls `sched_toidle()` (cpu.c:653-683); `cpu_boot_secondary_processors` loops over CPUs (cpu.c:613-625). For pdp64 this is a start-register write with `r1` = the `cpu_info` address.
- *IPL.* `splraise`, soft interrupts, `IPL_MPFLOOR`, the `IPL_MPSAFE` flag for interrupts that need no kernel lock (read: riscv64 intr.h:61-65). OpenBSD riscv64 runs a software-emulated spl over the interrupt controller's threshold (the `plic.c` has `sc_threshold[IPL_IPI]`, read imsic.c:148); with the pdp64 PSW the levels are hardware, an advantage (fewer instructions per `spl`, priority 2), subject to the 12 IPLs against 8 levels map (§8).
- *Rwlocks, mutexes.* `kern_rwlock.c` (769 lines) and mutexes are MI and use atomics (part A): `CAS`, `SWAP` and `LL/SC` available, the `_DB` forms for acquire/release.
- *SMR and srp.* `kern_smr.c`, `kern_srp.c` are MI and use `CPU` IPIs/idle observation (`smr_idle`, read: kern_sched.c:188); they need the idle loop to be quiescent-state friendly.
- *kern.smt.* The `hw.smt` emulation is in `kern_sched.c`; on pdp64 with no SMT it always reports off.

### 6.2 Machine-dependent SMP work for a pdp64 port (estimate from riscv64 line counts)

### 6.3 At sixteen cores: what the kernel will meet

- The giant lock: 142 `KERNEL_LOCK()` sites in the sparse tree and a ticket lock mean sixteen cores spend time spinning; the `LL; WFE` form (§3) keeps the spin off the bus. Real unlocking is OpenBSD's work, not the architecture's.
- Scheduler: per-CPU queues and stealing scale to the dozens; the cost is cross-core wakeups, each an IPI NOP (cheap: one store).
- Interrupt distribution: the NVMe driver in OpenBSD uses `intrmap` (kern_intrmap.c, 239 lines; read) to map queues to CPUs; it needs the MSI-X plus remapping design of §1.
- `MAXCPUS` 32 on riscv64: ample.
- Soft interrupts and `softclock` per CPU.

**Options (for the port strategy).**
1. **Follow the riscv64 shape (interrupt file like IMSIC/APLIC, hardware registers, `sbi.c` removed).** Smallest delta from the newest port; the lean.
2. **Follow the arm64 shape (GIC-like).** Larger driver (2,166 lines); no benefit.
3. **Single CPU first, `MULTIPROCESSOR` off.** Valid as milestone one (the port boots uniprocessor; the SMP files come second). Costs nothing and is the order in the plan (FPGA phase 8 last).
4. **Master/slave first.** Unneeded; OpenBSD already has the giant lock.

**Lean.** Option 1, with option 3 as the staging. Score: (1) ++ (small code, hardware spl), (2) ++ (hardware spl and ECAUSE vector save instructions), OoO neutral.

**What the author must decide.** (a) Port staging: uniprocessor first, then SMP (assumed). (b) That the generic-kernel changes needed (tickless idle, class-based scheduling for dedicated cores) are carried as patches or proposed upstream. (c) Whether `IPL_MPSAFE` interrupts are the default so the giant lock is not taken in device handlers. (d) A kernel `cpu_info` field set from the class register: names of the fields.

## 7. SMP in the tools and simulators

**Question.** What do the simulators and test tools need so that atomics, interrupts, IPIs, timers and the memory model are tested before silicon, with four cores and with sixteen?

**Current state.** `sim64` runs user mode; QEMU runs the System v1 target single-core; the timing model is single-core (stated in the task; the FPGA plan phase 0 lists `sim64` "user mode", read: pdp64-fpga-plan.md:165). The plan's SMP gate: "two cores pass the litmus tests of §7 item 7; a kernel schedules on both" (read: :173); section 7 item 7 of that plan is the litmus check of sequential consistency (read: :177).

**History.** Multiprocessor simulators began with SimOS (1990s) and Simics (commercial); `gem5` has both a deterministic event queue and multi-core models. (from memory, not confirmed)

**What other systems do.**
- QEMU: TCG SMP. Multi-threaded TCG (MTTCG) runs each vCPU on a host thread when guest memory ordering is no stronger than host's, or inserts barriers; for a host weaker than the guest (an ARM host emulating x86) QEMU adds barriers and some pairs are marked unsupported (from memory, not confirmed). Without MTTCG all vCPUs round-robin on one thread (`-smp` with `thread=single`): slower, deterministic in practice, and sequentially consistent by construction. For a sequentially-consistent guest the single-thread mode gives the architecturally strongest model; MTTCG on an x86-64 host gives total store order, weaker than the guest's sequential consistency, so it would hide, not expose, store-load reordering bugs only if the guest relies on SC. A guest that relies on SC (this ISA) requires `thread=single` or fences emitted on every store in the translator. Atomics under MTTCG map to host atomics.
- `herd7`/`litmus7`: `herd7` simulates a formal memory model on small tests; `litmus7` runs tests on real hardware many times to see whether forbidden outcomes occur (from memory, not confirmed). The model for sequential consistency is trivial: any outcome that is not an interleaving is forbidden.
- Deterministic replay: QEMU `-icount` with record/replay; `rr`-style.

**Pain points.** kernel-pain-points.md:513 (LL/SC livelock was a real erratum: the ARC kernel needs a workaround for a named silicon erratum), :517 (a missing barrier found years later on a 2-socket Power9 with 128 hardware threads), :656.

**Options.**

1. **`sim64` multi-core, deterministic round-robin on one host thread.** Each core executes N instructions (a quantum) in turn, in a fixed order; a seed picks the quantum sizes. Gains: bit-for-bit repeatable, sequentially consistent by construction, trivial to log and replay, easy to run sixteen cores; interrupts and IPIs are events at quantum boundaries. Costs: finds only interleavings at quantum granularity (quantum of 1 instruction explores most, slowly); never exercises true parallelism or cache effects. Score: (1) ++ detection by seeds; OoO neutral. Do first.
2. **`sim64` multi-core with one host thread per core.** Gains: real parallelism; the atomics become host atomics. Costs: not repeatable; the memory model of the host (x86 TSO vs ARM) leaks in; needs care to be SC. Later.
3. **QEMU `-smp N`, single-thread TCG.** Gains: runs the OpenBSD kernel at speed, SC. Costs: the QEMU target needs the interrupt file, timer compare, start register and stop-and-drain devices (one QEMU device model, a few hundred lines, R1/R2 "a QEMU model"). Do second.
4. **QEMU MTTCG.** Gains: speed on many host cores. Costs: SC not guaranteed for the guest; requires translator-inserted fences for every store/load or stronger host ordering; not trustworthy for memory-model testing. Use only for speed, not for correctness runs.
5. **RTL simulation of 2 to 4 cores with litmus programs and a coherence checker.** Required for hardware (FPGA plan phase 8). Part A owns coherence; this part supplies interrupt, IPI and start-register tests.

**Test plan (this part's items).**
- Interrupt file: set a vector, take it at the right level, mask by the PSW, vector in `ECAUSE`, priority ordering, no loss under random store timing, a retargeting race test (entry changed while a device storm runs: every interrupt arrives exactly once on one core).
- IPI: nop, halt, xcall, ddb; multicast to 15 cores; a storm test; self-IPI.
- Start/stop: start N cores in parallel with a start mask; each reads its number and increments a shared counter with `XADD`; stop-and-drain mid-run; restart; class mismatch refusal.
- `WFE`: the lost-wake-up test: random interrupt timing around `SPL #7; test; WFE; SPL #0` over millions of iterations, with a check that no sleep ends later than one deliberate bound; the reservation-wake test of option 2; spurious wakes allowed and tolerated.
- Timer: compare programming, the shared counter monotonic across cores, a sleeping core woken by its compare, migration of a thread between cores sees non-decreasing `RDTIME`.
- Secure core: the interference test of crypto-secure-core.md:331 with an IPI storm.
- Heterogeneous: the class registers read back what the simulator was configured as; a mixed in-order/OoO model in `sim64` (the timing model differs per core; the architectural results must be identical): a differential test, same program on both core models, equal architectural state at every retired instruction (the plan's trace-match gate, read: pdp64-fpga-plan.md:166).
- Litmus: store buffering, message passing, IRIW (independent reads of independent writes), load buffering and the 2+2W tests; with sequential consistency the forbidden-outcome set is every non-interleaving; run millions of iterations under random quanta in `sim64` and under `litmus7` on the FPGA. (Part A owns these tests; this part reuses them for interrupts: "an interrupt write cannot pass the data writes", errata 71 item 2.4.4.)
- Kernel: boot OpenBSD with 2, 4 and 16 simulated cores; `make build`-style load; the lock-scaling profile at 16 shows what a four-core machine hides.

**Effort estimate (my estimate; large uncertainty).** `sim64` multi-core with interrupt file, timer, start and IPI: 1 to 2 weeks. QEMU device model for the same: 1 to 2 weeks. Litmus suite and harness (shared with part A): 1 week. Differential in-order/OoO model: depends on whether an OoO timing model exists (the timing model is single-core and in-order). Order of work: `sim64` multi-core (option 1) with the interrupt file; litmus tests on it; the QEMU model; boot OpenBSD uniprocessor then SMP; RTL tests on the FPGA.

**Lean.** Options 1 then 3, then 2 for speed; MTTCG excluded from correctness runs.

**What the author must decide.** (a) Priority of multi-core simulation relative to the single-core OpenBSD port (the port can start on one core, §6). (b) Whether `sim64` gets a per-core timing model with in-order and OoO variants. (c) Who owns the litmus suite (part A or this part). (d) The sixteen-core simulation as an acceptance gate for the architecture ceiling.

## 8. Other open items in this area

**Question.** What else in interrupts, SMP start, idle, timers and dedicated cores is unspecified?

**Open items found, each with where it sits.**

1. **Eight hardware levels against OpenBSD's twelve IPLs.** riscv64 defines IPL 0 to 12 (read: intr.h:45-58). The hardware levels 0 to 7 must be grouped: for example 0 none; 1 soft interrupts (softclock, softnet, softtty, in one level or by software lists); 2 block I/O and network; 3 terminal and VM; 4 audio; 5 clock/sched; 6 timer (the existing assignment is timer at 6, console at 4, read: R1 "Current state"); 7 high and IPI. Because every entry sets level 7 (P14), `IPL_IPI` above `IPL_HIGH` needs thought: IPI vectors at the same level as `IPL_HIGH` mean an IPI cannot interrupt a section at `splhigh`, which is what a stop request needs. Option: IPI level 7 and handlers lower the level; the `splhigh` section runs at level 7 with an additional "interrupts disabled for all but stop" meaning supplied by stop-and-drain. The author decides the table; a mapping is an ABI item. (Pain: manual commentary notes Q4's "only 8 classes; devices at the same level can't be ordered by the processor", read: decisions-pending.md around Q4 options.)
2. **Soft interrupts** (`softclock`, `softnet`, `softtty` in OpenBSD, implemented in MI code with a pending word and an `spl` check): either all software, or a hardware "request interrupt at level n on this core" via a store to the own interrupt file (the self-IPI of §2). The VAX `SIRR` is the precedent (from memory, not confirmed). Lean: self-store to the interrupt file.
3. **Interrupt-file write permission.** Only kernel mode, only through the controller's address window, never through a device's DMA except via the remapping table: state it in the bus chapter (F24, F25).
4. **Reset and reboot of one core, and a watchdog.** Stop-and-drain, start register (§2); a hardware watchdog per core or global; "restart and recovery together" (priority 1) wants a defined way to reset a hung core without a full reset. Not yet specified.
5. **Machine check and ECC error delivery to a core** (candidate 15: precise ECC and parity reporting; errata 84): which core receives an error from shared memory or a bus, and how a fatal one is broadcast (no NMI: a stop request via the controller).
6. **Per-core reset state and the first stack.** A secondary starts with translation off (docs/boot.md:277); who sets up its page tables, and the early stack (the `r1` structure).
7. **Interrupt delivery to a core in a stopped or reset state.** Pending bits persist across stop-and-drain or are cleared; the hot-plug order of §2 retargets first.
8. **Power states and idle depth.** Only `WFE` exists; clock gating of an idle core is allowed but wake latency is unspecified (the manual says `WFE` "stalls or gates the core's clock"; wake latency should be bounded and published, as the secure core's interrupt latency is, read: crypto-secure-core.md:100). Deep sleep states and frequency are outside the processor (read: pain-points :476).
9. **The core-class register's user visibility** and how a migrating process sees it (§5.2).
10. **Sixteen cores and R3 (coherence).** The snooping protocol is for two to four cores (manual 7.7.1, ISA open item 12); the number of general cores in a coherent domain at 16 is part A's decision and sets how many "groups" the scheduler has (a scheduling-domain structure like Linux's `sched-domains.rst`, which exists locally, read: Documentation/scheduler/).
11. **NUMA-like effects** between groups of four cores: OpenBSD has no NUMA awareness in the scheduler (from memory, not confirmed); at 16 cores in two groups the cost of cross-group coherence is the first non-uniformity software meets.
12. **SMT.** None. C6 holds trivially. If a future OoO core adds SMT, the scheduling rule of C6 and `hw.smt` (read: hardware-vulnerabilities.md:157) apply and the class register must report it.
13. **Hostile or failed dedicated core.** A dedicated core that crashes: stop, zeroise, restart (§2). A compromised one is bounded by its IOMMU domain and page tables (F20); the shared rings are untrusted input to the kernel side (validate every index and length).
14. **The `ICINV` cross-core rule** for JIT and module loading (kernel-pain-points.md:458, "UNKNOWN"): part A.
