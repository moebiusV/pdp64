# pdp64 on QEMU

`qemu-system-pdp64 -M pdp64-virt -kernel prog` runs the programs that `sim64` runs, with the same results.
This directory holds everything we write for it; `~/claude/qemu-src` (a QEMU v11.1.2 checkout) and
`~/claude/qemu-build` are scratch places where it is built, never committed here.

## Install, build, run

    qemu/build.sh [-j N]        # install.sh + configure + ninja; the result is ~/claude/qemu-build/qemu-system-pdp64
    qemu/install.sh [qemu-src]  # only put the target into a QEMU tree (idempotent)
    qemu/sync.sh [--check]      # refresh / verify the generated copies in target-pdp64/gen

    build/as64 -o t.o t.s && build/ld64 -o t.x t.o
    qemu-system-pdp64 -M pdp64-virt -display none -kernel t.x; echo $?

The exit status of the qemu process is the program's: `trap #0` (default machine) / `halt` give r0 & 255, a fault of the default machine gives 139 (with a message and
the registers on standard error).  `tools/check-qemu.sh` runs tests/sim and tests/qemu under it; `PDP64RUN=qemu tools/pdp64test-all.sh`
runs the C tests (PDP64CCOM needed).  `tools/check-all.sh` includes check-qemu when the binary exists.

## Layout

- `qemu-core.patch`: the changes to QEMU's own files (SysEmuTarget enum, QEMU_ARCH_PDP64, poison list, EM_PDP64 = 0xF064 in
  elf.h, and the target/hw Kconfig and meson lists).
- `target-pdp64/` becomes `target/pdp64/`; `hw-pdp64/` becomes `hw/pdp64/`; `configs/` is copied to `configs/`.
- `target-pdp64/gen/`: copies of common/pdp64exec.c/.h, common/calib.c/.h, as64/fmtp.c, as64/fmt.h and the generated
  build/pdp64-parser.c and pdp64-consts.h.  Generated by `sync.sh`, never edited; `sync.sh --check` fails if they are stale
  (install.sh and check-qemu.sh run it), so the grammar stays the only source of the decoder.

## Machine options

    -M pdp64-virt                     the original machine: user mode, no MMU, no devices, the system-call stand-in (trap #0..#2, halt)
    -M pdp64-virt,kernel-mode=on      System v1 (docs/pdp64-system-architecture.md section 15)

(The property is `kernel-mode` because `kernel` is QEMU's own name for the `-kernel` file of every machine.)  With `kernel-mode=on` the machine starts
in kernel mode at the ELF entry point with priority 7 and `MMUCTL` 0; the kernel stack pointer (r14 of the kernel bank) is the top of RAM; exceptions
and interrupts are delivered through the vector table at the physical address `VBR + 8 * vector`; `trap #n` is vector 256 + n (no stand-in), `halt`
(privileged) ends the machine with status `r0 & 255`; the timer and the console exist.  A console is the first `-serial` character device
(`-serial stdio`; with `-serial none` its output is dropped).  `tools/check-qemu.sh` runs the tests of tests/sim whose NAME.flags has -k or -K, and
all of tests/qemu, with this option.

## Memory map (pdp64-virt)

| range                       | what                                                  |
|-----------------------------|-------------------------------------------------------|
| 0x00000000 .. ram_size      | RAM, default 128 MiB (`-m`, at most 256 MiB)          |
| 0x10000000 (4 KB)           | timer (kernel-mode only)    `MAP_TIMER`               |
| 0x10001000 (4 KB)           | console (kernel-mode only)  `MAP_CONSOLE`             |
| up to 0x1fffffff            | reserved for devices                                  |

An address that no RAM or device answers is a bus fault (vector 13); the original machine reports it as a fault and exits with 139.  `-kernel` loads an ELF
executable (machine 0xF064, little-endian, as ld64 writes it; text at 0x10000) and starts at its entry point.  The numbers above are in spec/pdp64-system.hbnf
(rule `map`), the registers below too.

### Timer

Registers (64 bits, `TIMER_REG_*`): `counter` 0 (read only; counts at `TIMER_CLOCK_HZ` = 10 MHz of QEMU's virtual clock), `compare` 8 (reset value
all ones), `control` 16 (`TIMER_CTL_ENABLE` bit 0 writable; `TIMER_CTL_PENDING` bit 1, reads counter >= compare).  The interrupt, level 6 vector 32, is
asserted while counter >= compare and enable; it is level-sensitive, so the handler writes a new compare (or clears enable).

### Console

Registers (`CONSOLE_REG_*`): `rxcs` 0, `rxdb` 8, `txcs` 16, `txdb` 24.  `CONSOLE_CSR_READY` (bit 7) and `CONSOLE_CSR_IE` (bit 6) as in the KL11.  Reading `rxdb`
clears receive READY (one character is buffered; the character device is held back until it is read).  Writing `txdb` sends the byte at once; transmit READY is
always 1.  Input interrupt: level 4 vector 33 while receive READY and IE; output interrupt: level 4 vector 34 while transmit IE.

## The MMU (kernel-mode machine, MMUCTL.enable = 1)

`tlb_fill` walks the three-level table of section 15 for every access of every mode: canonical check (vector 5), V and reserved bits (page fault 6/7/8
by instruction/load/store), R/W/X/U permissions (protection fault 9/10/11), software A and D (a page fault of the kind of the access), 4 KB / 2 MB / 1 GB
leaves (misaligned superpage: page fault), a bus error while reading a table or the target (vector 13).  Permissions are checked before A and D.  The
walker never writes a table.  QEMU's TLB is per MMU index: 0 physical (translation off), 1 kernel, 2 user and supervisor.  Simplifications:

- ASID and G are not modelled: any write to `PTBR`, `ASID` or `MMUCTL`, and `TLBIA`, flush the whole TLB (an implementation may drop entries at any time, so this is a valid
  one); `TLBI` flushes the page (the whole superpage entry, for a 2 MB or 1 GB leaf); stale translations persist until then, as the architecture says.
- A write to a clean page (D = 0) re-walks even without `TLBI`, because the cached entry lacks write permission.
- The memory type MT is stored and ignored: RAM or device follows from the physical address.
- The supervisor mode is treated like user mode for page permissions.
- Instruction fetch is checked per two-byte parcel; an instruction whose second parcel is on a bad page faults with EPC = the instruction, EVA = that parcel.
- A fetch from an address that is not RAM is a bus fault.

## Design

Nothing is written twice.  The meaning of every instruction (and of exception entry, `rti`, interrupt acceptance, precise aborts) is in common/pdp64exec.c,
the decoder is generated from spec/pdp64.hbnf.in; the numbers are generated from the grammars into pdp64-consts.h.  The QEMU target only supplies the host's side
of `struct pdp64_env`:

- `CPUPDP64State` embeds `struct pdp64_cpu`, so the core works on the CPU state directly.
- One instruction per translation block (the block is found per MMU index): the translator reads the first parcel, stores pc, calls `helper_exec` and does
  `lookup_and_goto_ptr`.  `helper_exec` runs `pdp64_step()`, which fetches (through the instruction-fetch path of the MMU), decodes and executes.
- Aborts: the core's `raise` hook (and `tlb_fill`, `do_transaction_failed`) set the vector and EVA and unwind with `cpu_loop_exit_restore`; `cpu_do_interrupt` calls
  `pdp64_exception`, which undoes the instruction (the core keeps a snapshot of the registers) and enters the handler.
- Interrupts: a device line goes to a GPIO input of the CPU; `cpu_exec_interrupt` takes the best asserted line with `pdp64_interrupt` (level above the priority).  When the
  priority falls with a line asserted the translation-block chain is left so that the request is looked at.  `wfe` halts the CPU until an interrupt can be taken.
- The core and decoder are built as a separate static library with `-w` and the symbol renames of tools/build-as64.sh.

## Deliberately not done

No TCG fast paths (every instruction is a helper call: correctness first, speed later), no user-mode `qemu-pdp64`, no gdbstub, no disassembler, no migration state (vmstate), no multi-CPU,
no DMW translation (stored only), no ASID/G, no reset vector (vector 0).
