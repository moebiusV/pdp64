# Which vector instructions the compiled kernels use

Generated by `llvm/bench/usage.py` from the blocks that `llc -pdp64-vecloop` (approach (b): one `vec` block for a whole loop) makes for 15 programs: the kernels of `docs/encoding-work/arch-data/vec-forms/` (`kernels.c`, `games`, `blas`, `seg`), `llvm/bench/simple.c`, and `llvm/tests/vec/*.c`. 77 blocks in 72 functions. The words are those of the vector family of the grammar (372 mnemonics). **A static count is a count of instructions in the blocks; the dynamic counts (vector instructions executed, elements) are in `llvm/bench/results.csv` and `llvm/README.md`.** Re-run: `llvm/bench/usage.py --out llvm/vector-usage.md`.

## Instructions no kernel used, and why (what a compiler would need)

* `vlen` (block, 6 words): only needed by a program that must know VL (explicit tail folding, approach (c)); the loop-to-block pass has hardware strip mining and never asks
* `vlseg2` (segment, 22 words): the pass makes one strided load (`vldt`) for each field instead; a grouping of the fields of one structure would use these
* `vlseg3` (segment, 22 words): same
* `vlseg4` (segment, 22 words): same
* `vsseg2` (segment, 13 words): same (stores)
* `vsseg3` (segment, 13 words): same
* `vsseg4` (segment, 13 words): same
* `vldx` (gather, 22 words): a gather (k_hist, k_ssm): the loop reads an address from a load; not recognised
* `vabdu` (lane operations, 4 words): the kernels take `abs(a - b)` of widened bytes: the signed `vabd` serves
* `vmla` (multiply-add, 4 words): integer multiply-add by a scalar (`vmla.l vD, vA, Rs`): the pass emits `vmul` then `vadd` for integers; not fused yet
* `vfmab` (multiply-add, 2 words): the broadcast multiply-add of a GEMM micro-kernel: needs a loop nest, not an innermost loop
* `vdot` (int8 dot, 1 words): int8 dot products (k_q8dot, k_q4dot): the block of the pass already runs 8 elements per strip because the reduction `vacc.l` makes the widest lane 32 bits; `vdot.b` would not widen the strip (see the findings)
* `vdotu` (int8 dot, 1 words): same
* `vdotsu` (int8 dot, 1 words): same
* `vfir` (sliding window, 6 words): needs the recogniser for a window of consecutive loads times invariant taps (put8h): the pass makes eight shifted streams instead (8 loads, 8 multiplies, 7 adds)
* `vclr` (accumulators, 6 words): hidden accumulation across strips: nothing here reads an accumulator after the block ends (there is no vector-to-scalar move outside a block), so a block that needs one must reduce inside it (`vacc` each strip), which is what the compiler does
* `vtclr` (tile and GEMM, 1 words): tile and GEMM: no kernel loop nest is turned into tiles (`k_sgemm_nt` is vectorised on its inner dot product)
* `vtfmopa` (tile and GEMM, 2 words): same
* `vtld` (tile and GEMM, 2 words): same
* `vtst` (tile and GEMM, 2 words): same
* `vtadd` (tile and GEMM, 2 words): same
* `gemm` (tile and GEMM, 1 words): same: a call of the GEMM unit would be recognised from `llvm.matrix.multiply` or the triple loop; not done
