# pdp64 on LLVM

> **Status: stage 1 (the scalar code generator), stage 2 (the check instructions; the vector blocks made from scalar loops by a pass, as inline assembly) and stage 2b (LLVM's own LoopVectorize runs for this target, with a cost model, and its vector loops are lowered to the same blocks).** `llc -mtriple=pdp64-unknown-elf` turns LLVM IR into assembly text that `as64` assembles; `llvm/check.sh` compiles, assembles, links and runs the test programs under `sim64`. Not done: the vector, tile and GEMM instructions (stage 2, list at the end), an integrated assembler (`llc -filetype=obj`, `llvm-mc`), varargs, position-independent code. The machine-code layer of the earlier milestone (an assembler, disassembler and object writer for the old encoding) is not built any more; its sources are kept, frozen, in `target/frozen-M1/` (design notes: `docs/pdp64-system-architecture.md` section 14).

The back end is for two things: to try different ways of vectorising and tiling with LLVM's own vectorisers (the vector instructions come in stage 2), and to compile code with LLVM so that the prefix optimiser can be run again on instruction statistics that are not pcc's.

## Build and test

    llvm/build.sh [-j N]    # install.sh + configure (PDP64 as an experimental target) + ninja llc llvm-tblgen llvm-mc ...
    llvm/install.sh         # only copy the target into ../llvm-project (applies patch/llvm-core.patch; idempotent)
    llvm/check.sh           # the tests (below); -v shows why one failed; --host checks the expected values with the host's x86 clang; needs opt for the lv variants (ninja -C ../llvm-build opt)
    llvm/bench/bench.py     # the benchmark of the vectorising variants (46 kernels: 31 of the study and 15 for the words of waves 1 and 2, sim64 -P -V); gaps.py: why LoopVectorize refuses what it refuses; usage.py: which vector words are used
    tools/gen-llvm-td.py [--check]   # write / verify llvm/target/PDP64/gen from spec/pdp64/pdp64.hbnf

    ../llvm-build/bin/llc -mtriple=pdp64-unknown-elf -O2 x.ll -o x.s      # llc --version lists pdp64

`llvm/build.sh` needs LLVM 21.1.8 in `../llvm-project` and builds in `../llvm-build` (`LLVM_SRC`, `LLVM_BUILD`); on 12 cores `llc` takes about ten minutes with `-j 10`.

**`llvm/check.sh`** compiles every `llvm/tests/*.ll` (first line `; expect: N` or `; expect: fault` or `; expect: fault:REGEX`; lines `; llc: FLAGS` make variants, `; asm:`, `; asm-vec:` and `; noasm:` check the assembly) (`; expect: N` on the first line, `i32 @test()`), assembles with `as64`, links with `ld64` against the crt of `tools/pdp64test.sh` and `llvm/tests/lib/main.ll` (the driver that prints `test()`), runs `sim64` and compares. Then it takes the C programs of `tests/c/*.c` (and `tests/c-new/*.c`) through the host's `clang -S -emit-llvm -O1 -m64 -fno-builtin -ffreestanding -fno-stack-protector -mlong-double-64 -mno-sse -fno-vectorize` (triple, data layout and the x86 target attributes are dropped; `llc -mtriple=pdp64-unknown-elf` supplies its own) and `llc`, the same way. `tests/vec/*.c` are the vector kernels (`/* expect: N vec: K flags: CLANGFLAGS */`): each runs three ways, plain llc, `-pdp64-vecloop` and `-pdp64-vecloop -pdp64-vecloop-strip`, all must print N and the block count must be K (twice that for the strip form). `LLC_OPT` (default `-O2`) and `COPT` (clang, default `-O1`) choose the levels; the C results are reported and do not decide the exit status.

The expected values of the `.ll` tests were produced by compiling the same IR for the host (`check.sh --host` repeats that), so the tests do not rest on the author's arithmetic.

## Design choices

**Data layout** `e-m:e-p:64:64-i8:8-i16:16-i32:32-i64:64-i128:64-f32:32-f64:64-n64-S64`: little-endian, no symbol prefix (appendix D), 64-bit pointers, natural alignment (data alignment is architectural, ISA 7.4: a quad access that is not a multiple of 8 aborts, and `sim64` does abort), `i128` aligned to 8 (no register or type is wider than a quad), native width 64, the stack a multiple of 8. A load or store LLVM cannot prove aligned is split into byte accesses. The stack is not realigned (`StackRealignable = false`): an alloca with `align 16` is clamped to 8, which is all the machine needs.

**Registers** (appendix D, and pcc where the appendix is silent): one class holds integers, pointers and floating point (`i64`, `f64`, `f32`); a binary32 is the low 32 bits of a register, sign-extended, so `movl` loads and stores it and `fadd32` and friends are two-register instructions. `r12` (linker scratch), `r13` (fp) and `r14` (sp) are not allocatable. Caller-saved: `r0`-`r7`, `r16`-`r23`; callee-saved: `r8`-`r11`, `r15` (the appendix), `r24`-`r31` (pcc's choice; the appendix leaves them open) and fp. The allocation order is the caller-saved registers first.

**Types.** `i1`, `i8`, `i16`, `i32` are promoted to `i64`: a value carries garbage in the high bits and is extended where the bits matter (`movb`/`movw`/`movl` sign-extend a register, `movzb`/`movzw`/`movzl` or an `and` with a mask zero-extend, a load extends as it loads). That is `llc`'s ordinary any-extension scheme, not pcc's "always extended" one; the difference is only visible at an ABI boundary, where a narrow argument or result is passed **sign-extended unless it is marked `zeroext`** (`i1` zero-extended), which is what pcc's registers hold for `int`, `short`, `char` and the unsigned types after their own extension. A front end must therefore put `zeroext` on `unsigned char`, `unsigned short` and `_Bool` parameters and results to call pcc code. The callee never assumes more than the attributes say.

**Calling convention.** Arguments in `r0`-`r5`, then 8-byte stack slots at `0(sp)`, `8(sp)` ... in the caller's outgoing area (the callee sees them at `16(fp)`); results in `r0` (`r0:r1` for an `i128`); a `byval` aggregate is copied into as many slots as it needs; `sret` is the first argument. The frame is pcc's: `push fp; movq sp,fp; sub #n,sp`, the callee-saved registers just below fp (stored with `movq`, not `pushm`), the locals, the outgoing area at the bottom (a reserved call frame; a function with dynamic allocas adjusts `sp` around each call); the epilogue is `movq fp,sp; pop fp; ret`. A function with nothing in its frame has none. Varargs are not implemented.

**Instruction selection.** All integer comparisons are `cbCC ra, rb|#imm, label` (a 16-bit signed immediate, else the constant goes into a register); the assembler chooses the length and relaxes (checked with a 15 KB branch). No flags are modelled, so `cmp`-style compares appear only for floating point, as one pseudo that prints `fcmp x,y` and one `b<cc>` (`PDP64CC::fpSequence`: the flags after `fcmp` are N a<b, Z a==b, V unordered, so `bgt`/`bge`/`blt`/`ble` with the operands swapped cover ten predicates and `bvc`/`bvs` the other two; `one` and `ueq` are expanded by LLVM into two compares). A comparison used as a value, and `select`, are a branch diamond. Constants: `clr`, `movq #imm32`, `movq =K` (the literal pool of as64) for anything wider. Addresses: `d(rN)` (28-bit), `d(rN)(rX*s)` (index shifted by 1, 2 or 3), globals `sym` / `lea sym` (pc-relative, so no absolute addressing `@expr`), `lea` as the three-address add (`lea d(rN),rd`, `lea (rN)(rX*s),rd`), `(rN)+` and `-(rN)` when the pointer moves by the size of the access (found by the DAG combiner), `bic`, `rori`/`rol`, `min`/`max`/`minu`/`maxu`, `mulh`/`mulhu`, `div`/`divu`/`mod`/`modu`, `clz`/`ctz`/`popcnt`/`bswap`/`bitrev`. An `i64` to `float` conversion goes through `double` (one extra rounding). Switches: LLVM's jump tables (a `.quad` table in `.data`, `lea table,r; movq 0(r)(i*8),r; jmp (r)`) and compare trees. Atomics are library calls (`__atomic_*`, which the crt does not have).

**Output.** Only `.text`, `.data`, `.bss` (as64 knows no others): read-only data, constant pools, jump tables and internal zero-initialised objects go to `.data` (`.local`/`.comm` do not exist in as64). A symbol that as64 would read as something else (`r0`..`r31`, `sp`, `fp`, and `ch`, found by trying) is written in double quotes. `.align n` is in bytes, `.space` for zeros, no `.type`/`.size`/`.file`/`.note.GNU-stack`.

## Stage 2

### The check instructions (`ctCC`, `cteq`, `ctne`, `chk2`)

* `llvm.trap` and `llvm.ubsantrap(k)` are one instruction, `ctcc r0, #0` (every unsigned value is higher than or the same as 0: a fault on vector 16 with EPC at the instruction, and a record in `__bug_table`); `llvm.debugtrap` is `bpt`. The argument of `ubsantrap` (clang's handler number) gives the kind of the record: 18 out-of-bounds = 1 (bounds), 14-17 and 22 = 2 (null), 20 and 24 = 3 (range), the rest 4 (assertion); a plain `llvm.trap` gets the kind from the compare (unsigned: bounds, against zero: null, else assertion).
* `PDP64CheckFold` (a machine pass before register allocation, `-pdp64-fold-checks`, on by default) turns `cbCC a, b, fail` where `fail` is a block that only traps into one `ctCC a, b` (the condition of `ctCC` is that of `cbCC`: it traps when the branch would have been taken; with the trap on the fall-through arm the condition is inverted), removes the branch and, when nothing else reaches it, the failure block. The immediate form exists only for `ctcc`, `cthi`, `cteq`, `ctne` and is **12 bits unsigned** (found in the grammar by `tools/gen-llvm-td.py`, never typed in): anything else goes through a register (`movq #n, rT`). `x == 0` / `x != 0` is the one-register `cteq rs` / `ctne rs`. `x < lo` followed by `x >= hi` on one value (the second in the only successor of the first, only instructions without side effects between) is `chk2 x, lo, hi` (kind 3). Before each, the AsmPrinter writes `.chk KIND, "file", LINE`; file and line come from the debug location of the trap (else of the branch), without `-g` the file is the module's source name and the line 0.
* Not done: a block that calls a noreturn function (`panic_bounds_check`, `__stack_chk_fail`) instead of trapping is left alone (turning it into a trap would change what the program does).
* Tests: `tests/check_*.ll` (7: bounds with an immediate, with registers, null, `chk2`, debug location, and two that must FAIL: `expect: fault` is "sim64's message `check failed` and exit status 139"), with `; asm:` / `; noasm:` lines that check the assembly.
* Measured (`bl.c`: five subscripts of tables that cannot be proved, `clang -O2 -fsanitize=bounds -fsanitize-trap=bounds`; sim64 `-P`; text is the whole linked image including the 40 bytes of crt, the same in all three): no checks 23,687 instructions executed, 74,818 bytes executed, 320 bytes of text; checks as a `cbCC` to one shared trap block per function (`-pdp64-fold-checks=0`) 27,727 / 99,058 / 344; checks folded 27,727 / 90,978 / 328. So with LLVM's shared trap block **a check costs one instruction either way** (+4,040 instructions, +17%): the fold saves 2 bytes for each check executed (a `cbcc rX, #n, L` is 6 bytes, a `ctcc rX, #n` is 4) and the failure block (4 bytes each time the function has one): -16 bytes of text here, 8,080 fewer bytes fetched. The large saving of the study (about 85% of the cost of a check is the failure block) is pcc's call-and-stub; LLVM's tail merging had already removed most of it.

### Vectors: what is built

There is **no vector register class and no selection pattern for a vector type** (stage 2b below adds a `TargetTransformInfo` and a lowering of LoopVectorize's output to the same blocks; a vector value that is not lowered is legalised to scalar code by the ordinary type legaliser). The vector instructions are made by one IR pass, `PDP64VecLoop` (`-pdp64-vecloop`, off by default), as inline assembly: `getRegForInlineAsmConstraint` ("r") and `PrintAsmOperand` are the only target support it needs. The hidden registers `v0`-`v15` are assigned by the pass (a linear scan over the straight-line body; more than 16 live values: the loop stays scalar).

**(b) a loop becomes one block (`-pdp64-vecloop`).** An innermost loop in simplified form with one block, a trip count SCEV can compute, and a body of: loads and stores whose addresses are recurrences `{p,+,size}` (consecutive) or `{p,+,k*size}` (strided, k*size <= 1000: `vldt`/`vstt`), zero- or sign-extended loads (`vld.bu.l`), truncated or clamped stores (`vst.l.b`, `vsts.l.bu`), integer and floating-point lane operations with a vector, an invariant register or a 16-bit immediate as the second operand (`vadd vsub vsubr vmul vand vor vxor vshl vshr vsar`, `smin smax umin umax`, `abs(x-y)` as `vabd`, the saturating `vadds vsubs vaddsu vsubsu`, `fneg`), multiply-adds (`fmuladd`/`fma` and a contractable `fmul`+`fadd`: `vfma`, `vfnma`), loop-invariant loads and arithmetic (made once in the preheader), and reductions into scalars (chains of adds: `vacc`; signed max/min and `fcmp ogt`+`select`: `vmaxacc`/`vminacc`; floating-point sums only with `reassoc`) is replaced by `vec Rs, Re` ... `vend` over the whole region, with the pointers and accumulators as the `(Ra)+`/`vacc` operands of one inline-assembly statement. There is no scalar remainder loop, no loop control: the hardware's short last strip is the remainder, and a trip count of 0 or 1 works. **Aliasing**: accesses at the same address in each iteration are fine when the load comes first in the body; accesses to different identified objects, or fields of one structure (equal step, constant distance, disjoint bytes in the period), are fine; anything else gets a run-time test of the address ranges and the **original loop is kept as the fallback** (versioning). With `restrict` the tests and the fallback go (k_fmac with `restrict` is 40 bytes of text, 9 instructions, against 36 bytes scalar). **Safety**: the block has no hidden accumulation (no `vclr`, no tile), so it restarts at the strip it stopped in with the integer registers as at the start of the strip; the registers it changes are the (Ra)+ pointers and the reduction registers, committed when the strip ends; the outputs are early-clobber so no input shares a register with them; the only things a block reads from integer registers are those operands. `tests/vec_fault.ll` runs a block off the end of mapped memory: sim64 stops at the strip that touches the page with the pointer register equal to that strip's first address (checked by hand: `r0 = 0x12000` = the fault address).

**(a) one block for each strip, a scalar loop around it (`-pdp64-vecloop -pdp64-vecloop-strip`).** The shape that a fixed-width vectoriser's loop gets when every vector operation of an iteration is one block: the same block body over VL elements, with a counter, `lea` of the end of the strip and a branch in the loop, and a second block for the remainder (the scalar epilogue of LLVM's vectoriser, as one more block). A vector value cannot live from one iteration to the next (the hidden registers that are not accumulators are zeroed at each strip, and a block is only run to its end), so only **in-loop reductions** (`vacc` each iteration) fit this shape, which is also what `-prefer-inloop-reductions` asks of LLVM's vectoriser. Built from the same recogniser, so it measures the cost of the shape, not LLVM's `LoopVectorize` (which would need the register class, the patterns and the cost model).

**(c) VP intrinsics, tail folding with `vlen`** (not done). `vlen.<t> Rd` gives VL, which is what RISC-V's `vsetvli` is, but the pdp64 block already strip-mines by itself: an explicit-VL loop would need `llvm.vp.*` ISel, scalable vector types and `vlen` per iteration, and would only repeat in IR what `vec ... vend` does in hardware, with the extra instructions of the loop. What blocks it here is the missing ISel (no vector register class), not the ISA.

### Findings for the next run of the encoding optimiser

`llvm/vector-usage.md` (made by `llvm/bench/usage.py`) lists which words of the family the compiled kernels use (counts as of stage 2b, before wave 1 of errata 170: 77 blocks in 72 functions, 72 of the 372 words, 33 of the 55 base mnemonics; vector-usage.md is regenerated: 86 of the 347 words used); **no kernel uses** (as of stage 2b; see stage 2c below for the words of waves 1 and 2, which the kernels `newk.c` and the tests use now) `vlen`, `vclr`, `vfir`, `vlseg2/3/4`, `vsseg2/3/4`, `vldx`, `vdot*`, `vmla`, `vfmab`, `vabdu`, `vtclr vtfmopa vtld vtst vtadd`, `gemm.f` (the reasons are in the file: the pass has no recogniser for them yet, or they need a loop nest). Observations that came out of the work, to be checked against the owner's intentions (all from reading `common/pdp64exec_vec.inc` and from the measurements; none from hardware):

* **The strip width is the widest lane type in the block, and a widening reduction makes it narrow.** `vacc.l` over bytes needs 32-bit lanes (`vld.bu.l`), so `k_dctop_sum`, `k_sad`, `k_q8dot` run 8 elements for each vector instruction, not 32. A zero-extending `vacc` on byte lanes (there is only the signed sum) would make those four times cheaper (63 vector instructions instead of 250 for 1,000 bytes); and `vdot.b` followed by `vacc.l` in one block gets the strip of 8, not 32, so `vdot` as specified would not help a dot product until VL is decided by the first stream's element size.
* **A hidden register does not live from one block to the next**, and non-accumulator registers are zeroed at each strip, so nothing in a block can be read after it: the only exits are the (Ra)+ stores and the reductions into integer registers. `vclr` accumulators therefore have no user in a loop-to-block compiler.
* The one-instruction prefix needs a `(Rs)+` memory operand, so it is useful only for loads and stores (a fill, a copy): an operation on registers has no stream to iterate.
* In the hand-written `k_sad` of the study (`k_sad.vec.s`) `vld.bu.w v0,(r0)+` followed by `vacc.l r6,v0` reduces 16-bit lanes as 32-bit lanes: minimal reproduction in the report of this work (sum of the bytes 1..8: `vacc.l` gives 16, `vacc.w` gives 36).
* sim64's `-P` profile counts a block as one instruction; the counters `-V` are needed for any comparison (the flag is new, `docs/sim64.md`).

## Stage 2b: LLVM's own vectorisers

**Why.** The owner's point of the LLVM back end is that LLVM's vectorisers tell which vector instructions are worth having. Stage 2's pass recognised scalar loops itself and so said nothing about LoopVectorize. Now `opt -passes='default<O2>' -mtriple=pdp64-unknown-elf` runs the real middle end with a pdp64 `TargetTransformInfo`, and the vector loops that LoopVectorize makes are lowered, by `PDP64VecLoop` (extended, same machinery), to ONE `vec Rs, Re ... vend` block over the whole range.

**The pipeline** (`check.sh` variant `lv`, `bench.py` variants `lv` and `lv0`): `clang -O2 -Xclang -disable-llvm-passes` (IR with no LLVM pass; the pdp64 data layout comes from `opt`), `opt -passes='default<O2>' -mtriple=pdp64-unknown-elf`, `llc`. The old variants (clang -O2 with the host vectoriser off, llc with and without `-pdp64-vecloop`) are kept. `lv0` is `lv` with `-pdp64-vecblock=0`: what the vectoriser made, legalised to scalar code, the correctness fallback for anything the lowering does not take. `check.sh` also runs the 26 C programs of `tests/c` and `tests/c-new` through this pipeline (`CPIPE=lv`).

**The TargetTransformInfo** (`PDP64TargetTransformInfo.cpp`; the table of what is legal, Invalid and expensive is in `vectorizer-gaps.md`): 16 registers of 256 bits (reported as 32: LoopVectorize counts a splat of an invariant as a live vector register, here it is a scalar operand; the lowering checks the real 16); lanes b w l q f d; `shouldMaximizeVectorBandwidth` (bytes give VF 32); one vector instruction for each 256 bits for lane arithmetic, consecutive loads and stores, the interleaved groups of 2, 3, 4 fields (`vlseg`/`vsseg`) with every field used; extensions and truncations free only as part of a load or store; reductions `add`, `fadd` (reassoc), `smax smin umax umin`, `fmax fmin` (nnan); vector `icmp fcmp select`, masked and gather/scatter operations, divisions, `sqrt`, conversions, extensions of computed values: Invalid; shuffles other than splats 1000, insert/extract 64, vectors of fewer than 4 lanes x32. Policy: no tail folding, no active vector length, interleave count 1, no epilogue vectorisation, no unrolling (`getUnrollingPreferences`), in-loop reductions requested for the kinds the machine cannot accumulate (so that LoopVectorize's cost for them is Invalid), SLP off (`getMaximumVF` 1: a vector outside a loop has no instruction). Two surprises found by running it: LoopVectorize drops a VF "that will not generate any vector instructions" unless `getNumberOfParts` says a legal vector is a part or more (the type legaliser would split to scalars), and an Invalid cost compares as 0 in the passes that only compare totals (VectorCombine, SLP), so shuffles are expensive, not Invalid.

**Fixed-width vectors, not scalable/VP.** The pass takes `<N x iM>` bodies because the block is the loop: LoopVectorize's VF and the hardware's VL need not agree (the hardware strips by 32 bytes / the widest lane), so the pass throws the vector loop away and takes from it only the operations, the streams and the reductions. VP intrinsics with EVL (RISC-V's way) would put `vlen` and a loop around the block and need ISel for scalable types; the machine has no use for that (stage 2 (c)). Nothing here says that a scalable form could not be lowered; it was not tried.

**The lowering** (`PDP64VecLoop::transform`, vector mode). It recognises LoopVectorize's shape `pred -> vector.ph -> vector.body -> middle.block -(cmp.n)-> exit / scalar.ph -> epilogue loop` and: (1) takes the original trip count TC from `cmp.n = icmp eq n.vec, TC` (or the exact count by SCEV if there is no remainder); (2) analyses the body with the stage-2 `Analyzer` (generalised: vector values are held lane by lane, a splat of an invariant is the scalar operand, `insertelement`+`shufflevector` splats in the loop are recognised, interleaved groups are found from the wide load/store and its shuffles by looking through concatenations, an extension of a load or `fpext` and a `trunc`/`fptrunc`/clamp before a store are fused into `vld.bu.l`, `vld.f.d`, `vst.l.b`, `vsts`, a rotate by a constant is `vshl`/`vshr`/`vor`, unsigned and `maxnum` reductions are `vmaxacc.bu`, `vmaxacc.f`...); (3) emits one block over TC elements, so the scalar epilogue is not reached on the block path; (4) rewrites the CFG: `vector.ph` branches to the block, `middle.block` goes to the exit, the minimum-iterations test (`min.iters.check`) is removed (the block takes 0 and up), the reduction results (the `llvm.vector.reduce.*` of the lcssa phis) are replaced by the block's scalar results, the start of each accumulator is the reduction of the vector start (the lane-0 start, or a splat), and LoopVectorize's own run-time overlap test (`vector.memcheck`, which compares the ranges of the WHOLE trip count) stays and sends the failing case to `scalar.ph` with the values the other bypasses give; (5) if no `vector.memcheck` is there and the analysis needs an overlap test, it makes its own and branches to `scalar.ph` the same way. What stays a safety rule of stage 2: loads of a strip before its stores, strips in order, so a load BEHIND a store of the same array (a true dependence) or a constant distance below the strip is refused, and a load AHEAD of it by a whole number of elements (`a[i] = a[i + 1] + 1`) is accepted (new: write-after-read). Anything the pass cannot take is left as LoopVectorize made it and legalised to scalar code: always correct (`lv0`: all 31 kernels give the scalar result) and about as slow as scalar code (`lv0` over the 31 kernels: geometric mean 1/1.21 of the scalar instruction count, the worst kernel `k_q4dot` at 1.03 times it).

## Stage 2c: the words of waves 1 and 2 (errata 170 and 171) from LoopVectorize's output and from the scalar-loop recogniser

**What was done.** `PDP64VecLoop`'s `Analyzer` (the one analysis that both modes share: the vector loops of LoopVectorize in `opt -passes='default<O2>'`'s output, and the scalar loops of `-pdp64-vecloop`) now finds the IR idioms below before it emits the block, and `PDP64TargetTransformInfo` lets LoopVectorize form them (select, compare, conversions legal; the costs of the widening reductions). Nothing was added to LLVM itself (`llvm-core.patch` is as it was) and nothing to the target's selection patterns: as before, the block is inline assembly. The same idioms are found in scalar and in vector IR, so the tests run each program as scalar, `-pdp64-vecloop`, `-pdp64-vecloop-strip` and `lv` and on the host.

**Never selected, and why.** `vtbl.b`: a 16-entry table lookup is a gather in IR (`tbl[a[i] & 15]`), LoopVectorize refuses it before any cost (`g_lut16`), and there is no intrinsic: assembly only. `vdot.w`, `vdot.b`, `vdotu`, `vdotsu`: a dot product is a reduction and `vdacc` (a whole strip into the scalar register in one instruction, strip of 32 bytes) is better than `vdot` followed by `vacc` (32-bit lanes, strip of 8); LLVM reaches `vdot` only as a partial reduction into a vector accumulator, and the block has no vector state across strips. `vmulhr.w` without the written saturation, `vshrr.l` for C unsigned (no `nuw`).

**Gaps that remain** (list for the instruction-set review, with the loops, in `vectorizer-gaps.md`): a masked load or store (`g_cond_store`, `g_thresh_cond`: a conditional access); a clamp to a byte written as nested `?:` (`k_clamp8`); a select whose arms are narrower than its mask is widened only if they are loads or constants; a compare with an `int` threshold against halfwords or bytes runs in 32-bit lanes (8 per strip, not 16 or 32: the compiler cannot narrow `x > t` without knowing `t` fits; a hand-written `vcgt.w v, v, r4` with a 16-bit t does it in 16); no `vcvt` for 64-bit lanes or `double`; `vcgtu.f`; no scalar `fcvtsl` pattern (one instruction instead of two, saturating at 32 bits); `k_q4dot`, `k_put8h`, `k_gray`, `k_hist`, `k_ssm` as before.

**Cost model.** Select (b w l f lanes) one strip, compare one strip (three for the floating predicates that need two compares and an or), `and or xor` of masks one, conversions one, `fneg` one (it had no cost: it was Invalid although `vneg` exists), the multiply of two extended bytes or halfwords into a sum 64 bits wide legal (it is `vdacc`). Corrected: wave 1 removed `vmul.q`, `vmin.q`, `vmax.q`, `vminu.q`, `vmaxu.q`, `vabd.q`; the cost model still called them legal, so LoopVectorize vectorised `(uint64_t)a * b >> 32` and the lowering found no word (the loop stayed legalised vector code); they are Invalid now.

**Also found.** A constant-trip-count vector loop with no remainder (`for (b) { for (i < 32) ... }`) is followed directly by the outer latch, not by `middle.block`: the lowering did not know the shape and now does (`k_q8blk`: 31 blocks). `check.sh` takes a `file.c` argument for one vector test, and the first line of a `tests/vec` program takes `words: ...` and `lvwords: ...` (mnemonics that must be in the assembly of the vec and lv builds), `nowords:`, `strip: N` (the block count of the strip build) and `scalar: N` (the value the scalar build gives, where it differs).

### What is not done (stage 2)

Register classes for `v0`-`v15` and `t0`-`t7` and selection patterns for the vector types (a vector value that the lowering does not take is legalised to scalar code); the tile and GEMM instructions (`vt*`, `gemm.f`) and `llvm.pdp64.*` intrinsics; recognisers for `vfir`, `vldx` gathers, `vdot`, `vmla`; spilling of vector registers (a loop that needs more than 16 stays scalar); restart of a block through an operating system handler (only sim64's user mode was run: the fault stops the program with the registers at the strip start); an integrated assembler (as before). **Stage 2b did the `TargetTransformInfo` and the lowering of LoopVectorize's output (previous section); `vlseg`/`vsseg` are now made (from interleaved groups).**

### Smaller things still open

* **Integrated assembler and objects**: `MCCodeEmitter` + `MCAsmBackend` + `MCELFObjectWriter` that call `common/pdp64enc.c` (the table codec), then `llc -filetype=obj`, `llvm-mc`, `llvm-objdump`; `target/frozen-M1/` shows the fixup and relocation arrangement (`ELFRelocs/PDP64.def` is still in the patch). Branch relaxation would then be LLVM's, not as64's.
* **Smaller things**: varargs (`va_start` with the register save area of appendix D.2), `pushm`/`popmret`/`movcall`/`mov2` in the frame code, tail calls, `cbz`/`sob` forms, ALU forms with a memory operand (`add mem,r`, `addm`), `maskeqz`/`masknez`/`bsel` for branch-free `select`, a hot-register preference in the allocation order (the tables are in `gen/PDP64GenLayout.h`), absolute addressing `@expr`, `fma`/`fmin`/`fmax`/`frint*` once their semantics are checked against `sim64`, PIC (`d(pc)` globals, `got(PC)` imports), TLS, debug information and unwind tables, GlobalISel.
